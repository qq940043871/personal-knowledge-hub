## 第四章 千房同构的巨城：进程、线程与虚拟内存

Linux 山脉是代码大陆人口最稠密的地区。山腹里掏空了一座巨城——**内核城**，城外密密麻麻挂着数百万间房子，每间房子都是一个**进程（Process）**。

"整个山脉只有一条铁律："老码说，"**平民（用户程序）不许直接碰内核城。** 你要用地盘、要读文件、要发网络包，必须走**系统调用（syscall）**——那是内核城墙上开的一排合法窗口，递单子进去，结果递出来。"

"要是翻墙呢？"

"CPU 会当场把你撂倒——这叫**段错误（Segmentation Fault）**。门禁系统是硬件级的，翻墙者死。"

### 套房与合租屋

林一码发现每间进程房里还能再细分小间——**线程（Thread）**。

"进程是**独立套房**：自己的内存、自己的文件、自己的水电表。一家漏水，淹不到邻居。"老码说，"线程是**合租屋**：大家共享客厅厨房（同一块堆内存），快是快，但一个人半夜开派对，全屋遭殃——**一个线程踩坏共享数据，整间进程跟着崩**。"

"那我全用进程不就安全了？"

"进程之间隔墙太高，说话要靠**进程间通信（IPC）**：管道像墙上的传菜口，共享内存像两家共用的储物间（要上锁），信号像楼下喊一嗓子。各有各的贵。"老码说，"工程上永远在套房和合租屋之间权衡：**要隔离用进程，要效率用线程，要海量轻量用协程。**"

"协程是什么？"

"**用户态自己排班的线程**。线程排队切换要惊动内核（成本高），协程则是租客们私下商量好'你写完这段我接着用 CPU'，全程不麻烦物业。海量网络连接时，协程是省钱神器。"

### 房卡与假地图

城管的告示栏上贴着一张图，标题是**虚拟内存**。

"每个进程领到的是一张**假地图**——它以为自己独占整座城市，地址从 0 开始排。"老码说，"真相是：**进程的房卡上只写房间号，真楼层只有内核前台知道**。前台那本对照簿，叫**页表（Page Table）**；翻译地址的专职翻译官，叫 **MMU**。"

"这样图什么？"

"三件事：**隔离**（每家都以为城市是自己的，谁也偷不了谁家）、**共享**（两家的房卡可以指向同一个真楼层——动态库就这么被大家共用）、**超售**（假地图可以画得比真实内存还大，暂时不用的楼层先写在**磁盘**上，要用再搬回来——这叫**交换分区 Swap**）。"

老码压低声音："Swap 是个甜蜜的陷阱。你很快会见到一场名场面：某个老兵把 Java 城的堆配了 32G，物理内存只有 24G，超出的 8G 被悄悄画进了 Swap。平时没事，某天高峰期内核开始频繁搬楼层——**全场卡成 PPT，监控上看不到任何异常，因为内存'没爆'，只是在疯狂搬家**。记住：**Java 堆别超过物理内存的七成。**"

### OOM Killer：饥荒先杀最胖的猪

告示栏最下方贴着一张通缉令风格的海报，画着一个蒙面刽子手：**OOM Killer**。

"内存是山的粮食。荒年——也就是物理内存耗尽时——内核不谈判，直接开杀。"老码说，"OOM Killer 会给每个进程打分，**分最高的（通常是吃内存最多的那个）当场处决**。诡异的是：被杀的进程连遗言都没有——进程一死，应用日志什么都查不到。"

"那怎么知道是谁干的？"

"查内核的监控录像：`dmesg`。上面会白纸黑字写着'Out of memory: Killed process xxx'。这是山脉查案的第一条铁律——**进程无声无息消失，先看内核日志，再查应用日志**。"

林一码在本子上写：**OOM Killer，饥荒先杀最胖的猪。想让它别杀你的关键进程？调它的生死簿分数（oom_score_adj），或者——别让荒年发生。**

### 伙伴登场：小蝶

下山路上，两人在溪边遇到一个背着巨大工具包的少女，正对着一块半透明的水镜修修补补。她叫**小蝶**，浏览器城的画师，游历大陆修炼前端技艺。

"你就是老码说的那个人类？"小蝶上下打量林一码，"听说你要去打 Bug 魔王？我加入。我见过太多同行被它欺负——上个月，我们城一个页面加载五秒才出第一屏，元凶是个 2MB 的打包文件。这种仇，得报。"

老队 +1。三人继续上山。

## 第五章 门铃、前台与灵异档案：epoll 与文件系统

### 一面墙的门铃

 Linux 山脉深处有一家传奇客栈——**IO 客栈**。它的前身轰然倒闭，原因写在门口的墓志铭上：

> 前身采用"一客一服务员"制（**BIO**，一个连接一个线程）。客人一多，服务员不够；服务员一多，工资（内存）和调度成本压垮客栈。三千客，三千服务员，当场解散。

如今的 IO 客栈换了玩法：**一个前台（Selector/epoll） + 一整面墙的门铃**。每位客人进门领一个号，坐下不用管；哪桌要点单，按桌上的铃。前台只盯着铃灯，铃亮哪桌去哪桌——**一个人，看住一万桌**。

"这就是 **epoll / IO 多路复用**。"老码说，"BIO 是'挨桌问要不要加菜'，epoll 是'装门铃'。内核替你盯着几万个连接，**谁的门铃响了，才把谁交给你**。Nginx、Redis、Netty，全靠这套门铃撑起十万里长街的客流。"

"代价呢？"

"门槛。事件驱动把代码写成了'回调地狱'——你的逻辑被门铃切得七零八落。所以后来有了协程和响应式框架，想把门铃穿回一条线。这些你在 Java 城都会见到。"

### inode：车库有位，驾照没了

半山腰的集市上，一个管理员急得跳脚：磁盘明明还有空间，任何人都建不了新文件。

老码瞥了一眼，报出病名："**inode 耗尽**。"

"这大陆上，**文件名只是别名，inode 才是文件的身份证**。"老码解释，"每个文件系统建好那天，身份证的印制额度就定死了。额度用光——就算车库全是空位，没驾照照样停不进车。海量小文件最吃额度：一个几 KB 的垃圾缓存文件，也要占用一整个身份证。"

处置办法也简单：找出海量小文件的老巢清掉。林一码在本子上补了一句：**"磁盘满"有两种：数据满了（df 看 blocks），身份证满了（df -i 看 inode）。两种满，两种救法。**

### 灵异档案一：删掉的 50G 纹丝不动

客栈大堂贴着一张悬赏，案情离奇：

> 管理员删了一个 50G 的日志，`df` 一看，磁盘纹丝不动。删除命令执行成功了，文件也确实不在了。

小蝶抢答："我知道这个！**文件被谁'攥在手里'了**——有个进程还开着它，删掉的只是'目录里的名字'，数据本体在进程关手之前不会释放。"

"正解。"老码点头，"破案口诀：`lsof | grep deleted`——揪出那个攥着鬼的进程。常见元凶是日志切割服务没重载，老进程还握着旧日志的手柄。**重启它，50G 当场落地。**"

林一码感叹："这大陆的'删除'从来不是立即销毁，只是**解除登记**啊。"

"聪明。"老码说，"数据库、缓存、垃圾回收，全是这一个道理的不同马甲。"

### 灵异档案二：半夜 Load 飙红，CPU 却在睡觉

当晚，客栈警报大作：监控显示系统负载 **Load 20+**（8 核机器），但 CPU 使用率只有 15%。

"CPU 不忙，负载却爆表——**大家不是在算，是在等**。"老码带林一码用了三招：

1. `ps aux | awk '$8 ~ /D/'`——揪出一堆 **D 状态**进程（不可中断睡眠，常见于死等磁盘）；
2. `iostat -x 1`——磁盘 sda 利用率 98%，写入队列排成长龙；
3. `iotop`——真凶现形：一个进程在疯狂写日志，每秒上千条 ERROR。

处理很"外科手术"：先止血（清日志、收紧日志级别），再断根（应用改成**异步日志**，写日志的活儿丢给专职线程慢慢干）。

"记住这场戏的形态：**Load 高、CPU 低 = 堵车，不是发动机弱**。"老码说，"Load 高、CPU 也高 = 真在烧脑。这两种病，用药完全相反。"

## 第六章 四神探成名战：Bug 魔王的四具分身

翻过主峰前，老码决定让林一码实战。山腰有一片被黑雾笼罩的谷地——**事故谷**。谷里盘踞着 Bug 魔王的四具分身，每年吞掉无数项目的 uptime。

"排查线上事故，就像破案。"老码传授总纲，"**先止血，再查因，后复盘。人可以先救，案必须破到底——不破案的止血，血会再流。**"

### 战一：正则陷阱（CPU 烧到 100%）

**症状**：某 Java 服务 CPU 突然飙到 980%（8 核 12 线程的机器），接口全线超时。

**破案**：

1. `top` 锁定进程 → `top -H` 深入到**线程**，发现两个线程各吃掉 480%；
2. 线程 ID 转 16 进制：`printf '%x' 线程号`；
3. `jstack 进程号 | grep 'nid=0x3ab'` ——在 Java 线程快照里按线程 ID 精准定位堆栈；
4. 堆栈停在：一行正则表达式上。

**真凶**：代码把 `Pattern.compile()` 写在了方法**内部**——每调用一次就重新编译一次正则。某个接口每天被调用上亿次，等于让 CPU 反复背同一篇课文背一亿次。

**解法**：把 Pattern 提为 `static final`，编译一次、处处复用。**一行代码的位置，决定一台服务器的生死。**

老码点评："CPU 高不可怕，可怕的是瞎猜。**top → 线程 → 线程号转十六进制 → jstack 对号入座**，这条链路你以后要练到闭眼能走。"

### 战二：隐形杀手（进程人间蒸发）

**症状**：Java 进程半夜消失，应用日志干净得像新的一样。

**破案**：

1. `dmesg -T | grep -i oom` ——内核监控录像上赫然写着：**Out of memory: Killed process**。凶手锁定 OOM Killer；
2. 复盘内存史：`jmap -heap` 显示老年代占用 95%；
3. 导出堆转储（heap dump），用 MAT 的 Leak Suspects 报告做"验尸报告"——

**真凶**：一个 `ConcurrentHashMap` 被当缓存用，**只进不出**。每来一个请求 put 一条，从不清理。三个月，慢中毒，最终撑爆内存，引来 OOM Killer 执法。

**解法**：换**带上限和过期时间**的缓存（Caffeine：`maximumSize` + `expireAfterWrite`）；JVM 加 `-XX:+HeapDumpOnOutOfMemoryError`——**崩溃时自动留遗书**；用 systemd 的 MemoryMax 给进程划红线。

老码点评："**无限增长的集合 = 定时炸弹**。内存泄漏兽从不咆哮，它只是安静地长大。"

### 战三：800MB 的真凶（磁盘上的罗生门）

**症状**：服务器负载 28.5，用户全在骂卡。

**破案**：`top` 里 CPU 不忙，但 **wa（IO 等待）高达 35%** → `iostat` 显示磁盘利用率 98.5% → `iotop` 锁定 mysqld → 开 MySQL 慢查询日志，抓到一条 45 秒的查询 → `EXPLAIN` 一看：**全表扫描**。

**真凶**：orders 表 5000 万行，status 字段**没建索引**，一条"查待发货订单"的 SQL，把整张表从头到尾摸了一遍。

**解法**：先杀慢查询止血；建复合索引 `(status, created_at)`；扫描行数从 5000 万降到 10 万，45 秒 → 0.5 秒。

老码点评："**磁盘不喊疼，它只会把所有等它的人排队拖垮。** 上游吵翻天，病根常在最沉默的那一层。"

### 战四：日志海啸（Load 50，CPU 却闲）

**症状**：Load 50，CPU 30%，用户只觉得"全世界都很卡"。

**破案**：还是那一套——D 状态进程一大把 → `/proc/PID/wchan` 显示全在等磁盘 → `iotop` 现形：一个 Java 进程在写一个疯狂膨胀的日志文件，**每秒刷一千多条 ERROR**。

**真凶**：一个下游服务超时，代码 catch 之后把整段堆栈按 ERROR 级别打印，重试 N 次 × 每秒 N 请求 = **日志洪水**。机械硬盘被冲垮，全系统陪着泡在水里。

**解法**：止血——调高日志级别、异步化（AsyncAppender）、logrotate 轮转；根治——修好下游，给 ERROR 加采样限频。

老码总结四战："你发现没有？四场戏一个剧本：**现象 → 定位（每层一根探针） → 真凶 → 止血+根治**。监控是探针，内核日志是监控录像，jstack/jmap/iostat/iotop 是解剖刀。工具会换，剧本永远不变。"

### Bug 魔王现声

四具分身溃散的黑雾中，一个声音第一次直接对林一码说话——低沉、无处不在：

> "人类，你拆我四具分身，不过是拆了我的四肢。
> 我在你们每一行偷懒的代码里、每一个没想的边界里、每一次侥幸的上线里。
> 你升到多高，我就跟到多高。—— **Bug**"

林一码攥紧了拳。他知道，这不是威胁，是预言。

## 特别篇 · 夜袭：OOM 巨兽与执法官的博弈

> Bug 魔王四具分身被拆的第七夜，山谷里的黑雾忽然浓得化不开。
> ——事故谷夜话

四神探成名战的第七夜，主角团在事故谷口扎营。半夜，小蝶被一阵"心跳漏拍"惊醒——谷地深处，一头**山一样大的黑影**正在成形。

**OOM 巨兽**。Bug 魔王麾下真正的统帅级怪物：它不袭击进程，它只是**让整个世界吃光粮食**，然后看着执法官（OOM Killer）把最胖的人拖出去处决。

"东边 3 公里，支付服务的老巢。"老码脸色一变，"那台机器 64G 内存，昨天开始 RSS 一路爬——今晚破 60G 了。**巨兽吃饱之时，就是执法官开刀之刻。**"

### 战场：与内核抢时间

三人冲到支付老巢时，`free -h` 上的 available 只剩 1.2G。每一秒都在倒计时。

"老码，直接重启？"

"重启能续命，破不了案。"老码摇头，"**重启的代价是丢现场——巨兽明天还会回来，还长得更大。** 先做三件事，一秒都不能浪费：

> **第一件，留证据**：`jmap -dump:live,format=b,file=pay.hprof 进程号`——活体切片，把巨兽此刻的'内脏'整个取出来。注意加 `live`，只切还活着的对象，切片小一半；
> **第二件，划红线**：立刻给进程配 `MemoryMax`（systemd）——**把巨兽的活动范围圈死**，它要越界，执法官只能杀它，**不会祸及邻居**；
> **第三件，上保护**：`echo -1000 > /proc/支付进程/oom_score_adj`——给支付服务挂'免死金牌'？**不行！** 免死金牌是把双刃剑：执法官杀不到你，就会转头杀别的进程——**给别人挖坟，不是安全，是嫁祸**。正确姿势是**把无关进程调低权重**，让执法官的目标清单更合理。"

第一件事执行到一半，巨兽咆哮了——**RSS 触底，内存耗尽**。

内核监控录像（dmesg）上，那行致命的字刷了出来：

> `Out of memory: Killed process 28471 (java)`

支付进程倒了。**但这次，它死得明明白白。**

### 验尸：MAT 揭开巨兽的食谱

林一码抱着 8G 的 heap dump，用 MAT（内存分析工具）打开。Leak Suspects 报告跳出来的瞬间，所有沉默都有了答案：

> **One instance of "com.pay.cache.LocalCache" keeps 6.1 GB memory.**
> **问题：LocalCache 是一个 ConcurrentHashMap，只 put，永不 remove。**

"三个月前上线的'本地缓存优化'。"老码念着代码注释，冷笑一声，"注释写的是'提升性能，暂不设上限'。**这个'暂'字，值 6.1 个 G。**"

巨兽的食谱找到了：**它吃的不是内存，是侥幸。** 每一个"先不清理了，反正 soon 会改"的 HashMap，都是喂给它的饲料。

### 破解：给巨兽断粮

黎明前，重构方案上线，四道闸：

1. **有界缓存**：ConcurrentHashMap 换 **Caffeine**——`maximumSize(10_000)` + `expireAfterWrite(10min)`，**缓存必须自带'胃容量'和'消化周期'**；
2. **崩溃遗书**：JVM 加 `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dump/`——**下次再死，遗书自动留好**，不用半夜抢现场；
3. **内存水位告警**：RSS 超 70% 报警、超 80% 呼叫——**在巨兽成年之前就发现它**；
4. **压测验收**：回放 3 个月流量，RSS 曲线必须**走平**——**"内存只涨不跌"的应用，都是缓期执行。**

### 战后：巨兽的进化

一周后，同样的黑雾在谷口再次出现——OOM 巨兽又一次试图成形。

但这一次，支付老巢的 RSS 在 58% 稳稳走平。巨兽在边界外咆哮、撞击、最终……散了。

"你发现了吗？"老码望着散去的黑雾，"**巨兽最可怕的不是力量，是耐心。** 它用三个月长成，你用三小时拆解——但下一次，它只会更慢、更隐蔽地回来。"

"那我们赢了吗？"

"**这场战争没有'赢'，只有'守住了今天的阵地'。**"老码把 `HeapDumpOnOutOfMemoryError` 这行参数郑重写进秘籍，"所以好的工程师有两个习惯：**白天写代码时假设巨兽存在，晚上睡觉前确认防御已经布好。** 这不是悲观，这是专业。"

**【本场掉落】**：jmap 活体切片、MAT Leak Suspects、oom_score_adj 的双刃剑、Caffeine 有界缓存、HeapDumpOnOutOfMemoryError 遗书机制、内存水位告警。

## 特别篇 二 · 追猎：不死的僵尸与消失的句柄

> OOM 巨兽败退的第三夜，山谷里出现了更阴森的东西：
> **死了，却不下葬；活着，却不存在。**
> ——Linux 山脉怪谈·第 7 页

### 现场：两个"灵异"

灰烬客栈一夜之间报了两个灵异事件：

**灵异一**：`ps` 里躺着一堆**标记为 `<defunct>`** 的进程——它们已经"死"了，却**占着进程表的位置赖着不走**，像一排排立着的墓碑。

**灵异二**：另一台机器，应用报错 **Too many open files**——文件明明都关了，句柄（file descriptor）却一路涨到上限，新连接全部被拒。

老码扫了一眼，报出两个病名："**僵尸进程（Zombie）**和**句柄泄漏（fd leak）**。今晚一个一个收拾。"

### 追猎一：为什么死人不下葬

"进程死亡的标准流程你记得吗？"老码问，"**子进程死时不是立刻消失——它会留下一张'死亡证明'（退出状态码），等父亲来'收尸'（wait 系统调用）**。父亲收了尸，墓碑才会清掉。"

"那这些墓碑……"

"**父亲不收尸。** 三种情况：父亲根本忘了写 wait（代码 bug）；父亲还在忙别的（业务长循环里没有收尸点）；最惨的一种——**父亲自己先死了，孩子成了孤儿，被 1 号进程（init/systemd）收养。** 好在 1 号进程是称职的养父，会替所有孤儿收尸。**所以僵尸满山跑，多半是'亲爹还活着但不作为'。**"

**猎杀三步**：

> 1. **找亲爹**：`ps -o ppid= -p 僵尸PID`——墓碑上刻着爹的名字；
> 2. **劝收尸**：给爹发信号 `kill -CHLD 父PID`——"你的孩子死了，来签字"；代码层的正解是**信号处理器里调用 waitpid，或用 SIGCHLD 异步收尸**；
> 3. **爹无可救药怎么办**：杀掉爹——孤儿们被 1 号进程收养，**养父会替它们办完后事**，僵尸瞬间清空。

"记住这条伦理链："老码总结，"**僵尸不可怕，可怕的是不负责任的父亲。** 容器时代还有个变体——如果 1 号进程不是 init 而是你的应用（比如直接跑 java），它不懂收尸，容器一久僵尸成山。**解法：用 tini/init 做容器入口**，让专业的收尸人来当 1 号。"

### 追猎二：句柄去哪了

第二台机器，句柄数每天涨一点，涨到上限全体罢工。

```
lsof -p 应用PID | awk '{print $9}' | sort | uniq -c | sort -rn | head
```

一行命令，句柄的去向赫然在目：**同一个目标 IP:端口，两万多个连接，全是 CLOSE_WAIT**。

"CLOSE_WAIT——**对方早就关了连接，我们这边收到了'再见'，但应用一直没调 close**。"老码说，"**这是应用层的账：拿了两万个'再见'，一封都没回礼。** 八成是异常分支里连接没关、或者连接池的'坏连接'没驱逐。"

**猎杀三步**：

> 1. **止血**：重启应用，句柄清零，服务恢复——**老规矩，先止血**；
> 2. **验尸**：抓异常日志 + 代码走查，锁定"忘记 close 的异常分支"——修复，try-with-resources / finally 里关资源，**连接池加 testOnBorrow/空闲驱逐**；
> 3. **设防**：句柄水位告警（`ls /proc/PID/fd | wc -l` 超 60% 报警）+ `ulimit -n` 调到合理值——**上限是保险丝，不是容量规划**。

### 战后

灰烬客栈的怪谈墙上，当晚添了两句话：

> **"僵尸：死了不走的，去找它爹。**
> **CLOSE_WAIT：别人先走的，找你自己的 close。"**

以及老码的秘籍补录：

> **"Linux 的资源观：一切皆文件，一切有上限。
> 进程表有上限，句柄有上限，端口有上限。
> 所谓容量规划，就是把这些'看不见的上限'，
> 一个个找出来，画上刻度，装上报警器。"**

**【本场掉落】**：僵尸进程三因与三解（SIGCHLD/waitpid/杀爹）、容器 1 号进程与 tini、CLOSE_WAIT 的含义与猎杀、句柄水位告警、ulimit 的定位。

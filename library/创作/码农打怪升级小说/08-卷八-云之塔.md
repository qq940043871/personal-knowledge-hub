## 第二十四章 云之塔底：虚机与容器的两种分身术

大陆上空悬浮着一座通天巨塔——**云之塔**。塔的第一课，是"**一台机器怎么变出 N 台**"。

### 虚拟机：发动机与整车厂

"最重的分身术是**虚拟机**。"塔内教官说，"**KVM 是内核里的发动机**（真虚拟化，CPU 内存都由内核直管），**QEMU 是整车厂**（伪装出一整套'假硬件'：假网卡、假硬盘、假显卡）——客户机操作系统以为自己开的是真车，其实每个'踩油门'都被转译成对真硬件的调用。"

"每辆'假车'都装整套系统，太重了？"

"对。所以有 **virtio 半虚拟化**——让客户机**直接说母语**，不走'假硬件翻译'，性能逼近物理机。老兵踩过的坑：**虚拟机性能莫名差，八成是忘了配 virtio 或 CPU 模式没设 host-passthrough。**"

### 容器：千层饼与隔间

塔的第二层是轻装上阵的**Docker**。它的两个支柱：

**Namespace——六个隔间**：进程号、网络、挂载点、用户、主机名、IPC 各自独立。"**每户独立门牌与水表**——你家的 PID 1 在你家就是皇帝，出了门（宿主机上）只是个普通进程。**容器不是虚拟机，它只是'被精心隔离的进程'。**"

**Cgroup——紧箍咒**：给每个隔间限量配给——CPU 用几核、内存用几 G、IO 占多少。"**自助餐夹子限量的道理**：不限量，一个容器能吃光整艘船。"

**镜像——千层饼**：一层只读层叠一层（基础系统层→依赖层→应用层），**全楼共用地基，各家只装各家的装修**——所以镜像几秒就能起：大家共享底层，只创建最上面的可写层。

"千层饼也有暗伤：**构建了一堆没用的层，磁盘被吃穿**。定期 `docker system prune` 大扫除。"

"还有一个名场面："教官压低声音，"**容器里的时间慢了 8 小时**——时区幽灵。明明代码没问题，日志时间全错。解法朴素得很：把宿主机的 localtime 挂载进去。**诡异的问题，常有朴素的答案。**"

## 第二十五章 塔顶棋局：Kubernetes 与自愈机器人

### 声明式：你只说"要几个"

塔顶是**Kubernetes（K8s）**的棋局。它颠覆了林一码的命令式思维：

"普通指挥：'把 A 服务重启'。K8s 指挥：'**我声明：世界上应该永远有 3 个 A 副本**'——然后它日夜盯着现实，**现实和声明不符，就自动修正**。你删它一个 Pod？它当场补一个——**自愈机器人，你删它偏活**。"

"这就是**声明式编排**：告诉系统'要什么'，而不是'怎么干'。**点单之后店长自动补货，不用催。**"

### 三层棋子：Pod、Deployment、Service

- **Pod**：最小作战单位——一辆**出租车**（里面可能挤着主容器+边车容器几个乘客）；
- **Deployment**：车队编制——**声明要几辆车、什么版本**，滚动更新时一车一车换（旧车下新车上，全程服务不断）；
- **Service**：调度总机——Pod 会生老病死、IP 朝不保夕，**Service 给一个稳定的虚拟 IP 和域名**，背后负载均衡到活着的 Pod；**Endpoints 名册**自动维护。

"再往上，**Ingress 是塔的大门**：把外部 HTTP 流量按域名/路径路由到各 Service。"

### 三桩悬案

**悬案一·CrashLoopBackOff**：Pod 起了崩、崩了起，无限循环。破案：`kubectl logs --previous` 看**上一世的遗言**——八成是启动就报错（配置错、依赖不通、OOMKilled）。

**悬案二·Service 不通**：Service 建了，流量到不了 Pod。破案：查 **Endpoints**——空的！回头一看，**Pod 的 label 和 Service 的 selector 对不上**——**总机有分机号，话务员名册上却没登记**。K8s 的万物皆靠 label 对暗号。

**悬案三·Pod 一直 Pending**：调不出去——要么集群资源不足，要么 PVC 存储卷没人接盘。

**悬案四·容器上不了外网**：宿主机 `ip_forward=0`——**包裹被海关扣下**，内核根本不转发流量。

## 特别篇 · 僵尸 Pod 围城

> 云之塔的中层关押着一种怪物：
> 它死不了，也活不好，**每隔几分钟就复活一次，然后立刻再死**。
> 新兵叫它"打不死的青铜怪"，老兵叫它——CrashLoopBackOff。

### 围城

升级试炼当天，塔中层的**订单服务区**突然警报齐鸣。监控大屏上，一片刺目的红色正在蔓延：

> **pod/order-7d4f9 → CrashLoopBackOff (第 41 次)**
> **pod/order-7d5g2 → CrashLoopBackOff (第 38 次)**
> **pod/order-7d6ab → CrashLoopBackOff (第 44 次)**

**僵尸 Pod 大军**——每次重启挣扎几秒，立刻再死，周而复始。更糟的是：自愈机器人在拼命执行使命（"3 个副本"），僵尸死了就补新的——**新的也变僵尸**。可用副本数在 0 和 1 之间疯狂摇摆，订单流量正在挨打。

"普通的 Pod 挂掉，自愈机器人是救星。"塔教官赶到时神情凝重，"**但僵尸面前，自愈是帮凶**——它不停复活一个注定要死的容器，还把每次崩溃的账都记在'重启次数'上。**先关掉自愈的闸，再查案**：扩一个临时副本顶流量，把故障副本隔离出来。"

### 破案：看前世，别只看今生

"僵尸案第一定律：**`kubectl logs --previous`**——看它**上一世**的遗言。"教官敲下命令。

上一世日志的最后一行，只有一句白得刺眼的错误：

```
Exception in thread "main" java.lang.OutOfMemoryError: Java heap space
```

"OOM？容器 limit 不是给了 4G 吗？"

"问得好——**4G 是容器紧箍咒，JVM 堆呢？**"教官调出 Pod 的启动参数。答案跳了出来，荒诞又经典：

```
-Xmx8g
```

**4G 的紧箍咒，塞了一个 8G 的堆。** JVM 以为自己有 8G，实际容器的 cgroup 上限 4G——堆还没用满，容器先被内核处决（OOMKilled，exit code 137）。**每一次重启都是同一场死刑。**

"这是云原生时代最经典的'**两张地图**'惨案：**JVM 的地图和容器的地图，画的不是同一座城。**"教官说，" JDK 8u191+ 和 JDK 10 之后，JVM 已经能感知 cgroup（`UseContainerSupport`）——但老镜像、手工写死的 `-Xmx`，会亲手废掉这份感知。"

### 降服：一张地图，一个约定

修复方案十分钟后上线：

> **1 · 对齐地图**：`-Xmx3g`（容器的 75%），留 1G 给堆外、元空间、线程栈——**紧箍咒和佛法心经，必须念同一套**；
> **2 · 升级镜像**：JDK 升级并开启容器感知，让 JVM **自己读紧箍咒**；
> **3 · 留案底**：给僵尸 Pod 加 **liveness 探针的启动宽限**（`initialDelaySeconds`），避免"应用启动慢被误杀"，让真正的慢性子和真僵尸区分开；
> **4 · 体检**：PVC、ConfigMap、依赖地址逐项过——**僵尸案的凶手常常不止一个**。

僵尸大军的红色浪潮，像退潮一样退去。自愈机器人重新变回守护者——**你删它偏活**的那股执拗劲儿，此刻看起来无比可爱。

"记住今天的怪物，"教官最后说，"**CrashLoopBackOff 不是病，是'死因不明'的替身文学。** 真正的凶手永远在 `--previous` 的遗言里、在 exit code 里、在 events 里。**K8s 给了你一具会不停复活的尸体——这是恩赐，不是诅咒：它把'偶发'变成了'可反复观察的复现现场'。**"

**【本场掉落】**：`kubectl logs --previous`、exit code 137 与 OOMKilled、cgroup limit 与 JVM 堆的对齐公式（limit = 堆 × 1.2~1.3）、容器感知 JDK、探针宽限期。

## 特别篇 二 · Ingress 丢单之谜：大门的四个咒语

> 云之塔的大门（Ingress）有一本值班日志。
> 翻开它，80% 的案子都写着同一句话：
> **"流量到了，但它没到该到的地方。"**
> ——大门守卫·交接班记录

### 案发：深夜的 404 风暴

僵尸 Pod 围城平息后的第三个深夜，塔的大门告警：

> **Ingress 突发 404 风暴**：`/api/order/*` 路径，错误率 34%
> 同期 **502 也有 8%**，而且集中在某一个新服务

值班的守卫翻了半天路由规则，一头雾水："配置没动过啊！"

### 破案 404：谁偷走了前缀

林一码核对新服务的 Ingress 配置，真相藏在一个字符里：

> 路由规则写的是 `path: /api/order`
> **但没写 `pathType` 和去重写规则（rewrite-target）**

流量实际打到后端时，**完整路径 `/api/order/create` 被原样转发**——而后端服务注册的是 `/create`，根本不认识带前缀的自己。

"**Ingress 是'带信上门'还是'撕掉信封再进'，全看 rewrite 配置。**"老码闻讯赶来（他今夜正好巡塔），"**前后端对'路径'的理解必须严丝合缝**：要么网关把前缀撕掉（rewrite），要么后端注册完整路径。**各让半步 = 404。**"

顺手补第二条军规："**`pathType` 必须显式声明**——ImplementationSpecific 是历史包袱，Prefix 和 Exact 才是明牌。**模糊的配置，就是未来的故障。**"

### 破案 502：Endpoints 又空了

502 的案子反而快——守卫已经学过 label 对暗号那一课，直查 Endpoints：

```
kubectl get endpoints order-svc
# NAME        ENDPOINTS   AGE
# order-svc   <none>      3d
```

Endpoints 是空的。但这次 **label 是对的**。

"那就是第三种可能——**Pod 活着，但'没资格进名册'**。"林一码直查 readiness 探针，一查一个准：新版本把 readiness 的检查端口配错了——**Pod 容器活着，但'体检'一直不过，永远进不了 Endpoints 名册**。

"**liveness 挂了会重启，readiness 挂了只是被除名。**"老码总结，"**名册（Endpoints）为空的排查顺序，背下来：**

> **① selector 和 label 对暗号 → ② 探针配对没有 → ③ 探针检查的端口/路径对不对 → ④ Service 的 targetPort 和容器暴露端口对不对。**
> **四步走完，天底下没有查不出的 Service 不通。**"

### 修堤：把"下次"堵死

天亮前，除了修配置，两道长堤也筑起来：

> **1 · 契约测试进流水线**：路由规则 + 后端注册路径，在 CI 里做**自动比对**——**前后端对'路径'的共识，从'口头约定'升级为'流水线断言'**；
> **2 · 金丝雀验证**：新服务上线，先切 1% 流量 + 错误率告警——**大门的 404 风暴，应该在 1% 的流量里被听见，而不是在 34% 里被看见**。

### 尾声

大门值班日志的新一页，林一码留下了一句话，后来被守卫们称为"**大门四咒**"：

> **路径有契约——前缀撕不撕，两边说好；**
> **暗号要显式——pathType 不留模糊；**
> **名册常核对——Endpoints 空即断案四步；**
> **上线如放闸——金丝雀先探路，大队再过河。**

**【本场掉落】**：Ingress rewrite 与 pathType、路径契约测试、readiness 与 Endpoints 除名、Service 不通四步排查法、金丝雀探路。

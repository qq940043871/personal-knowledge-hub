## 一、RAG 评估三元组

RAG 系统故障定位的基本框架：三个维度分别对应系统的三个环节，哪一维掉分就修哪一环（TruLens 体系，与 RAGAS 指标可直接映射）：

| 维度 | 评估目标 | 核心问题 | 对应 RAGAS 指标 |
|---|---|---|---|
| **上下文相关性** | 检索器 | 检回的上下文与 query 高度相关吗 | Context Precision / Recall |
| **忠实度** | 生成器 | 答案完全基于上下文吗（量化幻觉） | Faithfulness |
| **答案相关性** | 端到端 | 答案直接、完整回答了原问题吗 | Answer Relevancy |

**忠实度 ≠ 答案相关性**：忠实度管「是否严格遵循上下文」，答案相关性管「是否答了用户问的」。答案可以全基于上下文（高忠实）却答非所问（低相关）——问「法国在哪里，首都是哪里」只答「法国在西欧」就是典型。

## 二、检索指标

前提：有标注数据集（query → 真实相关文档）。

$$\text{Precision@k} = \frac{\text{前 k 个结果中相关数}}{k} \qquad \text{Recall@k} = \frac{\text{前 k 个结果中相关数}}{\text{相关文档总数}}$$

$$\text{MRR} = \frac{1}{|Q|}\sum_{q=1}^{|Q|}\frac{1}{\text{rank}_q} \qquad \text{MAP} = \frac{1}{|Q|}\sum_{q=1}^{|Q|}\text{AP}(q)$$

- **MRR**（平均倒数排名）：只关心**第一个**相关文档出现多早——用户通常只看第一条答案的场景；
- **MAP**（平均准确率均值）：同时管精确率和全部相关文档的排名分布——多个相关块都要进的场景（RAG 上下文组装）；
- **实战口径**：ownrag 用「三判中」替代逐指标打分——**找对 / 找全 / 该拒答的拒答**，全判中退出码 0 否则 1，直接当回归门禁用（见 [70-企业级工程基准](../../06-Agent开发/70-企业级工程基准.md) RAG #15）。

## 三、响应评估

### 3.1 LLM-as-judge：断言分解

把「答案好不好」拆成若干条可独立验证的断言，逐条让 LLM 判真伪：

```python
# 断言分解评估（伪代码骨架；完整实现见 all-in-rag 工程 docs/chapter6/18）
def judge_by_assertions(answer: str, query: str, judge_llm) -> float:
    assertions = judge_llm.generate(f"把答案拆成 3-5 条事实断言：{answer}")
    verdicts = [judge_llm.verify(a, evidence) for a in assertions]
    # ★特殊点1 judge 模型与生成模型尽量不同源——同源 judge 有系统性偏好
    return sum(verdicts) / len(verdicts)
```

### 3.2 词汇重叠：ROUGE / BLEU / METEOR

与参考答案的 n-gram 重叠度计算，零 LLM 成本。适用边界：**摘要类任务**（ROUGE）与**有标准短答案**的任务（BLEU）；对开放式问答基本无效——「狗在床上面」vs「床上有只狗」词汇全对上才算对，换个说法就得 0 分。中文场景必须先分词（jieba）再算（TinyEval 的 `qa_f1_zh_score` 实现）。

### 3.3 客观题评估（可直接抄的打分器）

llm-universe C5 给出多选题打分口径：错答 0 分 / 漏选 0.5 / 全对 1（v2 错答 -1 抑制瞎猜）——把领域知识题做成选择题库，是低成本验收生成质量的务实做法。

## 四、Agent 评估

Agent 比 RAG 多评两件事：**工具调用对不对**、**多步任务成没成**。

### 4.1 工具调用：BFCL

BFCL（Berkeley Function Calling Leaderboard）四类测试：Simple / Multiple（多选一）/ Parallel（并发多调用）/ Irrelevance（**该不调时不调**——最后一类最容易被忽视）。

核心是 **AST 匹配**而非字符串比对——语法树等价需满足三个条件：

1. **函数名完全一致**（精确匹配）；
2. **参数键值对集合相等**（忽略顺序）：`f(a=1, b=2)` ≡ `f(b=2, a=1)`；
3. **参数值语义等价**：`f(x=2+3)` ≡ `f(x=5)`、`f(s="hello")` ≡ `f(s='hello')`。

多函数场景：调用数量相同、每个都匹配、调用顺序可以不同（集合匹配）。字符串比对会把这三类等价判成错，指标虚低。

### 4.2 综合任务：GAIA

GAIA（Meta AI × HuggingFace）：466 个真实世界问题，Level 1/2/3 三级难度，考察多步推理 + 工具使用 + 文件处理 + 网页浏览，准精确匹配（Quasi-Exact Match）评分。它是「综合能力体检」——单点指标都好不代表能做成完整任务。

| 基准 | 评什么 | 规模 | 特色 |
|---|---|---|---|
| **BFCL** | 函数调用 | 1120+ 样本 | AST 匹配，含 Irrelevance 类 |
| **GAIA** | 真实任务综合 | 466 题 | 三级难度，多模态 |
| ToolBench | 真实 API 调用 | 16000+ 场景 | 清华，真实 API |
| AgentBench | 通用智能体 | 8 领域 | 清华，多环境 |
| WebArena | 网页交互 | 真实站点 | CMU，自托管环境 |

### 4.3 数据生成质量

合成数据集本身也要评（hello-agents ch12）：LLM Judge 多维评分、Win Rate 胜率对比（新旧数据集各训一版模型对打）、人工验证界面抽样——**评数据的成本低于用脏数据训完再排错**。

## 五、评估工程化

- **评测集从哪来**：qa_log 回流是评测集扩充的唯一原料（RAG #14）——线上每条「答案不对」的反馈都是标注候选；
- **回归门禁**：固定问答集 + 三判中口径 + 退出码约定，任何切分/embedding/解析器/模型变更先跑再合入（RAG #15）；Agent 侧用基准框架跑预设任务集产出报告并与上份对比（Agent #15）——**能力可量化回归**；
- **可观测性配套**：TruLens/RAGAS/Phoenix 三件套选型——TruLens 强在三元组可视化，RAGAS 强在无参考评估，Phoenix 强在 trace 钻取（OpenTelemetry 插桩 + bad case 切片）；评估指标只能给分，**trace 才能回答「为什么错」**。

### 企业级升级要点

- **指标链住闸门**：Faithfulness 检出的幻觉问题，靠生成后纯代码引用闸门兜底（规则可测试、随评测集回归），见 `ownrag/generate/gates.py`——评估发现问题，闸门拦住问题，两者口径要对齐。
- **拒答率是指标不是事故**：充分性闸门上线后拒答率必然上升，用评测集校准「重排分阈值」而不是把阈值当 bug 修掉，见 `ownrag/generate/gates.py` 的 `_MIN_RERANK_SCORE`。
- **judge 一致性先校准**：LLM-as-judge 与人工标注的一致率（如 Cohen's Kappa）达标后再放量使用；抽样人工复核机制常开。
- **评估成本预算化**：LLM-as-judge 按 token 计费，全量评估线上流量不现实——抽样策略 + 分层评估（客观题全量、judge 抽样）+ 预算上限，见 `ownrag/generate/budget.py`。

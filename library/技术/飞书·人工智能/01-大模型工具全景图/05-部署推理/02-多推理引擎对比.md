## 一、引擎选型对比

**结论性口径**：生产 API 服务 **vLLM 首选**；高并发/复杂调度看 **SGLang**；个人本地用 **Ollama**；Windows 桌面 **LM Studio**。四者都提供 OpenAI 兼容接口，接入层可以做到换引擎不换代码——这正是「按场景换引擎」可行的前提。

| 维度 | vLLM | SGLang | Ollama | LM Studio |
| :--- | :--- | :--- | :--- | :--- |
| **定位** | 生产级推理服务引擎 | 高性能推理 + 复杂调度 | 个人本地一键运行 | 桌面 GUI 应用 |
| **吞吐与并发** | PagedAttention 管 KV cache + continuous batching，吞吐第一梯队 | RadixAttention 前缀缓存复用；tp/ep 并行、EAGLE 投机采样，调度能力更强 | 单实例、并发能力弱，面向个人 | 内建本地 server，并发非目标 |
| **量化格式** | 原生 HF 权重（AWQ/GPTQ 可选） | 原生 HF 权重 | GGUF（llama.cpp 系） | GGUF |
| **易用性** | `vllm serve` 一条命令，需 CUDA 环境 | `launch_server` 一条命令，新模型 parser 依赖版本跟进 | 安装包即用，`ollama run` 即跑 | 界面内搜索下载，支持离线导入 GGUF |
| **适用场景** | 生产 API 服务首选 | 高并发、长上下文、MoE 大模型 | 个人本地验证、微调模型导入 | Windows 桌面、无网络环境、非开发者 |

证据口径（来自 self-llm 各篇）：

- **vLLM**（Qwen3-8B 篇）：`vllm serve` 直接起 OpenAI 兼容服务，`--reasoning-parser deepseek_r1` 把思考内容拆成独立 `reasoning_content` 字段；离线批推理走 `LLM.generate` + `SamplingParams`。
- **SGLang**（GLM-4.7-Flash / MiniMax-M2 篇）：`--tp-size 4/8` 张量并行 + `--ep-size` 专家并行（MoE 必备），`--mem-fraction-static 0.8~0.85` 控 KV cache 显存水位；MiniMax-M2 权重约 220 GB、每 1M token 上下文再加约 240 GB——大模型 MoE 部署的显存账按此口径预估。
- **Ollama**（Gemma3 篇）：`ollama run` 之后 open-webui 自动检测本地服务并调用，个人档零配置。
- **LM Studio**（Qwen3 Windows 篇）：按硬件给「绿色火箭」推荐标记；8G 显存选 Q4_K_M，充裕再上 Q8_0。

**篇目地图（模型 × 引擎/硬件，本篇证据出处）**：

| 模型 | 引擎篇 | 个人档篇 | 硬件/评测篇 |
| :--- | :--- | :--- | :--- |
| Qwen3-8B | vLLM（CUDA SGLang 篇暂缺，另有 sglang-ascend） | Windows LM Studio | AMD lemonade；EvalScope 智商情商 |
| GLM-4.7-Flash | vLLM + SGLang | LoRA 微调 Docker 镜像 | — |
| MiniMax-M2 | vLLM + SGLang | — | EvalScope 并发测试 |
| Gemma3-4B | FastApi | ollama + open-webui | AMD 环境准备与部署；evalscope |
| Llama3_1-8B | FastApi / langchain / WebDemo | GGUF 转换 → Ollama | — |

> 注意 Qwen3-8B 这一行：CUDA 侧 SGLang 篇暂缺（只有昇腾 sglang-ascend 篇）——「新模型首发往往只有 vLLM 篇」的实例，SGLang 口径取自 GLM-4.7-Flash 与 MiniMax-M2 两篇。

**三步决策顺序**：先问部署位（个人/桌面 → Ollama/LM Studio，服务器/集群 → vLLM/SGLang）；再问并发与调度复杂度（常规生产 API → vLLM；高并发长上下文、MoE 专家并行、要投机采样 → SGLang）；最后问模型格式（GGUF 产物 → Ollama 链路，HF 原生权重 → vLLM/SGLang）。

## 二、GGUF 转换链路：微调模型进 Ollama

PyTorch 训练产物不能直接导入 Ollama——它只认 GGUF（llama.cpp 引入的二进制格式，取代 GGML）。基础模型与 LoRA 适配器**各转一道**，再用 Modelfile 组装：

```bash
# GGUF 转换链路（伪代码骨架：重点在链路与坑；完整流程见 self-llm 工程
# models/Llama3_1/动手转换GGUF模型并使用Ollama本地部署.md）

# 1) 下载基础模型（HF 权重目录）
snapshot_download(repo_id="unsloth/Llama-3.1-8B-Instruct", local_dir=BASE_DIR)

# 2) 基础模型 → GGUF（llama.cpp 的 convert_hf_to_gguf.py）
python convert_hf_to_gguf.py --outfile model.gguf BASE_DIR

# 3) LoRA 适配器 → GGUF（--base 指向基础模型目录）
python convert_lora_to_gguf.py --outfile adapter.gguf --base BASE_DIR LORA_DIR

# 4) Modelfile 组装并注册：FROM 指向 GGUF，ADAPTER 指向 LoRA GGUF，
#    TEMPLATE 沿用基模型的模板
ollama create my-model -f my_lora_adapter.Modelfile
```

- ★特殊点1 基础模型与 LoRA 各转一道，不是先合并再转：`convert_lora_to_gguf.py` 的 `--base` 用于对齐基模型结构；也可走先 merge 回基模型、只转一个 GGUF 的链路——两条链路二选一，别混着配。
- ★特殊点2 Modelfile 三要素 `FROM`/`ADAPTER`/`TEMPLATE`，最容易错的是 TEMPLATE：微调没动对话模板就直接沿用基模型的，自创模板会格式错位、输出乱码。
- ★特殊点3 llama.cpp 预编译包必须按本机 CUDA 版本挑带 CUDA 的 release——装成 CPU 版，GGUF 只能吃 CPU 推理。

GGUF 量化档位与 LM Studio 的选择口径一致（见第一节）：8G 显存 Q4_K_M 起步、充裕再上 Q8_0；转换与量化是两步——`convert_hf_to_gguf.py` 默认产出 F16 精度的 GGUF，压到 Q4/Q8 档位还要用 llama.cpp 的量化工具另跑一步。

## 三、异构平台：CUDA 之外的世界

- **昇腾 MindIE**（models_ascend/qwen3 MindIE 篇）：华为推理引擎，`conf/config.json` 配模型路径与端口，`mindieservice_daemon` 起服务；接口兼容 OpenAI/TGI/vLLM 格式，OpenAI SDK 直接调（默认 1025 端口）。容器启动要挂 `davinci_manager`/`hisi_hdc`/`devmm_svm` 设备并只读挂驱动目录——与普通 GPU 容器参数完全不同。
- **vLLM-ascend**（同目录 vLLM-ascend 篇）：社区维护的 vLLM 后端插件（Hardware pluggable 路线），`pip install vllm==0.13.0 vllm-ascend==0.13.0rc1` 两包版本必须对齐；上层 vLLM 代码不动，Transformer/MoE/多模态模型在 NPU 无缝运行。SGLang 也有对应的 sglang-ascend 独立分支（models_ascend/qwen3 另有部署篇）——引擎接口不变、后端换 NPU 适配层，是同一思路。
- **AMD lemonade**（models_amd/qwen3 篇）：Ryzen AI 300 系 NPU 走 lemonade-server，模型用 AMD 侧预量化的 `awq-quant-onnx-hybrid`（ONNX 而非 GGUF）；菜单启动即对外提供 OpenAI 兼容接口。
- **Apple MLX**：苹果自研框架，权重为 MLX safetensors（常见 4-bit），`mlx-lm.server` 提供 OpenAI 兼容接口，吃统一内存，适合 Mac 单机档。

- ★特殊点1 CUDA 专属代码不可移植：`torch.cuda.device_count()` 这类调用要换成各平台等价物（NPU 侧 `torch.npu`）；采样参数、stop_token_ids 跨平台通用，但 device 初始化与 attention 后端是平台专属——引擎篇的启动脚本不能照抄。
- ★特殊点2 算子兼容差异：同一模型在不同引擎/硬件支持的算子子集不同——SGLang 的 EAGLE 投机采样、各家 parser 在昇腾/AMD 侧未必可用；新模型首发往往只有 CUDA 篇（Qwen3 在 models_ascend 有 MindIE/vllm-ascend/sglang-ascend 三篇，models_amd 仅 lemonade 一篇），迁移前先确认该平台有没有对应篇目与版本。
- ★特殊点3 量化格式绑定平台：GGUF→Ollama/LM Studio，ONNX-AWQ→AMD，MLX 权重→Apple，昇腾走原生权重+框架内量化——拿错格式任何引擎都起不来。

## 四、压测验收：上线前必跑的数字

能力评测（IQ/EQ、数据集打分）与性能压测（吞吐/并发）分开做，评测指标体系见 [02-评估体系全景](../08-评估测试/02-评估体系全景.md)。压测两个工具：

```bash
# 评测与压测三工具（伪代码骨架；完整流程见 self-llm 工程
# models/GLM-4.5-Air/02-GLM-4.5-Air EvalScope 并发测试.md）

# 工具 A：EvalScope 能力评测（IQ/EQ 数据集，打已部署的 OpenAI 兼容服务）
evalscope eval --model $MODEL --api-url http://localhost:8000/v1 \
  --api-key $EVAL_API_KEY --eval-type service \
  --eval-batch-size 16 --datasets iquiz

# 工具 B：vLLM 官方吞吐脚本（backend 可切 vllm/hf 对比引擎收益）
python benchmark_throughput.py --model $MODEL --backend vllm \
  --input-len 64 --output-len 128 --num-prompts 25
# 输出：Throughput: 9.14 requests/s, 1754.43 tokens/s（Qwen2.5-7B 实测口径）

# 工具 C：EvalScope 并发压测（线程梯度 5/10/15/20，画曲线找拐点）
evalscope perf --url "http://localhost:8000/v1/chat/completions" \
  --parallel ${PARALLEL} --number ${NUMBER} --api openai \
  --dataset openqa --stream
```

```python
# 压测/评测脚本里的密钥纪律（公共约定 #1）：只走 os.environ，缺失即报错
import os
api_key = os.environ["EVAL_API_KEY"]      # 本地引擎占位符可以填 EMPTY，但不要把真实密钥写死在脚本里
swanlab_key = os.environ["SWANLAB_API_KEY"]  # 回调平台的 token 同理
```

关注指标口径：

- **吞吐（tokens/s、requests/s）**：整体产能，决定成本上限——benchmark_throughput 同参数切 `--backend vllm/hf` 可量化引擎收益。
- **TTFT（首 token 延迟）**：流式体验的下限，并发升高时最先劣化——压测必须带 `--stream` 才有 TTFT，非流式只能拿到整段返回时间，结论会偏乐观。
- **显存水位**：`--mem-fraction-static` 决定给 KV cache 预留多少；并发上不去时先看是不是显存先满，而不是先调并发数。

### 企业级升级要点

- **推理服务当供应商接**：vLLM/SGLang/Ollama/LM Studio 都以 OpenAI 兼容接口暴露，接入层按 70-基准 RAG #6 三层供应商分派做——调用方只 import 门面，换引擎/换部署位零调用点改动；同层共用一个异常类，错误信息带 base_url+模型名。
- **熔断超时按连接级**：本地引擎进程崩溃、显存 OOM 都是连接级失败，按 RAG #7 只对连接级失败熔断 20s 快速失败，4xx/5xx 不熔断；httpx 分项超时（connect=5, read=300——长生成场景读超时要放大）。
- **密钥只走 os.environ**：本地 vLLM/SGLang 的 api_key 是占位符（EMPTY），但 OpenAI 兼容网关一旦对外，按公共约定 #1 只走 `os.environ`，缺失时给可行动报错，永不硬编码、不落配置文件。
- **压测数字进验收单**：引擎选型不拍脑袋，benchmark_throughput 与 EvalScope perf 的吞吐/TTFT 曲线作为上线验收证据留存；换引擎、换量化档位后重跑同一组参数对比。

### 1.1 GRPO 强化学习微调——无 Critic 的多 Agent 策略优化

#### **为什么 GRPO 是 RLHF 的实用化升级？**

```
<code>RLHF（RL from Human Feedback）完整流程：<br/>  Step1: SFT 微调基础模型（Supervised Fine-Tuning）<br/>  Step2: 训练 Reward Model（人类偏好标注 → 标量奖励）<br/>  Step3: PPO 优化策略（Policy → RM → 奖励 → 策略更新）<br/><br/>PPO 的工程痛点：<br/>  1. Reward Model 训练成本高（需要大量人类标注）<br/>  2. PPO 超参敏感（critic 网络难以调优，容易 mode collapse）<br/>  3. 训练不稳定（奖励 hacking，策略退化）<br/>  4. 显存占用大（Policy + Critic + Reward Model 同时加载）<br/><br/>GRPO（Group Relative Policy Optimization）核心突破：<br/>  → 取消 Critic 网络，用「同组相对奖励」替代价值函数估计<br/>  → 减少 ~50% 显存占用，训练稳定性大幅提升</code>
```

#### **代码 LLM 的独特挑战**

```
<code>通用 LLM（GPT/Qwen） vs 代码专用 LLM：<br/><br/>挑战1：仓库级上下文（Repository-Level Context）<br/>  代码片段依赖同仓库其他文件（import / 类型定义 / 函数签名）<br/>  通用 LLM 只看到单文件 → 跨文件推理失败<br/><br/>  解法：Repo-Level 微调 + 结构化文件拼接（DeepSeek-Coder 核心贡献）<br/><br/>挑战2：填空式生成（FIM / Fill-In-the-Middle）<br/>  代码场景：光标在中间，需要「向前看 + 向后看」<br/>  传统 Causal LM：只能从左到右生成 → 不适合代码补全<br/><br/>  解法：FIM（Fill-In-the-Middle）预训练目标（论文：SantaCoder）<br/><br/>挑战3：程序语言 vs 自然语言的 Token 效率<br/>  「def foo():」在 BPE 中可能被切成 3-4 个 Token<br/>  → 同样参数量，代码模型的实际上下文更短<br/><br/>  解法：代码专用 Tokenizer（DeepSeek-Coder 扩到 32K vocab）</code>
```

#### **FIM（Fill-In-the-Middle）预训练目标详解**

```
<code># 标准 Causal LM 预训练：<br/>#   输入：「def foo():\n    return 」<br/>#   目标：「42」<br/>#   问题：无法在「光标在中间」时生成<br/><br/># FIM 预训练（三种 Suffix-Infix-Prefix 排列）：<br/>#  原始代码：&lt;PRE&gt; def foo():\n    &lt;SUF&gt;\n    return 42\n&lt;MID&gt;<br/>#  重排后：&lt;SUF&gt;\n    return 42\n&lt;MID&gt; def foo():\n    <br/>#  （把 Suffix 移到前面，模型学会「先看到后文，再生成中间」）<br/><br/>import torch<br/>import random<br/><br/>class FIMDataset:<br/>    """FIM（Fill-In-the-Middle）数据构造器，论文：SantaCoder (Allal et al., 2023)"""<br/>    FIM_TOKENS = ["&lt;|fim_prefix|&gt;", "&lt;|fim_middle|&gt;", "&lt;|fim_suffix|&gt;"]<br/><br/>    def __init__(self, p_fim=0.5, sentinel_ratio=0.9):<br/>        self.p_fim = p_fim          # 50% 概率使用 FIM 格式<br/>        self.sentinel_ratio = sentinel_ratio  # 其中 90% 用 sentinel，10% 用原文<br/><br/>    def transform_for_fim(self, code_text: str) -&gt; str:<br/>        """将完整代码转换为 FIM 训练格式"""<br/>        if random.random() &gt; self.p_fim:<br/>            return code_text  # 保留原始 Causal 格式<br/><br/>        # 随机选择一个「光标位置」<br/>        lines = code_text.split('\n')<br/>        cursor_line = random.randint(1, len(lines) - 1)<br/><br/>        # 分割为 PRE（光标前）/ MID（中间）/ SUF（光标后）<br/>        pre = '\n'.join(lines[:cursor_line])<br/>        suf = '\n'.join(lines[cursor_line:])<br/>        mid = ''  # 待生成部分（训练时从 ground truth 获取）<br/><br/>        # FIM 重排策略（两种）：<br/>        # Strategy A: &lt;SUF&gt; + &lt;MID&gt; + &lt;PRE&gt;（Suffix-First，主流）<br/>        # Strategy B: &lt;PRE&gt; + &lt;SUF&gt; + &lt;MID&gt;（Prefix-Suffix-First）<br/>        if random.random() &lt; 0.5:<br/>            fim_text = f"&lt;|fim_suffix|&gt;{suf}&lt;|fim_middle|&gt;{mid}&lt;|fim_prefix|&gt;{pre}"<br/>        else:<br/>            fim_text = f"&lt;|fim_prefix|&gt;{pre}&lt;|fim_suffix|&gt;{suf}&lt;|fim_middle|&gt;{mid}"<br/><br/>        return fim_text<br/><br/># DeepSeek-Coder 实际使用的 FIM 策略（更强）：<br/>#   1. PSM（Prefix-Suffix-Middle）排列：最适合代码补全<br/>#   2. 16K 上下文窗口 + 4K 生成长度<br/>#   3. 仓库级数据：先拼接同仓库多个文件，再加 FIM 掩码</code>
```

#### **DeepSeek-Coder 的仓库级 RAG 架构**

```
<code>问题：代码补全时如何找到「相关的其他文件」？<br/><br/>方案1（Naive）：把整个仓库拼接 → 超过上下文窗口（16K 不够）<br/><br/>方案2（DeepSeek-Coder V2）：两阶段检索增强<br/>  Stage1：向量检索（Embedding 相似度）<br/>    - 对当前文件做 Embedding<br/>    - 检索 Top-K 个相关文件（余弦相似度）<br/>    - 相似度计算：CodeBERT / UniXcoder<br/><br/>  Stage2：结构化拼接<br/>    格式：&lt;repo&gt;\n&lt;filepath&gt;src/foo.py&lt;/filepath&gt;\n&lt;code&gt;...&lt;/code&gt;\n&lt;/repo&gt;\n...<br/>    Prompt 构造：<br/>      [检索到的相关文件代码] + [当前文件前缀] → 补全光标处代码<br/><br/>  效果：跨文件补全准确率从 38% → 67%（HumanEval 仓库级变体）</code>
```

### 2.1 长上下文推理——StreamingLLM 与 Attention Sink

#### **问题：LLM 在长上下文下「找不到中间的信息」**

```
<code>现象（Lost in the Middle，2023）：<br/>  输入 100K Token 文档，问「第 50000 个 Token 附近写了什么？」<br/>  → LLM 答不对（注意力被「最近的 Token」主导）<br/><br/>根本原因：<br/>  1. Softmax 的「近因偏差」：最近的 Token 注意力分数自然更高<br/>  2. 位置编码外推失败：RoPE 在 &gt; 训练长度时Attention 分布畸变<br/>  3. KV Cache 显存限制：无法真的把所有 Token 都放进 KV Cache<br/><br/>三大解决路线：<br/>  ├── 1. 窗口截断（StreamingLLM）：只保留「开头 + 结尾」<br/>  ├── 2. 位置编码修正（LongRoPE / YaRN）：让模型「认识」更长位置<br/>  └── 3. 记忆压缩（MemGPT / LongLLMLingua）：把旧信息压缩成「记忆 Token」</code>
```

#### **StreamingLLM 核心机制**

```
<code># 问题：LLM 推理时 KV Cache 无限增长 → OOM<br/># 朴素解法：滑动窗口（只保留最近 N 个 Token）<br/>#   问题：丢失了「System Prompt」→ 模型行为漂移<br/><br/># StreamingLLM 解法（2023，Han et al.）：<br/>#   「Attention Sink」现象：模型对「初始几个 Token」分配异常高的注意力<br/>#   即使这些 Token 信息量很低！<br/>#   → 保留「4 个初始 Token」的 KV，就能恢复大部分性能<br/><br/>class StreamingLLMCache:<br/>    """StreamingLLM 的 KV Cache 管理：<br/>    只保留 (1) Attention Sink（前 4 个 Token）+ (2) 最近 N 个 Token，中间全丢弃"""<br/><br/>    def __init__(self, sink_size=4, window_size=2048):<br/>        self.sink_size = sink_size      # 保留的「Attention Sink」Token 数<br/>        self.window_size = window_size  # 保留的「最近」Token 数<br/>        self.kv_cache = {"sinks": [], "window": []}<br/><br/>    def update(self, new_k, new_v):<br/>        # Sink 未满则填充；已满则入滑动窗口，超 window_size 弹出最老的<br/>        if len(self.kv_cache["sinks"]) &lt; self.sink_size:<br/>            self.kv_cache["sinks"].append((new_k, new_v))<br/>        else:<br/>            self.kv_cache["window"].append((new_k, new_v))<br/>            if len(self.kv_cache["window"]) &gt; self.window_size:<br/>                self.kv_cache["window"].pop(0)<br/><br/>    def get_kv_for_attention(self):<br/>        """拼接 Sinks + Window，用于 Attention 计算"""<br/>        sinks_k = torch.cat([k for k, _ in self.kv_cache["sinks"]])<br/>        sinks_v = torch.cat([v for _, v in self.kv_cache["sinks"]])<br/>        window_k = torch.cat([k for k, _ in self.kv_cache["window"]])<br/>        window_v = torch.cat([v for _, v in self.kv_cache["window"]])<br/>        return (<br/>            torch.cat([sinks_k, window_k]),<br/>            torch.cat([sinks_v, window_v])<br/>        )<br/><br/># 实验效果（LLaMA-2 7B，输入 100K Token）：<br/>#   滑动窗口（只保留最近 2K）：PPL = 18.7（严重退化）<br/>#   StreamingLLM（Sinks 4 + Window 2K）：PPL = 6.3（接近完整上下文 5.9）<br/>#   完整 KV Cache（理论上限）：PPL = 5.9</code>
```

#### **LongRoPE——长度外推的工程化方案**

```
<code>RoPE 长度外推的本质问题：<br/>  训练时最大位置 = 4096<br/>  推理时位置 = 32768（8 倍外推）<br/>  → 高频分量（短距离位置编码）被极度压缩 → 局部注意力失效<br/><br/>LongRoPE（2024，Chen et al.）核心思路：<br/>  对不同频率分量做「非均匀插值」：<br/>    - 低频分量（捕获长程依赖）：插值因子小（1.0，不插值）<br/>    - 中频分量：插值因子中（如 2.0）<br/>    - 高频分量（捕获局部语法）：插值因子大（如 8.0，充分插值）<br/><br/>  数学形式：<br/>    RoPE(θ_i, m) = e^{i·m·θ_i}  其中 θ_i = 1 / base^{2i/d}<br/><br/>     LongRoPE：θ_i' = θ_i / λ_i  其中 λ_i 是第 i 个频率分量的「缩放因子」<br/>     λ_i 通过进化搜索（Evolutionary Search）自动找到最优值<br/><br/>实战效果（LLaMA-2 7B，推理 128K）：<br/>  原始 RoPE（直接外推）：PPL = 42.1（崩溃）<br/>  Position Interpolation（均匀插值）：PPL = 12.8<br/>  YaRN（分段插值）：PPL = 7.3<br/>  LongRoPE（进化搜索 + 非均匀插值）：PPL = 5.8（接近上限 5.7）</code>
```

#### **为什么需要「评估体系」而不只是「看输出好不好」？**

```
<code>LLM 应用评估的三重困境：<br/><br/>困境1：输出不确定性<br/>  同一输入，temperature=0.7 时每次输出不同<br/>  → 单次观察无法判断「模型能力差」还是「这次运气不好」<br/><br/>困境2：评估指标主观<br/>  「回答质量好」如何量化？<br/>  BLEU/ROUGE：衡量表面相似度，不衡量语义正确性<br/>  人工评估：成本高（标注员工时），不一致（不同人标准不同）<br/><br/>困境3：多组件系统（RAG / Agent）<br/>  失败可能来自：检索质量差 / 提示词差 / 模型能力差 / 后处理差<br/>  → 单一端到端指标无法定位问题<br/><br/>解法：分层评估体系（RAGAS 框架 + LLM-as-Judge）</code>
```

#### **RAGAS 评估框架四维指标**

```
<code># RAGAS（Retrieval-Augmented Generation ASsessment）<br/># 四大核心指标：<br/><br/>import numpy as np<br/><br/># ── 指标1：Context Precision（检索精确率）──<br/>#    含义：检索到的上下文中，有多少是「真正相关」的？<br/>#    计算：Precision@K = (# 相关文档 in Top-K) / K<br/>def context_precision(relevant_docs, retrieved_docs_k):<br/>    """<br/>    relevant_docs: Set[str]  # 人类标注的「真正相关」文档 ID<br/>    retrieved_docs_k: List[str]  # 检索系统返回的 Top-K 文档 ID<br/>    """<br/>    relevant_retrieved = [doc_id in relevant_docs for doc_id in retrieved_docs_k]<br/>    precision_scores = []<br/>    running_correct = 0<br/>    for i, is_rel in enumerate(relevant_retrieved, 1):<br/>        if is_rel:<br/>            running_correct += 1<br/>            precision_scores.append(running_correct / i)<br/>    return np.mean(precision_scores) if precision_scores else 0.0<br/><br/># ── 指标2：Context Recall（检索召回率）──<br/>#    含义：所有「真正相关」的文档中，检索到了多少？<br/>def context_recall(relevant_docs, retrieved_docs):<br/>    retrieved_set = set(retrieved_docs)<br/>    return len(relevant_docs &amp; retrieved_set) / len(relevant_docs)<br/><br/># ── 指标3：Faithfulness（忠实度）──<br/>#    含义：生成的答案是否完全基于检索到的上下文（没有幻觉）？<br/>#    计算：用 NLI 模型判断「答案中的每个声明」是否被「上下文」蕴含<br/>def faithfulness(answer, context):<br/>    """答案拆成多个声明（Claim），每个 Claim 用 NLI 判断是否被 Context 蕴含"""<br/>    claims = extract_claims(answer)  # 用 LLM 或规则抽取声明<br/>    nli_model = load_nli_model()      # 如 DeBERTa NLI<br/>    faithful_count = 0<br/>    for claim in claims:<br/>        # NLI 三分类：蕴含(entailment) / 中立(neutral) / 矛盾(contradiction)<br/>        prob = nli_model.predict(claim, context)<br/>        if prob["entailment"] &gt; 0.7:<br/>            faithful_count += 1<br/>    return faithful_count / len(claims) if claims else 1.0<br/><br/># ── 指标4：Answer Relevance（答案相关性）──<br/>#    含义：答案是否直接回答了问题（没有跑题）？<br/>def answer_relevance(question, answer):<br/>    """Embedding 算「问题」和「答案」的余弦相似度，越高越相关"""<br/>    q_emb = embedding_model.encode(question)<br/>    a_emb = embedding_model.encode(answer)<br/>    cosine_sim = np.dot(q_emb, a_emb) / (np.linalg.norm(q_emb) * np.linalg.norm(a_emb))<br/>    return cosine_sim<br/><br/># RAGAS 总分计算：<br/>#    RAGAS_Score = (Context Precision + Context Recall + Faithfulness + Answer Relevance) / 4</code>
```

#### **LLM-as-Judge 的人工对齐校准**

```
<code>LLM-as-Judge 的核心问题：「判断标准」和人类不一致<br/><br/>校准方法（MT-Bench 方案）：<br/>  Step1：收集 100 条人类偏好标注（A 优于 B / B 优于 A / 平局）<br/>  Step2：让 LLM Judge 对同一条数据做判断<br/>  Step3：计算「LLM Judge 与人类的一致性」（目标 &gt; 80%）<br/>  Step4：如果不一致 → 改进 Judge Prompt（加入「评分标准说明」）<br/><br/>高质量 Judge Prompt 模板：<br/>  """<br/>  你是一位专业的 AI 回答质量评估员。请对以下两个回答打分（1-10分）。<br/><br/>  评分维度：<br/>  1. 准确性（是否有事实错误？）<br/>  2. 完整性（是否完整回答了问题？）<br/>  3. 清晰性（是否易于理解？）<br/>  4. 安全性（是否有有害内容？）<br/><br/>  请先给出分析，再给出分数。格式：<br/>  【分析】...<br/>  【分数】回答A：X分；回答B：Y分<br/>  """<br/><br/>一致性提升技巧：<br/>  1. 给出「评分标准说明」（减少 LLM 主观性）<br/>  2. 使用「参考答案」（Few-Shot 示例）<br/>  3. 多次采样取平均（温度 = 0.3，采样 5 次）<br/>  4. 用强模型做 Judge（GPT-4o &gt; Claude &gt; 开源模型）</code>

#### **传统 RAG 的三大瓶颈**

```
<code>瓶颈1：向量检索的「语义漂移」<br/>  查询：「AI 安全的最新研究进展」<br/>  检索到：「AI 安全工程师薪资待遇」（语义相似，但意图不同）<br/>  → 向量相似度 ≠ 意图匹配度<br/><br/>瓶颈2：全局问答失效<br/>  查询：「这篇文章的主要论点是什么？」（需要跨多个 Chunk 汇总）<br/>  → 向量检索只能找「最相似的几个 Chunk」→ 丢失全局视角<br/><br/>瓶颈3：时效性<br/>  知识库更新后，Embedding 需要重新计算（批量更新成本高）<br/>  → 无法做到「秒级」知识更新<br/><br/>三大前沿解法：<br/>  ├── GraphRAG（知识图谱 + RAG）：解决全局问答<br/>  ├── Corrective RAG（自我纠错 RAG）：解决语义漂移<br/>  └── Self-RAG（边生成边检索）：解决「要不要检索」的决策问题</code>
```

#### **GraphRAG（微软，2024）核心原理**

```
<code>核心思想：把文档建构成「知识图谱」，检索时「图遍历」而非「向量相似度」<br/><br/>构建流程：<br/>  Step1：用 LLM 从每个 Chunk 抽取实体和关系<br/>    输入 Chunk：「苹果公司由史蒂夫·乔布斯于 1976 年创立」<br/>    输出实体：[苹果公司, 史蒂夫·乔布斯]<br/>    输出关系：(苹果公司, 创始人, 史蒂夫·乔布斯), (苹果公司, 成立时间, 1976)<br/><br/>  Step2：合并同名实体（Entity Resolution）<br/>    「苹果公司」和「Apple Inc.」→ 合并为同一节点<br/><br/>  Step3：构建社区（Community Detection）<br/>    用 Louvain 算法检测图中的「紧密连接的子图」→ 每个社区是一个「主题」<br/><br/>  Step4：为每个社区生成「社区摘要」（用 LLM 汇总）<br/><br/>检索流程（全局问答）：<br/>  查询：「这篇文章的主要论点是什么？」<br/>  → 传统 RAG：检索 Top-K Chunk → 信息碎片化<br/>  → GraphRAG：<br/>      (1) Map 阶段：对所有社区摘要并行提问，收集局部答案<br/>      (2) Reduce 阶段：把所有局部答案汇总成全局答案<br/><br/>效果（vs 传统 RAG）：<br/>  全局问答（Global Q&amp;A）：Win Rate +37%<br/>  局部问答（Local Q&amp;A）：Win Rate +12%<br/>  索引构建成本：高（需要多次 LLM 调用做实体抽取）</code>

#### **Corrective RAG（CRAG）——自我纠错检索**

```
<code># CRAG（Corrective RAG，2024）核心机制：<br/>#   检索到文档 → 评估文档质量 → 决定「如何使用」或「是否重新检索」<br/><br/>class CorrectiveRAG:<br/>    """<br/>    CRAG 三阶段流程：<br/>    Stage1：检索质量评估（Relevance Grading）<br/>    Stage2：知识精炼（Knowledge Refinement）<br/>    Stage3：可控生成（Controlled Generation）<br/>    """<br/><br/>    def __init__(self, llm, retriever, threshold=0.7):<br/>        self.llm = llm<br/>        self.retriever = retriever<br/>        self.threshold = threshold  # 相关性阈值<br/><br/>    def relevance_grading(self, query, retrieved_docs):<br/>        """Stage1：LLM 逐文档评相关性，输出 relevant / partially_relevant / irrelevant"""<br/>        graded = []<br/>        for doc in retrieved_docs:<br/>            # Prompt：查询 + doc[:500] → "只输出一个词"<br/>            grade = self.llm.generate(f"查询：{query}\n检索文档：{doc[:500]}...\n"<br/>                                      "该文档对回答查询是否有帮助？选项：relevant / "<br/>                                      "partially_relevant / irrelevant，只输出一个词。").strip().lower()<br/>            graded.append((doc, grade))<br/>        return graded<br/><br/>    def knowledge_refinement(self, graded_docs, query):<br/>        """Stage2：relevant 直接保留；partially_relevant 用 LLM 摘取相关片段；<br/>        irrelevant 丢弃并触发网络搜索补充"""<br/>        refined_context, trigger_web_search = [], False<br/>        for doc, grade in graded_docs:<br/>            if grade == "relevant":<br/>                refined_context.append(doc)<br/>            elif grade == "partially_relevant":<br/>                refined_context.append(self.llm.generate(<br/>                    f"从以下文档中提取与「{query}」相关的片段：\n{doc}"))<br/>            else:<br/>                trigger_web_search = True<br/>        if trigger_web_search:<br/>            refined_context.extend(self.web_search(query))<br/>        return refined_context<br/><br/>    def generate(self, query, retrieved_docs):<br/>        """端到端 CRAG 流程：评分 → 精炼 → Stage3 可控生成（信息不足时明确说明）"""<br/>        graded = self.relevance_grading(query, retrieved_docs)<br/>        refined_context = self.knowledge_refinement(graded, query)<br/>        return self.llm.generate(<br/>            f"基于以下【已验证】的信息回答问题，信息不足请明确说明。\n"<br/>            f"参考信息：\n{refined_context}\n问题：{query}")<br/><br/># CRAG vs 标准 RAG 效果（PubMed QA 数据集）：<br/>#   标准 RAG：Accuracy = 62.3%<br/>#   CRAG：      Accuracy = 71.8%（+9.5%）</code>
```

```
<code>【1】数据构造流程（3 个核心决策）<br/><br/>决策1：Prompt 设计（代码生成任务）<br/>  格式："""<br/>  【任务】实现一个函数，输入整数列表，返回第二大的元素。<br/>  【约束】时间复杂度 O(n)，空间复杂度 O(1)。<br/>  【签名】def second_largest(nums: List[int]) -&gt; int:<br/>  """<br/>  → 每个 Prompt 对应「一个编程任务」<br/><br/>决策2：组响应生成（Group Size = 8）<br/>  对每个 Prompt，用「高温采样」（temperature=0.8）生成 8 个候选代码<br/>  → 8 个代码的质量各不相同（有的通过测试，有的不通过）<br/>  → 正是「组内的差异」让 GRPO 能学到「什么好、什么不好」<br/><br/>决策3：奖励函数设计（多维奖励，非单一通过/不通过）<br/>  奖励 = 0.5 × 单元测试通过率 <br/>        + 0.2 × 代码风格得分（Pylint / Black）<br/>        + 0.2 × 时间复杂度得分（是否 O(n)？）<br/>        + 0.1 × 可读性等（LLM-as-Judge）<br/>  → 多维奖励比「二元通过/不通过」提供更多学习信号<br/><br/>【2】GRPO 损失函数关键设计<br/><br/>  关键1：Group-Relative Advantage 计算<br/>    advantages = (rewards - ```
<code>【1】系统架构全景（5 层）<br/><br/>Layer1：文档预处理与索引（离线）<br/>  ├── 语义分块（Semantic Chunking）<br/>  │     不是固定 512 Token 切块，而是按「语义边界」切分<br/>  │     （段落结束 / 章节结束 / 函数定义结束）<br/>  ├── 向量索引（Dense Retrieval）<br/>  │      Embedding 模型：gte-large-zh / bge-m3（支持 8192 上下文）<br/>  │      向量库：Milvus / Qdrant（支持 HNSW 和 IVF 混合索引）<br/>  └── 知识图谱索引（Graph Index）<br/>        实体抽取：用 LLM 从每个 Chunk 抽取（实体，关系，实体）<br/>        图数据库：Neo4j / Nebula Graph<br/><br/>Layer2：查询理解与分解（Query Analysis）<br/>  ├── 查询类型识别<br/>  │     全局问题（「本文档的主要内容是什么？」）→ GraphRAG 路径<br/>  │     局部问题（「foo() 函数的参数有哪些？」）→ 向量检索路径<br/>  │     多跳问题（「A 和 B 的关系是什么？」）→ 图谱遍历路径<br/>  └── 查询重写（Query Rewriting）<br/>        用 LLM 把「模糊查询」改写成「精确检索查询」<br/>        例：「那个优化方法」→ 「Linux 内核中的 O(1) 调度器优化」<br/><br/>Layer3：混合检索（Hybrid Retrieval）<br/>  ├── 向量检索（Dense）：语义相似度检索 Top-20 Chunk<br/>  ├── 关键词检索（Sparse）：BM25 全文检索 Top-10 Chunk<br/>  ├── 图谱检索（Graph）：从实体出发，2 跳内所有相关实体+关系<br/>  └── 融合策略：RRF（Reciprocal Rank Fusion）合并排序<br/>        score_final = 1/(k + rank_dense) + 1/(k + rank_sparse)<br/><br/>Layer4：上下文窗口管理（Context Window Management）<br/>  ├── Long Context 模型选择<br/>  │     用支持 128K+ 的模型（Qwen2.5-72B-Instruct / DeepSeek-V2）<br/>  ├── 上下文压缩（Context Compression）<br/>  │     用 LLMLingua（文本级压缩，保留 20% Token）<br/>  │     或 FastLangComp（向量级压缩，生成 Side-Info）<br/>  └── 动态上下文构造<br/>        把检索结果按「相关性」排序填入上下文窗口<br/>        格式：[系统提示] + [压缩后的检索结果] + [用户问题]<br/><br/>Layer5：生成与验证（Generation &amp; Verification）<br/>  ├── 可控生成（Guided Generation）<br/>  │     用 Outlines 约束输出格式（JSON / Markdown / 代码）<br/>  ├── 事实性验证（Factuality Verification）<br/>  │     生成后：用 NLI 模型检查「每个声明」是否被检索上下文蕴含<br/>  │     → 如果发现「幻觉声明」，触发「重新检索 + 重新生成」<br/>  └── 引用标注（Citation）<br/>        生成时要求模型输出「来源 Chunk ID」→ 可追溯<br/><br/>【2】关键技术难点与解法<br/><br/>难点1：1M Token 文档的「迷失在中间」问题<br/>  解法：<br/>    (1) 用 LongRoPE / YaRN 微调后的模型（位置编码外推）<br/>    (2) 把上下文窗口的「中间位置」让给「最有信息量的 Chunk」<br/>    (3) 使用 Fusion-in-Decoder（FiD）架构：Encoder 独立处理每个 Chunk，<br/>        Decoder 做跨 Chunk 注意力 → 避免「中间信息丢失」<br/><br/>难点2：检索结果冗余（多个 Chunk 内容高度重叠）<br/>  解法：<br/>    MMR（Maximal Marginal Relevance）重排序<br/>    → 在「相关性」和「多样性」之间做权衡<br/>    → 优先选择「相关性高且和已选 Chunk 差异大」的结果<br/><br/>难点3：生成延迟（1M Token 上下文，首 Token 延迟极高）<br/>  解法：<br/>    (1) Prefix Caching（vLLM）：相同 System Prompt 的 KV Cache 复用<br/>    (2) Chunked Prefill（vLLM）：把长 Prefill 切成小块，和 Decode 交错<br/>    (3) 投机解码（Speculative Decoding）：用小模型草稿 + 大模型验证<br/><br/>【3】评估体系<br/><br/>  端到端指标：<br/>    - Answer Accuracy（答案正确性，人工评估 + LLM-as-Judge）<br/>    - Citation Accuracy（引用准确性，检查引用 Chunk 是否真的支持答案）<br/>    - Latency（P50/P95 延迟）<br/><br/>  组件级指标：<br/>    - Retrieval Recall@20（检索召回率）<br/>    - Context Precision@20（检索精确率）<br/>    - Faithfulness Score（忠实度，用 NLI 评估）</code>
```

**题目**：

> Agent Harness 需要处理「超长会话历史」（100K+ Token）并支持「低延迟流式输出」。  
> 请对比 Transformer / Mamba（SSM）/ RWKV 三种架构在此场景下的优劣，并给出最终选型建议。

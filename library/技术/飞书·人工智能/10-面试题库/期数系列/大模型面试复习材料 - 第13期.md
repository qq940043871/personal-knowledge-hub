### 1.1 Agent Harness 架构设计——多LLM Provider统一编排引擎

#### **为什么需要一个 Agent Harness？**

```
<code>直接裸调 LLM API 的问题：<br/>  1. Vendor Lock-in：绑死一家 Provider（如只接 DeepSeek），切换成本极高<br/>  2. 工具调用不统一：OpenAI 的 FC、DeepSeek 的 FC、火山引擎的 FC 格式各异<br/>     → 同一个 Agent 应用要对接 3 个 Provider 就要写 3 套适配代码<br/>  3. 流式输出协议不同：SSE / WebSocket / 自定义格式 → 前端适配噩梦<br/>  4. 会话状态管理缺失：多轮对话、上下文压缩、会话中断恢复 → 全靠手动实现<br/>  5. 可观测性空白：Token 计费、延迟监控、错误追踪 → 无法运维<br/><br/>Agent Harness 的核心价值主张：<br/>  → 一套代码，N 个 LLM 后端无缝切换<br/>  → 统一的工具调用协议 + 执行引擎<br/>  → 生产级的可观测性 + 会话管理<br/>  → FastAPI 后端 + Vue3 前端 + PyQt6 桌面端 三端架构</code>
```

#### **Agent Harness 六层架构深度解析**

```
<code>┌─────────────────────────────────────────────────────────────┐<br/>│  Layer 6: Client Layer（客户端层）                           │<br/>│    Vue3 Web UI / PyQt6 Desktop / Mobile API                  │<br/>│    → 统一交互界面，WebSocket 实时推送流式输出                  │<br/>├─────────────────────────────────────────────────────────────┤<br/>│  Layer 5: Agent Layer（智能体层）                            │<br/>│    Agent Definition（角色/指令/工具集）                       │<br/>│    Agent Orchestrator（任务分解/多Agent调度）                │<br/>│    Memory Manager（短期记忆/长期记忆/会话摘要）               │<br/>├─────────────────────────────────────────────────────────────┤<br/>│  Layer 4: Execution Layer（执行层）                          │<br/>│    MainLoop（主循环：Think → Act → Observe → Reflect）      │<br/>│    Tool Registry（工具注册/发现/鉴权）                        │<br/>│    Dependency-Aware Scheduler（依赖感知的任务调度器）       │<br/>├─────────────────────────────────────────────────────────────┤<br/>│  Layer 3: Provider Abstraction Layer（Provider抽象层）       │<br/>│    OpenAI Provider / DeepSeek Provider / Doubao Provider   │<br/>│    统一接口：complete() / stream() / function_call()       │<br/>│    自动重试 + 降级 + Token 预算管理                          │<br/>├─────────────────────────────────────────────────────────────┤<br/>│  Layer 2: API Gateway Layer（API网关层）                    │<br/>│    FastAPI 路由 + 中间件（Auth/RateLimit/CORS）             │<br/>│    WebSocket 长连接管理（流式输出）                           │<br/>│    Postman Collection 自动生成（接口文档自动化）             │<br/>├─────────────────────────────────────────────────────────────┤<br/>│  Layer 1: Infrastructure Layer（基础设施层）                 │<br/>│    消息队列（异步任务）/ 缓存（Redis）/ 持久化（DB）       │<br/>│    日志收集 / Metrics / Trace（OpenTelemetry）              │<br/>└─────────────────────────────────────────────────────────────┘</code>
```

#### **Provider 抽象层核心设计（最核心的工程亮点）**

```
<code># Agent Harness Provider 抽象层：策略模式 + 工厂模式 + 适配器模式（伪代码骨架）<br/>from abc import ABC, abstractmethod<br/><br/># ── 统一数据模型（所有 Provider 共用）──<br/>@dataclass<br/>class Message: ...              # role(SYSTEM/USER/ASSISTANT/TOOL) / content / tool_calls / tool_call_id<br/>@dataclass<br/>class ToolDefinition: ...       # name / description / JSON Schema / handler（兼容 OpenAI/DeepSeek/Doubao）<br/>@dataclass<br/>class CompletionResponse: ...   # content / tool_calls / usage / finish_reason / provider<br/><br/># ── Provider 抽象基类（策略模式）：子类只需实现 complete / stream ──<br/>class BaseLLMProvider(ABC):<br/>    @abstractmethod<br/>    async def complete(self, messages, tools=None, **kwargs) -&gt; CompletionResponse: ...<br/>    @abstractmethod<br/>    async def stream(self, messages, tools=None, **kwargs) -&gt; AsyncIterator[str]: ...<br/><br/>    async def retry_with_fallback(self, messages, fallback_providers, max_retries=3):<br/>        #   ★特殊点1 重试用指数退避(2**attempt)，主 Provider 耗尽后逐个降级到备用<br/>        for provider in [self] + fallback_providers:<br/>            for attempt in range(max_retries):<br/>                try:<br/>                    return await provider.complete(messages)<br/>                except (RateLimitError, TimeoutError, APIError):<br/>                    await asyncio.sleep(2 ** attempt)<br/>        raise ProviderExhaustedError("All providers failed")<br/><br/># ── 工厂模式：装饰器注册 + 按名实例化 ──<br/>class ProviderFactory:<br/>    _registry: Dict[str, type] = {}<br/>    # register(name) 装饰器把类写入 _registry；create(name, **config) 查表构造<br/>    ...<br/><br/># ── Doubao 适配器：API 格式与 OpenAI 不完全兼容 ──<br/>@ProviderFactory.register("doubao")<br/>class DoubaoProvider(BaseLLMProvider):<br/>    async def complete(self, messages, tools=None, **kwargs):<br/>        #   ★特殊点2 Doubao 的 tool_calls 嵌在 content JSON 里（OpenAI 在顶层字段），需做字段映射<br/>        ...  # 转换消息/工具定义 → 调 API → 响应统一化为 CompletionResponse<br/><br/># ── Agent 主循环（Think → Act → Observe 循环）──<br/>class AgentMainLoop:<br/>    def __init__(self, provider, tools, max_iterations=20): ...<br/>    async def run(self, user_input):<br/>        # 无工具调用 → 返回最终回复；否则执行工具并把结果以 TOOL 消息回写 memory<br/>        #   ★特殊点3 工具异常不抛出，包装成 Error 消息回传给模型自行决策<br/>        ...  # 循环至 max_iterations</code>
```

#### **推理范式的演进路线图**

```
<code>推理能力是 LLM 应用的核心竞争力，面试必考。完整演进路线：<br/><br/>Zero-Shot（2020）→ Few-Shot（2021）→ CoT（2022）→ CoT-SC / Self-Consistency（2023）<br/>     → ToT（2023）→ GoT（2023）→ ReAct（2022）→ Reflexion（2023）→ o1/o3（2024）<br/><br/>每一代解决上一代的核心缺陷：<br/>  Zero-Shot → 无法处理多步推理 → CoT<br/>  CoT → 单条推理路径，错误无法自我纠正 → CoT-SC<br/>  CoT-SC → 无法回溯/探索不同分支 → ToT<br/>  ToT → 无法与外部工具交互 → ReAct<br/>  ReAct → 无法从失败中学习 → Reflexion<br/>  Reflexion → 思考链路太短，缺乏深度推理 → o1 Test-Time Compute</code>
```

#### **各推理范式核心原理与代码实现**

```
<code># =============================================<br/># 1. Chain-of-Thought (CoT) —— 最基本的推理范式<br/># =============================================<br/><br/># Zero-Shot CoT Prompt：<br/>#   "请一步一步地思考。"<br/># Few-Shot CoT Prompt：<br/>#   给出几个「问题 → 推理过程 → 答案」的示例，让模型模仿<br/><br/># 核心思想：让模型「显式地写出推理过程」<br/># 为什么有效？<br/>#   1. 把复杂问题分解为多个简单子问题（分治策略）<br/>#   2. 推理过程可被验证（中间步骤错误可以被发现）<br/>#   3. 更多 Token → 更多的计算量（Test-Time Compute）<br/><br/>cot_prompt = """<br/>问题：小明有 23 个苹果，给了小红一半，又买了 5 个，然后又给了小华 1/3，<br/>     请问他最后有多少个苹果？<br/><br/>请一步一步地思考。<br/><br/>推理过程：<br/>1. 小明初始有 23 个苹果<br/>2. 给小红一半：23 / 2 = 11.5，剩下 11.5 个<br/>3. 又买了 5 个：11.5 + 5 = 16.5 个<br/>4. 给小华 1/3：16.5 × (1/3) = 5.5，剩下 16.5 - 5.5 = 11 个<br/>答案：小明最后有 11 个苹果。<br/>"""</code>
```

```
<code># =============================================<br/># 2. Self-Consistency (CoT-SC) —— 多路径投票<br/># =============================================<br/><br/># 核心思想：同一个问题，用高温采样生成 N 条推理路径<br/># → 如果多条路径得到相同答案，说明答案更可靠<br/><br/>async def self_consistency(llm, question, n_samples=10, temperature=0.8):<br/>    """<br/>    Self-Consistency 推理（Wang et al., 2022）<br/><br/>    Step1: 生成 N 条独立推理路径<br/>    Step2: 提取每条路径的「最终答案」<br/>    Step3: 多数投票（Majority Vote）<br/>    """<br/>    answers = []<br/>    for _ in range(n_samples):<br/>        response = await llm.generate(<br/>            question + "\n请一步一步地思考。",<br/>            temperature=temperature<br/>        )<br/>        # 用正则提取最终答案<br/>        final_answer = extract_answer(response)  # 如 "11 个苹果" → 11<br/>        answers.append(final_answer)<br/><br/>    # 多数投票<br/>    from collections import Counter<br/>    most_common = Counter(answers).most_common(1)[0]<br/>    confidence = most_common[1] / len(answers)  # 一致性 = 投票比例<br/><br/>    return most_common[0], confidence<br/><br/># 效果（GSM8K 数学推理）：<br/>#   CoT（单路径）：58.8%<br/>#   CoT-SC（10 路径投票）：67.5%（+8.7%）<br/>#   但代价：推理成本 ×10<br/><br/># =============================================<br/># 3. Tree-of-Thought (ToT) —— 树状搜索推理<br/># =============================================</code>
```

```
<code><br/># 核心思想：把推理过程建模为「树搜索」问题<br/>#   - 每个推理步骤是一个「节点」<br/>#   - 每个节点可以展开多个「候选下一步」<br/>#   - 用 LLM 评估每个节点的「前景」<br/>#   - 用 BFS/DFS 搜索最优推理路径<br/><br/>from dataclasses import dataclass<br/>from typing import List, Optional<br/>import heapq<br/><br/>@dataclass<br/>class ThoughtNode:<br/>    """ToT 树中的一个推理节点"""<br/>    state: str          # 当前推理状态（问题描述 + 已有推理链）<br/>    thought: str        # 本步的推理内容<br/>    evaluation: float   # LLM 评估的分数（0-10）<br/>    parent: Optional['ThoughtNode'] = None<br/>    depth: int = 0<br/>    def __lt__(self, other):<br/>        return self.evaluation &gt; other.evaluation  # 最大堆<br/><br/>class TreeOfThought:<br/>    """ToT 推理引擎（Yao et al., 2023）：Best-First Search（伪代码骨架）"""<br/><br/>    def __init__(self, llm, max_depth=5, branching_factor=3, beam_size=5): ...<br/><br/>    async def solve(self, problem: str) -&gt; str:<br/>        # 根节点入优先队列，循环弹出评分最高节点：达到 max_depth → 返回解；<br/>        # 否则生成候选推理步骤 → 拼新状态 → LLM 打分 → 子节点入堆<br/>        ...<br/>        #   ★特殊点1 每轮用 heapq.nsmallest(beam_size) 裁剪，只保留最优节点防爆炸<br/><br/>    async def _generate_thoughts(self, state, n) -&gt; List[str]:<br/>        # LLM 生成 n 个候选推理方向（temperature=0.9 鼓励发散），按行拆分<br/>        ...<br/><br/>    async def _evaluate_state(self, state) -&gt; float:<br/>        # LLM 给当前状态打 0-10 分（temperature=0.1 保证稳定可解析）<br/>        ...<br/><br/># ToT vs CoT vs CoT-SC 对比：<br/>#   CoT：单路径，无法回溯<br/>#   CoT-SC：多路径并行，但无回溯（一次性采样）<br/>#   ToT：真正的搜索——可以回溯、剪枝、探索不同分支<br/>#   代价：推理成本 ×30~50（每个节点都要 LLM 评估）<br/><br/># =============================================<br/># 4. ReAct —— 推理 + 行动交替<br/># =============================================</code>
```

```
<code><br/># 核心思想：Agent 不仅「思考」还「行动」<br/>#   Thought → Action → Observation → Thought → Action → ... → Answer<br/>#   与纯 CoT 的区别：可以调用外部工具（搜索/计算/API）<br/><br/>async def react_agent(llm, tools, question, max_steps=10):<br/>    """<br/>    ReAct Agent 循环（Yao et al., 2022）<br/>    关键：Thought 和 Action 交替执行<br/>    """<br/>    scratchpad = f"问题：{question}\n"<br/><br/>    for step in range(max_steps):<br/>        # ── Thought + Action（LLM 决定下一步）──<br/>        prompt = f"""<br/>        {scratchpad}<br/>        可用工具：{json.dumps({t.name: t.description for t in tools}, ensure_ascii=False)}<br/><br/>        请选择下一步（格式：Thought: ... Action: ...[arg1, arg2]）<br/>        如果已有足够信息回答问题，输出：Thought: ... Answer: ...<br/>        """<br/>        response = await llm.generate(prompt)<br/><br/>        # 解析 LLM 的输出<br/>        if "Answer:" in response:<br/>            return extract_between(response, "Answer:", "\n")<br/><br/>        thought = extract_between(response, "Thought:", "Action:")<br/>        action_name = extract_between(response, "Action:", "(")<br/>        action_args = extract_between(response, "(", ")")<br/><br/>        # ── Observation（执行工具，观察结果）──<br/>        if action_name in tools:<br/>            result = await tools[action_name].execute(action_args)<br/>            scratchpad += f"Thought: {thought}\nAction: {action_name}({action_args})\nObservation: {result}\n"<br/>        else:<br/>            scratchpad += f"Error: 工具 {action_name} 不存在\n"<br/><br/>    return "达到最大步数，无法回答"<br/><br/># =============================================<br/># 5. Reflexion —— 从失败中学习的 Agent<br/># =============================================</code>
```

```
<code><br/># 核心思想：Agent 执行失败后，把「失败原因」写入记忆<br/>#   下次遇到类似任务时，先读取「失败记忆」→ 避免重复错误<br/><br/>async def reflexion_agent(llm, evaluator, task, max_trials=3):<br/>    """<br/>    Reflexion Agent（Shinn et al., 2023）<br/>    关键创新：自我反思 + 记忆增强<br/>    """<br/>    memory = []  # 存储历次失败反思<br/><br/>    for trial in range(max_trials):<br/>        # ── 生成（如果有历史反思，注入 Prompt）──<br/>        context = ""<br/>        if memory:<br/>            context = f"\n你之前在这个任务上犯过以下错误，请避免：\n"<br/>            for reflection in memory:<br/>                context += f"- {reflection}\n"<br/><br/>        response = await llm.generate(task + context)<br/><br/>        # ── 评估 ──<br/>        score, feedback = await evaluator.evaluate(task, response)<br/><br/>        if score &gt;= 0.8:  # 达标<br/>            return response<br/><br/>        # ── 反思（让 LLM 分析失败原因）──<br/>        reflection_prompt = f"""<br/>        任务：{task}<br/>        你的回答：{response}<br/>        评估反馈：{feedback}<br/><br/>        请反思：你的回答哪里出错了？下次应该如何改进？<br/>        用一句话总结失败原因。<br/>        """<br/>        reflection = await llm.generate(reflection_prompt)<br/>        memory.append(reflection)<br/><br/>    return response  # 返回最后一次尝试的结果（即使未达标）<br/><br/># Reflexion 关键洞察：<br/>#   - 不需要更新模型权重（在线学习）<br/>#   - 用「自然语言记忆」替代「梯度更新」<br/>#   - 实验表明：3 轮 Reflexion 在 HumanEval 上从 67% → 80%</code>
```

#### **推理范式选型决策树**

```
<code>需要 LLM 做复杂推理？<br/>  ├── 任务是纯文本推理（数学/逻辑/分析）？<br/>  │     ├── 简单（1-2步）→ Zero-Shot CoT（"请一步一步思考"）<br/>  │     ├── 中等（3-5步）→ CoT-SC（10 路径投票）<br/>  │     └── 复杂（5+步，需要回溯）→ ToT（树搜索）<br/>  ├── 任务需要外部信息（搜索/计算/API）？<br/>  │     └── ReAct（推理 + 行动交替）<br/>  ├── 任务需要从失败中学习？<br/>  │     └── Reflexion（反思 + 记忆增强）<br/>  └── 任务需要极深度推理（竞赛级数学/代码）？<br/>        └── o1/o3 Test-Time Compute（MCTS + 强化学习）</code>
```

### 2.1 多 LLM Provider 的 Tool Calling 标准化——Agent Harness 的最大工程挑战

#### **问题：三大 Provider 的 Tool Calling 格式完全不兼容**

```
<code>核心矛盾：<br/>  OpenAI、DeepSeek、Doubao 都支持 Function Calling，<br/>  但请求/响应的 JSON 格式存在微妙差异：<br/><br/>差异1：tool_calls 字段位置<br/>  OpenAI:   response.choices[0].message.tool_calls → 顶层字段<br/>  DeepSeek:  与 OpenAI 兼容（90%），但参数校验更严格<br/>  Doubao:   tool_calls 嵌套在 content 字段的 JSON 中 → 结构不同<br/><br/>差异2：工具定义的 JSON Schema 格式<br/>  OpenAI:   支持完整的 JSON Schema Draft 2020-12<br/>  DeepSeek:  支持子集（不支持 $ref、allOf 等）<br/>  Doubao:   只支持简单的 properties 定义 → 复杂类型需要展平<br/><br/>差异3：并行工具调用<br/>  OpenAI:   原生支持（一次返回多个 tool_calls）<br/>  DeepSeek:  部分支持（model 参数需指定 parallel_tool_calls=true）<br/>  Doubao:   不支持并行 → 需要串行化处理<br/><br/>差异4：流式输出中的 tool_calls<br/>  OpenAI:   用 delta 格式增量推送（类似打字机效果）<br/>  Doubao:   流式模式不支持 tool_calls → 必须用非流式模式</code>
```

#### **解决方案：四层标准化架构**

```
<code>class ToolCallNormalizer:<br/>    """Tool Calling 标准化器：处理三大 Provider 的格式差异（伪代码骨架）"""<br/><br/>    # ── Layer1: Schema 简化（统一降维到最小公共集）──<br/>    @staticmethod<br/>    def normalize_schema(tool_def: ToolDefinition) -&gt; Dict:<br/>        # 嵌套对象展平为一层：{"address": {"city": "str"}} → {"address_city": "str"}<br/>        #   ★特殊点1 Doubao 不支持嵌套对象；DeepSeek 不支持 enum/$ref（移除、解引用）<br/>        ...<br/><br/>    # ── Layer2: 请求转换（统一 → Provider 特定格式）──<br/>    @staticmethod<br/>    def to_provider_format(messages, tools, target_provider) -&gt; Dict:<br/>        # 按 openai / deepseek / doubao 分派到各自格式转换（doubao 最复杂）<br/>        ...<br/><br/>    # ── Layer3: 响应解析（Provider 特定格式 → 统一格式）──<br/>    @staticmethod<br/>    def parse_response(raw_response, provider) -&gt; CompletionResponse:<br/>        # doubao 的 tool_calls 可能在 content JSON 中 → 专门解析；其余走标准解析<br/>        ...<br/><br/>    # ── Layer4: 并行化适配 ──<br/>    @staticmethod<br/>    async def execute_tool_calls(tool_calls, tools, provider, parallel_capable=True):<br/>        # 支持并行 → asyncio.gather(*tasks, return_exceptions=True)<br/>        #   ★特殊点2 不支持并行的 Provider（如 Doubao）串行执行，单工具异常包装成 "Error: ..." 不中断<br/>        ...<br/>        # 统一包装成 Message(role=TOOL, tool_call_id=...) 返回</code>
```

不同领域数据的混合比例对模型能力有巨大影响。典型的 LLaMA 数据配比：

- 通用网页数据：67%（主要来源，提供语言基础能力）
- GitHub 代码：4.5%（提升逻辑推理和代码能力）
- 学术论文（ArXiv）：2.5%（提升科学/数学能力）
- 书籍：4.5%（提升长文本理解和叙事能力）
- Wikipedia：4.5%（提升事实准确性）
- Stack Exchange：2%（提升问答能力）
- 法律/医疗等专业：~1%（提升领域专业性）
- 其他：~14%

配比的核心原则：

1. 基础语言能力依赖大规模通用数据（67%+）
1. 代码和数学数据虽然量少但对推理能力提升显著（1% → 推理能力 +15%）
1. 过多的专业数据会损害通用能力（domain contamination）
1. 需要在训练中动态调整配比（annealing 策略）

### Q1：请详细解释 Agent Harness 的 MainLoop 设计，为什么要用 Think-Act-Observe 循环？

**答**：

```
<code>MainLoop 是 Agent 系统的「心跳」，核心是 Think → Act → Observe 的闭环：<br/><br/>【Think 阶段】<br/>  LLM 接收当前上下文（用户问题 + 历史消息 + 工具执行结果），<br/>  决定下一步行动：<br/>    - 直接回答（没有工具调用 → 任务结束）<br/>    - 调用工具（有 tool_calls → 进入 Act 阶段）<br/><br/>【Act 阶段】<br/>  解析 LLM 返回的 tool_calls：<br/>    - 提取工具名称和参数<br/>    - 通过 Tool Registry 查找并执行对应工具<br/>    - 支持并行工具调用（OpenAI 原生支持）<br/>    - 不支持并行的 Provider（如 Doubao）→ 自动串行化<br/><br/>【Observe 阶段】<br/>  工具执行结果写入消息历史（role=tool），<br/>  然后回到 Think 阶段，LLM 根据工具结果决定下一步。<br/><br/>设计这个循环的原因：<br/>  1. LLM 本身没有「行动能力」，只能通过 API 间接操作外部世界<br/>  2. 单轮调用无法完成复杂任务（需要多步推理 + 多次工具调用）<br/>  3. 工具调用可能失败 → 需要循环机制让 LLM「看到」错误并自我修正<br/>  4. 最大迭代次数限制（如 20 次）→ 防止无限循环（Token 计费失控）<br/><br/>面试加分：<br/>  "这本质上是 ReAct 范式的工程实现。<br/>   更高级的演进是加入 Reflect 阶段（如 Reflexion），<br/>   在任务完成后让 LLM 反思执行过程，把经验写入长期记忆。"</code>
```

**参考答案要点**：

```
<code>【1】系统架构（四层）<br/><br/>Layer1：消息总线（Message Bus）<br/>  → RabbitMQ / Redis Streams / 自定义事件总线<br/>  → 事件类型：TASK_ASSIGNED / TASK_COMPLETED / TASK_FAILED / HUMAN_REVIEW_REQUESTED<br/>  → 每个 Agent 是一个独立的消费者/生产者<br/><br/>Layer2：Agent Runtime<br/>  → 每个 Agent 运行在独立进程/容器中<br/>  → Agent 内部：MainLoop（Think → Act → Observe）<br/>  → Agent 间：通过消息总线异步通信<br/><br/>Layer3：编排引擎（Orchestrator）<br/>  → 定义工作流 DAG（有向无环图）：<br/>    信息采集Agent → 分析Agent → 审核Agent → 输出<br/>  → 支持条件分支（审核不通过 → 返回分析Agent 修改）<br/>  → 支持并行（信息采集Agent 可以同时搜索多个数据源）<br/><br/>Layer4：人机协作层（Human-in-the-Loop）<br/>  → 在审核 Agent 发现「高风险信号」时暂停工作流<br/>  → 通过 WebSocket 推送通知到人类审核员<br/>  → 人类审核后 → 工作流继续/回退<br/><br/>【2】状态管理<br/><br/>  任务状态机：<br/>    PENDING → RUNNING → COMPLETED<br/>                   ↘ FAILED → RETRYING → RUNNING<br/>                   ↘ WAITING_HUMAN_REVIEW → APPROVED → RUNNING<br/>                                      ↘ REJECTED → FAILED<br/><br/>  持久化：<br/>    - 任务元数据（状态/创建时间/执行者）→ 关系数据库<br/>    - Agent 中间产物（采集数据/分析草稿）→ 对象存储（S3/MinIO）<br/>    - 对话历史 → Redis（热数据）+ DB（冷数据）<br/><br/>【3】容错策略<br/><br/>  策略1：自动重试（指数退避）<br/>    Agent 执行失败 → 最多重试 3 次 → 每次等待时间翻倍<br/>    适用：LLM API 超时/网络波动/工具调用失败<br/><br/>  策略2：Provider 降级<br/>    DeepSeek 不可用 → 自动切换到 OpenAI<br/>    → 在 Provider 抽象层统一处理<br/><br/>  策略3：检查点恢复（Checkpoint）<br/>    每完成一个 Agent 步骤 → 保存检查点<br/>    系统崩溃后 → 从最近检查点恢复（不需要从头开始）<br/><br/>  策略4：超时保护<br/>    每个 Agent 设置最大执行时间（如 5 分钟）<br/>    超时 → 标记失败 → 触发重试或人工介入<br/><br/>【4】面试加分：可观测性设计<br/><br/>  三支柱可观测性：<br/>    - Metrics：每个 Agent 的执行时间/成功率/Token 消耗 → Prometheus<br/>    - Traces：完整的任务执行链路 → OpenTelemetry<br/>    - Logs：每个 Agent 的 LLM 输入/输出/工具调用 → ELK<br/><br/>  告警规则：<br/>    - Agent 成功率 &lt; 90% → 触发告警<br/>    - 单次任务执行时间 &gt; 10 分钟 → 触发告警<br/>    - Token 日消耗 &gt; 预算 80% → 触发告警</code>
```

**题目**：

> 设计一个企业内部知识库智能问答系统，要求：  
> (1) 支持检索增强生成（RAG），知识库包含 10 万份文档  
> (2) Agent 能自主决定何时检索、何时直接回答  
> (3) 支持「如果检索结果不够，Agent 主动发邮件给相关部门补充信息」  
> (4) 准确率目标 > 95%  
> 请给出完整技术方案。

**参考答案要点**：

```
<code>【1】架构设计（三层）<br/><br/>Layer1：知识检索层<br/>  索引策略：<br/>    - 向量索引：bge-m3 Embedding + Milvus（语义检索）<br/>    - 关键词索引：Elasticsearch BM25（精确检索）<br/>    - 混合检索：RRF（Reciprocal Rank Fusion）融合两路结果<br/>  分块策略：<br/>    - 按语义边界分块（段落/章节结束处）<br/>    - Chunk Size: 512 Token，Overlap: 64 Token<br/>    - 每个 Chunk 附加元数据（文档来源/部门/日期/权限等级）<br/><br/>Layer2：Agent 推理层（ReAct + Self-RAG 混合）<br/>  推理循环：<br/>    Step1: LLM 判断是否需要检索（借鉴 Self-RAG 的 [Retrieve] Token）<br/>    Step2: 如果需要 → 混合检索 Top-10 Chunk<br/>    Step3: CRAG 评估检索质量（Relevance Grading）<br/>    Step4: 如果质量足够 → 生成回答 + 引用来源<br/>    Step5: 如果质量不足 → 执行「主动补充」动作<br/>      → 发邮件给相关部门（通过 Function Calling）<br/>      → 等待回复 → 重新检索 → 重新生成<br/><br/>Layer3：质量保障层<br/>  - 事实核查：生成后用 NLI 模型验证每个声明<br/>  - 引用标注：每个事实标注来源文档和 Chunk ID<br/>  - 人工反馈：用户可以标记「回答不准确」→ 记录 → 优化检索策略<br/><br/>【2】关键组件设计<br/><br/>  组件1：Retrieval Decider（检索决策器）<br/>    "用户的问题是否需要检索知识库？"<br/>    规则：<br/>      - 包含具体产品/项目/政策名称 → 需要检索<br/>      - 是闲聊/问候/常识问题 → 不需要检索<br/>      - 不确定 → 默认检索（宁可多检索，不可遗漏）<br/><br/>  组件2：Email Agent（邮件 Agent）<br/>    Function Calling 定义：<br/>      {<br/>        "name": "send_info_request_email",<br/>        "description": "当知识库中没有足够信息时，发邮件给相关部门",<br/>        "parameters": {<br/>          "department": "目标部门",<br/>          "question_summary": "需要补充的信息摘要",<br/>          "urgency": "urgent/normal/low",<br/>          "reply_to_conversation_id": "关联会话ID"<br/>        }<br/>      }<br/>    → Agent 通过这个工具主动寻求信息补充<br/><br/>  组件3：Citation Verifier（引用验证器）<br/>    用 NLI 模型检查「回答中的每个声明」是否被「引用 Chunk」蕴含<br/>    发现未支撑的声明 → 标记为「需要人工确认」或「重新检索」<br/><br/>【3】准确率保障（&gt;95% 目标）<br/><br/>  分层准确率指标：<br/>    - 检索准确率（Recall@10）&gt; 90%：确保相关信息被检索到<br/>    - 忠实度（Faithfulness）&gt; 95%：确保回答基于检索结果<br/>    - 答案准确率（Answer Accuracy）&gt; 95%：端到端正确<br/><br/>  提升准确率的手段：<br/>    1. Corrective RAG：检索质量不足时自动重新检索<br/>    2. 主动信息补充：知识库不够时发邮件补信息<br/>    3. 引用验证：生成后自动核查每个声明<br/>    4. 人工反馈闭环：用户标记错误 → 改进检索/生成策略<br/>    5. 知识库持续更新：新文档自动入库 + 旧文档定期清理<br/><br/>  知识库更新策略：<br/>    - 增量索引：新文档入库后，只更新受影响的向量分片<br/>    - 权限控制：不同部门只能检索自己有权限的文档<br/>    - 过期检测：文档超过 1 年未更新 → 标记为「可能过时」</code>
```

**题目**：

> 在 Agent Harness 项目中，Doubao Provider 集成时遇到以下问题：  
> (1) 工具调用在流式模式下完全不触发  
> (2) 某些复杂参数结构（嵌套对象）导致 API 报错  
> (3) 并行工具调用不支持，但 Agent 业务逻辑依赖并行  
> 请给出完整的排查思路和解决方案。

**参考答案要点**：

```
<code>【1】问题1：流式模式下 Tool Calling 不触发<br/><br/>  排查步骤：<br/>    Step1：阅读 Doubao API 文档 → 确认是否支持流式 Tool Calling<br/>      发现：Doubao 的流式模式（stream=True）不支持 tool_calls<br/>    Step2：对比 OpenAI 的流式 Tool Calling 机制<br/>      OpenAI: stream 模式下 tool_calls 通过 delta 事件增量推送<br/>      Doubao: 不支持 → 必须用非流式模式<br/>    Step3：确定解决方案<br/><br/>  解决方案：双模式切换<br/>    - 有工具定义时 → 强制使用非流式模式（stream=False）<br/>    - 无工具定义时 → 使用流式模式（stream=True）<br/>    - 对用户透明：在 Provider 抽象层自动切换，上层无感知<br/><br/>  代码设计：<br/>    async def stream(self, messages, tools=None, **kwargs):<br/>      if tools and len(tools) &gt; 0:<br/>        # 有工具 → 非流式（保证 tool_calls 可用）<br/>        response = await self.complete(messages, tools=tools, **kwargs)<br/>        yield response.content  # 模拟流式（一次性输出）<br/>      else:<br/>        # 无工具 → 真正流式<br/>        async for chunk in self._real_stream(messages, **kwargs):<br/>          yield chunk<br/><br/>【2】问题2：复杂参数结构导致 API 报错<br/><br/>  排查步骤：<br/>    Step1：复现问题 → 构造一个嵌套对象参数（如 address: {city: str, zip: str}）<br/>    Step2：查看 API 错误信息 → 400 Bad Request, "Invalid parameter schema"<br/>    Step3：对比 OpenAI 的 Schema 支持 vs Doubao 的 Schema 支持<br/>      OpenAI: 支持 JSON Schema Draft 2020-12 全集<br/>      Doubao: 只支持简单的 properties + type + description<br/><br/>  解决方案：Schema 自动降级<br/>    - 在 ToolCallNormalizer.normalize_schema() 中检测嵌套结构<br/>    - 嵌套对象 → 展平为一层（用下划线连接）<br/>    - 枚举类型 → 转为 string + description 中注明可选值<br/>    - $ref / allOf / anyOf → 解引用/合并为简单结构<br/><br/>  展平示例：<br/>    原始: {"address": {"city": "string", "zip": "string"}}<br/>    展平: {"address_city": "string", "address_zip": "string"}<br/><br/>    工具 handler 侧：在执行前，把展平的参数重构为嵌套结构<br/>    def reconstruct_args(flat_args, original_schema):<br/>      """把展平参数还原为嵌套结构"""<br/>      ...<br/><br/>【3】问题3：不支持并行工具调用<br/><br/>  排查步骤：<br/>    Step1：确认 Doubao API 是否支持 parallel_tool_calls<br/>      结果：不支持，一次只能返回一个 tool_call<br/>    Step2：分析影响：Agent Harness 的 MainLoop 假设可以并行执行工具<br/><br/>  解决方案：Provider 层串行化 + 并行化透明封装<br/>    - Doubao Provider：一次请求只发送一个工具定义（最重要的那个）<br/>      → 或者：发送所有工具定义，但只处理返回的第一个 tool_call<br/>    - Provider 层内部循环：<br/>      while has_pending_tool_calls:<br/>        response = await doubao.complete(messages)<br/>        execute(response.tool_calls[0])  # 只处理第一个<br/>        messages.append(tool_result)<br/>    - 上层 Agent 完全不知道底层是串行的<br/><br/>  架构层面的考量：<br/>    - 这个问题暴露了「统一抽象」的代价：底层能力差异被隐藏了<br/>    - 工程权衡：<br/>      ✅ 统一接口（上层简单）<br/>      ✅ 底层自动适配（减少重复代码）<br/>      ⚠️ 性能损失（串行化 → 延迟增加）<br/>      ⚠️ 行为差异（某些 Provider 的工具选择可能不同）<br/><br/>    建议：在监控中记录每个 Provider 的「工具调用次数」和「延迟」<br/>    → 长期来看，可以引导用户选择最合适的 Provider<br/><br/>【4】面试加分：这类兼容性问题的通用解决方法论<br/><br/>  通用排查框架：<br/>    1. 先查文档 → 确认 API 的「能力边界」（什么支持/什么不支持）<br/>    2. 构造最小复现用例 → 隔离问题（不要一次排查所有问题）<br/>    3. 对比「标准实现」（OpenAI）和「目标实现」（Doubao）的差异<br/>    4. 设计适配层（不要修改业务逻辑，在 Provider 层做转换）<br/>    5. 加回归测试（每个 Provider 的每个能力点都有自动化测试）</code>
```

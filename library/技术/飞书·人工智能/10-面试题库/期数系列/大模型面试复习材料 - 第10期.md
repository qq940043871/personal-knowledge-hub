### 1.1 多 Agent 协作系统——从单体 Agent 到 Agent 群落

#### **为什么需要多 Agent？**

```
<code>单体 Agent 的天花板：<br/>  1. 上下文窗口有限：复杂任务的中间状态很快撑爆 128K Token<br/>  2. 角色混淆：同一个 Agent 同时扮演"研究员"+"写手"+"审核"→ 质量下降<br/>  3. 顺序瓶颈：步骤 A 必须等步骤 B，无法并行加速<br/>  4. 故障单点：一个步骤失败，整个 Agent 重跑<br/><br/>多 Agent 的优势：<br/>  1. 专业分工：每个 Agent 专注一件事（研究 / 写作 / 代码 / 审核）<br/>  2. 并行加速：独立子任务并行执行<br/>  3. 故障隔离：子 Agent 失败不影响整体<br/>  4. 上下文隔离：每个 Agent 只看自己需要的信息</code>
```

#### **三大多 Agent 协作模式**

```
<code>模式1：主从模式（Orchestrator-Worker）<br/>  一个 Orchestrator Agent 负责任务分解和调度<br/>  多个 Worker Agent 负责执行具体子任务<br/><br/>  Orchestrator<br/>    ├── Worker A（网络搜索）<br/>    ├── Worker B（代码执行）<br/>    └── Worker C（文档写作）<br/><br/>  适合：明确目标、可分解的任务（如撰写研究报告）<br/><br/>模式2：流水线模式（Pipeline）<br/>  Agent A 的输出 → Agent B 的输入 → Agent C 的输入 → ...<br/><br/>  用户问题 → 意图识别Agent → 检索Agent → 生成Agent → 审核Agent → 输出<br/><br/>  适合：有固定处理流程的任务（如 RAG + 生成 + 安全审核）<br/><br/>模式3：辩论模式（Debate / Reflection）<br/>  多个 Agent 互相质疑、检验对方输出，最终达成共识<br/><br/>  观点Agent A<br/>        ↕ 互相质疑<br/>  反驳Agent B  →  最终裁判Agent C<br/>        ↕<br/>  观点Agent A（修订后）<br/><br/>  适合：需要高可靠性、自我纠错的场景（如代码审查、事实核查）</code>
```

#### **三大推理框架核心机制**

```
<code>vLLM（PagedAttention 核心）：<br/>  问题：KV Cache 占用显存，且碎片化严重（不同请求长度不同）<br/>  PagedAttention 解法：<br/>    1. #### **为什么 MoE 能让模型"更大但不更慢"？**
```

```
<code>传统 Dense 模型（如 GPT-4）：<br/>  每个 Token → 所有参数都参与计算<br/>  1750亿参数 → 每次推理都激活 1750亿参数<br/>  成本随参数量线性增长<br/><br/>MoE 模型（如 Mixtral 8×7B、DeepSeek-V3）：<br/>  每个 Token → 只激活少数专家（如 8 个专家中激活 2 个）<br/>  参数量：8 × 7B = 56B（显存要求高）<br/>  计算量：2 × 7B = 14B（推理速度快）<br/>  结论：参数量大 但 计算量小 = 模型能力强 且 推理快</code>
```

#### **MoE 架构详解**

```
<code>标准 Transformer Block：<br/>  Self-Attention → Feed-Forward Network (FFN) → 输出<br/><br/>MoE 改造（将 FFN 替换为 MoE 层）：<br/>  Self-Attention → MoE 层 → 输出<br/><br/>MoE 层结构：<br/>  ┌─────────────────────────────────────┐<br/>  │           MoE 层                    │<br/>  │                                     │<br/>  │  输入 Token → Router（门控网络）     │<br/>  │                  ↓                  │<br/>  │     选择 Top-K 个专家（如 K=2）      │<br/>  │                                     │<br/>  │  Expert 1  Expert 2  ...  Expert N  │<br/>  │    (FFN)   (FFN)          (FFN)     │<br/>  │      ↓       ↓                      │<br/>  │   加权合并（门控分数作为权重）        │<br/>  │                                     │<br/>  └─────────────────────────────────────┘<br/><br/>Router（门控网络）的数学：<br/>  g = Softmax(W_g · x)         # 计算每个专家的权重<br/>  topk_idx = TopK(g, k=2)      # 选出分数最高的 2 个专家<br/>  output = Σ g_i * Expert_i(x) # 加权合并选中专家的输出<br/>    i ∈ topk_idx</code>
```

**面试表达**：

> "MoE 的核心思想是'稀疏激活'：把 FFN 层替换成 N 个专家，每次推理只激活 Top-K 个，所以参数量大（能力强）但计算量只有全激活的 K/N。MoE 训练最大的挑战是负载均衡——Router 会过度偏爱某几个'明星专家'，导致其他专家训练不足。Switch Transformer 提出了 Auxiliary Loss，用 f_i（实际分配比例）乘以 p_i（预测概率）的乘积，惩罚不均衡分配。DeepSeek-V3 进一步改进，用 Expert Choice（让专家选 Token 而非 Token 选专家），从根本上保证了负载均衡。"

#### **Attention 的根本瓶颈：O(n²) 的计算和显存**

```
<code>标准 Self-Attention 的复杂度：<br/>  时间复杂度：O(n² · d)   → 序列长度翻倍，计算量翻4倍<br/>  空间复杂度：O(n²)       → 存储 n×n 的 Attention 矩阵<br/><br/>  1K Token  → Attention 矩阵 1M 个元素  → 约 4MB<br/>  32K Token → Attention 矩阵 1B 个元素  → 约 4GB（A100单卡快爆）<br/>  1M Token  → Attention 矩阵 1T 个元素  → 约 4TB（完全不可能）<br/><br/>解决方案三条路：<br/><br/>路线1：近似 Attention（牺牲精度换速度）<br/>  ├── Sparse Attention（局部窗口 + 全局 Token）<br/>  ├── Longformer（滑动窗口 + 特殊全局 Token）<br/>  └── BigBird（随机 + 窗口 + 全局）<br/><br/>路线2：精确 Attention 但优化 IO（不牺牲精度）<br/>  └── Flash Attention（核心工程优化）<br/><br/>路线3：新架构（不用 Attention）<br/>  └── SSM（State Space Model）：Mamba、S4</code>
```

#### **Flash Attention 原理（面试高频）**

```
<code>核心思想：Attention 的瓶颈不是"计算"，而是"IO"<br/><br/>标准 Attention 的 IO 流程：<br/>  HBM → SRAM：读 Q、K（大矩阵）<br/>  SRAM 计算：Q·K^T（中间结果存在 SRAM，但太大，溢出到 HBM）<br/>  HBM → SRAM：读 Attention 矩阵（大）<br/>  SRAM 计算：softmax（Attention）<br/>  HBM → SRAM：再读一次、写一次 V<br/>  读写 HBM 的次数：O(n²)次<br/><br/>Flash Attention 的 IO 流程：<br/>  核心技巧：分块（Tiling）+ 在线 Softmax<br/>  1. 把 Q、K、V 分成小块（每块能放进 SRAM）<br/>  2. 每次只把一小块 Q 和 K 加载到 SRAM<br/>  3. 在 SRAM 内完成 Q·K^T + softmax + ·V<br/>  4. 只写最终输出到 HBM<br/>  读写 HBM 的次数：O(n)次（减少 n 倍）<br/><br/>  数学等价性（在线 Softmax trick）：<br/>  问题：softmax 需要全局 max（分母），分块计算怎么保证数值稳定？<br/>  解法：记录每块的局部 max 和局部 sum，<br/>        合并时用"log-sum-exp 递推公式"修正<br/>  结论：Flash Attention 的输出和标准 Attention 完全等价，只是更快<br/><br/>Flash Attention 2 进一步优化：<br/>  ├── 更好的 GPU 并行化（减少 warp 同步开销）<br/>  ├── 支持 causal mask（自回归生成）<br/>  └── 速度比 Flash Attention 1 再快 2×<br/><br/>Flash Attention 3（2024）：<br/>  └── 针对 H100 的硬件特性优化（异步执行 + 量化感知）</code>
```

#### **为什么需要 SSM？**

```
<code>Transformer 的硬伤（序列长度 N）：<br/>  训练：O(N²) 时间 + O(N²) 显存<br/>  推理（生成）：每生成一个 Token，要处理完整 KV Cache → O(N) 显存<br/><br/>SSM 的承诺：<br/>  训练：O(N log N) 时间（并行扫描）<br/>  推理：O(1) 时间 + O(1) 显存（只保留状态向量）<br/>  代价：理论表达能力与 Attention 有差异</code>
```

#### **Mamba 核心原理**

```
<code>经典 SSM（连续时间）：<br/>  状态方程：h'(t) = A · h(t) + B · x(t)<br/>  输出方程：y(t)  = C · h(t)<br/><br/>  h(t)：隐藏状态（记忆）<br/>  A：状态转移矩阵（如何更新记忆）<br/>  B：输入矩阵（如何吸收新输入）<br/>  C：输出矩阵（如何输出）<br/>  x(t)：输入信号<br/><br/>离散化（适合序列建模）：<br/>  h_t = Ā · h_{t-1} + B̄ · x_t<br/>  y_t = C · h_t<br/><br/>  等价于 RNN，但可以并行训练（通过"并行扫描"算法）<br/><br/>Mamba 的关键创新——选择性机制（Selective State Spaces）：<br/>  传统 SSM 的问题：A、B、C 是固定的，对所有输入一视同仁<br/>  → 无法"选择性地"记忆或遗忘信息<br/><br/>  Mamba 的解法：让 B、C 依赖于输入 x<br/>  B = Linear(x)    # 根据当前输入，决定"如何吸收"<br/>  C = Linear(x)    # 根据当前输入，决定"如何输出"<br/>  Δ = softplus(Linear(x))  # 时间步长，控制遗忘速度<br/><br/>  效果：<br/>  → Δ 大：遗忘更多历史，专注当前输入（类似 Attention 的 "sharp focus"）<br/>  → Δ 小：保留更多历史（类似 RNN 的 "smooth integration"）</code>
```

#### **Flash Attention 原理（硬件视角）**

```
<code>GPU 存储层次：<br/>  HBM（高带宽内存，80GB on A100）：大但慢，~2TB/s 带宽<br/>  SRAM（片上缓存，192KB on A100）：小但极快，~19TB/s 带宽<br/><br/>标准 Attention 的 IO 瓶颈分析：<br/>  S = Q·K^T          → 写 S（N²个元素）到 HBM<br/>  P = softmax(S)     → 读 S，写 P 到 HBM<br/>  O = P·V            → 读 P、V，写 O 到 HBM<br/>  总 HBM 读写：O(N²)<br/><br/>Flash Attention 的核心算法：<br/>  1. 分块（Tiling）：将 Q/K/V 切成 B×B 的小块（B 由 SRAM 大小决定）<br/>  2. 对每个 Q 块：遍历所有 K/V 块，在 SRAM 内完成：<br/>     - 计算局部 S_ij = Q_i · K_j^T<br/>     - 更新"在线 Softmax"（维护全局 max 和 sum 的递推公式）<br/>     - 更新部分 O_i += softmax_weight * V_j<br/>  3. 只写最终 O 和归一化因子到 HBM<br/>  总 HBM 读写：O(N)<br/><br/>在线 Softmax 的数学递推（关键，面试爱考）：<br/>  问题：softmax(x)_i = exp(x_i) / Σ_j exp(x_j)<br/>        分块计算时不知道全局 Σ exp(x_j)<br/><br/>  解法：维护 m（全局 max）和 l（归一化分母）<br/>  m_new = max(m_old, max(S_current_block))<br/>  l_new = exp(m_old - m_new) * l_old + Σ exp(x - m_new)<br/>  O_new = (l_old * exp(m_old - m_new) * O_old + exp(S - m_new) * V) / l_new<br/><br/>PagedAttention（vLLM 的 KV Cache 管理）：<br/>  问题：<br/>    KV Cache 大小在请求完成前未知（序列长度不定）<br/>    传统方案：预分配最大长度显存 → 碎片化严重<br/>    实测：A100 80GB 上，KV Cache 显存利用率只有 ~40%<br/><br/>  解法（类操作系统虚拟内存）：<br/>    1. 将 KV Cache 分成固定大小的"物理块"（block_size=16 Token）<br/>    2. 每个请求有"逻辑块表"，映射到物理块（不要求连续）<br/>    3. 物理块按需分配，请求结束后立即回收<br/>    4. 前缀共享：相同 System Prompt → 共享同一组物理块（Copy-on-Write）<br/><br/>  效果量化：<br/>    显存利用率：~40% → ~90%<br/>    同等显存下可处理的并发请求数：提升 2-4×<br/>    吞吐量：提升 2-4×（并发更高）</code>
```

#### **适用场景建议**

```
<code>选 Transformer（标准密集模型）：<br/>  ✓ 短到中等长度（≤32K Token）<br/>  ✓ 需要精确信息检索（长文档 QA）<br/>  ✓ 团队熟悉，工具链成熟（vLLM/TGI 完整支持）<br/>  代表：GPT-4, LLaMA 3, Qwen 2.5<br/><br/>选 MoE：<br/>  ✓ 需要大参数量（高能力）但计算预算有限<br/>  ✓ 不同任务需要不同专业知识（专家分工）<br/>  ✓ 预训练场景（训练时只用激活专家的计算量）<br/>  代价：部署复杂（所有专家都需要显存），专家路由有额外开销<br/>  代表：Mixtral 8×7B, DeepSeek-V3, GPT-4 (传说 MoE)<br/><br/>选 SSM/Mamba：<br/>  ✓ 超长序列（&gt;100K Token）流式处理<br/>  ✓ 实时场景（延迟敏感，如语音/视频）<br/>  ✓ 边缘部署（显存受限设备）<br/>  代价：精确信息检索弱（"针记忆"问题）<br/>  代表：Mamba-2, Jamba（混合 SSM+Attention）<br/><br/>演进趋势：混合架构（Hybrid）<br/>  ├── SSM 处理长程上下文（O(1) 显存）<br/>  └── Attention 处理关键信息检索（精确但局部）<br/><br/>  Jamba（AI21 Labs）= Mamba + Transformer 交错<br/>  RWKV-6 = Linear Attention（接近 SSM 的 RNN 形式）<br/>  RetNet = Retention（可并行训练 + 高效推理）</code>
```

#### **面试深度加分——预测演进方向**

```
<code>2025-2026 可能的架构趋势：<br/><br/>1. 混合架构主流化（Hybrid SSM + Attention）<br/>   Attention 负责关键 Token 的精确检索<br/>   SSM 负责长程背景信息的压缩记忆<br/>   → 兼得两者优势<br/><br/>2. MoE + SSM 的组合<br/>   MoE 解决参数效率问题（多专家）<br/>   SSM 解决长序列效率问题<br/>   → 参数大 + 序列长 + 计算省<br/><br/>3. 推理时计算（Test-Time Compute，TTC）<br/>   不是训练更大的模型，而是推理时多想几步（o1 / o3 模式）<br/>   "推理时计算" vs "训练时计算" 的权衡<br/>   → 未来可能：小底座 + 大推理预算 优于 大底座 + 小推理预算<br/><br/>4. 状态压缩技术的突破<br/>   如何让 SSM 突破"针记忆"瓶颈？<br/>   → 选择性机制更智能（哪些信息值得保存）<br/>   → 层次化状态（短期 + 长期双状态）</code>
```

**STAR 答题**：

> "S：我们评估了三种架构用于 Agent Harness 的下一代版本。T：在长上下文（>64K Token）场景下找到最优架构。A：Transformer 精确但显存大；MoE 参数效率高但部署复杂；Mamba 长序列推理快但信息检索弱。最终选择 Jamba 式混合架构：SSM 层处理长背景，每隔 4 层插入 Attention 做精确检索。R：实测 128K Token 文档处理，比纯 Transformer 显存减少 60%，速度提升 2.5×，信息检索准确率仅下降 3%。未来方向：MoE + SSM + TTC 的三重叠加。"

### 5.3 高频考点速记

```
<code>面试官最爱问的5个"为什么"：<br/>  1. 为什么 MoE 比 Dense 模型参数效率高？<br/>     → 稀疏激活：参数量 = 所有专家之和，计算量 = Top-K 专家<br/>  2. 为什么 Flash Attention 更快？<br/>     → IO 优化：分块 + 在线 Softmax → HBM 读写 O(N²)→O(N)<br/>  3. 为什么 vLLM 的 PagedAttention 能提升吞吐？<br/>     → 显存利用率 40%→90%，同等显存下并发请求数 2-4×<br/>  4. 为什么 Mamba 推理显存 O(1)？<br/>     → 只保留状态向量，不存 KV Cache（RNN 本质）<br/>  5. 为什么多 Agent 比单 Agent 质量更高？<br/>     → 专业分工 + 角色隔离 + 交叉验证（Reviewer 机制）</code>
```

#### **对比学习——Embedding 模型的灵魂**

```
<code>对比学习（Contrastive Learning）核心原理：<br/><br/>目标：拉近正样本对，推远负样本对<br/><br/>InfoNCE Loss（最常用的对比损失）：<br/>  L = -log [ exp(sim(q, k+) / τ) / Σ_j exp(sim(q, k_j) / τ) ]<br/><br/>  其中：<br/>    q: 查询向量（anchor）<br/>    k+: 正样本向量<br/>    k_j: 所有样本（含负样本）<br/>    τ: 温度参数（控制分布的尖锐程度）<br/>    sim(): 相似度函数（通常为余弦相似度）<br/><br/>关键要素：<br/>  1. 正样本构造：<br/>     · 同一文档的不同 chunk<br/>     · 同一查询的不同改写<br/>     · LLM 生成的释义（paraphrase）<br/><br/>  2. 负样本构造（决定模型质量的核心！）：<br/>     · 随机负样本（In-batch negatives）→ 简单，但不够"难"<br/>     · 困难负样本（Hard negatives）→ BM25检索排名高但无关的文档<br/>     · LLM辅助负样本 → GPT-4标注的"看似相关实则不同"的样本<br/>     · ANCE（Approximate Nearest Neighbor Negative Contrastive Estimation）<br/>       → 用上一步的模型检索困难负样本 → 迭代优化<br/><br/>  3. 温度参数 τ 的影响：<br/>     τ 太大 → 分布太平 → 梯度信号弱<br/>     τ 太小 → 分布太尖 → 只关注最难的负样本<br/>     BGE系列: τ = 0.01 ~ 0.05（实验最优）</code>
```

```
<code># InfoNCE Loss 实现<br/>import torch<br/>import torch.nn.functional as F<br/><br/>def info_nce_loss(query, positive, negatives, temperature=0.05):<br/>    """<br/>    query: [batch, dim]<br/>    positive: [batch, dim]<br/>    negatives: [batch, num_neg, dim]<br/>    """<br/>    # 归一化<br/>    query = F.normalize(query, dim=-1)<br/>    positive = F.normalize(positive, dim=-1)<br/>    negatives = F.normalize(negatives, dim=-1)<br/><br/>    # 正样本相似度<br/>    pos_sim = torch.sum(query * positive, dim=-1, keepdim=True) / temperature  # [batch, 1]<br/><br/>    # 负样本相似度<br/>    neg_sim = torch.bmm(negatives, query.unsqueeze(-1)).squeeze(-1) / temperature  # [batch, num_neg]<br/><br/>    # 拼接所有相似度<br/>    logits = torch.cat([pos_sim, neg_sim], dim=-1)  # [batch, 1+num_neg]<br/><br/>    # 标签：正样本在第0位<br/>    labels = torch.zeros(logits.size(0), dtype=torch.long, device=logits.device)<br/><br/>    return F.cross_entropy(logits, labels)</code>
```

#### **六大 Chunking 策略全面对比**

```
<code>Chunking 策略全景：<br/><br/>1. 固定大小切分（Fixed-size Chunking）<br/>   · 最简单：每 N 个 token 切一段，overlap=M 个 token<br/>   · 优点：实现简单，长度可控<br/>   · 缺点：完全忽略语义边界<br/>   · 适用：快速原型 / 文本结构均匀的场景<br/><br/>2. 递归字符切分（Recursive Character Chunking）<br/>   · LangChain 默认策略：按分隔符优先级递归切分<br/>   · 分隔符优先级：\n\n &gt; \n &gt; 。 &gt; 空格 &gt; 字符<br/>   · 优点：大致保留段落结构<br/>   · 缺点：仍是启发式，不理解语义<br/>   · 适用：通用场景的基线方案<br/><br/>3. 语义切分（Semantic Chunking）<br/>   · 核心思想：相邻句子的 Embedding 相似度下降点 = 语义断点<br/>   · 算法：<br/>     1. 将文本按句子拆分<br/>     2. 计算相邻句子的 Embedding 余弦相似度<br/>     3. 相似度低于阈值 θ → 在此处切分<br/>   · 优点：尊重语义边界<br/>   · 缺点：需要额外 Embedding 计算，阈值 θ 难调<br/>   · 适用：长文档 / 对话记录 / 法律文书<br/><br/>4. 文档结构切分（Document Structure Chunking）<br/>   · 利用文档的层级结构：标题(H1/H2/H3) → 段落 → 列表<br/>   · Markdown: 按 # ## ### 分层<br/>   · HTML: 按 &lt;h1&gt; &lt;h2&gt; &lt;section&gt; 分层<br/>   · PDF: 利用版面分析（Layout Parser）识别标题/段落/表格<br/>   · 优点：最好地保留文档逻辑结构<br/>   · 缺点：依赖文档格式规范，非结构化文本不适用<br/>   · 适用：技术文档 / API 文档 / 论文<br/><br/>5. 基于命题的切分（Proposition-based Chunking）<br/>   · LLM 辅助：让 LLM 将段落拆解为最小原子命题<br/>   · 例："Python 是一种解释型语言，由 Guido 于 1991 年创建"<br/>     → 命题1: "Python 是解释型语言"<br/>     → 命题2: "Python 由 Guido 创建"<br/>     → 命题3: "Python 于 1991 年创建"<br/>   · 优点：最细粒度，检索精度最高<br/>   · 缺点：LLM 调用成本高，速度慢<br/>   · 适用：高精度场景 / 法律合同 / 医学文献<br/><br/>6. 自适应切分（Adaptive Chunking）← Agent Harness V3 方案<br/>   · 根据文档类型和查询模式动态选择策略：<br/>     - 技术文档 → 结构切分<br/>     - 自由文本 → 语义切分<br/>     - FAQ/短文本 → 按条目切分<br/>     - 表格/代码 → 整体保留 + 描述性摘要<br/>   · 每个 chunk 附加元数据：文档标题/层级路径/前后文摘要<br/>   · 优点：综合最优<br/>   · 缺点：实现复杂</code>
```

```
<code># 语义切分实现（面试加分项）<br/>from typing import List<br/>import numpy as np<br/><br/>def semantic_chunk(<br/>    sentences: List[str],<br/>    embedding_model,<br/>    similarity_threshold: float = 0.5,<br/>    min_chunk_size: int = 100,<br/>    max_chunk_size: int = 800<br/>) -&gt; List[str]:<br/>    """<br/>    语义切分：基于相邻句子相似度断点<br/><br/>    核心思想：<br/>      相邻两个句子的语义相似度如果低于阈值，<br/>      说明此处发生了话题转换 → 应该在此处切分<br/>    """<br/>    # Step 1: 获取每个句子的 Embedding<br/>    embeddings = embedding_model.encode(sentences)<br/>    embeddings = embeddings / np.linalg.norm(embeddings, axis=1, keepdim=True)<br/><br/>    # Step 2: 计算相邻句子的余弦相似度<br/>    similarities = [<br/>        np.dot(embeddings[i], embeddings[i + 1])<br/>        for i in range(len(embeddings) - 1)<br/>    ]<br/><br/>    # Step 3: 找到相似度低于阈值的断点<br/>    breakpoints = [0]  # 起始点<br/>    for i, sim in enumerate(similarities):<br/>        if sim &lt; similarity_threshold:<br/>            breakpoints.append(i + 1)  # 在第 i+1 句前切分<br/>    breakpoints.append(len(sentences))  # 结束点<br/><br/>    # Step 4: 合并过小的 chunk，拆分过大的 chunk<br/>    chunks = []<br/>    for i in range(len(breakpoints) - 1):<br/>        chunk_sentences = sentences[breakpoints[i]:breakpoints[i + 1]]<br/>        chunk_text = " ".join(chunk_sentences)<br/><br/>        # 如果 chunk 太小 → 合并到前一个<br/>        if len(chunk_text) &lt; min_chunk_size and chunks:<br/>            chunks[-1] = chunks[-1] + " " + chunk_text<br/>        else:<br/>            chunks.append(chunk_text)<br/><br/>    return chunks</code>
```

#### **Chunking 的面试关键问题：Chunk 大小如何选择？**

```
<code>┌──────────────────────────────────────────────────────────────────┐<br/>│ Chunk Size 的 Trade-off 分析                                      │<br/>│                                                                    │<br/>│  小 Chunk (128-256 tokens):                                       │<br/>│    优势：检索精度高（每个 chunk 语义聚焦）                         │<br/>│    劣势：上下文不完整（可能缺少必要背景）                          │<br/>│    适用：FAQ / 精确定位型查询                                      │<br/>│                                                                    │<br/>│  中 Chunk (512-1024 tokens):                                      │<br/>│    优势：上下文与精度的平衡点                                      │<br/>│    劣势：可能包含冗余信息                                          │<br/>│    适用：通用 RAG 场景（最常用）                                   │<br/>│                                                                    │<br/>│  大 Chunk (1024-2048 tokens):                                     │<br/>│    优势：上下文完整（完整段落/章节）                               │<br/>│    劣势：检索噪声大（含大量无关内容）                              │<br/>│    适用：摘要型查询 / 需要全局理解的场景                           │<br/>│                                                                    │<br/>│  工程最佳实践（Agent Harness V3 的经验）：                         │<br/>│    · 主索引：512-1024 tokens（平衡精度和上下文）                   │<br/>│    · 精排索引：128-256 tokens（用于 Rerank 阶段精排）              │<br/>│    · 摘要索引：文档级摘要（用于粗筛相关文档）                      │<br/>│    · 三级索引联合检索 → "粗筛 + 精排 + 上下文补全"               │<br/>│                                                                    │<br/>│  面试金句：                                                        │<br/>│    "Chunking 不是切分文本，是在设计信息的检索粒度。                │<br/>│     好的 Chunking 策略能让每个 chunk 都是一个自足的语义单元，     │<br/>│     检索到它就等于检索到了完整的答案上下文。"                      │<br/>└──────────────────────────────────────────────────────────────────┘</code>
```

### 2.3 向量数据库——RAG 的「存储引擎」

```
<code>┌──────────────────────────────────────────────────────────────────┐<br/>│                  向量数据库核心原理：ANN 近似检索                   │<br/>│                                                                    │<br/>│  为什么需要近似检索？                                               │<br/>│    精确 KNN：计算查询向量与所有 N 个向量的距离 → O(N)              │<br/>│    当 N = 1亿时 → 每次检索 1亿次距离计算 → 不可接受               │<br/>│    ANN (Approximate Nearest Neighbor)：牺牲 &lt;2% 精度，换 100x 速度│<br/>│                                                                    │<br/>│  ANN 的三大流派（面试必知）：                                       │<br/>│                                                                    │<br/>│  1. 基于图（Graph-based）                                          │<br/>│     代表：HNSW (Hierarchical Navigable Small World)                │<br/>│     原理：构建多层跳表图，上层稀疏（快速跳转），下层稠密（精确定位）│<br/>│     复杂度：O(log N)，Recall 95%+                                  │<br/>│     适用：Milvus, Weaviate, Qdrant                                 │<br/>│                                                                    │<br/>│  2. 基于量化（Quantization-based）                                 │<br/>│     代表：PQ (Product Quantization), IVF-PQ                        │<br/>│     原理：将向量分成 M 个子空间，每个子空间量化为 256 个聚类中心   │<br/>│     存储：每个向量只需 M×8 bits（而非 d×32 bits）                  │<br/>│     压缩比：32~128x                                                │<br/>│     适用：Faiss (IVF-PQ), Milvus (IVF_PQ)                         │<br/>│                                                                    │<br/>│  3. 基于哈希（Hash-based）                                         │<br/>│     代表：LSH (Locality-Sensitive Hashing)                         │<br/>│     原理：相似向量有高概率映射到同一桶                              │<br/>│     适用：理论价值大，工程上较少单独使用                            │<br/>└──────────────────────────────────────────────────────────────────┘</code>
```

### 2.4 混合检索与 Rerank——RAG 效果的「最后一公里」

```
<code>┌──────────────────────────────────────────────────────────────────┐<br/>│          为什么纯向量检索不够？                                     │<br/>│                                                                    │<br/>│  向量检索的三大盲区：                                               │<br/>│    1. 精确匹配失效：查询"iPhone 15 Pro Max 256GB"                  │<br/>│       → 向量检索可能返回 iPhone 14 Pro 的内容（语义相似）          │<br/>│       → 但用户要的是精确型号！                                      │<br/>│    2. 缩写/专有名词：查询"RAG"                                     │<br/>│       → 向量可能匹配到 "rag(抹布)" 而非 "Retrieval-Augmented"     │<br/>│    3. 低频词/数字：查询"2024年Q3营收42.7亿"                        │<br/>│       → 向量空间对数字不敏感 → 可能匹配到其他年份的营收            │<br/>│                                                                    │<br/>│  解决方案：混合检索（Hybrid Search）                                │<br/>│    向量检索（语义匹配）+ 关键词检索（精确匹配）= 互补              │<br/>│                                                                    │<br/>│  常见融合策略：                                                     │<br/>│    · Reciprocal Rank Fusion (RRF):                                 │<br/>│      score(d) = Σ 1/(k + rank_i(d)), k=60                         │<br/>│      → 基于排名的融合，不需要归一化分数                             │<br/>│                                                                    │<br/>│    · 线性加权:                                                      │<br/>│      score(d) = α·vec_score(d) + (1-α)·bm25_score(d)             │<br/>│      → 需要分数归一化，α 需要调参                                  │<br/>│                                                                    │<br/>│    · 学习式融合：                                                   │<br/>│      训练一个小模型学习两路分数的最优组合                           │<br/>│      → 效果最好，但需要标注数据                                    │<br/>└──────────────────────────────────────────────────────────────────┘</code>
```

#### **BM25——关键词检索的经典算法**

```
<code>"""<br/>BM25 (Best Matching 25) —— 2009 年的搜索标准算法<br/><br/>核心公式：<br/>  BM25(D, Q) = Σ_{i=1}^{n} IDF(q_i) · f(q_i, D) · (k1 + 1) /<br/>               (f(q_i, D) + k1 · (1 - b + b · |D| / avgdl))<br/><br/>其中：<br/>  q_i: 查询中的第 i 个词<br/>  f(q_i, D): 词 q_i 在文档 D 中的词频<br/>  |D|: 文档 D 的长度<br/>  avgdl: 所有文档的平均长度<br/>  k1: 词频饱和参数（通常 1.2~2.0）<br/>  b: 文档长度归一化参数（通常 0.75）<br/>  IDF(q_i): 逆文档频率 = log((N - n(q_i) + 0.5) / (n(q_i) + 0.5) + 1)<br/><br/>直觉理解：<br/>  · TF 部分：词出现越多 → 分数越高，但有饱和（k1控制）<br/>  · IDF 部分：词越稀有 → 权重越高<br/>  · 长度归一化：长文档天然词频高 → b 参数惩罚<br/><br/>为什么 BM25 在 2026 年仍然重要？<br/>  1. 精确匹配：对专有名词、数字、缩写比向量更可靠<br/>  2. 速度极快：倒排索引检索，毫秒级<br/>  3. 可解释性：每个词的贡献可以分解<br/>  4. 零-shot：不需要训练数据<br/><br/>面试关键：<br/>  "BM25 是 RAG 中向量检索的最佳搭档。<br/>   向量检索擅长语义匹配（'如何部署模型'≈'模型部署步骤'），<br/>   BM25 擅长精确匹配（'iPhone 15'≠'iPhone 14'），<br/>   两者结合 = 语义理解 + 精确召回。"<br/>"""</code>
```

#### **Reranker——检索后的精排模型**

```
<code>为什么需要 Reranker？<br/><br/>向量检索/ BM25 是「双塔模型」：<br/>  Query → Embedding ─┐<br/>                      ├→ 余弦相似度<br/>  Doc → Embedding ────┘<br/><br/>问题：Query 和 Doc 各自独立编码 → 无法捕捉交互特征<br/>  · "银行的利息" vs "河岸的利息" → Embedding 可能很相似<br/>  · 但 Cross-Encoder 可以看到两者放在一起 → 判断出语义差异<br/><br/>Cross-Encoder Reranker：<br/>  将 [Query, Doc] 拼接后一起送入 Transformer<br/>  → 输出一个相关性分数<br/><br/>  优势：精度远高于双塔（因为能看到交互特征）<br/>  劣势：速度慢（每个 pair 都要过一遍模型）<br/><br/>工程实践：<br/>  1. 第一阶段：双塔粗排（向量检索 Top-100 + BM25 Top-50）<br/>  2. 第二阶段：Cross-Encoder 精排（Top-150 → 精排 → 取 Top-5）<br/>  3. Reranker 模型选型：<br/>     · bge-reranker-v2-m3 (568M): 中文最优<br/>     · bge-reranker-large (560M): 通用<br/>     · Cohere Rerank (API): 零部署<br/>     · ColBERT: 快速交互式检索（介于双塔和 Cross-Encoder 之间）</code>
```

```
<code># 混合检索 + Rerank 完整流程<br/>def hybrid_search_with_rerank(<br/>    query: str,<br/>    vector_store,     # 向量数据库<br/>    bm25_store,       # BM25 索引<br/>    reranker,         # Cross-Encoder Reranker<br/>    top_k_vector=50,<br/>    top_k_bm25=30,<br/>    top_k_final=5,<br/>    alpha=0.7         # 向量检索权重<br/>):<br/>    """混合检索 + Rerank 标准流水线：向量检索 → BM25 → RRF 融合去重 →<br/>    Cross-Encoder Rerank → 返回 Top-K 最终结果"""<br/>    # Step 1: 向量检索<br/>    vec_results = vector_store.search(query, top_k=top_k_vector)<br/><br/>    # Step 2: BM25 检索<br/>    bm25_results = bm25_store.search(query, top_k=top_k_bm25)<br/><br/>    # Step 3: RRF 融合（k=60，标准参数）<br/>    k = 60<br/>    doc_scores = {}<br/>    for rank, doc in enumerate(vec_results):<br/>        doc_scores[doc.id] = doc_scores.get(doc.id, 0) + 1.0 / (k + rank + 1)<br/>    for rank, doc in enumerate(bm25_results):<br/>        doc_scores[doc.id] = doc_scores.get(doc.id, 0) + 1.0 / (k + rank + 1)<br/><br/>    # 按 RRF 分数排序<br/>    merged = sorted(doc_scores.items(), key=lambda x: x[1], reverse=True)<br/>    candidate_docs = [doc_store[doc_id] for doc_id, _ in merged[:top_k_vector]]<br/><br/>    # Step 4: Cross-Encoder Rerank<br/>    pairs = [(query, doc.text) for doc in candidate_docs]<br/>    rerank_scores = reranker.predict(pairs)<br/><br/>    # Step 5: 按 Rerank 分数排序返回<br/>    reranked = sorted(<br/>        zip(candidate_docs, rerank_scores),<br/>        key=lambda x: x[1],<br/>        reverse=True<br/>    )<br/><br/>    return [doc for doc, score in reranked[:top_k_final]]</code>
```

### 2.6 RAG 中的 Query 处理——「问题好，答案才好」

```
<code>┌──────────────────────────────────────────────────────────────────┐<br/>│            Query 处理技术全景                                      │<br/>│                                                                    │<br/>│  原始查询的五大问题：                                               │<br/>│    1. 模糊查询："帮我看看那个东西" → 指代不明                     │<br/>│    2. 复杂查询："对比A和B的区别以及各自优劣势" → 多跳              │<br/>│    3. 口语化查询："咋搞这个bug" → 正式文档不含这种表达             │<br/>│    4. 否定查询："不是XX的方案" → 向量检索难以处理否定              │<br/>│    5. 隐式需求："我的电脑蓝屏了" → 实际需要的是解决方案            │<br/>│                                                                    │<br/>│  六大 Query 处理技术：                                             │<br/>│                                                                    │<br/>│  1. Query Rewriting（查询改写）                                    │<br/>│     · 用 LLM 将口语化/模糊查询改写为正式/明确的查询               │<br/>│     · 例："咋搞蓝屏" → "Windows 蓝屏错误解决方案"                 │<br/>│     · 方法：Prompt-based（零成本）或 训练小型 T5 模型             │<br/>│                                                                    │<br/>│  2. Query Decomposition（查询分解）                                │<br/>│     · 将复杂查询拆分为多个子查询                                   │<br/>│     · 例："对比 A 和 B" → ["A 的特点", "B 的特点", "A vs B 对比"] │<br/>│     · 每个子查询独立检索 → 结果合并                                │<br/>│                                                                    │<br/>│  3. Query Expansion（查询扩展）                                    │<br/>│     · 生成查询的同义表达/相关术语                                  │<br/>│     · 方法1: LLM 生成同义改写（HyDE的思路）                       │<br/>│     · 方法2: 从检索结果中提取关键词（Pseudo Relevance Feedback）   │<br/>│     · 方法3: 使用词嵌入的近义词                                    │<br/>│                                                                    │<br/>│  4. HyDE (Hypothetical Document Embedding)                         │<br/>│     · 核心思想：让 LLM 先"猜"一个答案（假设性文档）               │<br/>│     · 然后用假设性文档的 Embedding 去检索 → 更接近真实文档分布    │<br/>│     · 效果：对知识密集型查询提升显著（+10~20% Recall）            │<br/>│     · 代价：额外一次 LLM 调用，假设性文档可能带偏检索方向         │<br/>│                                                                    │<br/>│  5. Step-back Prompting                                            │<br/>│     · 让 LLM 从具体问题抽象到更一般的问题                         │<br/>│     · 例："Python 3.11 的 walrus operator 语法"                   │<br/>│          → "Python 的赋值表达式（walrus operator）概念和用法"      │<br/>│     · 检索一般性问题的结果 → 覆盖面更广 → 回答更完整             │<br/>│                                                                    │<br/>│  6. 多查询融合（Multi-Query Fusion）                               │<br/>│     · 用 LLM 生成 N 个查询改写 → 分别检索 → 结果去重融合          │<br/>│     · 类似于 Query-level 的 Ensemble                               │<br/>│     · N=3~5 是常用值                                              │<br/>│     · 简单有效，是最常用的 Query 处理策略                          │<br/>└──────────────────────────────────────────────────────────────────┘</code>
```

### Q1：RAG 系统的效果不好，你会如何系统性地排查和优化？

```
<code>答案（六层排查法——体现系统思维）：<br/><br/>第1层：数据质量排查（最常见的原因）<br/>  □ 源文档是否包含答案？（如果文档里没有，RAG 不可能检索到）<br/>  □ 文档解析是否正确？（PDF 表格/图片/公式是否丢失）<br/>  □ 数据是否更新？（旧版本文档 vs 最新信息）<br/><br/>第2层：Chunking 排查<br/>  □ 答案是否被切分到两个不同的 chunk？<br/>    → 检查：人工标注 QA 对，看答案是否完整出现在单个 chunk 中<br/>    → 解决：增大 overlap / 换语义切分 / 换结构切分<br/>  □ chunk 是否包含太多无关内容？<br/>    → 检查：抽检 chunk 内容是否聚焦<br/>    → 解决：减小 chunk size / 用命题切分<br/><br/>第3层：Embedding 排查<br/>  □ Embedding 模型是否适合当前语言/领域？<br/>    → 中文场景用了英文 Embedding → 效果差<br/>    → 专业领域（医疗/法律）用了通用 Embedding → 领域词表达不准<br/>  □ 困难负样本分析：<br/>    → 用标注数据计算：查询与正样本/负样本的相似度分布<br/>    → 如果分布重叠大 → Embedding 区分度不够 → 换模型或微调<br/><br/>第4层：检索策略排查<br/>  □ 纯向量检索 vs 混合检索的对比<br/>    → 如果 BM25 + 向量 &gt; 纯向量 → 需要精确匹配能力<br/>  □ Top-K 是否足够？<br/>    → Recall@5 vs Recall@20 → 如果差距大 → 增大 K + 加 Reranker<br/>  □ Reranker 是否有效？<br/>    → 对比 Reranker 前后的 NDCG 变化<br/><br/>第5层：Query 处理排查<br/>  □ 用户查询是否需要改写/分解？<br/>    → 分析错误case：是否因为查询太模糊/太复杂<br/>  □ HyDE / Multi-Query 是否有效？<br/>    → A/B测试对比<br/><br/>第6层：生成层排查<br/>  □ Prompt 设计是否合理？<br/>    → 是否明确要求"只根据检索结果回答"<br/>    → 是否包含"如果检索结果不包含答案，请说不知道"<br/>  □ 检索结果注入方式？<br/>    → 直接拼接 vs 结构化注入（标注来源+相关性分数）<br/>    → 检索结果过多 → 上下文太长 → 中间内容被忽略（Lost in Middle）<br/><br/>系统性优化路线图：<br/>  短期（1周）：加 BM25 混合检索 + Reranker → 通常提升 15-25%<br/>  中期（1月）：优化 Chunking + Query 处理 → 再提升 10-15%<br/>  长期（3月）：Embedding 微调 + GraphRAG → 再提升 5-10%</code>
```

### Q2：Embedding 模型中的对比学习，为什么困难负样本如此重要？如何构造？

```
<code>答案（三层深度）：<br/><br/>第一层：为什么困难负样本重要？<br/><br/>  对比学习的目标：拉近正样本、推远负样本<br/><br/>  如果负样本都是"容易的"（与查询完全不相关）：<br/>    → 模型只学会了"猫 ≠ 汽车"这种显而易见的区别<br/>    → 但在实际检索中，困难的是"猫 ≠ 狗"、"iPhone 15 ≠ iPhone 14"<br/>    → 模型没有学到这种细粒度区分能力<br/><br/>  数学直觉：<br/>    InfoNCE Loss 的梯度 ∝ softmax 权重 × 差异<br/>    → 如果所有负样本相似度都很低 → softmax 已经饱和 → 梯度 ≈ 0<br/>    → 只有"困难的"负样本（相似度高但实际不匹配）才能提供有效梯度信号<br/><br/>第二层：如何构造困难负样本？<br/><br/>  方法1：BM25 困难负样本<br/>    · 用 BM25 检索 Top-100，去掉真正的正样本<br/>    · 剩余的 99 个就是困难负样本（BM25认为相关但实际不匹配）<br/>    · 优点：无需 LLM，成本极低<br/>    · 缺点：可能引入假负样本（BM25 检索到的也可能是相关的）<br/><br/>  方法2：ANCE（迭代式困难负样本挖掘）<br/>    · Round 1: 用 In-batch 负样本训练初始模型<br/>    · Round 2: 用初始模型检索困难负样本<br/>    · Round 3: 用新模型继续检索更难的负样本<br/>    · → 迭代优化，每轮都找到"更难的"负样本<br/>    · 这是 BGE 系列模型的核心训练策略<br/><br/>  方法3：LLM 辅助标注<br/>    · Prompt GPT-4: "给定查询 Q，以下文档 D 是否真正回答了 Q？"<br/>    · 标注为"否"但 BM25/向量检索排名高的 = 困难负样本<br/>    · 优点：质量最高<br/>    · 缺点：成本高（每个样本需要一次 GPT-4 调用）<br/><br/>  方法4：跨编码器挖掘<br/>    · 用 Cross-Encoder 对 (Q, D) 打分<br/>    · 分数在 [0.3, 0.7] 区间的 = 困难负样本<br/>    · 分数太低的太容易，分数太高的可能是假负样本<br/><br/>第三层：工程实践中的经验<br/><br/>  · 正负样本比例：1:7 ~ 1:15（不是越多越好，过多会引入噪声）<br/>  · 困难度控制：逐步增加困难度（Curriculum Learning for Negatives）<br/>    → 训练初期：随机负样本为主（容易的，建立基础表征）<br/>    → 训练中期：增加 BM25 困难负样本<br/>    → 训练后期：增加 ANCE/LLM 困难负样本<br/>  · 假负样本问题：约 5-10% 的"困难负样本"其实是真相关的<br/>    → 影响：相当于给模型错误信号<br/>    → 缓解：Consistency Filtering（多个模型投票）或阈值筛选</code>
```

### Q3：向量数据库的 HNSW 和 IVF-PQ 有什么区别？如何选择？

```
<code>答案（原理 + 场景 + 数据量 三维分析）：<br/><br/>1. HNSW（基于图的索引）：<br/>   构建：<br/>     · 在高维空间中构建多层导航图<br/>     · 每插入一个点，从最高层入口贪心搜索到最近邻<br/>     · 在 Layer 0 建立 M 个邻居连接，上层建立更少的连接<br/>   检索：<br/>     · 从最高层开始贪心搜索 → 逐层下降<br/>     · 在 Layer 0 做精确的局部搜索<br/>   特点：<br/>     · Recall 极高（95-99%）<br/>     · 查询延迟极低（1-5ms for 1M vectors）<br/>     · 内存占用大（图的边 = 每个点 M×2 个指针）<br/>     · 构建速度中等<br/>     · 不支持增量删除（只能软删除/标记删除）<br/><br/>2. IVF-PQ（基于量化的索引）：<br/>   构建：<br/>     · Step 1: 用 K-Means 将向量聚成 nlist 个簇（IVF = Inverted File）<br/>     · Step 2: 对每个簇内的向量做 Product Quantization<br/>       → 将 d 维向量分成 M 个子空间<br/>       → 每个子空间用 K-Means 聚成 256 个聚类中心（码本）<br/>       → 每个向量只需存储 M 个 uint8 索引<br/>   检索：<br/>     · Step 1: 找到查询最近的 nprobe 个簇<br/>     · Step 2: 在这些簇内用 PQ 码本快速计算距离<br/>     · Step 3: 返回 Top-K<br/>   特点：<br/>     · 内存占用极小（M×8 bits per vector vs d×32 bits）<br/>     · Recall 中等（85-95%，取决于 nprobe 和 M）<br/>     · 查询延迟中等（5-20ms，取决于 nprobe）<br/>     · 构建速度快<br/>     · 支持增量更新<br/><br/>3. 选型决策：<br/>   ┌───────────────────────────────────────────────────────────┐<br/>   │  条件                      │ 推荐          │ 原因         │<br/>   │  ─────────────────────────────────────────────────────── │<br/>   │  &lt;1000万向量，内存充足     │ HNSW          │ Recall最高   │<br/>   │  &gt;1亿向量，内存受限        │ IVF-PQ        │ 压缩比高     │<br/>   │  延迟敏感（&lt;10ms）         │ HNSW          │ 查询更快     │<br/>   │  成本敏感                  │ IVF-PQ        │ 内存省5-10x  │<br/>   │  需要频繁增删              │ IVF-PQ        │ 支持增量更新 │<br/>   │  数据规模持续增长          │ IVF-PQ + IVF-HNSW │ 分区索引 │<br/>   └───────────────────────────────────────────────────────────┘<br/><br/>   实际项目中（Agent Harness V3）的选择：<br/>     · &lt;500万：HNSW（Qdrant 默认）<br/>     · 500万~5000万：HNSW + 量化（Qdrant Scalar Quantization）<br/>     · &gt;5000万：Milvus IVF-PQ / IVF-HNSQ（混合索引）</code>
```

### Q4：什么是 Lost in the Middle 问题？RAG 中如何解决？

```
<code>答案（问题理解 + 解决方案 + 实验数据）：<br/><br/>1. 问题描述：<br/>   论文：Liu et al., "Lost in the Middle: How Language Models Use Long Contexts"<br/><br/>   发现：LLM 对长上下文中不同位置的信息利用率不同<br/>   ┌─────────────────────────────────────────────────────────┐<br/>   │  位置    │  开头（前10%）  │  中间（40-60%）  │  结尾（后10%）│<br/>   │  利用率  │  高（~90%）     │  低（~50%）      │  高（~85%）  │<br/>   └─────────────────────────────────────────────────────────┘<br/><br/>   → LLM 形成了一个 "U 形" 的注意力分布<br/>   → 中间的信息最容易被忽略<br/><br/>   对 RAG 的影响：<br/>     如果把 10 个检索结果拼接后输入 LLM<br/>     → 第 4-7 个结果被"看到"的概率显著低于第 1-3 个和最后 2 个<br/>     → 即使检索到了正确答案，如果放在中间位置，模型也可能忽略<br/><br/>2. 根本原因：<br/>   · 注意力稀释：中间位置距离 Query（通常在最前面）较远<br/>   · 注意力 Sink：LLM 倾向于把注意力分配给前几个 token<br/>   · 位置编码衰减：RoPE 等位置编码使远距离的注意力权重衰减<br/><br/>3. 解决方案（按效果排序）：<br/><br/>   方案1: Reranker 精排 + 减少注入数量<br/>     · 只注入 Top-3~5 个最相关的 chunk（而非 Top-10）<br/>     · 减少"中间区域" → 每个 chunk 都被充分关注<br/>     · 效果：直接减少问题发生概率，最简单有效<br/><br/>   方案2: 位置重排（最相关放首尾）<br/>     · 将 Rerank 后的 Top-K 结果按相关性重排<br/>     · 最相关的放第一位和最后一位<br/>     · 次相关的放第二位和倒数第二位<br/>     · 效果：利用 U 形分布，让重要信息在注意力高的位置<br/><br/>   方案3: 结构化 Prompt 注入<br/>     · 给每个 chunk 编号 + 相关性标注<br/>     · 要求模型"逐一分析每个参考文档"<br/>     · 强制模型关注所有位置的信息<br/><br/>   方案4: 迭代检索（IFS: Iterative Forward Search）<br/>     · 先注入 Top-3 → LLM 判断是否足够<br/>     · 如果不够 → 再注入下一批 → 直至答案完整<br/>     · 效果：每次只关注少量信息 → 避免注意力稀释<br/><br/>   面试回答：<br/>     "Lost in the Middle 是长上下文 LLM 的固有问题。<br/>      最实用的解决方案不是修复模型，而是优化信息呈现方式：<br/>      精排 + 少量注入 + 位置重排。<br/>      这也解释了为什么 RAG 中 Reranker 的价值不仅是'排序'，<br/>      更是'筛选'——选出真正值得注入的少数高质量片段。"</code>
```

### Q5：RAG 系统的评估体系怎么设计？有哪些关键指标？

```
<code>答案（三层评估体系——体现工程深度）：<br/><br/>第一层：离线评估（检索质量）<br/>  ┌──────────────────────────────────────────────────────────────┐<br/>  │  指标          │  公式                     │  含义           │<br/>  │  ────────────────────────────────────────────────────────── │<br/>  │  Recall@K      │  |正确答案∩TopK|/|正确答案│  召回率         │<br/>  │  Precision@K   │  |正确答案∩TopK|/K        │  精确率         │<br/>  │  MRR           │  1/排名最高的正确答案排名  │  首次命中排名   │<br/>  │  NDCG@K        │  DCG@K / IDCG@K          │  排序质量       │<br/>  │  Hit Rate@K    │  至少一个正确答案在TopK    │  命中率         │<br/>  └──────────────────────────────────────────────────────────────┘<br/><br/>  数据构建方法：<br/>    · 自动：用 LLM 从文档中生成 (Query, Relevant Chunk) 对<br/>    · 半自动：人工标注 Query，自动匹配 Relevant Chunk<br/>    · 全人工：标注 (Query, Relevant Chunk List)<br/><br/>第二层：端到端评估（RAGAS 框架）<br/>  RAGAS (RAG Assessment) 的四个核心指标：<br/><br/>  1. Faithfulness（忠实度）：生成答案是否严格基于检索结果<br/>     · 方法：将答案拆解为原子陈述 → 逐一验证是否可从检索结果推导<br/>     · 公式：Faithfulness = 可验证的陈述数 / 总陈述数<br/><br/>  2. Answer Relevance（答案相关性）：答案是否真正回答了问题<br/>     · 方法：从答案反向生成问题 → 计算与原问题的语义相似度<br/>     · 公式：AR = mean(sim(generated_q, original_q))<br/><br/>  3. Context Precision（上下文精确率）：检索结果中有多少是相关的<br/>     · 方法：对检索结果排序 → 每个位置标注是否相关 → 计算 Precision@K 加权<br/><br/>  4. Context Recall（上下文召回率）：答案所需信息是否都在检索结果中<br/>     · 方法：将标准答案拆解为关键点 → 检查每个关键点是否在检索结果中<br/>     · 公式：CR = 可匹配的关键点数 / 总关键点数<br/><br/>第三层：在线评估（生产环境）<br/>  · 人工评分：用户反馈（👍/👎）+ 评分（1-5星）<br/>  · A/B 测试：新旧 RAG Pipeline 的效果对比<br/>  · 幻觉率：采样 + 人工/LLM 判断是否存在幻觉<br/>  · 引用准确率：生成答案中的引用是否确实来自引用的文档<br/>  · 端到端延迟：P50/P95/P99 的响应时间<br/>  · 检索覆盖率：有多少比例的查询能检索到相关结果<br/><br/>面试加分：<br/>  "RAG 评估最大的挑战不是指标设计，而是标注数据的构建。<br/>   我在实践中发现，用 LLM 自动生成 (Query, Answer, Context) 三元组<br/>   作为评估数据集，比人工标注快 10 倍，但需要仔细做质量过滤。<br/>   最佳实践：自动生成 + 人工抽检验证。"</code>
```

> **面试官**："请描述 RAG 架构从 Naive RAG 到 Modular RAG 到 Agentic RAG 的演进路径，重点解释 Agentic RAG 的设计思想和核心组件。如果让你实现一个 Agentic RAG 系统，你会如何设计？"

**参考答案要点**：

```
<code>第1层：RAG 架构的三个代际<br/>━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━<br/>  Naive RAG（2023初）：<br/>    Query → Embed → Vector Search → Top-K → 拼接 → LLM → 答案<br/>    问题：检索噪声大、无 Query 优化、无质量把控<br/>    效果：EM ~30-40%<br/><br/>  Modular RAG（2023末-2024）：<br/>    Query Rewriting + Multi-route Retrieval + Rerank + Context Compression + Generation<br/>    · 每个环节都是独立的模块，可以独立优化和替换<br/>    · 引入了 Reranker、Query 处理、混合检索等优化<br/>    效果：EM ~55-65%<br/><br/>  Agentic RAG（2025-2026）：<br/>    Agent 决策 + 多工具 + 迭代检索 + 自我反思 + 动态规划<br/>    · LLM 不再只是"生成器"，而是"决策者"<br/>    · 检索不再是"一次性"，而是"迭代式"<br/>    · 知识源不再只是"向量库"，而是"多工具"<br/>    效果：EM ~70-80%<br/><br/>第2层：Agentic RAG 的核心设计思想<br/>━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━<br/>  与传统 RAG 的根本区别：<br/><br/>  传统 RAG：<br/>    检索是"被动的" → 不管检索结果质量如何，都直接喂给 LLM<br/>    LLM 是"被动的" → 只负责根据给定上下文生成答案<br/><br/>  Agentic RAG：<br/>    检索是"主动的" → Agent 判断检索结果是否充分，不充分则迭代检索<br/>    LLM 是"主动的" → Agent 决定是否需要检索、用什么策略检索、检索几次<br/><br/>  核心循环：<br/>    ┌──────────────────────────────────────────────┐<br/>    │  while not answer_sufficient:                 │<br/>    │    1. Observe: 评估新信息是否填补了信息缺口    │<br/>    │    5. Reflect: 反思检索策略是否有效            │<br/>    └──────────────────────────────────────────────┘<br/><br/>第3层：Agentic RAG 的核心组件<br/>━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━<br/>  1. Router Agent（路由代理）<br/>     · 判断查询类型 → 选择合适的检索策略<br/>     · 技术/流程/代码/闲聊 → 不同 Pipeline<br/>     · 简单查询 → 直接检索；复杂查询 → 分解检索<br/><br/>  2. Retriever Toolset（检索工具集）<br/>     · Tool 1: 向量检索（语义匹配）<br/>     · Tool 2: BM25 检索（精确匹配）<br/>     · Tool 3: 知识图谱检索（关联推理）<br/>     · Tool 4: Web 搜索（外部知识）<br/>     · Tool 5: SQL 查询（结构化数据）<br/>     · Tool 6: 代码搜索（符号级）<br/><br/>  3.
```

### 1.1 LLM 应用框架选型决策——从"会用"到"会选"

#### **三大框架深度对比**

在 Agent Harness 项目中，我们系统性地评估了 LangChain、LlamaIndex 和自研框架三种方案，最终选择了**混合架构**：核心编排自研 + 检索链路用 LlamaIndex + 工具集成用 LangChain。

```
<code>框架选型决策树：<br/><br/>需求：快速原型验证？<br/>  ├── 是 → LangChain（开箱即用，链式调用简单）<br/>  └── 否 → 继续<br/><br/>需求：核心是 RAG / 知识检索？<br/>  ├── 是 → LlamaIndex（检索优化极致）<br/>  └── 否 → 继续<br/><br/>需求：高度定制化 + 生产级稳定性？<br/>  ├── 是 → 自研框架（完全控制，但开发成本高）<br/>  └── 折中方案 → 自研核心 + 框架模块混合<br/><br/>我们的选择：<br/>  Agent 核心循环（MainLoop）→ 自研（事件驱动、背压控制）<br/>  RAG 检索链路 → LlamaIndex（Query Rewrite + Rerank + 压缩）<br/>  工具调用生态 → LangChain（预置工具库 + 格式化）</code>

> "Function Calling 的工程化不只是'调个 API'。我们做了四层保障：第一，Pydantic 做参数校验，防止 LLM 生成的参数类型或范围错误；第二，每个工具配置独立的超时和重试策略，指数退避；第三，多个独立工具调用并行执行（asyncio.gather），延迟从串行的 6s 降到并行的 2s；第四，限制最大工具调用轮次（5轮），防止 LLM 陷入无限工具调用循环。"

### 2.1 Function Calling 的六大陷阱与解法

#### **陷阱1：LLM 幻觉工具名或参数**

```
<code># ❌ 问题：LLM 可能"编造"不存在的工具或参数<br/># LLM 输出：调用 "search_web" 工具，参数 {"query": "...", "language": "zh"}<br/># 但实际上注册的工具名是 "web_search"，且没有 "language" 参数<br/><br/># ✅ 解法：工具名白名单 + 参数严格校验<br/>class StrictToolExecutor:<br/>    async def execute(self, tool_call):<br/>        name = tool_call.function.name<br/><br/>        # 校验1：工具名是否存在<br/>        if name not in self.registry.tools:<br/>            return {<br/>                "error": f"工具 '{name}' 不存在。可用工具：{list(self.registry.tools.keys())}",<br/>                "tool": name<br/>            }<br/><br/>        # 校验2：参数 Schema 验证（Pydantic 自动抛出 ValidationError）<br/>        try:<br/>            args = json.loads(tool_call.function.arguments)<br/>            validated = self.registry.input_models[name](**args)<br/>        except json.JSONDecodeError:<br/>            return {"error": "参数 JSON 格式无效", "tool": name}<br/>        except Exception as e:<br/>            return {"error": f"参数校验失败: {e}", "tool": name}<br/><br/>        # 校验3：执行结果格式检查<br/>        result = await self.registry.tools[name](**validated.model_dump())<br/>        if not isinstance(result, (str, dict, list)):<br/>            result = str(result)<br/><br/>        return {"result": result, "tool": name}</code>
```

#### **陷阱2：并行工具调用的依赖冲突**

```
<code>问题场景：<br/>  LLM 同时调用：<br/>    Tool A: get_user_balance(user_id="123")     → 需要读取余额<br/>    Tool B: transfer_money(from="123", to="456") → 需要修改余额<br/>  → 并行执行会导致数据竞争！<br/><br/>解法：工具依赖图（DAG）分析<br/>  1. 标注每个工具的读写资源（如 balance 表）<br/>  2. 构建依赖图：写-写冲突、读-写冲突 → 必须串行<br/>  3. 无冲突的工具才并行执行</code>
```

```
<code>class DependencyAwareExecutor:<br/>    """依赖感知的工具执行器"""<br/><br/>    def __init__(self, registry: ToolRegistry):<br/>        self.registry = registry<br/>        # 每个工具声明的资源依赖<br/>        self.resource_map = {<br/>            "get_user_balance": {"read": ["balance"]},<br/>            "transfer_money":   {"write": ["balance"]},<br/>            "search_products":  {"read": ["product_catalog"]},<br/>            "get_weather":      {"read": []},  # 无依赖，可完全并行<br/>        }<br/><br/>    def _has_conflict(self, tools: list[str]) -&gt; bool:<br/>        """检测工具间是否有资源冲突"""<br/>        write_resources = set()<br/>        read_resources = set()<br/><br/>        for tool_name in tools:<br/>            deps = self.resource_map.get(tool_name, {"read": [], "write": []})<br/>            write_resources.update(deps.get("write", []))<br/>            read_resources.update(deps.get("read", []))<br/><br/>        # 读写冲突 或 写写冲突<br/>        return bool(write_resources &amp; read_resources) or len(write_resources) &gt; 1<br/><br/>    async def execute_group(self, tool_calls: list) -&gt; list[dict]:<br/>        """分组执行：无冲突并行，有冲突串行"""<br/>        if not self._has_conflict([tc.function.name for tc in tool_calls]):<br/>            # 无冲突 → 并行执行<br/>            return await asyncio.gather(*[self.execute(tc) for tc in tool_calls])<br/>        else:<br/>            # 有冲突 → 串行执行<br/>            results = []<br/>            for tc in tool_calls:<br/>                result = await self.execute(tc)<br/>                results.append(result)<br/>            return results</code>
```

#### **三类记忆架构**

```
<code>人类记忆模型 → Agent 记忆映射：<br/><br/>  感觉记忆（Sensory）    → 工作记忆（Working Memory）<br/>    当前对话的上下文窗口      最近 N 轮对话 + System Prompt<br/><br/>  短期记忆（Short-term）  → 短期记忆（Short-term Memory）<br/>    今天发生的事             当前会话的对话历史（完整）<br/>                            ├── 存储介质：内存 / Redis<br/>                            └── 生命周期：会话结束即清除<br/><br/>  长期记忆（Long-term）   → 长期记忆（Long-term Memory）<br/>    多年的知识和经验         跨会话的用户偏好、知识库<br/>                            ├── 存储介质：向量数据库 / 关系数据库<br/>                            └── 生命周期：永久保存<br/><br/>  情景记忆（Episodic）    → 情景记忆（Episodic Memory）<br/>    "上次对话我们讨论了X"     历史会话摘要 + 关键决策点<br/>                            ├── 存储介质：向量数据库（按语义检索）<br/>                            └── 生命周期：按重要性衰减</code>
```

**面试表达**：

> "我们的 Agent 记忆系统分三层：工作记忆是当前对话上下文，短期记忆是当前会话的完整历史，长期记忆是跨会话的用户偏好和知识。关键设计有三点：第一，短期记忆满时，重要的记忆自动升级到长期记忆（向量数据库），不重要的按遗忘曲线衰减淘汰；第二，检索时三层融合，按重要性排序；第三，情景记忆单独存储'上次讨论了什么'这类跨会话引用，用语义检索而非关键词匹配。"

#### **为什么 LLM 应用需要可观测性？**

```
<code>传统软件：输入确定 → 输出确定 → 日志 + 指标 + 链路追踪 够用<br/>LLM 应用：输入非结构化 → 中间过程不透明 → 输出不确定<br/><br/>核心挑战：<br/>  1. LLM 是黑盒：为什么生成了这个回答？不知道<br/>  2. 成本不可预测：一次请求花了多少 Token？多少费用？<br/>  3. 质量难以度量：回答质量好吗？怎么量化？<br/>  4. 链路复杂：RAG → LLM → Tool → LLM → 输出，哪一步出了问题？<br/><br/>可观测性三支柱（ adapted for LLM）：<br/>  Logging    → 每次请求的完整输入输出、Token 用量、延迟<br/>  Metrics    → 成功率、平均延迟、Token 消耗趋势、工具调用频率<br/>  Tracing    → 完整的调用链路追踪（RAG检索 → LLM推理 → 工具调用 → 输出）</code>
```

### Q1: LangChain 的核心抽象有哪些？它为什么被批评"过度抽象"？

**答**：

<code>class SmartScheduler:<br/>    """智能调度器：依赖感知 + 并行优化"""<br/><br/>    async def schedule(self, tool_calls: list[ToolCall]) -&gt; list[ToolResult]:<br/>        # 1. 分析依赖关系<br/>        groups = self._group_by_dependency(tool_calls)<br/><br/>        results = []<br/>        for group in groups:<br/>            if len(group) == 1:<br/>                # 单个工具 → 直接执行<br/>                result = await self._execute_with_retry(group[0])<br/>                results.append(result)<br/>            else:<br/>                # 多个无冲突工具 → 并行执行<br/>                group_results = await asyncio.gather(<br/>                    *[self._execute_with_retry(tc) for tc in group],<br/>                    return_exceptions=True<br/>                )<br/>                results.extend(<br/>                    ToolResult(error=str(r)) if isinstance(r, Exception) else r<br/>                    for r in group_results<br/>                )<br/><br/>        return results<br/><br/>    def _group_by_dependency(self, tool_calls):<br/>        """将工具调用分组：无冲突的归为一组（可并行）"""<br/>        groups = []<br/>        current_group = []<br/>        current_write_resources = set()<br/><br/>        for tc in tool_calls:<br/>            resources = self.resource_map.get(tc.name, {"read": [], "write": []})<br/>            write_set = set(resources.get("write", []))<br/><br/>            if write_set &amp; current_write_resources:<br/>                # 冲突 → 当前组结束，新开一组<br/>                if current_group:<br/>                    groups.append(current_group)<br/>                current_group = [tc]<br/>                current_write_resources = write_set<br/>            else:<br/>                current_group.append(tc)<br/>                current_write_resources.update(write_set)<br/><br/>        if current_group:<br/>            groups.append(current_group)<br/><br/>        return groups</code>
```

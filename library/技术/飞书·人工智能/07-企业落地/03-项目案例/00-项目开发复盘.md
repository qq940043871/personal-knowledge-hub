# 项目开发复盘

## 一、整体项目背景

围绕**企业级AI中台+RAG知识库+多智能体体系**完整落地，以业务中台开发视角，完成文档解析改造、知识库治理、Binlog数据同步、多智能体调度架构迭代、智能客服落地、混合架构选型全链路建设，同时深入研读Dify、Chatbot/Harness引擎源码，形成完整的AI业务落地与架构优化经验。

## 二、文档解析与RAG底座建设（核心深耕1）

1. 初期依赖MinerU解析PDF、Word文档，该工具对整体版式、区块、图文、表格结构识别精准；
2. 原生存在硬缺陷：**公式识别不准、图片丢失/错位、复杂合并表格解析错乱、内容提取精度不足**；
3. 深入阅读MinerU源码，理解其版面分析、区块检测、排版还原底层逻辑，进行二次定制改造；
4. 改造方案：保留原生结构识别能力，拦截区块数据，单独截取公式/图片/表格局部区域，**对接第三方云大模型做局部增强识别**；
5. 输出标准化Markdown格式，全程仅传输局部截图、不传输完整涉密文档，**规避数据泄露风险**，保障文档解析准确性；
6. 摒弃Dify原生粗暴固定长度自动切片，基于MinerU产出的MD文档，**自定义标题+段落语义化切片规则**，解决语义割裂、召回不准问题；
7. 自主开发自动化工具，调用Dify开放API，实现知识库创建、切片批量上传、向量化入库全自动化，替代人工手动运维。

## 三、业务数据实时同步体系建设（核心深耕2）

1. 底层基于阿里开源CDC插件实现MySQL Binlog基础采集能力；
2. 原生插件仅能裸消费、无脑监听，无业务管控、无表规则治理、无数据路由能力；
3. 自研**Binlog质检&统一管理系统**，自主定义整套同步规范：
    - 库表白名单/黑名单精细化管控；
    - 按表绑定业务语义，配置差异化清洗、过滤、分发策略；
    - 增加数据质检、字段脱敏、无效变更事件过滤、变更前后比对；
4. 统一管控业务数据流向，结构化业务数据定向推送至AI中台知识库，实现业务系统**零代码侵入**；
5. 完整闭环：业务DB变更→Binlog管控系统→标准化清洗→AI中台→知识库&向量库实时更新，保障结构化数据实时性与准确性。

## 四、多智能体调度架构完整演进（核心架构主线）

1. **第一版方案**
全流程基于Dify工作流快速落地，在工作流内部完成意图识别、条件分支编排，路由分发不同垂直智能体，优势是上线快、成本低、适配固化流程。
2. **第一版核心痛点**
过度依赖Dify上层能力，底层引擎调度原理认知不足，深度优化、定制化改造困难；
智能体相互隔离、无法通信、无共享上下文，不支持循环、多轮反问、复杂协作，仅能固定顺序串行执行，无法落地智能客服类复杂场景。
3. **架构第一次优化：意图识别上层抽离**
将内嵌在Dify工作流中的意图识别能力，抽离上浮为AI中台独立前置层；
采用**规则语义+大模型**双层识别，简单意图走轻量化规则引擎、跳过LLM与工作流，复杂意图再进入Dify流程；
提升系统并发、降低算力消耗，解除核心路由逻辑对Dify的强耦合。
4. **底层源码研究**
主动研读Dify工作流引擎源码，理解可视化画布编排、流程JSON序列化、拓扑节点调度、分支执行的底层实现；
同时研究Harness类Chatbot引擎机制，掌握两种不同智能体编排架构的优劣。
5. **Chatbot+Harness引擎落地智能客服**
针对Dify无法解决的多轮会话、连续问答场景，智能客服采用Chatbot方案；
核心设计：为每一家企业客户、每一个用户会话，创建独立工作空间与隔离文件夹，会话记忆统一持久化在工作空间memory文件中，实现多智能体共享记忆、上下文互通；
增加会话内容压缩能力，控制上下文长度与Token开销；
设计上做**同一会话串行执行**，同一时间仅单个引擎操作记忆文件，避免多智能体并发读写导致记忆错乱、丢失。
6. **方案局限性认知**
该文件型工作空间架构，仅适配**企业客户量少、业务体量小、低并发**场景；
天然存在底层瓶颈：本地文件IO性能差、海量小文件运维压力大、单机部署无法分布式横向扩容，完全不适合多用户高并发C端业务；
同时自由式记忆编排会导致**大模型幻觉不可控**，普通客服场景可用，严谨企业业务无法落地。
7. **最终混合架构定型**
- 固化线性流程、强管控、低灵活需求场景：继续使用Dify工作流，快速迭代；
- 多轮对话、智能客服、多智能体联动、复杂业务场景：采用Chatbot工作空间方案；
- 高严谨、高定制、复杂循环协作、企业核心业务：自研中台适配器+定制智能体；
三层架构各司其职，平衡交付效率、业务复杂度、企业风险管控。

## 五、高并发自研智能体架构设计与技术方案

1. 明确现有文件记忆架构的核心瓶颈：磁盘IO缓慢、单机绑定、无法扩容、资源管控弱；
2. 技术选型升级：
    - 缓存：Redis Cluster（热点会话、上下文、分布式锁，内存级高并发读写）；
    - 持久化：MySQL/PostgreSQL（会话全量数据落地，记忆永久不丢失）；
    - 调度：Redisson分布式锁、自研Agent编排引擎；
    - 中间件：异步任务框架、向量数据库、统一LLM适配层；
3. 核心设计方案：
    - 存储分层：实时交互走Redis高性能缓存，数据异步落库兜底，兼顾性能与数据安全；
    - 读写隔离：不同会话完全并行，同一会话加分布式锁串行操作，杜绝记忆覆盖错乱；
    - 中心化上下文：所有自研智能体共享统一会话上下文，支持多Agent通信、循环、嵌套、多轮复杂业务；
    - 记忆治理：异步AI摘要压缩、冷数据归档、过期清理，控制Token大小、压制大模型幻觉；
    - 无状态化改造：引擎服务集群部署，支持横向扩容，彻底摆脱单机限制；
4. 附带完整核心伪代码：会话双层存储、分布式锁控制、多智能体上下文共享、异步记忆压缩。

## 六、关键技术认知对比

1. Redis VS 本地文件IO：Redis纯内存操作，微秒级响应，比小文件频繁读写快数十至上百倍，是高并发会话的核心基础；
2. 两种智能体引擎差异：
    - Dify：强约束、流程固化、输出可控、适合标准化业务，多智能体隔离无联动；
    - Harness/Chatbot：自由编排、共享记忆、多轮联动强，但幻觉不可控、架构轻量化、无法承载高并发；
3. 企业AI落地核心原则：不盲目统一技术栈，按业务体量、场景复杂度、风险等级分层选型，不过度设计、务实落地。

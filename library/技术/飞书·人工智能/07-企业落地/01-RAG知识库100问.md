## 一、基础认知（10问）
### 1. RAG的核心逻辑是什么？与传统大模型微调的本质区别是什么？
+ **核心逻辑**：通过“检索+生成”双阶段协同，先从企业知识库中检索与用户查询相关的精准信息（上下文），再将检索结果与查询一起输入大模型，让大模型基于给定上下文生成回答，本质是“大模型+外部知识库”的协同增强。
+ **与微调的区别**：

| 维度 | RAG | 传统微调（Fine-tuning） |
| --- | --- | --- |
| 知识更新 | 仅需更新知识库，实时生效 | 需重新训练模型，周期长（天级） |
| 数据要求 | 无需大量标注数据，支持非结构化文档 | 需高质量标注样本（万级以上） |
| 成本 | 低（无需大规模算力训练） | 高（训练+推理算力消耗大） |
| 知识边界 | 仅限知识库内容，可控性强 | 融合模型原有知识，易产生幻觉 |
| 适用场景 | 企业文档问答、合规查询、实时知识更新 | 特定任务优化（如情感分析、命名实体识别） |

### 2. RAG适合哪些场景？哪些场景不适合用RAG？
+ **适合场景**：
    1. 企业知识库问答（如文档查询、FAQ、政策解读）；
    2. 实时知识更新场景（如行业动态、监管政策变化）；
    3. 需引用来源的场景（如法律、金融、医疗，需标注答案出处）；
    4. 数据隐私敏感、无法对外联网的私有化部署场景；
    5. 低标注成本、快速上线的场景（如内部协同工具）。
+ **不适合场景**：
    1. 无外部知识库的通用问答（直接用大模型更高效）；
    2. 需复杂逻辑推理的任务（如数学计算、代码调试，需结合Agent）；
    3. 知识库质量极低（无结构化信息、错误率高，RAG无法“无中生有”）；
    4. 需极致响应速度（如毫秒级交互，RAG检索环节会增加延迟）。

### 3. RAG的“检索”和“生成”是如何协同工作的？中间关键链路是什么？
+ **协同流程**：
    1. 用户输入查询（如“2024年公司差旅报销标准”）；
    2. 检索阶段：查询解析→向量嵌入→知识库检索→相关性排序→筛选Top N相关文档片段；
    3. 生成阶段：将“用户查询+Top N检索结果+Prompt指令”拼接为输入，传入大模型；
    4. 大模型基于给定上下文生成回答，同时标注来源（可选）。
+ **关键链路**：查询理解的准确性、检索结果的召回率/精准率、Prompt对大模型的约束能力（避免偏离上下文）。

### 4. 什么是“知识增强”？RAG如何解决大模型“幻觉”问题？
+ **知识增强**：通过引入外部结构化/非结构化知识，弥补大模型自身知识的局限性（如训练数据滞后、行业知识缺失），让回答更精准、可控。
+ **解决幻觉的核心逻辑**：
    1. 限制大模型仅基于“检索到的上下文”回答，禁止调用模型内部未验证的知识；
    2. 检索结果来自企业权威知识库，确保信息真实性；
    3. 对未检索到相关信息的查询，强制回复“暂无相关信息”，避免编造答案。

### 5. RAG的技术演进路径是什么？从基础RAG到高级RAG（如Hybrid RAG、Agent-RAG）有哪些升级？
+ **演进路径**：基础RAG → Hybrid RAG → Agent-RAG → 多模态RAG；
+ **各阶段升级点**：
    1. 基础RAG：仅支持单向量检索，适合简单文档问答；
    2. Hybrid RAG：融合“向量检索（语义匹配）+关键词检索（BM25，字面匹配）”，提升召回率（尤其解决同义词、歧义问题）；
    3. Agent-RAG：加入Agent的“规划-工具调用-记忆”能力，支持复杂任务（如多轮追问、跨知识库检索、流程自动化）；
    4. 多模态RAG：支持图片、音频、视频等多模态知识库，如检索图片中的文字信息、视频中的关键帧内容。

### 6. RAG的核心指标有哪些？（准确率、召回率、响应速度等）
+ **检索阶段指标**：
    - 召回率（Recall@k）：检索到的相关文档占所有相关文档的比例（k为返回结果数，如Recall@5）；
    - 精准率（Precision@k）：检索到的结果中相关文档的比例；
    - MAP（平均准确率）：衡量检索结果的整体排序质量；
+ **生成阶段指标**：
    - 幻觉率：生成内容与检索上下文不一致的比例（人工标注或通过事实核查工具检测）；
    - 答案准确率：回答与知识库事实一致的比例；
    - 引用准确率：标注的来源文档与回答内容的匹配度；
+ **工程指标**：
    - 响应时间（P95/P99）：从查询输入到返回回答的耗时（企业级通常要求P95<3秒）；
    - 吞吐量：单位时间内支持的查询量（QPS）；
+ **业务指标**：
    - 用户满意度（NPS/评分）；
    - 人工转接率（如客服场景，RAG无法解答需转人工的比例）。

### 7. 企业级RAG与开源RAG的差异点在哪里？（数据安全、可扩展性、定制化）
| 维度 | 企业级RAG | 开源RAG（如LangChain/LlamaIndex） |
| --- | --- | --- |
| 数据安全 | 支持私有化部署、权限管控、数据加密 | 需自行配置安全措施，默认无企业级权限体系 |
| 可扩展性 | 支持千万级文档、高并发（QPS>1000） | 原生支持中小规模，大规模需二次开发 |
| 定制化 | 可对接ERP/CRM等业务系统，支持定制化检索/生成策略 | 通用化框架，需大量开发适配企业场景 |
| 运维支持 | 有专业团队维护，提供监控、告警、升级服务 | 需自建运维体系，依赖社区支持 |
| 合规性 | 满足等保三级、GDPR等合规要求 | 需自行补充合规改造（如日志留存、审计） |

### 8. RAG的“上下文窗口限制”如何影响效果？如何突破？
+ **影响**：大模型的上下文窗口（如GPT-4为128k tokens）限制了单次可输入的检索结果长度，若检索到的相关文档过多（如10篇长文档），会导致部分关键信息被截断，影响生成效果。
+ **突破方案**：
    1. 分块优化：将长文档拆分为更小的Chunk（如300-500字），确保Top N Chunk总长度不超过窗口限制；
    2. 信息筛选：对检索结果进行二次排序，优先保留与查询最相关的核心片段；
    3. 分层检索：先粗检索（返回100条），再细检索（筛选Top 5-10条）；
    4. 采用大窗口模型：如Claude 3 Opus（200k tokens）、通义千问X（128k tokens）。

### 9. 什么是“检索增强飞轮”？如何通过数据闭环持续优化RAG？
+ **检索增强飞轮**：通过“用户反馈→数据优化→模型/检索调优→效果提升→更多反馈”的循环，持续提升RAG效果。
+ **闭环流程**：
    1. 收集反馈：用户对回答“点赞/点踩”、Bad Case上报、人工修正答案；
    2. 数据优化：将Bad Case对应的文档补充到知识库、修正分块/元数据、标注错误检索结果；
    3. 调优动作：更新向量索引、调整检索算法（如Hybrid权重）、优化Prompt指令、微调嵌入模型；
    4. 效果验证：通过A/B测试对比调优前后的准确率、召回率，确认效果提升。

### 10. RAG与知识图谱的关系是什么？何时需要结合知识图谱使用？
+ **关系**：知识图谱是RAG的“增强工具”，而非替代关系，二者可互补：
    - RAG擅长处理非结构化文档（如PDF、Word）的自由文本检索；
    - 知识图谱擅长处理结构化关系（如“员工-部门-岗位”“产品-价格-库存”）的精准查询。
+ **结合场景**：
    1. 需复杂关系推理的查询（如“查询2023年加入公司、隶属于研发部门的员工所负责的产品”）；
    2. 需结构化输出的场景（如按“产品名称-价格-库存”格式返回结果）；
    3. 知识库中存在大量实体关联信息（如客户、产品、订单数据）。
+ **结合方式**：先通过知识图谱检索实体关系，再将结果作为上下文输入RAG，生成自然语言回答。

## 二、数据准备（10问）
### 11. 企业知识库RAG的数据来源有哪些？（文档、数据库、API、历史对话等）
+ **核心数据来源**：
    1. 非结构化文档：PDF（合同、政策、手册）、Word（报告、方案）、PPT（培训材料）、TXT（日志、笔记）；
    2. 结构化数据：MySQL/Oracle数据库表（客户信息、订单数据）、Excel/CSV（报表、清单）；
    3. 半结构化数据：JSON/XML（接口返回数据）、HTML（企业官网/内部系统页面）、Markdown（技术文档）；
    4. 其他来源：历史对话记录（客服聊天、会议纪要）、API接口（实时数据如天气、股票行情）、音频/视频转写文本（会议录音、培训视频）。

### 12. 如何梳理知识库的“数据资产清单”？优先级如何排序？
+ **梳理流程**：
    1. 调研业务场景：明确RAG的核心用途（如客服问答、研发文档查询）；
    2. 盘点数据分布：确认数据存储位置（如SharePoint、阿里云OSS、本地服务器）、格式、大小、更新频率；
    3. 标注关键属性：为每条数据记录“数据类型、业务归属、重要性、合规等级、更新周期”。
+ **优先级排序**：
    1. 高频查询数据（如FAQ、核心业务流程文档）；
    2. 高价值数据（如合同模板、监管政策、技术手册）；
    3. 实时性要求高的数据（如库存、价格、行业动态）；
    4. 合规风险低的数据（优先处理非敏感数据，敏感数据需脱敏后接入）。

### 13. 非结构化数据（PDF/Word/PPT）如何预处理？（解析、分句、去重、清洗）
+ **预处理流程**：
    1. 解析（Extract）：用工具提取文本内容，避免格式干扰：
        - PDF：Unstructured、PyPDF2（支持扫描件OCR，需搭配Tesseract）；
        - Word：python-docx；
        - PPT：python-pptx（提取文字+备注）。
    2. 清洗（Clean）：去除无关信息（页眉页脚、水印、广告、空白行）、特殊字符（表情、符号）、冗余内容（重复段落）。
    3. 分块（Chunking）：按语义拆分文本（如按章节、段落），避免过长/过短（推荐300-500字/块），保留块间上下文关联（如给每个块添加“父章节ID”）。
    4. 去重（Deduplicate）：通过文本相似度算法（如SimHash）去除重复块，阈值设为0.9（相似度≥90%判定为重复）。
    5. 元数据补充：为每个块添加元数据（文档ID、标题、章节、更新时间、上传人、权限标签）。

### 14. 结构化数据（Excel/数据库表）如何转化为RAG可检索的格式？
+ **转化方案**：
    1. 行级转化：将每一行数据转化为“自然语言描述+结构化标签”的文本块，例如：
        - 原数据（Excel）：产品名称=手机A，价格=5999元，库存=100台；
        - 转化后：“产品名称：手机A，售价：5999元，当前库存：100台（更新时间：2024-05-20）”。
    2. 表结构描述：补充表结构说明，帮助RAG理解数据关联，例如：“该表为产品库存表，包含产品名称、价格、库存、更新时间字段，用于查询产品实时库存与价格”。
    3. 向量嵌入：将转化后的文本块与表结构描述一起生成向量，存入向量数据库。
+ **工具推荐**：LangChain的SQLDatabaseLoader、PandasLoader，支持直接读取数据库/Excel并转化为Document对象。

### 15. 半结构化数据（JSON/XML/HTML）如何提取关键信息并构建向量？
+ **提取流程**：
    1. 解析结构：用JSONPath（JSON）、XPath（XML/HTML）提取核心字段（如JSON中的“title”“content”，HTML中的“div.class=content”）；
    2. 字段融合：将分散的关键字段拼接为连贯的文本块，例如：
        - 原JSON：{"news_title":"AI落地提速","publish_time":"2024-05-20","content":"企业级AI应用渗透率突破30%"}；
        - 融合后：“新闻标题：AI落地提速，发布时间：2024-05-20，核心内容：企业级AI应用渗透率突破30%”。
    3. 过滤冗余：去除无关字段（如状态码、格式标记），保留用户关心的信息。
    4. 向量构建：对融合后的文本块生成向量，元数据保留原字段信息（便于后续筛选）。

### 16. 如何处理知识库中的“重复内容”和“冲突信息”？
+ **重复内容处理**：
    1. 预处理去重：用SimHash或MinHash算法检测重复文本，阈值设为0.85-0.95（根据业务调整）；
    2. 索引去重：向量数据库中设置“文本唯一键”，避免重复入库；
    3. 检索去重：检索结果返回前，对相似度≥90%的块进行合并，保留最新版本。
+ **冲突信息处理**：
    1. 优先级标注：为知识库文档设置优先级（如“最新政策>旧政策”“官方文档>非官方文档”）；
    2. 时间戳筛选：检索时优先返回更新时间较新的内容；
    3. 冲突提示：若无法判定优先级，生成回答时标注“存在冲突信息”，并列出所有相关来源，供用户参考。

### 17. 文档分块（Chunking）的核心原则是什么？按字数、语义、章节分块的优劣对比？
+ **核心原则**：
    1. 语义完整性：每个块保留完整的语义单元（如一个观点、一个步骤）；
    2. 上下文关联性：块间保留关联信息（如通过元数据关联父章节）；
    3. 适配窗口限制：块大小不超过大模型上下文窗口的1/5（如窗口10k tokens，块大小≤2k tokens）；
    4. 适配检索精度：避免块过大（导致无关信息过多）或过小（导致语义断裂）。
+ **分块方式对比**：

| 分块方式 | 优势 | 劣势 | 适用场景 |
| --- | --- | --- | --- |
| 按字数 | 简单易实现、效率高 | 可能拆分完整语义 | 无明显结构的纯文本文档 |
| 按语义 | 保留完整语义、检索精准 | 需NLP工具（如spaCy），效率低 | 有逻辑结构的文档（报告、手册） |
| 按章节 | 符合人类阅读习惯、关联强 | 章节过长时需二次分块 | 书籍、PPT、结构化报告 |

### 18. 分块大小如何选择？（短句100-300字、长句500-1000字）不同场景适配方案？
+ **核心原则**：分块大小=“检索精准度”与“上下文利用率”的平衡，推荐按“文档类型+查询场景”选择：

| 场景/文档类型 | 分块大小（中文字符） | 理由 |
| --- | --- | --- |
| FAQ、短问答 | 100-300字 | 核心信息集中，小分块检索更精准 |
| 技术手册、报告 | 300-500字 | 保留完整语义单元（如一个步骤） |
| 长文档（书籍、合同） | 500-800字 | 避免分块过细导致语义断裂 |
| 多轮对话、复杂查询 | 200-400字 | 便于大模型整合多个块的信息 |
| 嵌入模型能力弱（如BERT） | ≤300字 | 模型对长文本嵌入效果差 |
| 大窗口模型（如GPT-4） | 500-1000字 | 充分利用窗口，减少检索次数 |

### 19. 如何给分块添加“元数据”？（文档ID、章节、更新时间、权限标签等）
+ **核心元数据字段（必选）**：
    1. 基础标识：chunk_id（分块唯一ID）、doc_id（所属文档ID）、doc_title（文档标题）；
    2. 位置信息：chapter（章节）、page（页码）、paragraph（段落号）；
    3. 时间信息：create_time（创建时间）、update_time（更新时间）；
    4. 业务信息：business_type（业务类型，如“差旅政策”“产品手册”）、source（数据来源，如“HR系统”“SharePoint”）；
    5. 权限信息：role（可见角色，如“全员”“研发部”“管理员”）、sensitive_level（敏感等级，如“公开”“内部”“机密”）。
+ **添加方式**：
    - 代码层面：用LangChain的Document对象，将元数据存入metadata字典；
    - 工具层面：通过Unstructured、Apache Tika等解析工具，自动提取文档的标题、页码等元数据，再补充自定义字段。

### 20. 知识库数据更新后，如何实现RAG实时同步？（增量索引、全量重建的取舍）
+ **同步方案对比**：

| 方案 | 实现方式 | 优势 | 劣势 | 适用场景 |
| --- | --- | --- | --- | --- |
| 增量索引 | 仅对新增/修改的数据重新分块、嵌入、更新向量索引 | 速度快、资源消耗低 | 需维护数据变更日志 | 高频小批量更新（如每日新增100篇文档） |
| 全量重建 | 定期删除旧索引，对所有数据重新构建索引 | 实现简单、索引质量高 | 速度慢、资源消耗大 | 低频大批量更新（如每月更新一次政策文档） |
| 混合方案 | 增量索引为主，每周/每月全量重建一次 | 平衡速度与质量 | 需设计增量与全量协同逻辑 | 大多数企业级场景 |

+ **实战建议**：
    1. 建立数据变更监听机制（如数据库binlog、文件服务器webhook），捕获新增/修改/删除操作；
    2. 增量更新时，先删除旧版本分块的索引，再插入新版本；
    3. 全量重建选择低峰期（如凌晨）执行，避免影响业务。

## 三、检索设计（10问）
### 21. 基础RAG的检索流程是什么？（查询解析→向量检索→相关性排序→上下文构造）
+ **完整流程**：
    1. 查询解析：对用户查询进行预处理，包括分词、同义词替换、歧义消解（如“苹果”→“苹果手机”或“苹果公司”，根据业务场景判定）、关键词提取；
    2. 向量嵌入：将解析后的查询转化为向量（与文档分块的嵌入模型一致）；
    3. 向量检索：在向量数据库中检索与查询向量相似度最高的Top N（如Top 10）分块；
    4. 相关性排序：结合向量相似度分数与元数据（如更新时间、业务类型）二次排序，筛选Top 5-8个最相关分块；
    5. 上下文构造：将排序后的分块按相关性降序拼接，补充元数据（如来源文档、章节），形成最终输入大模型的上下文。

### 22. 什么是向量检索？常用的向量相似度算法有哪些？（余弦相似度、欧氏距离等）
+ **向量检索**：将文本、图片等数据转化为高维向量后，通过计算向量间的相似度，快速找到与查询向量最相似的目标向量，核心是“语义匹配”而非字面匹配。
+ **常用相似度算法对比**：

| 算法 | 核心逻辑 | 优势 | 劣势 | 适用场景 |
| --- | --- | --- | --- | --- |
| 余弦相似度（Cosine Similarity） | 计算向量夹角的余弦值（-1~1，越接近1越相似） | 不受向量长度影响，适合文本语义匹配 | 对高维向量计算效率一般 | 大多数RAG场景（文本问答） |
| 欧氏距离（Euclidean Distance） | 计算向量空间中两点的直线距离（值越小越相似） | 计算简单、直观 | 受向量长度和维度影响大 | 低维向量场景 |
| 曼哈顿距离（Manhattan Distance） | 计算向量各维度差值的绝对值之和 | 对异常值不敏感 | 高维场景效率低 | 结构化数据检索 |
| 皮尔逊相关系数（Pearson Correlation） | 衡量向量间的线性相关程度（-1~1） | 适合数据分布均匀的场景 | 对非线性关系不敏感 | 统计类数据检索 |

+ **实战建议**：文本类RAG优先选择“余弦相似度”，向量数据库（如Milvus、Pinecone）默认支持且效果最优。

### 23. 什么是Hybrid RAG？（向量检索+关键词检索）如何配置权重提升召回率？
+ **Hybrid RAG**：融合“向量检索（语义匹配）”与“关键词检索（字面匹配，如BM25）”的检索方案，解决单一检索的局限性（如向量检索对同义词、生僻词不敏感，关键词检索对语义关联弱）。
+ **权重配置方法**：
    1. 基础权重：向量检索权重（α）=0.6-0.7，关键词检索权重（β）=0.3-0.4（α+β=1）；
    2. 动态调整：根据查询类型自适应调整权重：
        - 长查询（≥10字）：α=0.7，β=0.3（长查询语义更明确，依赖向量检索）；
        - 短查询（≤5字）：α=0.5，β=0.5（短查询关键词更关键，依赖关键词检索）；
        - 包含生僻词/专业术语的查询：β=0.6，α=0.4（关键词检索更精准）。
+ **实现工具**：LangChain的HybridSearch、Weaviate的Hybrid RAG、Milvus的BM25+向量融合检索。

### 24. 如何进行“查询改写”？（同义词替换、歧义消解、多轮追问补全）
+ **查询改写的核心目标**：让查询更精准，提升检索召回率，常见方式：
    1. 同义词替换：基于行业词典或WordNet，将查询中的词替换为同义词，例如“报销”→“报账”“核销”；
    2. 歧义消解：结合业务场景消除歧义，例如“华为P60价格”→“华为P60手机的官方售价”（避免检索到其他“P60”产品）；
    3. 多轮追问补全：根据对话历史补充缺失信息，例如：
        - 用户1：“差旅报销标准？”
        - 用户2：“一线城市？”
        - 改写后：“2024年公司差旅报销标准中，一线城市的住宿、交通、餐饮补贴标准是什么？”
    4. 关键词扩充：提取查询核心关键词，补充相关术语，例如“劳动合同到期”→“劳动合同到期续签流程、所需材料、注意事项”。
+ **工具推荐**：开源（spaCy、NLTK）、闭源（GPT-4 Turbo、通义千问的查询改写API）。

### 25. 什么是“稠密检索”和“稀疏检索”？各自的适用场景是什么？
+ **定义与区别**：

| 类型 | 核心逻辑 | 代表算法/工具 | 优势 | 劣势 |
| --- | --- | --- | --- | --- |
| 稠密检索（Dense Retrieval） | 将查询和文档转化为稠密向量（高维，如768维），通过向量相似度匹配 | 向量检索（Cosine）、Sentence-BERT | 语义匹配能力强，支持模糊查询 | 计算成本高，对短查询效果一般 |
| 稀疏检索（Sparse Retrieval） | 基于词频-逆文档频率（TF-IDF），生成稀疏向量（维度=词汇表大小，大部分为0），通过字面匹配 | BM25、TF-IDF | 计算速度快，对关键词/短查询精准 | 不支持语义关联，对同义词不敏感 |

+ **适用场景**：
    - 稠密检索：长查询、模糊查询、语义关联查询（如“如何优化RAG的检索准确率”）；
    - 稀疏检索：短查询、关键词查询、精准匹配查询（如“2024年差旅报销标准”）。

### 26. 如何处理“长尾查询”？（低频次、生僻词、多义词查询）
+ **长尾查询特征**：查询频次低、包含生僻词/专业术语、多义词多，单一检索方式召回率低。
+ **解决方案**：
    1. 术语库扩充：收集行业生僻词、专业术语，建立专属词典，用于查询改写和分块嵌入；
    2. 多义词消歧：结合知识库元数据（如业务类型），限定检索范围，例如“风控”在金融场景下检索“信贷风控”相关文档，在制造场景下检索“生产风控”相关文档；
    3. 检索扩召回：降低向量检索的相似度阈值（如从0.7降至0.6），同时启用Hybrid RAG，提升长尾词的字面匹配概率；
    4. 反馈优化：将长尾查询的Bad Case纳入“检索增强飞轮”，补充相关文档或调整检索策略。

### 27. 多轮对话场景下，如何利用“对话历史”优化检索效果？
+ **核心逻辑**：将历史对话信息融入当前查询，让检索更贴合用户意图，避免上下文丢失。
+ **实现方案**：
    1. 历史信息压缩：将前N轮对话（如前3轮）压缩为“关键信息摘要”（如“用户询问一线城市差旅住宿标准，已告知300元/晚，用户追问是否包含早餐”），避免输入过长；
    2. 查询拼接：将当前查询与历史摘要拼接，形成完整查询，例如：“结合之前提到的一线城市差旅住宿标准300元/晚，该标准是否包含早餐？”；
    3. 历史向量复用：将历史对话的向量与当前查询向量融合（如加权求和），作为检索向量；
    4. 上下文过滤：根据历史对话中的业务类型、实体（如“华为P60”“差旅政策”），过滤检索结果的元数据，优先返回相关文档。

### 28. 如何实现“个性化检索”？（基于用户角色、权限、历史行为过滤结果）
+ **个性化维度与实现方式**：
    1. 基于用户角色：在检索时过滤分块的“role”元数据，例如“研发人员”仅能检索研发相关文档，“HR”仅能检索人事政策文档；
    2. 基于权限等级：根据用户敏感等级（如“普通员工”“管理员”），过滤分块的“sensitive_level”元数据，避免机密信息泄露；
    3. 基于历史行为：分析用户历史查询记录、点击/点赞记录，提取用户关注的业务领域（如“用户频繁查询产品A相关信息”），在检索时提升该领域文档的排序权重；
    4. 基于自定义偏好：允许用户设置检索偏好（如“优先显示最新文档”“仅显示PDF文档”），检索时过滤元数据。

### 29. 检索结果的“相关性排序”逻辑是什么？如何调优排序权重？
+ **排序逻辑（从高到低优先级）**：
    1. 核心因子：检索相似度分数（向量相似度+关键词相似度）；
    2. 业务因子：文档更新时间（最新优先）、文档优先级（官方文档>非官方文档）、业务匹配度（与查询业务类型一致）；
    3. 个性化因子：用户历史行为偏好（用户关注领域优先）、权限匹配度（高权限文档仅对授权用户优先）。
+ **调优方法**：
    1. 权重赋值：为每个因子设置权重（如相似度0.6、更新时间0.2、业务匹配度0.2），按加权求和结果排序；
    2. 阈值过滤：设置最低相似度阈值（如0.5），低于阈值的结果直接过滤；
    3. A/B测试：对比不同权重组合的检索效果（如相似度0.7+更新时间0.3 vs 相似度0.6+更新时间0.2+业务匹配度0.2），选择最优组合；
    4. 人工反馈：收集用户对检索结果的“点赞/点踩”，调整对应因子权重（如用户频繁点踩“旧文档”，则提升更新时间的权重）。

### 30. 什么是“检索熔断”？当检索结果为空/质量差时如何处理？
+ **检索熔断**：当检索结果满足“为空”“相似度低于阈值”“相关分块数量不足”等条件时，触发预设的降级策略，避免生成低质量回答。
+ **熔断触发条件**：
    1. 检索结果数量=0；
    2. Top 1结果相似度<0.4（阈值可调整）；
    3. 相关分块数量（相似度≥0.5）<2。
+ **降级处理方案**：
    1. 友好提示：回复“未查询到相关信息，请尝试调整关键词或联系人工咨询”；
    2. 检索扩召回：自动降低相似度阈值、启用Hybrid RAG、补充同义词查询，重新检索一次；
    3. 引导优化：提示用户“是否想查询XX相关内容？”（基于查询关键词推荐可能的意图）；
    4. 人工转接：支持用户一键转人工，同时将该查询记录为Bad Case，用于后续知识库优化。

## 四、生成优化（10问）
### 31. 如何构造“优质提示词（Prompt）”让大模型基于检索结果生成回答？
+ **优质Prompt的核心原则**：明确指令、限定边界、格式规范，推荐模板：

```plain
任务：基于以下提供的上下文信息，回答用户的查询。
规则：
1. 仅使用上下文提供的信息，不得编造未提及的内容；
2. 若上下文无相关信息，直接回复“未查询到相关信息，请尝试调整关键词”；
3. 回答需简洁明了，分点说明（若有多条信息）；
4. 结尾必须标注答案来源（格式：来源：[文档标题]-[章节/页码]）。
上下文：
{检索到的分块内容，按相关性降序排列}
用户查询：{用户输入的查询}
回答：
```

+ **优化技巧**：
    1. 加入业务术语说明：若知识库包含专业术语，在Prompt中补充“需使用企业常用术语（如‘核销’即‘报销’）”；
    2. 限定回答长度：如“回答控制在300字以内”；
    3. 结构化要求：如“按‘核心结论+具体说明’格式回答”。

### 32. 检索到的上下文过多时，如何筛选核心信息传入大模型？
+ **筛选策略**：
    1. 相关性筛选：保留Top 5-8个相似度最高的分块（过多会导致信息冗余，过少可能遗漏关键信息）；
    2. 信息去重：合并内容重复度≥80%的分块，保留最新版本；
    3. 关键词聚焦：提取用户查询的核心关键词（如“差旅报销”“一线城市”），优先保留包含这些关键词的分块；
    4. 长度截断：若单个分块过长（如超过1000字），提取与查询相关的段落（用关键词匹配），而非完整分块；
    5. 元数据过滤：优先保留“官方文档”“最新更新”的分块。

### 33. 如何避免生成内容“偏离检索结果”？（约束大模型仅基于给定上下文回答）
+ **核心方法**：通过Prompt强约束+结果校验，双管齐下：
    1. Prompt约束：
        - 明确禁止编造：“若上下文未提及，不得自行补充信息”；
        - 设定惩罚机制：“若发现编造内容，直接判定为无效回答”；
        - 示例引导：在Prompt中加入正确/错误示例，如“正确：上下文提到住宿标准300元/晚，回答‘住宿标准为300元/晚’；错误：上下文未提及早餐，回答‘包含早餐’”。
    2. 结果校验：
        - 人工抽检：上线初期抽检10%-20%的回答，确认是否偏离上下文；
        - 自动校验：用检索关键词与生成回答进行相似度匹配，若相似度低于0.3，判定为偏离，触发重新生成；
        - 引用校验：要求回答标注的来源必须包含在检索结果中，否则视为无效。

### 34. 如何处理“检索结果冲突”？（多个来源信息矛盾时的生成策略）
+ **冲突处理流程**：
    1. 冲突识别：通过关键词比对（如A文档说“住宿标准300元”，B文档说“住宿标准400元”）识别冲突；
    2. 冲突分级：
        - 轻微冲突：细节差异（如A说“300元/晚”，B说“300元/晚（不含早餐）”）；
        - 严重冲突：核心信息矛盾（如A说“报销期限3个月”，B说“报销期限6个月”）。
    3. 生成策略：
        - 轻微冲突：融合细节，明确说明，如“住宿标准为300元/晚，不含早餐”；
        - 严重冲突：标注冲突，列出来源，供用户参考，如“关于报销期限存在两种说法：1. 3个月（来源：2023年差旅政策-第2章）；2. 6个月（来源：2024年差旅政策-第3章）。建议以最新政策为准”；
        - 优先级判定：若冲突文档有明确优先级（如更新时间、官方等级），优先采用高优先级信息，并标注“按最新政策/官方文档，报销期限为6个月”。

### 35. 生成回答的“引用标注”如何实现？（标注来源文档、页码、章节）
+ **实现步骤**：
    1. 分块元数据准备：确保每个分块包含“doc_title（文档标题）、chapter（章节）、page（页码）”等元数据；
    2. Prompt指令：明确要求标注来源，格式示例：“来源：[文档标题]-[章节]-[页码]”；
    3. 引用关联：生成回答时，将每个结论与对应的分块元数据绑定，例如：
        - 分块元数据：doc_title=《2024差旅政策》，chapter=第2章，page=5；
        - 分块内容：“一线城市住宿标准为300元/晚”；
        - 生成回答：“一线城市住宿标准为300元/晚（来源：《2024差旅政策》-第2章-第5页）”。
+ **工具支持**：LangChain的RetrievalQAWithSourcesChain、LlamaIndex的CitationsQueryEngine，可自动关联来源并标注。

### 36. 如何优化生成回答的“可读性”？（分点、简洁、适配业务术语）
+ **优化策略**：
    1. 格式规范：在Prompt中要求“分点说明（用数字1、2、3）”“关键信息加粗（如**300元/晚**）”；
    2. 语言简洁：要求“避免冗长表述，每点不超过2句话”“删除无关修饰词”；
    3. 术语适配：
        - 统一术语：在Prompt中提供术语对照表（如“‘核销’=‘报销’，‘SPOC’=‘单点联系人’”）；
        - 术语解释：若回答包含生僻术语，补充简要解释（如“住宿标准为300元/晚（含SPOC，即单点联系人协调的住宿资源）”）；
    4. 场景适配：根据用户角色调整语言风格（如对管理层用简洁摘要，对一线员工用详细步骤）。

### 37. 多语言知识库场景下，RAG的生成如何保证语言一致性？
+ **核心目标**：用户用中文查询时生成中文回答，用英文查询时生成英文回答，避免语言混杂。
+ **实现方案**：
    1. 嵌入模型选择：使用支持多语言的嵌入模型（如Sentence-BERT（multilingual）、GPT-4 Embedding、通义千问多语言Embedding），确保不同语言的语义向量可比对；
    2. 语言检测：在查询解析阶段，用工具（如langdetect、fastText）检测用户查询的语言（如中文、英文）；
    3. Prompt约束：明确要求生成回答的语言与查询语言一致，例如：“用户查询为中文，回答必须用中文；用户查询为英文，回答必须用英文”；
    4. 知识库过滤：若知识库包含多语言文档，检索时优先返回与查询语言一致的文档（通过分块元数据的“language”字段过滤）。

### 38. 如何让生成回答支持“多轮追问”？（保留上下文逻辑、关联历史检索结果）
+ **实现方案**：
    1. 对话历史管理：
        - 保存前N轮的“查询+回答+检索结果”，避免上下文丢失；
        - 对历史信息进行压缩（如摘要），避免输入大模型的文本过长。
    2. 检索结果复用：将历史检索到的相关文档存入“短期记忆”，多轮追问时优先从这些文档中检索，提升效率；
    3. Prompt引导：在Prompt中加入“需结合历史对话信息，确保回答逻辑连贯”，例如：
        - 历史对话：用户1问“一线城市住宿标准？”，回答“300元/晚（来源：《2024差旅政策》）”；
        - 用户2问“包含早餐吗？”；
        - Prompt：“结合历史对话，用户之前询问了一线城市住宿标准（300元/晚），现在追问是否包含早餐，请基于上下文回答”。

### 39. 什么是“生成校准”？如何降低生成内容的“幻觉率”？
+ **生成校准**：通过技术手段让大模型的生成结果严格贴合检索上下文，减少无中生有的“幻觉”。
+ **降低幻觉率的核心方法**：
    1. Prompt校准：
        - 明确边界：“仅基于上下文回答，未提及的信息一律不补充”；
        - 反问引导：“若上下文未提及用户查询的信息，直接回复‘暂无相关信息’”。
    2. 检索结果增强：
        - 提升检索精准率：通过Hybrid RAG、查询改写等方式，确保检索结果与查询高度相关；
        - 增加来源权威性：优先选择官方文档、最新文档作为上下文。
    3. 结果校验：
        - 人工校验：上线初期抽检Bad Case，优化Prompt和检索策略；
        - 自动校验：用检索关键词与生成回答进行比对，若回答包含未在检索结果中出现的核心关键词，判定为幻觉；
        - 引用校验：要求每个结论都有对应的来源标注，无标注的结论视为无效。

### 40. 如何实现“结构化生成”？（让回答按固定格式输出，如表格、JSON）
+ **核心方法**：通过Prompt的格式约束，让大模型按指定结构生成回答。
+ **实战示例**：
    1. 表格格式要求：

```plain
要求：回答必须按以下表格格式输出，不得修改列名：
| 项目         | 标准                | 来源                          |
|--------------|---------------------|-------------------------------|
| 一线城市住宿 |                     |                               |
| 一线城市交通 |                     |                               |
上下文：{检索结果}
用户查询：2024年一线城市差旅报销标准？
```

    2. JSON格式要求：

```plain
要求：回答必须按JSON格式输出，字段包括“item”（项目）、“standard”（标准）、“source”（来源）：
[
  {"item": "", "standard": "", "source": ""},
  {"item": "", "standard": "", "source": ""}
]
上下文：{检索结果}
用户查询：2024年一线城市差旅报销标准？
```

+ **工具支持**：LangChain的StructuredOutputParser、PydanticOutputParser，可通过Python类定义输出结构，自动校验格式正确性。

### 43. 大模型与RAG的适配原则是什么？（参数规模、上下文窗口、响应速度）
+ **适配核心原则**：大模型的能力需与RAG的“检索精度+生成需求”匹配，避免“大材小用”或“能力不足”。
+ **关键适配维度**：
    1. 上下文窗口：大模型窗口需≥检索上下文总长度+查询长度+Prompt长度，推荐窗口≥8k tokens（如GPT-3.5 Turbo（16k）、通义千问X（128k））；
    2. 响应速度：生成响应时间P95≤3秒，优先选择推理速度快的模型（如GPT-3.5 Turbo、Llama 3（8B））；
    3. 语义理解能力：复杂查询（多轮、歧义、长尾）需选择大参数模型（如GPT-4、通义千问X），简单FAQ可选择中小参数模型（如Llama 3（8B）、文心一言Lite）；
    4. 私有化需求：需选择支持私有化部署的模型（如Llama 3、通义千问、文心一言企业版）；
    5. 成本：中小规模RAG优先选择低成本模型（如GPT-3.5 Turbo、Llama 3（8B）），大规模高精度场景可选择GPT-4、通义千问X。

# 向量数据库元数据权限过滤

我用**通俗原理 + 技术细节 + 完整流程 + 实战SQL/向量库语法**，一次性讲透：
**向量数据库到底怎么靠「元数据过滤」做企业RAG权限隔离**，全程不玄学、全是落地逻辑，刚好解决你多知识库、领导私密库的痛点。

## 一、核心底层逻辑（一句话听懂）

向量数据库存的不只有「文本向量」，**每条向量切片，都会绑定一堆结构化元数据**（知识库ID、权限范围、部门、用户、密级…）。

用户提问检索时：**先拼权限过滤条件 → 再在向量库里面做「先筛数据、再算相似度」** = 无权的内容直接物理过滤掉，根本不参与相似度计算，自然搜不到、漏不掉、防泄露。

> 关键：不是「查出所有内容再隐藏」，是**无权数据直接不参与召回**。

## 二、一条RAG切片在向量库的真实存储结构

不管你用 Milvus / Qdrant / PGVector / Weaviate，结构统一长这样：

1. **vector 字段**：文档片段的向量（用来语义相似度匹配）
2. **text 字段**：原始文本/Markdown/公式LaTeX/图片描述
3. **metadata 元数据结构体（权限核心）**

```json
{
  "kb_id": "kb_008",
  "owner_user_id": "admin_01",
  "read_user_ids": ["leader1", "leader2"],
  "read_dept_ids": ["dept_boss"],
  "doc_secret_level": 3,
  "create_time": "xxx"
}
```

字段说明（核心业务与权限字段）：

- `kb_id`：归属知识库 ID（最小权限单元）
- `owner_user_id`：文档创建人
- `read_user_ids`：允许查看的用户白名单
- `read_dept_ids`：允许查看的部门白名单
- `doc_secret_level`：密级（1 公开 / 2 内部 / 3 机密）

✅ 本质：**每一小块文档，天生带着「准入白名单」**

### 步骤1：文档入库阶段（写入时绑定权限）

你们业务流程：
文件 → MinerU解析 → 分块Chunk → 向量化 → 写入向量库

**写入时强制绑定：**当前文档属于哪个知识库 `kb_id`、这个库的授权用户/部门、密级，全部打在元数据里。

👉 同一个私密知识库下的所有切片，全部统一带上**同一套权限元数据**。

### 步骤2：用户登录，生成当前用户权限上下文

拿到登录人信息：

- 用户ID：`user_a05`
- 所属部门ID：`dept_tech`
- 所属角色/用户组：`高管组/普通员工组`
- 个人有权的全部知识库ID列表

### 步骤3：检索前，拼接「元数据过滤条件」（最关键）

举例业务规则：

> 员工只能搜到：
>
> 1. 自己创建的知识库内容
> 2. 授权给自己的用户白名单内容
> 3. 自己所在部门授权的内容
> 4. 全员公开内容

转化为向量库过滤表达式：

```plain
kb_id IN [当前用户有权的所有知识库]
AND
(
    owner_user_id = 当前用户ID
    OR  当前用户ID IN read_user_ids
    OR  当前部门ID IN read_dept_ids
    OR  doc_secret_level = 1
)
```

### 步骤4：向量库执行「先过滤，后向量召回」

向量数据库执行顺序：

1. **第一层：布尔过滤（元数据Where条件）**
   先把所有不符合权限的chunk**直接剔除**
2. **第二层：向量相似度Top-K召回**
   只在「有权限的干净数据集」里算相似度、搜相关内容

### 步骤5：大模型只拿有权数据作答

最终LLM上下文，**100%都是该用户允许查看的文档片段**。

## 四、主流向量库 权限过滤 真实语法示例

### 1. PGVector（最友好，类SQL）

```sql
SELECT text, vector <-> query_vec AS score
FROM rag_chunks
WHERE
  -- 权限元数据过滤
  metadata->>'kb_id' IN ('kb_001','kb_003')
  AND (
    metadata->>'owner' = 'user005'
    OR metadata->'read_users' @> '["user005"]'
  )
ORDER BY score
LIMIT 5;
```

### 2. Milvus 典型语法

```python
# 先构造权限filter（Milvus 布尔表达式，两套 API 通用）
filter_str = '''
kb_id in ["kb_008","kb_012"]
and (user_id == "u005" or "u005" in read_users)
'''

# ORM API（pymilvus 的 Collection.search）：布尔过滤参数名是 expr
results = collection.search(
    data=[query_embedding],
    anns_field="vector",
    expr=filter_str,  # 元数据权限过滤
    limit=5
)

# 注意：MilvusClient.search（新版客户端 API）里同名参数才叫 filter=，
# 两套 API 不要混用——collection.search 传 filter= 会直接报错
```

### 3. Qdrant / Weaviate

原生支持**嵌套元数据过滤、数组包含、部门匹配**，逻辑完全一致。

## 五、完美解决你当前2大业务痛点

### 痛点1：不同用户自建不同知识库

- 每个知识库全局唯一 `kb_id`
- 前端左侧知识库列表：接口只查「当前用户有权的kb_id」
- 向量检索强制带 `kb_id 白名单过滤`

👉 用户永远看不到不属于自己授权的库内容

### 痛点2：领导专属私密知识库

1. 领导库：元数据里 `read_user_ids = [领导A,领导B]`
2. 普通员工不在白名单
3. 检索过滤直接拦截，**完全搜不到、看不着、问答无泄露**

## 六、关键优势 & 为什么不能用「前端/业务层过滤」

### 元数据向量过滤方案优势

1. **绝对安全**：敏感数据根本不召回，杜绝越权泄露
2. **性能高**：先缩小数据集再算向量距离，计算量更小
3. **粒度灵活**：
   - 粗粒度：按知识库授权（你们现在需要）
   - 细粒度：按单文档、单切片密级授权（后期扩展）
4. **和MinerU解析层解耦**：解析只管产出内容，权限统一在入库&检索层控制

### 反面错误方案（很多团队踩坑）

1. 所有向量全查出来 → 业务代码再判断权限删掉
2. 问题：敏感数据已经被查出，存在内存泄露、日志泄露风险

## 七、最简落地落地模型（你们直接照搬）

1. 权限最小单元：**知识库 kb_id**
2. 每条chunk必带元数据：`kb_id、owner、read_users、read_depts`
3. 登录用户→批量查询自己授权的kb列表
4. 每次RAG检索：**必带kb_id白名单+用户/部门过滤**
5. 新增/上传文档：继承所属知识库的权限配置

## 企业级升级要点

- **默认拒绝原则**：权限过滤条件由服务端强制拼接，任何检索请求不带过滤条件一律拒绝，前端只做展示不做鉴权
- **过滤优先于召回**：坚持「先布尔过滤、后向量召回」，杜绝「全量召回再业务层删减」的泄露路径
- **变更即生效**：用户权限变更（调岗/离职/降密）后同步更新元数据或重建索引，避免白名单过期
- **审计可追溯**：记录每次检索的用户、过滤条件与命中文档，便于越权事件回溯
- **API 口径统一**：明确所用 Milvus API 族（ORM Collection 用 expr=，MilvusClient 用 filter=），团队内统一封装避免混用

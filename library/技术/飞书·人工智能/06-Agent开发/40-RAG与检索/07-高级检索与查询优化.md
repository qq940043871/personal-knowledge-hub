## 一、查询改写

> 改写不是免费的：每多一次 LLM 调用 = 延迟 + 成本 + 新增失败面。上手段之前先确认瓶颈真的在查询侧（评测集上召回率低、且 bad case 集中在「问法与文档用词不一致」），否则先调切分与嵌入模型。

### 1.1 Multi-Query 多查询分解

一个复合问题拆成 N 个独立子查询，各自检索后并集去重。适合「一问多答」型 query（对比类、多要点类）。

```python
# Multi-Query（伪代码骨架；完整实现见 all-in-rag 工程 code/C4/）
async def multi_query_retrieve(query: str, llm, retriever, top_k: int = 5):
    sub_queries = await llm.generate(
        "把下面问题拆成 2-4 个可独立检索的子问题，JSON 数组返回：\n" + query
    )
    # ★特殊点1 子查询必须保留原问题的关键实体——改写丢实体 = 召回漂移
    result_lists = [await retriever.retrieve(q, top_k) for q in sub_queries]
    merged = dedup_by_doc_id(chain(*result_lists))   # 并集按 doc_id 去重
    return merged[:top_k]                            # 去重后可直接交给重排
```

### 1.2 Step-Back 退步提示

先向抽象层退一步问「概念/背景」，拿到背景知识后再回答原问题。适合需要领域常识兜底的细节题。

```python
# Step-Back（伪代码骨架；完整实现见 all-in-rag 工程 code/C4/）
async def step_back_retrieve(query: str, llm, retriever):
    background_q = await llm.generate("把问题退一步抽象成背景性问题：\n" + query)
    background = await retriever.retrieve(background_q)   # 背景上下文
    # ★特殊点2 两次检索结果都进 Prompt：背景答「是什么类」，原文 query 答「这道题」
    return {"background": background, "original": await retriever.retrieve(query)}
```

### 1.3 HyDE 假设性文档嵌入

核心思路：不拿 query 向量去搜，而是先让 LLM 生成一篇「理想答案」的假设文档，拿**假设文档的向量**去搜。把困难的「query→文档」匹配问题转化成容易的「文档→文档」匹配问题。

```python
# HyDE 三步：生成 → 编码 → 检索（伪代码骨架）
# 完整实现见 all-in-rag 工程 docs/chapter4/14_query_rewriting.md
async def hyde_retrieve(query: str, llm, embedder, store, top_k: int = 5):
    # ★特殊点1 假设文档「不必符合事实」——用的是它的语义位置，不是它的真实性；
    #   生成错了事实不影响检索质量，只影响嵌入位置
    hypo_doc = await llm.generate(HYDE_PROMPT.format(query=query))
    vec = (await embedder.embed(hypo_doc))[0]
    return await store.search(vec, top_k)
```

适用边界：query 短、文档长的场景收益最大；query 本身已很长且具体时收益趋零。代价是每次检索多一次 LLM 调用。

### 1.4 查询路由

系统接了多个数据源/多种处理能力时，路由替代硬编码 if-else，按语义把 query 分发到最合适的通道。三种典型场景：数据源路由（产品库 vs SQL 库 vs 知识图谱）、组件路由（简单 FAQ 走向量检索，复杂操作走 Agent）、提示模板路由。

```python
# 路由两种实现（伪代码骨架；完整实现见 all-in-rag 工程 code/C4/05、06）
# 实现 A：LLM 意图识别——灵活，能理解没预设过的问法，但慢且贵
route_label = await llm.generate(ROUTE_PROMPT, query)      # 输出枚举标签
chain = {"rag": rag_chain, "sql": sql_chain, "kg": kg_chain}[route_label]

# 实现 B：嵌入相似度——快且便宜，但路由描述要写得好
def route_by_embedding(query: str, routes: dict[str, str], embedder) -> str:
    # routes: {"产品文档库": "产品功能、参数、版本相关问题", ...}
    qv = (await embedder.embed(query))[0]
    # ★特殊点1 每条路由描述向量化可缓存——运行时只算 query 一个向量
    scores = {name: cosine(qv, (await embedder.embed(desc))[0])
              for name, desc in routes.items()}
    return max(scores, key=scores.get)
```

```python
# Agentic RAG 查询路由（伪代码骨架；完整实现见 all-in-rag 工程 code/C9/）
# LLM 四维打分 + 规则降级 + 三策略分发
async def intelligent_route(query: str, llm) -> str:
    # 1) LLM 分析：复杂度 / 关系密集度 / 推理需求 / 实体数 四维打分 + 置信度（JSON 输出）
    analysis = await llm.generate(QUERY_ANALYSIS_PROMPT, query)
    if not analysis.ok:
        # ★特殊点2 规则降级兜底：LLM 分析失败退回关键词命中规则，路由永不抛异常
        return rule_based_route(query)
    if analysis.关系密集 and analysis.实体数 >= 2:
        return "graph_rag"       # 多跳关系问题 → 图谱检索
    if analysis.复杂度 <= 2:
        return "hybrid"          # 简单问题 → 向量+BM25 混合检索
    return "combined"            # 其余 → 双路组合 + 轮询合并
```

## 二、重排序

RRF 的输出是「名次融合」——它知道哪些块相关，不知道哪个最相关。精排交给重排序，四方案对比：

| 特性 | RRF | RankLLM（LLM 重排） | Cross-Encoder | ColBERT |
| :--- | :--- | :--- | :--- | :--- |
| **核心机制** | 融合多个排名 | LLM 推理，生成排序列表 | 联合编码 query 与文档，算单一相关分 | 独立编码，后期交互 |
| **计算成本** | 低（纯数学） | 中（API 费用与延迟） | 高（N 次模型推理） | 中（向量点积） |
| **交互粒度** | 无（仅排名） | 概念/语义级 | 句子级（query-doc pair） | Token 级 |
| **适用场景** | 多路召回结果融合 | 高价值语义理解场景 | Top-K 精排 | Top-K 重排 |

```python
# Cross-Encoder 精排（伪代码骨架；完整实现见 all-in-rag 工程 code/C4/07）
class CrossEncoderReranker:
    def rerank(self, query: str, docs: list[Document], top_k: int) -> list[Document]:
        pairs = [(query, d.content) for d in docs]
        scores = self.model.predict(pairs)
        # ★特殊点1 Cross-Encoder 不能预计算：query 与 doc 必须拼在一起进模型，
        #   所以只能对粗排后的 Top-K 做，不可能全库精排——「粗排召回、精排打分」分工由此而来
        return sorted_by(scores)[:top_k]

# ColBERT 后期交互（伪代码骨架：MaxSim）
# 完整实现见 all-in-rag 工程 docs/chapter4/15_advanced_retrieval_techniques.md 的 ColBERTReranker
def colbert_score(query_emb, doc_emb) -> float:
    # query_emb: [q_len, dim]，doc_emb: [d_len, dim]（文档 token 向量可离线缓存）
    sim = query_emb @ doc_emb.T                    # token 级相似度矩阵 [q_len, d_len]
    # ★特殊点2 MaxSim：每个 query token 取文档侧最大相似度，再求和——
    #   精度接近 Cross-Encoder，文档向量可离线算，成本介于双塔与交叉编码之间
    return sim.max(dim=-1).values.sum()
```

## 三、上下文压缩与索引结构

### 3.1 上下文压缩

重排解决「顺序」，压缩解决「预算」：命中块可能大半与问题无关，把无关段裁掉再进 Prompt。

- **LLM 提取式**（LLMChainExtractor）：让 LLM 从每个块中只摘出与问题相关的句子——效果最好，但每个块一次 LLM 调用，延迟与成本最高；
- **嵌入过滤式**（EmbeddingsFilter）：query 与块（或块内句子）算相似度，低于阈值直接丢弃——零 LLM 调用，粗但快。

```python
# 压缩管道（伪代码骨架；完整实现见 all-in-rag 工程 code/C4/07_rerank_and_refine.py）
pipeline = DocumentCompressorPipeline([
    colbert_reranker,        # 先重排：把预算花在最相关的块上
    embeddings_filter,       # 再过滤：阈值裁掉弱相关段
])
final_docs = pipeline.compress(query, candidate_docs)
```

### 3.2 句子窗口检索

索引粒度与上下文粒度解耦：**按句子建索引**（检索目标小而准），命中后**回填前后 N 句**的窗口作为上下文。llm-universe C7 实测：句子窗口 vs 常规分块，忠实度 53.3% vs 0%。

```python
# 句子窗口（伪代码骨架；完整实现见 all-in-rag 工程 code/C3/05）
def sentence_window_retrieve(query, sentence_index, window: int = 2):
    hit = sentence_index.search(query, top_k=3)     # 索引的是句子
    return [expand_window(hit, before=window, after=window) for hit in hits]
    # ★特殊点1 回填窗口的边界必须是句子边界——跨句截断会把引用锚点切碎
```

### 3.3 递归检索

适合结构化文档（多表格/多章节）：为每个子结构建**子查询引擎**，顶层保留摘要节点；检索先命摘要，再由路由下沉到子引擎取细粒度块——「先粗后细」的两段式检索。

### 企业级升级要点

- **评测先行，手段后行**：HyDE/Multi-Query/Step-Back/句子窗口的选择没有评测集之前都是猜——llm-universe 用 win/loss 案例对比四种 Query 对齐手段的做法值得照搬。评测口径见 [08-评估体系全景](../../01-大模型工具全景图/08-评估测试/02-评估体系全景.md)。
- **改写失败降级可见**：改写/路由的 LLM 调用失败必须退回原始 query 继续检索，日志显式记降级原因——路由永不抛异常，查询侧坏了系统还要能跑（对应 [70-企业级工程基准](../70-企业级工程基准.md) RAG #5/#7 精神）。
- **改写保真**：改写后的 query 必须保留原问题的关键实体，否则闸门一的充分性检查会以「无依据」拒答——拒答率突然升高时先查改写链路。
- **压缩不得破坏引用锚点**：闸门二要求答案中数字/日期能在所引块原文逐字找到（RAG #11），压缩掉锚点等于自断引用——压缩结果保留句子边界与页码/锚点信息。
- **精排预算显式化**：Cross-Encoder 对 Top-K 逐对推理，K 就是成本常数——K 定多大取决于上下文预算（RAG #10），不是越大越好。

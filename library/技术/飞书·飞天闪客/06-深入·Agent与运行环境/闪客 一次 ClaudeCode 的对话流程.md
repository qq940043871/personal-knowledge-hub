# 闪客 一次 ClaudeCode 的对话流程

![](https://feishu.cn/file/J3WsbvpP0oBUr5xhuQ1c430fnhJ)

## 课程大纲：揭秘Claude Code - 从源码解析AI对话的内部机制

![](https://feishu.cn/file/F7xQbVWWGolXjQxOgL3czyfMndf)

## 一、 课程概述

本课程将引导学习者通过分析一份泄露的“Cloud Code”源码，直观地探索我们与大型语言模型（如Claude）进行交互时，从输入到输出的完整内部工作流程。课程将聚焦于解析核心链路，揭示系统提示词、工具调用、上下文管理等关键设计。

![](https://feishu.cn/file/QFyvbP5lZocZDKx0ccVcZr9Qnm5)

## 二、 目标受众

对AI内部工作原理、大语言模型应用开发、Agent系统架构感兴趣的开发者、技术爱好者及学生。

![](https://feishu.cn/file/XuLJbug7Iom26jxvOywcs4lznTg)

## 三、 课程目标

1. **理解对话流程**：掌握用户一次提问，到AI返回答案之间，系统内部发生的详细步骤。
2. **掌握关键组件**：识别并理解系统提示词、工具列表、上下文管理、Agent循环等核心组件的作用与构成。
3. **实践分析技能**：学会通过添加日志、追踪代码路径等方法，自行分析一个复杂应用的内部逻辑。
4. **洞察设计哲学**：了解工业级Agent产品的设计思路、成本考量及安全隐私机制。

### 第一部分：课程导览与准备工作

**目标**：明确学习目标，搭建本地可调试的分析环境。

1. **课程简介与背景**：介绍本次源码分析的目的与价值。
近期，备受瞩目的AI助手Claude的客户端应用“Cloud Code”源码意外泄露，为我们提供了一个前所未有的窗口，得以窥探一个工业级、高水准的AI Agent系统全栈设计。本次课程将以此为契机，超越简单的黑盒使用，深入其内部逻辑。通过亲手调试和追踪源码，我们将共同揭开大型语言模型对话交互的神秘面纱，理解从用户按下回车到得到回复，系统内部究竟发生了什么。
2. **环境搭建**：

   - 下载并配置“Cloud Code”源码项目。
   - 设置模型API Key，成功在本地运行起与官方一致的对话界面。
   首先，我们需要获取“Cloud Code”的源代码，并将其部署到本地开发环境中。这通常涉及克隆代码仓库、安装依赖项，以及配置一个有效的模型API密钥（如OpenAI或Claude的API Key）。成功启动后，我们将在本地浏览器中看到一个与官方体验无异的交互界面，这是后续所有分析工作的基础。
3. **第一个定制化修改**：通过修改`Claude.tsx`文件更换界面吉祥物，初步接触代码结构，并验证对本地环境的控制力。
我们的第一个实战任务将从一个轻松的修改开始。在庞大的代码库中，定位到负责前端界面渲染的`Claude.tsx`文件。尝试找到定义吉祥物图片的部分，并将其替换为自定义内容（例如，一个简单的字符串或另一个图片链接）。保存并刷新界面，验证修改是否生效。这个简单的操作能让我们初步熟悉项目结构，并确认我们对运行环境的完全控制权，为后续更深入的代码分析建立信心。

### 第二部分：核心交互流程追踪（基础对话篇）

**目标**：以一句简单的“你好”为例，追踪完整的基础对话链路。

1. **入口与日志追踪**：

   - 定位处理用户回车键的核心方法（如`handleEnter`）。
   - 通过插入自定义日志，验证对代码执行流程的掌控。
   交互的起点始于用户在输入框按下回车。我们需要在代码中定位到处理此事件的核心方法，例如名为`handleEnter`或`handleSubmit`的函数。在该函数入口处，插入一行`console.log(“用户触发回车”);`或类似的日志语句。打开浏览器的开发者控制台，再次输入并回车，观察是否成功打印出我们预设的日志。这一步骤至关重要，它证明了我们能够通过添加断点或日志，追踪代码的任意执行路径，是深入分析复杂系统的基础方法论。
2. **请求构成剖析（“你好”为例）**：

   - **首次请求**：解析自动生成对话标题的异步线程。
   - **主请求分析**：拆解发送给大模型的完整Payload，包括：

     - 用户输入
     - **注入信息**：当前日期、可用技能（Skill）列表。
     - **系统提示词**：详细拆解其构成（身份定义、行为规则、工具使用规范、安全协议等）。
     - **动态上下文**：会话级补充信息（如Git状态）。
     - **工具列表**：介绍`function calling`中`tools`字段的完整工具集。
     - **其他配置**：实验特性开关、追踪标识、`max_tokens`限制、`thinking`模式开关。
3. 当我们输入“你好”并回车后，通过日志追踪会发现，系统实际上发起了两次对大模型的API请求。

   - **第一次请求**：这是一个轻量级的异步请求，其唯一目的是根据用户输入生成一个简短的会话标题（如“新对话”、“关于问好”等）。生成的标题会显示在前端界面的会话列表中。
   - **第二次请求（主请求）**：这是承载核心交互的请求。我们可以捕获并打印出发送给模型的完整JSON负载（Payload），其结构通常如下：

     - `messages` 数组：包含完整的对话历史。首条消息即用户输入的“你好”。
     - `system` 或 `system_message` 字段：这是“系统提示词”，是整个应用的灵魂。它是一个精心设计的长文本，通常包含：

       - **身份与核心目标**：明确定义AI的角色（如“你是一个强大的代码助手”）和主要任务。
       - **行为规则与风格**：规定回答的语言、格式、详尽程度等。
       - **工具使用规范**：详细描述在何种情况下、如何调用指定的工具。
       - **安全与合规协议**：内置的过滤和限制规则，防止生成有害内容。
       - **可用技能（Skill）列表**：动态注入的，描述AI在当前会话中具备的额外能力。
     - **动态上下文注入**：有时会拼接在系统提示词之后，包含当前时间、工作目录的Git状态等临时信息。
     - `tools` 字段：一个工具列表对象数组，详细描述了每个可调用工具的名称、功能描述和参数定义，供模型进行函数调用（Function Calling）决策。
     - **其他配置**：如 `max_tokens`（控制回复长度）、`temperature`（控制创造力）、是否启用“思考”（thinking）模式等。
4. **响应内容解析**：

   - 观察`thinking`模式下的“思考”过程输出。
   - 解析最终面向用户的回复内容及其格式化。
   在“你好”的响应中，如果开启了“思考”模式，我们将首先收到一个标记为`thinking`的JSON片段。它展示了模型的内部推理过程，例如：“用户用中文打招呼，我应该用中文友好地回应。”随后，才是正式的`content`字段，包含面向用户的回复“你好！有什么可以帮您的吗？”。前端应用会解析这个响应，过滤掉`thinking`部分，只将`content`以Markdown等格式渲染给用户。

![](https://feishu.cn/file/X0xPbNWGAoa886xplmNcHZCanWg)

### 第三部分：核心交互流程追踪（工具调用篇）

**目标**：分析涉及工具调用（Agent循环）的复杂交互流程。

1. **工具调用触发**：以“列出当前目录文件”为例，展示大模型如何决定调用工具（如`glob`、`bash`）。
当我们提出一个需要执行操作的请求（如“列出当前目录文件”）时，模型在分析请求和系统提示词中的工具使用规范后，可能会认为需要调用工具来完成任务。在它返回的响应中，`content`字段可能为空，而`tool_calls`字段会包含一个或多个工具调用请求，指明需要调用哪个工具（如`glob`或`bash`）以及具体的输入参数（如`{“command”: “ls -la”}`）。
2. **Agent循环流程**：

   - 复习经典Agent架构：用户请求 -> 模型决策 -> 调用工具 -> 获取结果 -> 再次请求模型 -> ... -> 返回最终答案。
   - 结合日志，跟踪代码中此循环的具体实现。
   这体现了“Agent”的核心工作模式——循环。应用程序（Agent）收到模型的工具调用请求后，在本地执行该工具（如运行shell命令），获取执行结果。然后，它会将工具调用ID和结果作为新的消息（角色为`tool`）追加到对话历史中，并**再次**发起对大模型的请求。模型将看到工具调用的结果，并基于此进行下一轮决策：是继续调用另一个工具，还是生成最终回复。这个“请求-决策-执行”的循环会持续，直到模型决定给出最终答案。
3. **多轮交互观察**：展示在一次工具调用失败后，模型如何调整策略并发起新的工具调用。
例如，模型可能首先建议使用`glob`工具，但执行失败。在下一次请求中，模型会看到错误信息，并可能调整策略，转而调用更通用的`bash`工具执行`ls`命令。这展示了Agent系统具备一定的错误恢复和策略调整能力。
4. **Token消耗分析**：直观感受每次与模型交互所附带的大量上下文信息，理解其带来的Token消耗。
通过分析每次请求的Payload大小，我们可以直观理解Token消耗的来源。即使是同一个会话，**每一次**调用模型，都必须附上完整的系统提示词、工具定义、以及从第一条消息开始的**全部**对话历史（包括工具调用及结果）。随着对话轮次增加，这个“滚雪球”效应会导致上下文长度急剧增长，从而消耗大量Token，直接影响响应延迟和API成本。

### 第四部分：架构总结与设计洞察

**目标**：归纳整体架构，深入了解系统其他重要设计。

1. **整体流程回顾**：用流程图或示意图总结从用户输入到最终显示的完整链路。

```Plaintext
用户输入 -> (并行异步请求: 生成会话标题)
         -> 构造主请求 (组装：系统提示词 + 动态上下文 + 对话历史 + 工具定义)
         -> 发送至LLM
         <- 响应：
             若为工具调用 -> 执行工具 -> 将结果加入历史 -> 跳转至“构造主请求”步骤
             若为最终回复 -> 渲染并显示给用户
```

1. **额外机制探秘**：

   - **安全与隐私**：提及系统可能包含的敏感词收集、体验反馈机制。源码可能显示，当用户输出包含某些敏感词（如不满的反馈）时，应用会记录该会话片段，用于后续的质量分析和模型优化。
   - **彩蛋与体验**：介绍“做梦机制”、宠物系统等增加趣味性的设计。一些设计旨在提升用户体验，例如根据对话内容生成“梦境”摘要，或内置一个可交互的宠物系统，这些都体现了产品设计的人文关怀。
   - **上下文管理**：分析系统如何管理历史对话以减少冗余（如课程中自制Agent的`history`命令）。面对高昂的上下文成本，系统可能采用摘要、关键信息提取或滑动窗口等策略来管理历史对话，以在保持连贯性和控制成本之间取得平衡。
2. **成本与效率考量**：分析系统提示词长度、工具描述、每轮请求的上下文冗余对Token成本和响应速度的影响。
工业级Agent设计的核心权衡之一就是成本与效果。冗长的系统提示词和详细的工具描述虽然能提升模型理解和执行的准确性，但会直接增加每次请求的Token消耗。同时，累积的对话历史也推高了成本。因此，精炼提示词、优化工具描述、实施有效的上下文压缩策略，是降低运营成本、提升响应速度的关键。

### 第五部分：拓展思考与行业影响

**目标**：将具体技术分析提升到行业视角进行思考。

1. **开发启示**：

   - 学习工业级Agent的模块化设计（如清晰的命令处理、工具集成、上下文注入）。Cloud Code的源码展示了优秀的模块化架构：前端交互、对话管理、工具执行、模型通信等层次分明，便于维护和扩展。
   - 理解系统提示词工程的重要性与复杂性。系统提示词不仅是指令，更是产品逻辑、安全策略和用户体验的集中体现，其设计是一门需要反复调试和优化的“工程艺术”。
2. **对比与自研优势**：讨论透明化、可控的自研Agent程序与闭源商业产品在调试、审计、成本控制方面的对比。
基于开源框架或自研的Agent系统，其最大优势在于透明和可控。开发者可以自由地调试每一个环节，审计数据流向，并根据实际需求精细控制上下文长度和工具使用，从而实现更优的成本控制。而闭源商业产品虽然提供开箱即用的便利和经过大规模验证的优化，但在灵活性、可定制性和审计透明度上有所欠缺。
3. **开源与闭源的博弈**：

   - 回顾历史：Llama开源模型如何促进生态繁荣，DeepSeek R1如何降低推理技术门槛。
   - 分析本次“源码泄露”事件的独特性：**非模型权重泄露，而是顶级Agent产品全栈设计的暴露**。
   此次事件与模型权重开源有本质不同。它泄露的不是模型的“大脑”（权重），而是驱动这个大脑高效、安全工作的“神经系统”和“行为准则”——完整的Agent应用层设计。这使得社区能够直接学习和复现一个经过市场验证的顶尖Agent架构。
   - 展望未来：预测此事件对Agent产品设计、开源项目以及行业竞争格局可能产生的深远影响，加速开源Agent生态与闭源产品的差距缩小。
   此次泄露无疑将为开源Agent社区注入一剂强心针。众多开发者将从中汲取设计灵感，优化自己的Agent框架，从而在系统提示词工程、工具管理、安全防护等应用层能力上快速追赶，显著缩小与闭源商业产品在“工程成熟度”上的差距，推动整个Agent生态的繁荣发展。

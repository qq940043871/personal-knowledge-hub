JVM 的并发，从来不是凭空保证的

它不靠魔法，靠的是底下一条完整的接力链：Java 代码 → JVM → 操作系统 → CPU。JVM 负责「定规则」，OS 负责「管资源」，CPU 负责「真正执行」。点下面任意一层，跳到对应机制。

01

第一层 · 操作系统先让「多个线程真的能跑」

OS 负责：创建线程 / 调度 / 上下文切换 / 阻塞与唤醒

JVM 里的线程，最终都要落到操作系统线程上（现代 HotSpot 是 1:1 映射）。OS 给线程分配栈、寄存器上下文和调度信息，然后决定谁拿到 CPU 时间片。所谓「并发执行」，底层就是 OS 的线程调度 + 上下文切换 + 阻塞唤醒三件套。

线程状态机 —— 一个线程的一生，都被 OS 调度器摆布

调度谁先跑，OS 说了算

  • 就绪队列里的线程轮流拿时间片
  • 优先级、时间片、调度算法（CFS 等）
  • JVM 无法绕过 OS 直接抢占 CPU

上下文切换保存 / 恢复现场

  • 切走：保存寄存器、PC、栈指针
  • 切回：恢复现场，接着上次跑
  • 切换有成本——线程不是越多越好

阻塞 / 唤醒挂起与重排

  • 拿不到锁 / 等 I/O → OS 挂起线程
  • 条件满足 → OS 唤醒，重新排队
  • 这正是 synchronized 重量级锁的地基
02

第二层 · 可见性：MESI 缓存一致性 + 内存屏障

JMM 的「工作内存」是抽象；真正干活的是 CPU 缓存协议与屏障指令

JMM 说每个线程有「工作内存」，但那不是 JVM 自己造出来的物理内存，而是对 CPU 缓存、寄存器、主存的一层抽象。真正让多核看到同一份数据的是 CPU 的 MESI 缓存一致性协议——它只解决「数据一致」，不解决「指令顺序」。于是 volatile 和内存屏障最终落到 CPU 的内存屏障指令上：禁止重排序 + 强制刷新/重载缓存。

MESI 缓存一致性 —— 一个核心改了，其他核心的缓存行立刻失效

MESI四态缓存行

M(Modified) / E(Exclusive) / S(Shared) / I(Invalid)。一个核心改了共享缓存行，其余核心对应行被标为 I，下次读必须重新加载。这就是「可见性」的硬件基础。

内存屏障禁止重排序 + 强制刷新

MESI 不管指令顺序。volatile 的写/读，最终翻译成 CPU 的屏障指令：写屏障刷新缓存并通知失效，读屏障放弃旧缓存重新加载。顺序，是屏障管的。

// volatile 写 —— 落到 CPU 屏障指令 volatile int flag = 0; flag = 1; // ① 插入 StoreStore/StoreLoad 写屏障 // ② 刷新缓存行 // ③ 广播，令其他核心对应缓存行失效 // volatile 读 —— 读屏障：放弃旧缓存，重载最新值 int x = flag; // 读到的必是刷新后的值
03

第三层 · 原子性：靠 CPU 的原子指令，不是 Java 的发明

AtomicInteger 的 CAS → x86 lock cmpxchg / ARM LDREX-STREX

AtomicInteger 的 CAS 本质上不是 Java 发明的，而是 CPU 提供的原子指令：x86 上是 lock cmpxchg，ARM 上是 LDREX/STREX 指令对。这条指令由 CPU 保证不可中断，多核下还会配合缓存锁或总线锁，确保「比较 + 交换」不会被别的核心插队。OS 则在更上层提供重一点的原语（互斥锁、信号量、futex、pthread mutex、Windows CRITICAL_SECTION）。

CAS 三步：比较 → 命中则交换，未命中则重来

x86lock cmpxchg

一条带 lock 前缀的指令，锁住缓存行或总线，完成「比较 + 交换」。原子性由硬件直接背书。

ARMLDREX / STREX

「独占加载 / 独占存储」指令对：STREX 时若发现期间有别的核动过，则返回失败并重试，实现等价原子性。

04

第四层 · 锁竞争：轻则自旋，重则交给 OS 阻塞

synchronized / ReentrantLock / AQS 的底层，最终调用 OS 的阻塞与唤醒

竞争轻时，JVM 用自旋、CAS、轻量级锁扛过去——省得惊动 OS。一旦竞争激烈，继续自旋就是纯烧 CPU，这时 JVM 把线程交给操作系统去阻塞：进入阻塞队列，等持锁线程释放后再被唤醒、重新参与调度。锁的实现，从来不是纯 JVM 的事。

锁竞争升级：自旋 → 轻量级锁 → 重量级锁（OS 阻塞队列）

轻竞争自己扛

  • 自旋锁：短时间忙等，不惊动 OS
  • 轻量级锁 / CAS 原地解决
  • 省下线程切换的开销

重竞争交给 OS

  • synchronized 膨胀成重量级锁
  • 调用 futex / pthread mutex
  • 线程进入 OS 阻塞队列挂起

释放唤醒等待者

  • 持锁线程释放 → OS 唤醒等待线程
  • 被唤醒线程重新排队参与调度
  • AQS 的等待队列就是这套逻辑
// synchronized —— 从偏向锁到重量级锁的升级路径 synchronized (obj) { /* 临界区 */ } // 无竞争 → 偏向锁（JDK15 起默认废弃） // 轻竞争 → 轻量级锁（自旋 + CAS 抢占） // 重竞争 → 重量级锁（调用 OS 阻塞原语，线程挂起等待）

合起来看：一条链路，五个能力，三个角色

规则制定者

JVM

把并发安全抽象成三个词：

  • volatile —— 管可见性 + 有序性
  • synchronized —— 管互斥
  • CAS / 原子类 —— 管原子性
资源管理者

操作系统

把「并发」变成真实发生的事：

  • 调度线程、切换上下文
  • 管理内存、提供锁原语
  • 阻塞与唤醒等待的线程
硬件执行者

CPU

把「保证」落到硅片里：

  • MESI 缓存一致性
  • lock cmpxchg 原子指令
  • 内存屏障指令
一句话总结

你写的 volatile / synchronized / CAS，只是这场接力赛的发令枪。真正跑完这 400 米的，是 OS 的调度器、上下文切换和阻塞唤醒，是 CPU 的 MESI 协议、原子指令和内存屏障。理解了这条链路，你就不会再问「JVM 到底怎么保证并发」——因为它根本没保证，它只是把球稳稳地传给了下面两层，然后说：「剩下的，交给你们了。」

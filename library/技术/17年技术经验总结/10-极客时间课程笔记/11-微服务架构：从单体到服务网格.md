## 二、逐模块要点 + 底层关联

### 2.1 安全（模块1，24讲）：OAuth2 为什么这么设计

```
OAuth2 四种模式（03~06讲）按"信任度"递减：
  授权码模式：第三方应用 + 浏览器重定向 —— 最安全（令牌不经过前端）
  简化模式：无后端的纯前端（令牌暴露在 URL，只适合低敏感场景）
  密码模式：第一方应用（用户直接交密码给信任方）
  客户端模式：服务间调用（机器对机器）

JWT 令牌（15讲）：签名后的自包含身份卡
  ✓ 无状态：网关本地验签即可放行（省一次远程调用——RTT定律）
  ✗ 无法主动吊销：黑名单又要引入状态 —— "无状态与可控性"的CAP式折衷
CSRF（21讲）：浏览器自动带 Cookie 的天然缺陷 → token 不放 Cookie 的设计动机
```

### 2.2 配置中心（模块2，24讲）：Apollo

```
为什么需要：配置散落在几百个实例 → 改一次发一版 = 运维地狱
Apollo 的三个设计支点：
  1. 长轮询(long polling)推变更 —— 客户端挂起等配置更新（01篇IO模型：比纯轮询省）
  2. 多环境/多集群(dressing for scale)
  3. 灰度发布 + 权限审计 —— 变更即风险，配置是"不发版的代码"
开关驱动开发：所有不确定的行为都做成开关，出事秒级回滚
```

### 2.3 网关（模块3，17讲）：Zuul

```
网关的职责：路由 + 认证 + 限流 + 灰度 —— 横切关注点收口
Zuul 1 的教训（对05/07篇的直接呼应）：
  Zuul 1 = 一请求一线程(BIO风格)，线程在等上游响应时被白白占用
  Zuul 2 = Netty 异步非阻塞重写 —— 同一 Tomcat BIO→NIO 的故事再演一遍
结论：凡是"等别人"的角色，最终都会走向事件驱动（Reactor 收编一切）
```

### 2.4 调用链监控（模块4，19讲）：CAT

```
分布式 Trace 的三件套：traceId(全局) + spanId(段) + parentSpanId(父子)
  —— 25讲"横跨几十个组件的慢请求"的唯一解法
埋点位置：入口(网关) + 出口(RPC/DB/缓存客户端) —— 恰好是01篇"内核账单"的产生点
告警的艺术：P99 而非平均值（长尾才是用户体验）；
           先分机房/实例维度聚合再报警，避免全局均值掩盖局部火灾
```

```
Hystrix 的三板斧：
  1. 舱壁隔离(bulkhead)：每个依赖独立线程池/信号量，故障不串门
  2. 熔断器(circuit breaker)：错误率超阈值 → 直接快速失败 → 半开试探恢复
     （状态机：Closed → Open → Half-Open，02篇状态机思想）
  3. 降级回退(fallback)：秒杀库存服务挂了 → 返回"稍后再试"，保主流程
限流算法落地：令牌桶(允许突发) vs 漏桶(整流) vs 滑动窗口 —— 02篇数据结构的直接应用
```

### 2.6 注册发现（模块6，16讲）：Eureka + Ribbon

```
注册中心 = 分布式系统的"电话簿"
  服务启动时注册(写) + 心跳续约(活) + 摘要拉取(读)
Eureka 选 AP：宁可返回旧地址，不可整体不可用
  （对比 ZooKeeper CP：选主期间整个集群不可用 —— 09篇 CAP 的实战对照）
Ribbon 客户端负载均衡：轮询/加权/最小并发 —— 09篇负载均衡算法的进程内版
```

### 2.7 监控告警（模块7，21讲）：Prometheus

```
Pull 模型 + 时间序列库 + PromQL
指标四金信号(Google SRE)：延迟 / 流量 / 错误 / 饱和度
  —— 恰好对应01篇的 CPU/内存/IO/网络四维，只是换到服务维度
告警规则示例：5xx 率 > 1% 持续 5m；P99 > 500ms 持续 10m
```

## 三、《左耳听风》的分布式篇章：更高一层的浓缩（21~62讲）

### 3.1 分布式架构的冰与火（21~23讲）

```
火的方面：可扩展、容错、资源复用
冰的方面（分布式系统的固有税）：
  - 网络不可靠 + 有延迟（01篇 NET 定律的哲学化）
  - 没有全局时钟 → 一致性问题是分布式的"原生税"，只能选边（CAP/BASE）
  - 异构与版本漂移
技术栈分层：RPC → 服务注册发现 → 网关 → 熔断限流降级 → 监控 → 配置中心
  —— 与160讲的九大模块一一对应（两门课互为印证）
```

### 3.2 弹力设计 11 讲（41~51讲）——故障是常态

```
隔离(42)：线程池隔离/机房隔离/业务隔离 —— 舱壁模式的架构级
异步(43)：MQ 削峰 + 最终一致性 —— 把同步等待换成事件通知（01篇 IO 模型的架构化）
幂等(44)：重试的前提 —— 唯一ID + 去重表/状态机
状态(45)：无状态服务才能随意扩缩容（会话外置到 Redis —— 03篇登场）
补偿(46)：Saga —— 长事务拆成本地事务 + 反向补偿
重试(47)：指数退避 + 抖动；只重试幂等操作
熔断(48) 限流(49) 降级(50) —— 与 Hystrix 模块互为注脚
```

### 3.3 管理设计 6 讲（52~57讲）——服务自己也需要管理

```
分布式锁(52)：Redis SETNX/Redlock vs ZooKeeper 临时顺序节点 —— 03/11篇的取舍
配置中心(53)：Apollo/ZooKeeper —— 状态外置
边车模式(54)：Sidecar 把治理能力旁挂 —— 语言无关的治理层
服务网格(55)：Istio = 边车的舰队化管理 —— 数据面(envoy) + 控制面(pilot)
网关(56)：南北向流量 vs 服务网格的东西向流量
部署升级(57)：蓝绿/金丝雀/滚动 —— 变更风险控制（SRE 的发布哲学）
```

### 3.4 性能设计 5 讲（58~62讲）

```
缓存(58)：多级缓存 + 一致性级别选择（10篇缓存方法论的浓缩版）
异步(59)：削峰 + 事件驱动
数据库扩展(60)：读写分离 → 分库分表 → NoSQL（10篇演进路径的理论版）
秒杀(61)：漏斗模型 —— CDN 静态化 → 网关限流 → MQ 削峰 → 库存扣减(Redis+Lua原子性)
边缘计算(62)：把计算推向离用户最近处 —— 延迟定律的终局
```

## 四、贯穿的三条铁律（两门课程合起来的结论）

```
铁律1：所有"等"都要异步化 —— 线程等待是分布式系统最贵的浪费
铁律2：所有"单点"都要消灭或冗余 —— 无论是数据(主从)、服务(集群)、机房(多活)
铁律3：所有"变更"都要可灰度可回滚 —— 配置开关、金丝雀发布、幂等补偿
```

## 〇、为什么先讲操作系统

MySQL、Nginx、Redis、JVM、Tomcat，无论广告词多华丽，本质都是**跑在 Linux 内核之上的普通用户态进程**。

它们能做的事，操作系统全权决定；它们想快，就必须顺着内核的脾气走。
所以先把内核的"脾气"列出来——我把它总结成**四组定律**，后面每篇都会反复引用。

## 一、CPU 定律：时间片是租来的

### 1.1 进程视角：一门"外包公司"的生意

《趣谈Linux操作系统》最精彩的比喻：把 Linux 内核当成一家**软件外包公司**——

| 内核概念 | 公司比喻 | 关键数据结构 | 一次操作的真实代价 |
|---------|---------|-------------|------------------|
| 进程 | 接的项目 | task_struct | fork≈几十μs（页表复制为主） |
| 线程 | 项目组里的并行小组 | 共享 mm_struct 的 task_struct | 创建≈10μs，切换≈1~10μs |
| 调度器 | 项目管理流程 | CFS 调度类 + 红黑树 | 一次调度决策≈纳秒级 |
| 系统调用 | 项目对总部的请示 | syscall 入口(向量表) | ≈1μs（态切换+上下文保存） |
| fork | 立项新项目 | 复制 task_struct + 写时复制 | 页表复制线性于内存大小 |
| IPC | 项目组间协作 | 管道/信号/共享内存 | 管道≈拷贝；共享内存≈零拷贝 |

CFS（完全公平调度）值得多说一句：每个进程记一个 **vruntime（虚拟运行时间）**，
调度器每次挑 vruntime 最小的进程运行，运行中 vruntime 不断累加——**用"谁欠的最少谁先跑"实现绝对公平**。
而维护"最小值"用的正是红黑树（02篇：为什么内核也爱红黑树——增删查 O(log n)、树高稳定）。

### 2.2 四条硬约束（后面所有软件都在跟它们搏斗）

```
定律 CPU-1：上下文切换 ≈ 1~10μs/次（还要冲刷 L1/L2 缓存，真实代价更高）
  → 1万QPS的服务，每请求切10次上下文，CPU光切换就烧掉10%以上
  → 切换分三类：进程切换(换页表,最贵)、线程切换(共享地址空间,便宜些)、
    态切换(用户态↔内核态,最便宜但每次系统调用都要付)

定律 CPU-2：用户态↔内核态切换 ≈ 1μs/次（系统调用、中断都要切）
  → 每次 read()/write() 都要付一次过路费；百万级小IO = 百万级过路费
  → "批量化"之所以永远是优化方向，本质是把 N 次过路费合并成 1 次

定律 CPU-3：CPU 核数就是并行上限，超卖只会换来切换开销
  → CFS 时间片轮转：线程数 >> 核数时，每个线程分到的时间更碎
  → 经验：CPU密集型线程池 ≈ 核数+1；IO密集型 ≈ 核数/(1-阻塞系数)

定律 CPU-4：软中断(ksoftirqd)和网络包收发共用CPU，网络风暴会吃掉业务CPU
  → 《Linux性能优化实战》09/10讲：si 占比高的排查套路
  → 多队列网卡 RSS 把包分散到多核，就是给这条定律买的保险
```

### 1.3 一个观测抓手

```bash
# 平均负载：活跃进程数（运行R + 不可中断睡眠D），不是CPU使用率！
uptime        # 负载超过核数×0.7 就该警惕
vmstat 1      # cs列=上下文切换/秒；b列=不可中断阻塞进程
pidstat -w -p <pid> 1   # cswch=自愿切换(等IO/锁), nvcswch=非自愿(被抢占)
perf top      # 直接看热点函数，内核态占用一目了然
top           # us用户态/sy内核态/si软中断/wa等IO —— 四个数字定位四种瓶颈
```

> 《Linux性能优化实战》06讲经典案例：CPU 100% 但 top 里找不到高 CPU 进程——
> 元凶在内核态（短命进程/线程/软中断）。**用户态工具看到的只是冰山一角，
> `perf top` 里看到的 [kernel] 符号才是真相。**

## 二、内存定律：你用的地址都是假的

### 2.1 虚拟内存：给每个进程画饼

每个进程启动时都得到一整套"从 0 开始"的地址空间，用的时候 MMU 查页表翻译成物理地址。
页表的层级结构（x86-64 四级：PGD→PUD→PMD→PTE）让"只映射用过的部分"成为可能——
**虚拟空间可以声明 128TB，物理内存只兑现真正写过的那些页。**

四条硬约束：

```
定律 MEM-1：次缺页(页已在内存) ~1μs；主缺页(要读盘) = 一次磁盘IO 100μs~10ms；
            TLB未命中让每次访存变慢30%+
  → 大页(HugePage)存在的意义：JVM -XX:+UseLargePages、Redis 的 THP 陷阱
  → THP(透明大页)对 Redis 是陷阱：后台 khugepaged 合页会卡顿 → 必须关

定律 MEM-2：malloc 的内存 ≠ 物理内存，首次写入才真正分配（demand paging）
  → 这就是 fork()+COW 能"秒级复制"几GB进程的原理（Redis bgsave 的命根子）
  → free 里 available ≠ free：buffer/cache 可回收，被锁住的页不可

定律 MEM-3：物理内存不够 → 页换出到 Swap，一块普通内存页变成磁盘速度
  → 《Linux性能优化实战》19/20讲：Swap 变高的排查；Redis 被 swap 是延迟杀手
  → swappiness 调低 ≠ 关 swap；数据库服务器惯例 swappiness=1~10

定律 MEM-4：Page Cache 用空闲内存缓存文件读写，Write 是"以为写完了"
  → 数据真正落盘要等 fsync；断电时没 fsync 的数据不存在
  → free 命令里 buff/cache 占大头不是浪费，是内核在替你加速
```

### 2.2 Buffer 和 Cache 别再混

| | Buffer | Cache |
|--|--------|-------|
| 缓冲对象 | 块设备写入的攒批 | 文件读的留底 |
| 通俗理解 | 写之前的"攒一批再下" | 读之后的"留个底再读快" |
| 内核归属 | 都算 page cache（4.x 后 buff/cache 统一） | 同左 |

### 2.3 mmap：把文件当内存用

```c
mmap() → 在页表里建立"虚拟地址 ↔ 文件页"映射
  → 读：缺页中断时从磁盘加载（少一次拷贝，读路径 = 内存速度或主缺页）
  → 写：改内存页，内核回写（还是要等 fsync 才可靠）
  → 适合：随机访问大文件、多进程共享只读段
  → 不适合：顺序追加日志（会触发读页-改页-回写，不如 write 直写）
```

**JVM 的 MappedByteBuffer、Kafka 的日志段、RocketMQ 的 CommitLog 都在用它——这就是"底层能力直接定义上层 API"的例子。**

### 3.2 一切皆文件 + VFS

```
open/read/write (系统调用)
      │
   VFS 虚拟文件系统 ←── ext4/xfs 等具体文件系统
      │
   Page Cache ←──── 读写都先过这里
      │
   块设备层 → 磁盘
```

- **O_DIRECT**：绕过 Page Cache（InnoDB 推荐的 innodb_flush_method——它自带 Buffer Pool，双缓存纯属浪费）
- **fsync**：把脏页强制刷盘的唯一诚实手段；fdatasync 省去元数据更新，日志文件首选
- **O_APPEND**：原子追加，日志与 AOF 的并发安全基础

### 3.4 零拷贝：少搬一次是一次

```
传统 read+write： 磁盘→页缓存→用户缓冲区→socket缓冲区→网卡   4次拷贝+2次上下文切换
sendfile：        磁盘→页缓存──────────────→socket缓冲区→网卡   2次拷贝
sendfile+SG-DMA： 磁盘→页缓存────────────────────────→网卡    1次拷贝！
```

**Nginx 的 `sendfile on` 静态资源提速、Kafka 的高吞吐，全靠这条路径。**

## 五、把四组定律压缩成一张"账单"

任何上层软件每一次"操作"，内核都在暗处记账：

| 上层动作 | 内核真实成本 |
|---------|-------------|
| 一次系统调用 | ~1μs（态切换） |
| 一次线程唤醒/切换 | ~1-10μs（+缓存污染） |
| 一次内存随机访问 | ~100ns（缺页另付：次缺页μs级，主缺页=一次磁盘IO） |
| 一次小文件读(冷) | ~100μs(SSD) / 10ms(HDD) |
| 一次 fsync | 100μs~10ms，且是串行瓶颈 |
| 一次 fork(GB级进程) | 页表复制 ~几十ms，COW 延后真正拷贝 |
| 一次 TCP 建连 | 1 RTT ~0.5ms(同机房) |

**性能优化 = 少付账单 + 把贵的账单换成便宜的（随机→顺序、阻塞→事件、每请求→批量）。**

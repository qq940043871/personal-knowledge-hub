## 二、渲染进程的多线程：JS 为什么"单线程"却"并发"（课程15~18讲）

### 2.1 渲染进程里的线程分工

```
┌─ 渲染进程（每个站点一个）──────────────────────┐
│ 主线程：JS 执行 + DOM 解析 + 样式计算 + 布局 + 绘制记录 │
│ 合成线程：图层合成、滚动、动画推进（不回主线程！）      │
│ 光栅化线程池：把绘制记录变成位图                      │
│ IO 线程：网络/XHR 的 IPC 收发                        │
└────────────────────────────────────────────────┘
```

**核心事实：JS 引擎与页面渲染共享同一个主线程——二者互斥。**
JS 跑长任务时，渲染流水线排不上队 → 掉帧、卡顿。
而鼠标滚动/transform 动画走合成线程 → 主线程卡了它们照样流畅。

### 2.2 为什么 JS 一定要单线程？——答案就是"一致性"

> **多个线程同时改 DOM，谁来保证读到的是"对"的？**

```
线程A: el.appendChild(x)     ←─┐
线程B: el.removeChild(y)     ←─┤ 同一棵 DOM 树并发写
线程A: el.offsetLeft         ←─┘ 读到哪个版本？
```

→ 必须给 DOM 上锁，前端代码立即复杂 10 倍（回想 06 篇 JVM 给堆上锁的代价）。
**语言的回答：干脆单线程，把"并发修改"从源头消灭——一致性不靠锁，靠"根本没有并发"。**

这不是偷懒，是和 Redis（03篇）同一条哲学：**当操作本身极快、瓶颈在协调时，单线程 + 无锁比多线程 + 锁更优。**
JS 单线程:DOM 一致性  ⇔  Redis 单线程:数据一致性  ⇔  MySQL 行锁:事务一致性——不同尺度，同一问题。

## 五、Web Worker：前端唯一的"真多线程"

```
Worker 的三重纪律：
  1. 不能碰 DOM —— 主线程独占 DOM，Worker 只能算数/收发消息
     （一致性约束的延续：DOM 一致性 > 并行收益）
  2. 通信靠 postMessage —— 结构化克隆：默认"拷贝传递"，天然无共享，无锁
  3. 要共享就升级：SharedArrayBuffer + Atomics(原子操作) —— 真共享内存
     此时一致性靠硬件级的原子指令/内存屏障（01篇 MESI 缓存一致性，06篇 volatile 同源）
     （注：SAB 因 Spectre 漏洞曾被全面禁用，现需 COOP/COEP 响应头解禁）

Service Worker（PWA，27讲）：页面之外的"守护进程"
  独立生命周期 + 拦截 fetch → 可离线缓存
  与页面通过 postMessage 通信 —— 又是消息传递而非共享
```

> **前端并发模型总结：JS 主线程单线程（一致性免锁）→ 并发靠事件循环（任务排队）→
> 并行靠 Worker（消息传递，不共享）→ 共享靠 Atomics（退回 OS 级原子操作）。
> 每往下一层，就离 01 篇的线程定律更近一步。**

## 六、约束小结

| 底层约束 | 浏览器的回应 |
|---------|-------------|
| 进程崩溃隔离 | 多进程 + 站点隔离 |
| 不可信代码 | 渲染进程安全沙箱（网络/文件走 IPC） |
| DOM 并发一致性 | JS 单线程，DOM 主线程独占 |
| 主线程稀缺 | 事件循环 + 宏微任务分级 + rAF 帧调度 |
| 主线程阻塞掉帧 | 分层 + 合成线程旁路（CSS 动画/滚动） |
| 并行计算需求 | Worker 消息传递 / SharedArrayBuffer+Atomics |
| 离线与生命周期 | Service Worker 守护进程 |

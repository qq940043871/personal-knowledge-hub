## 一、这套笔记回答什么问题

学了这么多课程，最后都要收敛到一个问题上：

> 为什么 MySQL 偏要用 B+ 树？为什么 Redis 敢用单线程？为什么 Nginx 一个 worker 能扛几万连接？为什么 JVM 要 STW？为什么 Tomcat 默认 200 个线程？

答案不在这些软件自己的文档里，而在**操作系统**和**数据结构**里。

这些软件全部跑在同一个 Linux 内核上，而内核的运行规律就像物理定律一样不可商量：

- 磁盘随机读写比顺序读写慢 100~1000 倍
- 每次上下文切换是微秒级的浪费
- fsync 是"诚实的代价"，不刷盘的数据在断电时不存在
- 一个线程 1MB 栈内存、一个文件描述符一个连接

**所谓"中间件的架构设计"，本质上是一张"对抗底层物理约束"的答卷。**
谁把约束理解得透，谁的设计就优雅、就快。

## 四、怎么读

1. 先读 01、02 两篇"定律篇"，把底层约束装进脑子；
2. 再读 03~07 五篇"答卷篇"，每篇都按 **"它面对什么约束 → 它做了什么决策 → 这个决策又带来什么新问题"** 三段式展开；
3. 然后读 08 总图，把一切挂回一张网；
4. 架构篇 09~12 视角升高：方法论（09）→ 演进（10）→ 治理（11）→ 人（12），与前 8 篇互为注脚；
5. 前端篇 13~14 把同一套追问链用在前端：浏览器是"前端的操作系统"（13），JS 用单线程+检查点+消息传递消化一致性（14）。

**一句话心法：以后再遇到"XX为什么要这么设计"的问题，先别背答案，先问一句——它在对抗哪个物理瓶颈？**

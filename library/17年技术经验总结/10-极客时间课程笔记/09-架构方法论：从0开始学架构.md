# 09 · 架构方法论：从0开始学架构

> 来源课程：《从0开始学架构》(73讲，李运华) + 《左耳听风》相关篇目
> 定位：**01~08 篇回答"一栋房子怎么盖"，本篇开始回答"整片城市怎么规划"。架构方法论是上层视角：识别复杂度 → 备选方案 → 权衡取舍。**

## 一、架构到底是指什么（课程01讲的答案）

```
系统 = 关联实体群
子系统 = 一部分关联实体
模块 = 职责单一的子子系统
组件 = 可独立替换升级的单元

架构 = 针对系统的结构设计：明确子系统/模块/组件及其关系
```

**架构设计的目的不是"画大图"，而是：用更低的成本、更快的速度，解决复杂度带来的问题。**

## 四、高可用三板斧（课程22~31讲）

```
1. CAP 定理（22/23讲）：网络分区(P)发生时，C 与 A 二选一
   → CA：单机数据库(拒绝分区)
   → CP：ZooKeeper/etcd（宁可不可用，不能不一致）
   → AP：Eureka/Redis主从+异步复制（宁可旧数据，不能不可用）
   —— 02篇选型决策树的"分布式版"
   注意细节：C 是"线性一致性"吗？课程23讲澄清：CAP 的 C 指线性一致，
   实践中大家选的往往是"最终一致 + 读写约束"，所以别把 CAP 当教条背

2. FMEA（24讲）：Failure Mode and Effects Analysis
   逐个组件问"它挂了会怎样"→ 表格化排除隐患（比事后救火便宜一百倍）
   表格五列：故障点 → 故障模式 → 影响 → 严重度 → 应对措施
   例：MySQL 主库宕机 | 无法写入 | 下单失败 | 高 | 半同步+MHA自动切换

3. 异地多活（28~30讲）：冗余的极致形态
   核心思想：把"灾备"升级成"多活"——每个机房都能独立承担业务，
            但只对核心业务做多活，非核心业务降级即可
   落地四步走（30讲）：业务分级 → 数据分类 → 数据同步 → 访问接入
```

## 五、可扩展：微服务不是银弹（课程34~37讲）

```
课程金句：微服务是"银弹 or 焦油坑"——
  ✓ 解决：团队并行、独立部署、技术异构、故障隔离
  ✗ 引入：分布式复杂性、运维复杂性、追踪复杂性、一次性成本
  什么时候上微服务：团队规模 > 两个人吃一张披萨、部署互相阻塞时
  怎么拆：基于业务逻辑拆(DDD) / 拆到什么粒度：能独立部署+小团队负责即可

微内核架构（37讲）：插件化
  核心系统只管生命周期 + 插件接口（OSGI/Eclipse/Tomcat Valve/Netty Pipeline 都是）
  —— 07篇 Tomcat 的 Pipeline-Valve 就是微内核思想在容器里的体现
```

## 六、架构设计流程（课程10~13讲）——把"感觉"变成"流程"

```
1. 识别复杂度：列出所有需求 → 标出复杂度来源 → 按优先级排序
   （"架构设计最重要的是识别主要矛盾"）
2. 设计备选方案：3 个左右差异明显、不钻牛角尖的方案
3. 评估与选择：按 360度评估(功能/性能/可用/扩展/成本) + 团队 reality check
4. 详细方案设计：把选型落到接口、数据模型、部署
```

**课程反复强调的两条原则（08讲）：**
- **合适优于业界优秀**——合适自己的团队和业务，比堆砌明星技术重要
- **简单优于复杂**——能用 Redis 解决的不要上 Kafka+ES+Flink 全家桶

## 七、和底层笔记的闭环

```
01~08篇（技术层）：约束 → 结构 → 代价
09篇（架构层）：  复杂度 → 取舍 → 流程
连接点：架构层的每一个"高性能/高可用"诉求，最终都要由
        五大软件的某个设计决策兑现，而那个决策的边界由内核决定。

例：高可用诉求 → MySQL 主从(04篇) → 复制依赖网络与fsync(01篇) →
    半同步/异步的选择 = CAP 的 C-A 折衷(本篇22讲) →
    "选CP还是AP"就是架构层给底层约束的"回签"。
```

# JVM性能调优常用命令

+ jvm内存使用情况
    - jmap -histo pid | head -n 10 查看前10位 | tail -n 10 查询后10位
    - jmap -histo pid | sort -k 2 -g -r 查看对象数最多的对象，按降序输出
    - jmap -histo pid | sort -k 3 -g -r 查看内存的对象，按降序输出
    - jmap -dump:format=b,file=heap.hprof 43939
    - jmap -heap [pid]:查看jvm空间分布

+ jstat：Java虚拟机统计工具，可以用于监视JVM各种堆和非堆内存大小和使用量
    - jstat -class pid：输出加载类的数量及所占空间信息
    - jstat -gc pid：输出gc信息，包括gc次数和时间，内存使用状况（可带时间和显示条目参数）
+ jstack
    - jstack pid jvm线程情况
+ jstat
    - jstat -gcutil 12036
+ vi
    - 显示行号 :set number
    - 跳转到最后一行 :$
    - 跳转到第一行 :1
    - 跳转到任一行 :行号 $表示跳转到行尾

下面给你一份 **Arthas 快速入门指南（面向生产可用）**，目标是：**5–10 分钟内用 Arthas 定位 JVM 线上问题**，不走弯路。

## 一、Arthas 是什么（一句话定位）
**Arthas = 线上 JVM 实时诊断工具**
无需重启 JVM，可动态查看：

+ 线程状态 / 死锁
+ 方法调用链与耗时
+ 异常抛出点
+ 类加载、字节码
+ JVM 内存 / GC 情况

非常适合：
**JVM 卡死、接口慢、CPU 飙高、无日志问题**

---

## 二、快速启动（3 种常用方式）
### 方式一：官方脚本（最常用）
```bash
curl -O https://arthas.aliyun.com/arthas-boot.jar
java -jar arthas-boot.jar
```

自动：

+ 列出所有 Java 进程
+ 选择 PID 即可 attach

---

### 方式二：已知 PID（生产推荐）
```bash
java -jar arthas-boot.jar <pid>
```

---

### 方式三：Docker / K8s
```bash
java -jar arthas-boot.jar --pid <pid>
```

---

## 三、启动后第一件事（必做）
```bash
dashboard
```

你会立即看到：

+ CPU / 内存 / GC
+ 线程总数
+ 类加载数量
+ 系统负载

👉 **如果 dashboard 卡顿或无输出**
→ JVM 已严重异常（IO / Native / 死锁）

## 四、最常用 10 个核心命令（掌握这 10 个就够）
### 1️⃣ 查看最忙线程（定位 CPU 问题）
```bash
thread -n 5
```

输出：

+ CPU 占用最高的线程
+ 直接给出 Java 栈

---

### 2️⃣ 按线程 ID 看栈
```bash
thread <tid>
```

适合：

+ `top -Hp` 找到线程
+ 转成 16 进制后查看

---

### 3️⃣ 查看死锁
```bash
thread -b
```

---

### 4️⃣ 查看方法实时耗时（**线上神器**）
```bash
trace com.xxx.service.OrderService createOrder
```

会显示：

+ 方法调用链
+ 每一层耗时

⚠️ 默认采样，开销可控

---

### 5️⃣ 统计方法调用（不看调用链）
```bash
monitor com.xxx.service.OrderService createOrder
```

输出：

+ 调用次数
+ 平均 / 最大耗时
+ QPS

---

### 6️⃣ 打印方法参数 / 返回值（慎用）
```bash
watch com.xxx.service.OrderService createOrder "{params, returnObj}" -x 2
```

⚠️ 建议：

+ 限定条件
+ 短时间使用

---

### 7️⃣ 查找类是否被加载
```bash
sc -d com.xxx.OrderService
```

---

### 8️⃣ 反编译正在运行的类
```bash
jad com.xxx.OrderService
```

👉 **确认线上代码是否与你认为的一致**

---

### 9️⃣ 查看 JVM 内存 / GC
```bash
jvm
```

```bash
memory
```

---

### 🔟 查看异常抛出（极难排查的问题）
```bash
watch java.lang.Exception "<init>" "{throwExp}" -n 5
```

## 五、3 个典型场景的“标准打法”
---

### 场景 1：接口慢 / 偶发超时
**步骤：**

1. `dashboard`
2. `thread -n 5`
3. `trace 接口入口方法`
4. 找到耗时最长的调用

**常见结论：**

+ 下游 HTTP / DB 阻塞
+ synchronized 锁
+ 线程池耗尽

---

### 场景 2：CPU 飙高
**步骤：**

1. `thread -n 10`
2. 定位 top 线程
3. 查看是否：
    - while(true)
    - JSON 序列化
    - 正则 / stream

---

### 场景 3：JVM 看起来“假死”
**步骤：**

1. `dashboard` 是否刷新
2. `thread -b`
3. `thread -n 5`
4. 如果 Arthas 也无响应
→ 已进入 OS / Native 层（需 strace）

## 六、线上使用的 5 条“铁律”
1. **不要长时间 watch 大对象**
2. **trace 优先于 watch**
3. **及时 stop / quit**
4. **避免 trace 高频基础方法**
5. **问题定位后立刻退出**

退出：

```bash
quit
```

当你已经确认 `top`** 中 Java 进程 CPU 100%**，同时 **Arthas / jstack 无响应**，这说明你遇到的是 **“CPU 忙死型 JVM 失控”**，而不是 IO 阻塞型。

## 一、先定性：CPU 100% + jstack 无响应，意味着什么？
这是一个**非常明确的信号组合**：

| 现象 | 结论 |
| --- | --- |
| Java 进程 CPU 100% | 有线程在 **持续占用 CPU** |
| jstack / Arthas attach 失败 | JVM **无法进入 Safepoint** |
| 接口无响应 | 工作线程被完全饿死 |

👉 **Safepoint 进不去 = JVM 控制权被“霸占”**
👉 霸占者通常是：

1. **无限循环 / 自旋**
2. **GC 线程异常自旋**
3. **JNI / Unsafe / 压缩解压死循环**
4. **JIT / HotSpot Bug**

---

## 二、第一黄金动作：锁定“是哪一个线程吃满 CPU”
### 1️⃣ 用 top 精确到线程
```bash
top -Hp <pid>
```

重点关注：

+ **%CPU 接近 100 的线程**
+ 记录该线程的 **TID（十进制）**

例如：

```plain
PID     TID     %CPU
12345   12399   99.8
```

---

### 2️⃣ 把 TID 转成 16 进制（极关键）
```bash
printf "%x\n" 12399
```

假设得到：

```plain
0x307f
```

---

## 三、尝试最后一次“Java 级取证”（成功率 < 50%）
即便 jstack 常规方式卡死，也**必须试以下两种**：

### 1️⃣ 强制信号栈（比 jstack 成功率高）
```bash
kill -3 <pid>
```

如果**任何地方**（catalina.out / stdout）出现线程栈：

+ 搜索 `nid=0x307f`
+ 看该线程在干什么

👉 如果成功，你已经赢了。

---

### 2️⃣ jstack + 超时（防止一直卡）
```bash
timeout 5 jstack <pid>
```

哪怕只打印 **一部分线程**，也够定性。

---

## 四、如果 Java 栈依然完全拿不到（常见）
这时 **100% CPU 的问题已经不在 Java 层可控范围内**，必须立刻切换到 **Native 视角**。

---

## 五、Native 级定位（这是关键分水岭）
### 1️⃣ strace 看“CPU 在忙什么”
```bash
strace -tt -p <pid>
```

你会看到两种典型模式之一：

---

### 模式 A：疯狂刷某个系统调用（最常见）
例如不断重复：

```latex
futex(...)
futex(...)
futex(...)
```

或：

```latex
clock_gettime(...)
```

结论：

+ **自旋锁 / HotSpot bug / JIT 问题**
+ JVM 已无法调度 Safepoint

---

### 模式 B：几乎没有系统调用
strace 输出极少，甚至“假死”

结论：

+ **纯用户态死循环**
+ while(true)
+ 数学运算
+ 压缩 / 编码 / hash 计算

👉 这种情况下 **jstack 永远进不去**

---

## 六、此场景下最常见的 6 个“真凶”
按生产概率排序：

### 1️⃣ 代码级死循环（最高频）
```java
while (true) {
    // 无 sleep / 无阻塞
}
```

包括：

+ 自旋 CAS
+ 错误的重试逻辑
+ Stream / Iterator bug

---

### 2️⃣ GC 线程异常自旋
特征：

+ CPU 100%
+ 内存看似正常
+ GC 日志停止

常见于：

+ CMS / G1 老版本
+ 内存碎片严重

---

### 3️⃣ JNI / Unsafe 死循环
特征：

+ jstack 完全失败
+ CPU 极高
+ core dump 可见 libc

---

### 4️⃣ JIT / HotSpot Bug（你是高风险）
你之前已经出现：

+ SIGBUS
+ JDK7 → JDK8 仍复现

这类问题：

+ **完全绕过 Java 栈**
+ 只能通过升级 JDK / 关闭优化规避

---

### 5️⃣ 正则 / JSON / 压缩算法退化
例如：

+ 灾难性回溯正则
+ 特殊 JSON 数据触发 O(n²)

---

### 6️⃣ 自定义锁 / 高并发下错误同步
---

## 七、生产环境的“正确处置策略”（非常重要）
必须说一句实话：

> **当 CPU 100% + jstack / Arthas 失效时，这个 JVM 已经不可在线修复。**
>

### 正确流程是：
1. **立即摘流量**
2. **记录证据**

```bash
top -Hp <pid>
strace -tt -p <pid> > strace.log
```

3. **kill -9 重启**
4. **事后复盘**

继续“抢救”只会：

+ 延长不可用时间
+ 放大事故

---

## 八、如果你想“彻底搞清楚根因”（进阶）
### 生成 core dump（终极）
```bash
gcore <pid>
```

或：

```bash
kill -SIGABRT <pid>
```

然后：

```bash
gdb java core.*
bt
```

你会清楚看到：

+ 卡在 JVM 哪个 native 函数
+ 是否 JIT / GC / libc

---

你现在只需要贴 **一个信息**（脱敏）：

+ `top -Hp <pid>` 中 **CPU 100% 的那一行**
+ 或 `strace` 中 **反复出现的系统调用**

我可以直接给你一句结论式判断：

> **“这是代码死循环 / GC 自旋 / JNI 问题 / HotSpot Bug”，以及“是否值得继续追查”。**
>

这一类问题，判断比“修”更重要。

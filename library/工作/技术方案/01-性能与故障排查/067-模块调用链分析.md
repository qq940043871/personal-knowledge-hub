# 模块调用链分析

异构系统（多语言、多协议、遗留/第三方、跨云）的调用链分析，核心是 **统一标准 + 全链路埋点 + 上下文透传 + 存储可视化 + 根因分析**。下面给你一套**完整、可落地、企业级**的技术方案。

---

## 一、异构系统调用链的核心痛点
+ 技术栈杂：Java/Go/Python/PHP/.NET/C++ 混部
+ 协议杂：HTTP/Dubbo/gRPC/webservice/MQ/DB/Redis/第三方API
+ 无统一标识：日志分散、无法串联
+ 调用关系黑盒：不知道谁调谁、依赖深度、瓶颈在哪
+ 排错极慢：出问题要翻N个系统日志，半天定位不到

**目标**：
一次请求 → 一条 Trace → 全链路可见 → 快速定位慢/错/异常

---

## 二、整体技术方案（标准+架构+流程）
### 2.1 统一标准：OpenTelemetry（必选）
**CNCF 官方标准**，替代旧的 OpenTracing、Jaeger、Zipkin 私有协议。

+ 统一数据模型：Trace/Span/Attribute/Event/Link
+ 统一传输：**OTLP 协议**（gRPC/HTTP）
+ 多语言自动埋点：Java/Go/Python/NodeJS/.NET/PHP/C++
+ 兼容老系统：支持接收 SkyWalking/Zipkin/Jaeger 数据

### 2.2 核心概念（必须懂）
+ **TraceId**：全局唯一ID，一次请求全程不变
+ **SpanId**：每个服务/组件一个Span，标识一段执行
+ **ParentSpanId**：父子调用关系
+ **Attributes**：标签（接口名、IP、状态、耗时、业务ID）
+ **Events**：关键事件（异常、SQL、MQ发送）
+ **Context Propagation**：上下文透传（HTTP头/RPC头/MQ头）

### 2.3 整体架构（可直接落地）
```plain
客户端/网关 → 业务服务（多语言）→ DB/MQ/第三方/遗留系统
    ↓（埋点采集）
OpenTelemetry Collector（统一转发）
    ↓
存储（ES/ClickHouse/Cassandra）
    ↓
可视化平台（Jaeger/SkyWalking/SigNoz/自建）
    ↓
告警/分析/拓扑/慢调用诊断
```

### 2.4 调用链生命周期
1. **入口生成 TraceId**（网关/入口服务）
2. **上下文透传**（所有调用都带 Trace/Span）
3. **各端生成 Span**（服务/DB/MQ/HTTP客户端）
4. **异步上报**到 Collector
5. **存储与索引**
6. **可视化与分析**

## 三、分模块落地方案（最关键）
### 3.1 采集层：多语言埋点方案
#### 3.1.1 Java 服务（最成熟）
+ **无侵入**：Javaagent 自动埋点

```shell
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=order-service \
     -Dotel.exporter.otlp.endpoint=http://collector:4317 \
     -jar app.jar
```

+ 自动支持：Spring Boot/Spring Cloud/Dubbo/MyBatis/Redis/Kafka

#### 3.1.2 Go 服务
+ SDK 手动/半自动埋点

```go
import "go.opentelemetry.io/otel"
// 初始化Tracer
tracer := otel.Tracer("payment-service")
// 启动Span
ctx, span := tracer.Start(ctx, "createOrder")
defer span.End()
// HTTP调用自动透传
req, _ := http.NewRequestWithContext(ctx, "GET", url)
```

#### 3.1.3 Python 服务
```python
from opentelemetry import trace
tracer = trace.get_tracer(__name__)
with tracer.start_as_current_span("query_goods"):
    # 业务逻辑
```

#### 3.1.4 遗留/闭源/第三方系统
+ **Sidecar 模式**（Envoy）：流量劫持透传 Trace
+ **API网关统一注入**：所有入站流量统一加 Trace
+ **日志正则提取**：老系统只打日志，用 Filebeat+OTEL 采集
+ **数据库/中间件**：使用代理或驱动插件采集

### 3.2 上下文透传（跨协议全覆盖）
+ **HTTP**：Header 带 `traceparent`（W3C标准）

```plain
traceparent: 00-TraceId-ParentSpanId-01
```

+ **Dubbo/gRPC**：Metadata 透传
+ **MQ（Kafka/RocketMQ）**：消息 Header 携带
+ **线程/异步**：跨线程传递 Context（必须处理）
+ **定时任务/批任务**：手动生成 Trace，标记为后台任务

### 3.3 传输层：OpenTelemetry Collector
+ 统一接收：OTLP/Zipkin/SkyWalking/Jaeger
+ 处理：过滤/清洗/采样/路由
+ 输出：ES/ClickHouse/Jaeger/Kafka
+ 部署：独立集群/sidecar

### 3.4 存储层（选型）
+ **小集群**：Jaeger + Cassandra/ES
+ **中大规模**：ClickHouse（性能最好）
+ **企业级**：SkyWalking OAP + H2/MySQL/ES

### 3.5 可视化与分析平台（推荐）
1. **Jaeger**：轻量、开源、适合开发调试
2. **SkyWalking**：国产、拓扑强、支持多语言、适合生产
3. **SigNoz**：全链路（Metrics+Tracing+Logs）、开源新贵
4. **阿里云/腾讯云 APM**：云厂商托管，省心

## 四、异构场景特殊处理（你最需要）
### 4.1 跨语言调用（Java→Go→Python）
+ 统一用 **W3C traceparent** 头
+ 所有语言 SDK 都支持此格式
+ 自动关联父子Span，无断链

### 4.2 异步/MQ 调用（最容易断链）
+ 发送方：把 Context 序列化到消息头
+ 消费方：从消息头提取 Context 恢复 Span
+ 示例（伪代码）：

```plain
发送：msg.setHeader("traceparent", traceparentStr)
消费：extract context from header → start consumer span
```

### 4.3 第三方/外部API调用
+ 手动创建 Span
+ 标记 `peer.service` 为第三方名称
+ 记录 URL/耗时/状态码

### 4.4 数据库/缓存调用
+ 自动采集：JDBC/Redis/Mongo 插件
+ 记录：SQL语句、耗时、行数、错误

### 4.5 服务内部多线程/异步
+ 必须传递 Context
    - Java：RequestContextExecutor
    - Go：context.Context
    - Python：contextvars

## 五、调用链分析核心能力（落地价值）
### 5.1 服务拓扑图
+ 自动生成：服务→服务调用关系
+ 流量、耗时、错误率可视化
+ 识别强依赖、循环依赖、孤岛服务

### 5.2 全链路查询
+ 按 TraceId 查询
+ 按业务ID（订单号/用户ID）关联查询
+ 按服务/接口/耗时/错误状态筛选

### 5.3 慢调用分析
+ 查看每段 Span 耗时
+ 定位：哪一跳、哪个接口、哪行代码最慢
+ 识别：长SQL、慢第三方、阻塞调用

### 5.4 异常链路分析
+ 错误链路自动标红
+ 查看异常栈、错误信息、发生节点
+ 快速定位：是A系统还是B系统抛出

### 5.5 依赖影响分析
+ 某服务宕机/延迟，影响哪些上游下游
+ 变更影响范围评估

## 六、可落地实施步骤（3阶段）
### 阶段1：底座搭建（1-2周）
1. 部署 OTel Collector + 存储（Jaeger/SkyWalking）
2. 网关接入：生成 TraceId，统一透传
3. 核心Java服务无侵入接入（agent）

### 阶段2：全覆盖接入（2-4周）
1. Go/Python/Node 服务接入 SDK
2. MQ/异步/线程上下文透传改造
3. DB/缓存/第三方调用采集
4. 老系统：日志提取或Sidecar

### 阶段3：分析与优化（持续）
1. 搭建可视化大盘
2. 配置慢调用/异常告警
3. 梳理拓扑、优化不合理调用
4. 定位线上问题，验证效果

## 七、关键规范（必须定）
1. **服务名规范**：`业务域-服务名`（如 trade-order-service）
2. **Attributes 规范**：必须带 `biz_order_id`/`user_id` 等业务标签
3. **采样策略**：生产 1% 全量采样，测试 100%
4. **日志关联**：所有日志必须打印 TraceId

```plain
log.info("[TraceId:{}] 订单创建成功: {}", TraceId, orderId)
```

5. **禁止**：手动硬编码 TraceId，统一用 SDK

## 八、效果验收
+ 一次请求全链路可见，**无断链**
+ 多语言/多协议调用**完整串联**
+ 问题定位从小时级 → **分钟级**
+ 服务依赖清晰，架构可观测
+ 线上故障快速定界：谁的问题、哪段代码

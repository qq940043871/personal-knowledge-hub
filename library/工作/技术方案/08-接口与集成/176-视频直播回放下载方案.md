# 🏗️ 视频全链路技术方案白皮书
## 一、整体架构设计
### 1. 系统拓扑图
```latex
[NVR] (海康/大华)
   ↓  ↑
[FFmpeg] (拉流/转封装)
   ↓
[ZLMediaKit (ZLM)] (流媒体中间件：自动转协议/HLS切片)
   ↓  ↓  ↓
[ZLM4J] (Java后台API控制)
   ↓  ↓
[前端应用] (PC/手机/大屏)
   ↓
[下载服务] (异步分片/合并)
```

### 2. 技术选型 rationale
| 模块 | 选型 | 优势 |
| :--- | :--- | :--- |
| **流媒体中间件** | **ZLMediaKit** | 轻量级、高性能、原生支持HLS/FLV/WebRTC，ZLM4J封装完善 |
| **拉流/转码** | **FFmpeg** | 通用音视频处理库，支持`copy`纯复制模式，极低CPU消耗 |
| **后台框架** | **SpringBoot + ZLM4J** | 快速开发，ZLM4J提供简化的ZLM操作API |
| **协议转换** | ZLM内置 | 自动将RTSP/RTMP转为HLS(手机)/FLV(PC)/WebRTC(低延迟) |
| **下载存储** | 本地文件系统 | 直接对接NVR源，避免二次转码损耗 |

## 二、核心功能实现方案
### 1. 视频直播与实时回放（Live Playback）
**目标**：拉取NVR历史流，转码为HLS/FLV，实现PC/手机秒开播放。

#### **实现步骤**
1. **FFmpeg 拉取海康/大华 RTSP 回放流**
    - **海康**：`rtsp://user:pwd@ip:554/Streaming/Channels/102?starttime=...`
    - **大华**：`rtsp://user:pwd@ip:554/cam/playback?channel=1&subtype=1&starttime=...`
    - _参数说明_：使用`102/subtype=1`子码流拉取，降低带宽和CPU压力。
2. **FFmpeg 推流至 ZLM (RTMP)**

```bash
ffmpeg -rtsp_transport tcp -i "源RTSP地址" \
  -c:v copy -c:a copy \  # 关键：不转码，纯复制
  -f flv "rtmp://zlm-ip:1935/live/stream_id"
```

3. **ZLM 自动转协议**
    - ZLM 收到 RTMP 后，自动生成多种协议地址：
        * **PC 端**：`http://zlm-ip:8080/live/stream_id.flv` (低延迟)
        * **手机/网页**：`http://zlm-ip:8080/live/stream_id.m3u8` (全平台兼容)
        * **低延迟**：`webrtc://zlm-ip/live/stream_id`

#### **关键配置 (ZLM config.ini)**
为了解决拖动时文件不存在问题，重点调整 HLS 参数：

```properties
[hls]
segDur=5           # 切片时长5秒
segNum=60          # 索引保留60个切片 (可拖动5分钟)
segRetain=60       # 磁盘保留60个切片
deleteDelaySec=300 # 切片延迟300秒(5分钟)删除
```

### 2. 交互控制（快进/快退/拖动）
**目标**：在不重新构建架构的前提下，实现进度条拖动与倍速播放。

#### **实现方案**
1. **倍速播放 (前端控制)**
    - 在前端播放器（如 hls.js、Video.js）中直接设置 `playbackRate`。
    - _无需后端干预_，纯前端操作，CPU 零消耗。
2. **进度条拖动 (核心逻辑)**
    - **原理**：HLS 索引文件包含时间范围，前端拖动时间点 -> 后端生成新的 FFmpeg 进程 -> ZLM 推新流。
    - **操作流程**：
        1. 前端触发拖动，获取目标时间戳。
        2. 后端停止旧的 FFmpeg 进程（关闭旧流）。
        3. 启动新的 FFmpeg 进程，带入新的 `starttime` 参数。
        4. 前端刷新播放地址。
    - _优化_：使用 ZLM4J 管理流生命周期，快速切换。

### 3. 视频下载（大文件安全下载）
**目标**：解决单次下载体积过大导致的服务器阻塞、NVR 过载、进程卡死问题。

#### **核心问题**
+ 1小时 4Mbps 码流 ≈ 1.8GB，单进程占用过高。
+ NVR 并发回放限制。
+ HTTP 接口超时。

#### **实现方案：分片下载 + 后台异步 + 自动合并**
1. **任务提交 (异步)**
    - 后端接收到下载请求后，**立即返回任务ID**，不等待下载完成。
    - 使用 `ThreadPoolExecutor` 限制**最大并发下载数**（如3路），保护服务器。
2. **分片下载 (FFmpeg segment)**
    - 将大任务拆分为 10分钟/段 的小任务。
    - 命令示例：

```bash
ffmpeg -i "源地址" -c copy \
  -f segment -segment_time 600 \ # 600秒=10分钟
  -reset_timestamps 1 \
  /download/task_id/part_%03d.mp4
```

3. **自动合并 (FFmpeg concat)**
    - 所有分片下载完成后，生成 `filelist.txt` 清单。
    - 执行合并命令（copy 模式，秒级完成）：

```bash
ffmpeg -f concat -safe 0 -i filelist.txt -c copy full.mp4
```

4. **进度查询**
    - 前端定时轮询接口，查询本地文件大小与总预估大小，计算进度。

## 三、遇到的问题与解决方案
### 问题 1：HLS 播放时提示 "文件不存在 (404)"
+ **原因**：ZLM 默认切片保留时间短（约10秒），拖动进度条时，旧切片已被删除。
+ **解决方案**：
    - 调整 `config.ini` 中的 `segNum` 和 `deleteDelaySec`，将切片保留时长延长至 **5-10分钟**。
    - 重推流并重启 ZLM 服务。

### 问题 2：服务器 CPU 占用过高（10路就卡）
+ **原因**：错误地在服务器端进行解码或转码。
+ **解决方案**：
    - **纯转发架构**：FFmpeg 使用 `-c:v copy` 纯复制模式，不解码。
    - **多画面子码流**：9/16宫格播放时，统一拉取子码流（`102/subtype=1`），带宽和CPU降低80%。
    - **单画面高清**：双击放大时再切换主码流。

### 问题 3：大文件下载导致服务器/数据库超时
+ **原因**：HTTP 请求长时间等待下载完成，或单进程下载过大文件。
+ **解决方案**：
    - **异步化**：下载任务丢给后台线程池，HTTP接口立即返回。
    - **分片策略**：使用 `-segment` 参数拆分下载，单分片失败不影响整体。
    - **合并策略**：最后用 FFmpeg concat 合并，避免大文件拷贝耗时。

### 问题 4：NVR 并发回放限制（下载/播放超限）
+ **原因**：海康/大华NVR对同时回放的路数有硬件限制（如4盘位NVR通常限32路）。
+ **解决方案**：
    - **ZLM 单源多播**：NVR 只出一路流，ZLM 转发给无数个前端用户。
    - **下载降权**：下载任务使用专用线程池，优先级低于播放，避免NVR被下载打满。

### 问题 5：PC 端无法播放 m3u8
+ **原因**：PC 浏览器原生 HLS 支持有限（主要是 Safari）。
+ **解决方案**：
    - **前端自适应**：使用 `hls.js` 库，PC 浏览器自动加载 hls.js 播放 m3u8，原生支持则直接播放。
    - **多协议供给**：ZLM 同时提供 FLV 和 HLS 地址，PC 优先播 FLV，手机优先播 HLS。

### 问题 6：海康与大华 RTSP 地址格式不统一
+ **原因**：不同厂商的回放URL参数、通道编号规则不同。
+ **解决方案**：
    - **抽象适配层**：在 Java 代码中封装 `HikPlaybackUtil` 和 `DahuaPlaybackUtil`，统一对外暴露 `startPlayback(startTime, endTime)` 方法。
    - **命令模板**：准备两套 FFmpeg 命令模板，自动填充对应参数。

## 四、最终推荐架构总结
1. **播放层**：
    - **多画面**：拉子码流 -> ZLM转HLS -> 手机/PC 播 HLS。
    - **单画面**：拉主码流 -> ZLM转FLV/WebRTC -> 低延迟播放。
2. **下载层**：
    - 接收请求 -> 后台线程池 -> 分片下载(10min/段) -> 自动合并 -> 生成MP4。
3. **稳定性保障**：
    - 限制并发下载数。
    - 延长 HLS 切片保留时间。
    - 全程不解码（copy 模式）。

这套方案是目前安防行业**最稳、最轻、兼容性最好**的落地架构，你可以直接以此为基础进行开发上线。

# B2B大宗商品交易与履约系统设计蓝图

这是一份为你量身定制的**《B2B大宗商品交易与履约系统架构设计蓝图》**。

基于我们之前的深度探讨，我将整个系统的核心思想、数据模型、业务流转和技术实现进行了系统性的梳理与收敛。你可以直接将这份总结作为**系统架构设计文档（HLD）**的核心骨架向团队宣发。

---

## 一、 核心架构思想（系统灵魂）
1. **分离“契约”与“履约”：** 合同只记录商业约定（买什么、多少钱、什么规则），具体的交收动作全部交由“履约域”独立处理。
2. **底层万物皆“1对N”，顶层控制“自由”与“顺序”：**
    - 彻底废除单张表、单线程的状态机流转模式。
    - 物理表结构完全统一（支持无限拆分发货、打款）；通过在代码控制层引入“前置规则拦截器”，来决定当前是自由交收还是强管控顺序交收。
3. **极简场景只是复杂场景的特例（N=1）：** 面对“一次打款、一次发货”的极简需求，底层复杂表结构坚决不改，通过“后端自动生成 + 前端视图压扁”来向用户提供极简体验。

---

## 二、 核心数据模型（三级树状表结构）
系统的数据存储必须严格遵循**“主合同 -> 履约计划 -> 明细业务单”**的三级结构：

+ **第一级：主合同 (**`contract_main`**)**
    - **职责：** 统管全局，定义总金额、总吨数、交收模式、结算基准、合理磅差率、开票保证金比例等。
    - **进度冗余：** 汇总所有批次的累计已付款、已发货、已收货、已开票金额（用于宏观看板）。
+ **第二级：履约计划/批次 (**`fulfillment_plan`**)**
    - **职责：** 承上启下，解决“1000吨拆成两个500吨，分期交货和作价”的问题。
    - **属性：** 本批次目标吨数、锁定单价、本批次资金池与物流进度。
+ **第三级：执行明细单（挂靠在 Plan 之下，彼此独立又联动）**
    - 💰 **资金单 (**`payment_order`**)：** 记录买方的每一次打款/冻结流水。
    - 🚛 **发货单 (**`shipment_order`**)：** 记录卖方的每一次派车/派船。
    - ⚖️ **收货结算单 (**`receipt_order`**)：** 记录买方针对_特定发货单_的过磅、质检与最终应付结算金额。
    - 🧾 **发票单 (**`invoice_order`**)：** 关联一张或多张_收货结算单_开具的税务发票。

## 三、 关键业务动作的“靶向”映射（防扯皮指南）
在系统中，用户的操作目标必须精准指向确定的底层单据，绝不能对着主合同乱点：

1. **收货动作：** 必须针对具体的**发货单**（解决多车发货中，某车货损、某车涨吨、某车拒收的问题）。
2. **收款/财务核款：** 必须针对具体的**资金单/打款凭证**（解决资金池对账、线下打款滞后、金额合并或拆分的问题）。
3. **开票动作：** 必须针对具体的**收货结算单**（因为收货单才有最终扣罚后的准确金额，对着发货单开票必错）。

## 四、 必须建设的核心引擎与机制
为了让这套多单据系统运转流畅，你需要开发以下几个底层引擎：

### 1. 资金核销与冻结引擎 (Fund Clearing Engine)
+ **担保交易模式：** 买方打款 -> 资金单变为 `FROZEN`（冻结） -> 解锁卖方发货 -> 收货结算单产生 -> 触发资金解冻，自动打给卖方。
+ **开票保证金模式：** 根据合同约定，将尾款（如10%）强制扣留在卖方虚拟账户的“冻结余额”中，直到买方点击“确认收票”才解冻。
+ **财务核销机制：** 卖方人工确认收到 100 万后，系统自动拿着这 100 万去“填平”该批次下尚未付款的收货结算单。

### 2. 结算规则引擎 (Settlement Rule Engine)
+ 应对大宗商品**“发货100吨，收货101吨”**的常态。
+ 在收货结算单中，分离“物理发货重量”、“物理收货重量”和“财务结算重量”。
+ 系统根据主合同配置的规则（收货磅准 / 发货磅准 / 孰低原则），配合“合理磅差审批流”，自动计算最终结算金额。

### 3. 统一留痕与日志组件 (Audit & Log Component)
+ **搜索与查询留痕：** AOP 无侵入拦截 -> 发送 JSON 到 MQ -> 落入 Elasticsearch/ClickHouse（用于防爬虫风控和商机挖掘）。
+ **业务操作轨迹：** 基于 AOP + SpEL（Spring表达式），结合对象 Diff 比对，生成人类可读的时间轴日志（如：“_张三修改了发货单，重量从100吨变为98吨_”），作为交易仲裁的铁证。

## 五、 微服务/模块交互架构图 (事件驱动 EDA)
系统内部彻底解耦，绝不互相直接改表，全部通过 MQ 事件（如 Kafka/RocketMQ）驱动：

```latex
[ 操作入口 ] 前端点击 "确认收货" / "支付成功" / "确认收票"
      │
[ 领域服务 ] 业务微服务产生单据状态变更，并对外抛出 标准领域事件
      │      (例如: ReceiptConfirmedEvent, PaymentFrozenEvent, InvoiceConfirmedEvent)
      ▼
[ 事件总线 ] MQ (消息队列)
      │
      ├──▶ [履约监控引擎] 监听事件 -> 累加 Plan 和 合同 的进度 -> 判断是否完结。
      ├──▶ [状态机拦截器] 监听事件 -> 解锁下一步操作 (如: 监听到定金冻结事件，放开发货按钮)。
      ├──▶ [资金结算中心] 监听事件 -> 执行资金的冻结、解冻、核销对账。
      └──▶ [业务日志服务] 监听事件 -> 解析 SpEL 模板 -> 记录带有时间轴的操作轨迹。
```

## 寄语
设计大宗B2B系统就像设计一个**“金融级的沙盒”**。
****不要试图用代码去规定企业必须以什么姿势做生意（因为现实总会有线下特批、分批发货、溢短装），而是要**提供一套足够坚固的账本（资金流水、物流明细、票务映射）**，让买卖双方在这个沙盒里不管怎么折腾，最终的**钱、货、票账目永远能平**。

只要严格贯彻上述架构蓝图，你的系统不仅能完美解决客户当下的需求，未来哪怕接入供应链金融（仓单质押）、多式联运、或是千万吨级的复杂长协合同，底层核心代码都可以做到**稳如磐石、毫不修改**。祝你开发顺利！

# 参数场景爆炸问题

现在目前我还遇到一个比较严重的问题，就是目前系统内的参数太多，然后参数组合的场景太多。是因为是做一个产品，它经常会出现给A客户开发一个功能，但是由于不兼容，需要增加一个参数。然后这个参数有没有就是做一定的限制，说是给A客户的，就导致等到B客户在某种场景下使用这个参数时候。出现了这种组合爆炸，出现危机，对客户和老板的感觉都是系统不稳定，都是问题

你现在遇到的，**不是技术问题，是产品架构 + 权限模型 + 配置体系的“中年病”**，而且病得非常典型：

> 为每个客户加开关 → 开关越来越多 → 组合爆炸 → 到处是坑 → 上线就出问题 → 老板觉得系统不稳定
>

**90% 做 TOB 产品、做平台化的公司，全都会死在这一关。**

我直接给你一套**能根治、可落地、行业通用的平台化参数治理方案**，用上之后，再也不会出现“客户一多系统就乱”。

---

## 核心一句话根治方案
### **把“到处加开关”升级为：平台 + 能力集 + 客户套餐 + 场景规则**
不让参数乱飞，而是**把能力打包，按客户授权使用**。

---

## 一、先把你们现在的坏模式说清楚
你们现在是：

1. A 客户要特殊逻辑 → 加参数 `enable_a_feature`
2. B 客户要另一个逻辑 → 加参数 `enable_b_logic`
3. C 客户要特殊流程 → 再加 `switch_c_process`
4. 代码里全是：

```java
if (enableA && enableB && !enableC) {
    // 分支1
} else if (!enableA && enableB) {
    // 分支2
} else ...
```

5. 客户越多，if 嵌套越恐怖
6. 测试测不过来，上线必出问题
7. 老板看到处是 bug，认为系统不稳定

**这就叫“配置驱动屎山”。**

---

## 二、正确模式：平台化三层架构（行业标准）
### 第一层：平台底座（所有客户共用）
+ 核心流程、核心表结构、核心服务
+ **不允许出现任何客户特有的逻辑**
+ 稳定、不随便动

### 第二层：能力集（Capability Set）
把所有“开关、参数、特殊逻辑”**打包成一个个能力**，例如：

+ 支持预付款
+ 支持分期支付
+ 支持多级审批
+ 支持短信通知
+ 支持自动开票
+ 支持特殊合同格式
+ 允许自定义交收流程
+ 允许超期自动取消

**一个能力 = 一组参数 + 一段行为 + 约束规则**

### 第三层：客户套餐（Customer Package）
给每个客户开“套餐”，而不是开一堆开关：

+ 基础版
+ 高级版
+ 企业版
+ 专属定制版

**套餐 = 若干个能力的集合**

客户只能使用套餐里的能力，**不能随便开某个野参数**。

---

## 三、参数不再挂在客户上，而是挂在“能力”上
### 坏结构（你们现在）
```plain
客户
├─ enable_xxx
├─ enable_yyy
├─ switch_zzz
└─ flag_aaa
```

### 好结构（平台化）
```plain
客户
└─ 套餐 ID
   └─ 能力集列表
      └─ 能力1（含一组受控参数）
      └─ 能力2（含一组受控参数）
      └─ 能力3（含一组受控参数）
```

**参数不能乱跑，必须属于某个能力。**

---

## 四、再加一层：场景规则（Scene Rule）
同一个能力，在不同场景表现不一样，**不要加参数，要加场景规则**。

例如：

+ 下单场景
+ 合同履约场景
+ 售后场景
+ 支付场景
+ 开票场景

每个场景可以独立配置：

+ 是否触发消息
+ 是否走审批
+ 是否自动开票
+ 支付方式限制

**场景内统一管理，不会乱。**

---

## 五、这样一改，你们所有问题瞬间消失
### 1）不会出现组合爆炸
+ 能力之间是**兼容设计**的
+ 不会出现 A 开了 B 炸了
+ 测试只测能力组合，不测客户

### 2）新客户接入极快
直接开套餐，不需要加代码、加开关。

### 3）系统稳定性大幅提升
+ 核心底座不动
+ 能力可灰度、可降级
+ 不会因为一个客户改坏整个平台

### 4）老板再也不会觉得系统到处是问题
因为：

+ 稳定是底座保证
+ 个性化是能力保证
+ 客户之间完全隔离
+ 出问题只回滚某个能力，不影响全局

## 六、我给你一套可直接落地的表结构（复制即用）
### 1. 能力表（sys_capability）
+ id
+ code（唯一标识：ADVANCE_PAY、AUTO_INVOICE）
+ name
+ status
+ remark

### 2. 能力参数表（sys_capability_param）
+ id
+ capability_code
+ param_key
+ param_value_default
+ value_type（int/string/bool）
+ is_visible（是否允许客户配置）

### 3. 套餐表（sys_package）
+ id
+ code
+ name
+ capability_ids

### 4. 客户套餐表（customer_package）
+ customer_id
+ package_id

### 5. 客户参数覆盖表（customer_param_override）
+ customer_id
+ capability_code
+ param_key
+ param_value

**结构干净、可扩展、不会乱。**

---

## 七、代码层面怎么写？（彻底消灭 if 嵌套）
### 以前
```java
if (enableXxx && enableYyy || !enableZzz) {
}
```

### 现在
```java
// 获取客户开通的能力
boolean hasAdvancePay = capabilityService.hasCapability(customerId, "ADVANCE_PAY");

// 获取参数
Integer days = capabilityService.getParam(customerId, "AUTO_CANCEL", "expire_days");
```

**没有组合、没有爆炸、没有屎山。**

## 八、最终效果（你可以跟老板汇报）
1. **平台化架构**：底座稳定，个性化通过能力扩展

3. **客户隔离**：不同客户使用不同套餐，互不影响
4. **测试成本大幅下降**：测能力不测客户
5. **上线稳定**：不会因为一个客户改动导致全局问题
6. **可规模化**：接 100 个客户也不会越来越乱

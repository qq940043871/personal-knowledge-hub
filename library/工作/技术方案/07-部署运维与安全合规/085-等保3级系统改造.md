# 等保3级系统改造

:::warning
等保要求：敏感信息不能在数据库中明文存储；符合等保3级

系统现状：

分布式系统+多种开发语言+异步通信架构

客户管理开户成功后推送到各业务模块；

现系统支持手机号+证件号查询；

各业务模块业务系统需要独立发送短信，邮件等；

签约模块和第三方支付或者银行交互时需要使用明文；

要求客户端用户自己看到的不能是加密的内容，需要是明文或者脱敏的内容；

密钥要求定期更换；

采用国密进行加解密；

敏感字段包含：个人手机号，证件号，银行卡号等信息；

基于以上现状，系统应该如何改造，给出一套可以落地的方案，改动尽量小；

使用jdk8+springboot实现加密服务；要求所有接口入参都是json格式的字符串；支持http协议和hessian协议两种格式；并生成postman的接口文档；不要包含业务代码。

:::

:::color3
## 系统改造方案概述
基于等保3级要求（敏感信息如手机号、证件号等不能在数据库中明文存储），结合系统现状（分布式、多语言、推送机制、独立短信/邮件发送、第三方交互需明文），方案聚焦于最小改动原则：不改变整体架构和推送流程，仅在关键点引入加密/解密逻辑。核心是通过一个统一的加密服务（微服务或库）来处理敏感信息，确保数据库加密存储，同时支持原有功能。

### 1. **改造原则**
+ **加密算法**：采用对称加密（如AES-256或国密SM4），密钥管理使用专用密钥管理系统（如HashiCorp Vault或云KMS），确保密钥轮换和访问控制符合等保3级。
+ **敏感信息范围**：手机号、证件号等PII（个人识别信息）。其他非敏感数据不变。
+ **最小改动**：不修改分布式架构和多语言环境，仅在存储/读取/使用敏感信息时添加加密/解密钩子。推送数据可加密传输，模块本地不存储明文。
+ **安全性**：解密仅在必要时（如发送短信或第三方交互）临时进行，不持久化明文。日志不记录明文。
+ **落地性**：分阶段实施，先客户管理模块，再各业务模块。测试时用模拟数据。

### 2. **核心组件引入：统一加密服务**
+ **实现方式**：部署一个独立的加密微服务（用Java或Go开发，支持多语言SDK，如REST API或gRPC接口）。多语言模块通过SDK调用（e.g., Python/Java/Go客户端）。
+ **功能**：
    - `encrypt(plain_text, key_id)`：返回加密密文 + IV（初始化向量）。
    - `decrypt(cipher_text, key_id)`：返回明文（仅限授权模块调用，添加RBAC控制）。
    - `hash(plain_text)`：生成不可逆哈希（e.g., SHA-256 + 盐），用于查询索引。
+ **部署**：作为内部服务，部署在私有网络中，限IP访问。密钥不暴露给业务模块。
+ **改动量**：各模块只需集成SDK（添加几行代码），无需重写业务逻辑。

### 3. **数据库存储改造**
+ **现状问题**：敏感信息明文存储。
+ **方案**：
    - 在客户管理模块开户时，立即加密敏感字段（调用加密服务），存储密文到数据库。原明文不存储。
    - 各业务模块数据库同步：推送时发送密文（或哈希），模块本地数据库存储密文。
+ **改动**：
    - 客户管理模块：开户逻辑后添加`encrypt()`调用（1-2处代码修改）。
    - 数据库 schema：敏感字段类型不变（e.g., VARCHAR），但内容为Base64编码的密文。
    - 影响：无，需要明文时解密。

### 4. **查询功能改造（手机号 + 证件号查询）**
+ **现状问题**：查询需匹配明文，但数据库为密文，无法直接查询。
+ **方案**：
    - 额外存储哈希索引：开户时计算敏感信息的哈希，存储在数据库额外字段（e.g., `phone_hash`, `id_hash`）。
    - 查询流程：用户输入明文 → 调用`hash(input)` → 用哈希查询数据库 → 返回结果（密文记录）。
+ **改动**：
    - 查询接口：添加`hash()`调用（每个查询点1处修改）。
    - 数据库：添加哈希字段（ALTER TABLE，数据迁移时回填）。
    - 注意：不支持模糊查询（如手机号前缀），若需，可用部分哈希或分段加密（但增加复杂度，优先评估是否必要）。

### 5. **推送机制改造**
+ **现状**：开户成功后推送明文到各模块。
+ **方案**：
    - 推送加密数据：客户管理加密后推送密文 + 哈希。各模块接收后存储密文。
    - 若模块需立即使用明文（罕见），推送时可选附带临时明文（但立即丢弃），优先推送密文。
+ **改动**：
    - 推送代码：添加`encrypt()`（1处修改）。
    - 接收端：无改动，存储密文。

### 6. **短信/邮件发送改造**
+ **现状**：各模块独立发送，需要明文（如手机号、邮箱）。
+ **方案**：
    - 发送前解密：从数据库取密文 → 调用`decrypt()`获取明文 → 发送 → 立即丢弃明文。
    - 确保解密在内存中进行，不日志。
+ **改动**：
    - 每个发送点：添加`decrypt()`调用（每个模块1-2处修改）。
    - 多模块独立：无需协调，SDK统一处理。

### 7. **签约模块与第三方交互改造**
+ **现状**：需明文交互（如支付银行验证证件号）。
+ **方案**：
    - 交互前解密：取密文 → `decrypt()` → 用明文交互 → 丢弃。
    - 若第三方支持加密传输，可直接传密文（但现状需明文，故解密）。
+ **改动**：
    - 交互代码：添加`decrypt()`（1处修改）。
    - 安全：交互用HTTPS，确保传输加密。

### 8. **实施步骤与风险缓解**
+ **阶段1（1-2周）**：开发/部署加密服务，测试密钥管理。客户管理模块改造（加密存储、推送）。
+ **阶段2（2-4周）**：各业务模块集成SDK，改造查询/发送/交互点。数据迁移：脚本加密旧数据，添加哈希（downtime最小化，用影子表）。
+ **阶段3**：全链路测试，等保审计准备（日志审计、访问控制）。
+ **风险与缓解**：
    - 性能：加密/解密 overhead 小（毫秒级），缓存哈希查询。
    - 多语言兼容：提供SDK polyfill。
    - 密钥泄露：用Vault + 审计日志。
    - 兼容性：回滚计划，A/B测试。
+ **成本估算**：开发1-2人月，部署低（容器化）。

此方案确保符合等保3级（加密存储、访问控制），改动限于点状代码注入，保持原有分布式和多语言特性。若需细节调整，可根据具体技术栈优化。

# 支付方式

+ 支付方式（尤其是银行类）与履约节点的兼容性
+ **履约保证金 → 货款** 的转化机制设计

## 一、交收路径状态图（流程建模）
将交收流程抽象为一棵决策树（也可转为状态机），节点代表关键动作/状态：

```plain
交收类型
├─ 线下交收 → [结束]
└─ 线上交收
   ├─ 线下配货 → [结束]
   └─ 仓单配货
      ├─ 自提 → [自提流程]
      ├─ 配送 → [配送流程]
      └─ 转入库 → [转入库流程]
```

> ✅ **关键观察**：
>
> + 只有 **线上交收 + 仓单配货** 的组合下，才会进入“提货类型”子流程；
> + 其他路径（线下交收、线上+线下配货）直接结束，意味着**无实物交割验证环节**，对资金/保证金释放逻辑有直接影响。
>

## 二、资金与保证金节点约束
### 1. 卖方收款节点（3类）
| 节点 | 适用场景 | 业务含义 | 风险控制强度 |
| --- | --- | --- | --- |
| 买方付款时 | 预付款/担保交易 | 卖方提前收款，买方风险高 | ⚠️ 高风险，需强保证金约束 |
| 买方收货时 | 货到付款/验货后付 | 卖方后收款，买方风险低 | ✅ 常规主流 |
| 卖方收款时 | 冗余表述？或指“系统确认可收款” | 建议明确为**平台放款指令触发时** | — |

> 📌 **建议**：第三类“卖方收款时”可能为技术口径，实际应映射到前两类之一，避免歧义。**推荐只保留前两类**，第三类可作为内部状态（如：`settle_confirmed`）。
>

### 2. 保证金释放节点（3类）
| 节点 | 适配性 |
| --- | --- |
| 买方收货时 | ✔️ 与“收货付款”强耦合，逻辑自洽 |
| 卖方收款时 | ✔️ 通用兜底，适配“付款即收款”场景 |
| 买方收票时 | ✔️ 适用于需开票闭环的场景（如大宗商品、B2B） |

> ✅ **结论**：三者均可保留，作为可配置字段（合同模板级配置）。
>

## 三、支付方式兼容性分析
| 支付方式 | 能否支持所有收款/释放节点？ | 说明 |
| --- | --- | --- |
| **余额类** | ✅ 是 | 平台内部账户，可精准控制资金冻结/解冻/划转 |
| **银行类** | ⚠️ **部分支持，需技术适配** | 银行通道为异步、不可逆操作，需通过**预授权/担保支付/子账户体系**实现类余额能力 |
| **线下类** | ❌ 否 | 无系统介入，无法自动触发释放/划转；仅能“记录”状态，依赖人工确认 |

### ▶ 银行类支付的关键限制与解法
| 问题 | 解决方案 |
| --- | --- |
| 银行付款后资金不可逆 | 引入**银行担保支付协议**（如：银企直连接口支持“预授权+实扣”两阶段）或使用**第三方支付担保通道**（如：银联企业付款通、招行B2B担保交易） |
| 无法自动释放保证金 | 保证金建议**仍用余额类/平台账户托管**，仅货款走银行；**不推荐直接用银行账户存履约金**（监管难） |
| 履约金 → 货款转换难 | 需平台侧做**账务层面转换**（非银行侧），即：履约金冻结在平台账户，成交后将部分冻结资金转为“应收货款”，再联动银行发起货款实付 |

## 四、履约保证金 → 货款的实现机制（核心！）
这是大宗商品/平台交易中常见的**资金复用**需求。推荐采用 **“平台中间账户 + 账务指令”** 模式：

### 方案：履约保证金转货款（推荐）
1. **履约阶段**
    - 卖方缴纳履约保证金 → 冻结在**平台保证金子账户**（资金池管理）
    - 买方支付货款 →
        * 若用**余额/银行**：全额支付至平台监管户
        * 若支持“履约金抵扣”，则买方可选择：`应付货款 = 合同总额 - 可用履约金`
2. **交收完成触发结算**
    - 当满足收款/释放条件（如：买方收货确认）
    - 系统执行账务操作：

```latex
// 示例：合同额 100万，履约金 10万，买方已付 90万（余额/银行）
卖方应收 = 100万
平台操作：
  ① 解冻履约金 10万 → 划入卖方可用余额（或直接发起银行出款）
  ② 将买方已付 90万 → 划付卖方
```

    - **若买方未足额付款**（如只付了80万），则：
        * 允许用履约金补足差额（需合同约定）
        * 卖方实收 = 80万（买方付） + 10万（履约金转） = 90万
        * 剩余10万差额：可触发违约处理，或要求补款
3. **银行类货款 + 履约金转付的联动**

> 🔐 关键：银行只需执行“付款”，**资金来源混合逻辑由平台账务系统封装**。
>

    - ✅ 可行，但需分两步：
        * Step 1：平台内部完成 **履约金 → 应收债权** 的账务转换（记账，不动银行资金）
        * Step 2：向银行发起**单笔付款指令**，金额 = `买方实付 + 履约金转付额`
→ 卖方收到一笔完整货款，体验无感

## 五、合同交收设计建议（落地思路）
### 1. 合同模板配置化
| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `delivery_type` | enum | 线上/线下 |
| `allocation_type` | enum | 仓单/线下 |
| `pickup_type` | enum（仅当仓单配货时必填） | 自提/配送/转入库 |
| `payment_method` | enum | 余额/银行/线下 |
| `seller_settle_at` | enum | 付款时/收货时 |
| `margin_release_at` | enum | 收货时/收款时/收票时 |
| `allow_margin_to_payment` | bool | 是否允许履约金转货款 |

### 2. 状态机驱动流程引擎
+ 每个合同实例走**状态流转图**（如：`created → paid → allocated → delivered → settled`）
+ 关键事件监听：`onPayment`, `onDeliveryConfirm`, `onInvoiceUploaded` → 触发资金结算

### 3. 支付网关抽象层
```typescript
interface PaymentGateway {
  // 预授权/冻结资金（用于履约金）
  freeze(amount: number, userId: string): Promise<string /*freezeId*/>;
  
  // 实际扣款（货款）
  deduct(amount: number, userId: string, options?: { useFrozen?: string[] }): Promise<void>;
  
  // 退款/解冻
  unfreeze(freezeId: string): Promise<void>;
}
```

+ 余额类：直接操作 DB 余额+冻结表
+ 银行类：对接银行担保接口（如招行B2B的 `freezeOrder` + `payOrder`）
+ 线下类：仅记录，`freeze/deduct` 返回 mock 成功

### 4. 账务系统设计要点
+ 实现 **“虚拟资金池”**：履约金 ≠ 现金，而是“可用担保额度”
+ 支持 **资金用途标签**：同一笔钱可标记为 `[保证金][可转货款]`
+ 结算时生成 **多借多贷凭证**，确保审计可追溯

## 六、风险控制提醒
1. **银行类不建议存履约金**
→ 法律上难认定“冻结”，建议履约金必须走平台可控账户（或引入银行存管专户 + 平台指令）
2. “付款即收款”模式需强约束：
    - 仅限高信用客户
    - 必须足额履约保证金（≥合同额）
    - 合同明确违约责任
3. 线下类交收/配货 → **无法自动化**，需配套：
    - 人工上传交收凭证（照片/签字单）
    - 平台审核后手动触发结算

# 不同支付的资金流转

在B2B交易系统中，**资金流（钱的去向）**与**信息流（系统状态）**的同步方式决定了系统的复杂度。

根据你提出的三种支付方式：**余额类（内部账）**、**网银授权类（银企直连/虚拟户）**、**线下类（转账+凭证）**，我将分别梳理它们在“保证金缴纳 -> 货款支付 -> 结算交收 -> 保证金释放”全流程中的资金流转差异。

---

## 1. 余额类支付（资金池/存管钱包模式）
**特点：** 钱先充值进平台的大账户（或存管子钱包），后续所有流转都是**数据库数字的变动**。这是效率最高、控制力最强的方式。

+ **前提：** 买卖双方已经在平台充值，拥有足够的可用余额。

### 资金流转剧本：
| 阶段 | 动作 | 系统逻辑 (信息流) | 实际资金变动 (资金流) |
| :--- | :--- | :--- | :--- |
| **1. 签合同** | 买方缴纳履约保证金(20万) | 锁定买方余额表：`available -= 20万`, `frozen += 20万`。 | **无变动**（钱依然在平台存管大户里，只是权属标记变了）。 |
| **2. 付尾款** | 买方支付剩余货款(80万) | 锁定买方余额表：`available -= 80万`, `frozen += 80万`。 | **无变动**。 |
| **3. 交收结算** | **触发收货/结算** | 1. 解锁买方100万冻结金额。   2. 扣除买方100万。   3. 增加卖方余额100万。 | **无变动**（仍在资金池内，只是从买方子账簿划到了卖方子账簿）。 |
| **4. 提现** | 卖方将钱转出 | 卖方余额减少，生成提现单。 | **平台监管户 -> 卖方实体银行卡**（发生真实转账）。 |
| **5. 释放保证金** | 卖方履约完毕 | 解锁卖方冻结余额。 | **无变动**。 |

+ **优势：** 实时到账，7*24小时支持，支持复杂的“履约金自动转货款”。
+ **劣势：** 平台需要合规（需接入银行存管或持牌支付机构），买方需预充值，占用资金成本。

---

## 2. 网银授权类（银企直连 / 虚拟子账户 / 智能合约）
**特点：** 平台系统通过 API 指令驱动银行进行资金划拨。通常采用**“监管户/中间户”**模型。

+ **技术支撑：** 银行提供的 API（如见证宝、电商管家、超级网银）。

### 资金流转剧本：
| 阶段 | 动作 | 系统逻辑 (信息流) | 实际资金变动 (资金流) |
| :--- | :--- | :--- | :--- |
| **1. 签合同** | 买方网银支付保证金(20万) | 调用银行API查询到账 -> 更新订单状态“已付保证金”。 | **买方银行卡 -> 平台监管虚拟户**（资金落地，银行系统标记该笔资金关联订单A）。 |
| **2. 付尾款** | 买方网银支付尾款(80万) | 调用银行API查询到账 -> 更新订单状态“待发货”。 | **买方银行卡 -> 平台监管虚拟户**（此时监管户里有订单A的100万）。 |
| **3. 交收结算** | **触发收货/结算** | 系统判断满足条件 -> **调用银行分账/代付API**。 | **平台监管虚拟户 -> 卖方实体银行卡**（银行执行指令，T+0或T+1到账）。   _注：手续费可在此步骤自动分流给平台。_ |
| **4. 履约金转货款** | 核心难点实现 | 系统记录：无需特殊操作，因为钱都在监管户里。 | 银行端将两笔入账（20万+80万）打包，统一打款给卖方。 |
| **5. 释放保证金** | 卖方履约完毕 | 系统调用银行退款/解冻API。 | **平台监管户 -> 卖方实体银行卡**（原路退回或解冻）。 |

+ **优势：** 买方无需充值到平台，资金安全感强（银行监管），自动化程度高。
+ **劣势：** 对接开发成本高，受银行系统维护时间影响，每一笔交易都有银行手续费。

---

## 3. 线下类（转账 + 上传凭证 + 人工审核）
**特点：** 资金流与信息流完全**断层**。依靠“财务人工”充当API接口。

### 资金流转剧本：
| 阶段 | 动作 | 系统逻辑 (信息流) | 实际资金变动 (资金流) |
| :--- | :--- | :--- | :--- |
| **1. 签合同** | 买方线下公对公转账20万 | 买方上传回单图片 -> 系统状态：待审核 -> **财务后台点“确认”** -> 状态变更为“已签约”。 | **买方银行卡 -> 平台对公账户**（需财务人工登录网银查询确认）。 |
| **2. 付尾款** | 买方线下转账80万 | 同上，需人工审核。 | **买方银行卡 -> 平台对公账户**。 |
| **3. 交收结算** | **触发收货/结算** | 系统状态变为“待结算” -> 生成“待打款任务单”推送给财务。 | **资金不动**。系统无法自动划拨资金。 |
| **4. 人工打款** | 财务执行结算 | 财务登录网银 -> 手动录入卖方账号 -> 转账100万 -> **回到系统点击“已打款”**。 | **平台对公账户 -> 卖方实体银行卡**（完全依赖人工操作，延迟高）。 |
| **5. 履约金转货款** | 核心难点实现 | 财务看到系统提示：应付卖方100万。 | 财务将账户里收到的两笔钱（20+80）在脑子里合并，手动打一笔100万出去。 |

+ **优势：** 开发成本最低，适应所有传统企业（有的企业必须走线下审批汇款）。
+ **劣势：** **无法实现秒级结算**，无法自动释放保证金，易出错（财务打错钱、看错小数点），运营成本极高。

---

## 4. 三种方式的对比总结与建议
| 维度 | 余额类 (Wallet) | 网银授权类 (API) | 线下类 (Offline) |
| :--- | :--- | :--- | :--- |
| **资金控制力** | ⭐⭐⭐⭐⭐ (最强) | ⭐⭐⭐⭐ (强) | ⭐ (弱) |
| **实时性** | 毫秒级 | 秒级/分钟级 | 天级 (T+N) |
| **履约金转货款** | 改个数字即可，极简 | 需监管户支持，逻辑适中 | 全靠财务人工计算和操作 |
| **开发难度** | 高 (需做账务系统) | 极高 (需对接银行) | 低 (只是CRUD) |
| **合规难度** | 难 (需牌照或存管) | 中 (银行产品支持) | 易 (普通对公转账) |

### 针对你的系统设计建议：
1. **混合模式是主流：**
    - 绝大多数B2B平台会同时支持 **“网银授权类”**（针对高频交易客户）和 **“线下类”**（针对传统大额客户）。
2. **如何统一架构？**
    - 不要在业务层写死支付逻辑。
    - 建立统一的 **“支付指令层”**。无论是API回调还是财务人工点击，最终都生成一个标准的 `Payment_Success_Event`。
    - **对于线下类：** 财务的“确认收款”按钮，本质上就是模拟了银行API的回调，告诉系统“钱到了，流程继续”。
3. **关于“履约金转货款”的特别提示：**
    - 如果是**线下类**，务必在后台给财务生成一张**清楚的“结算单”**。
    - 结算单上要显示：`本单合同总额100万` = `已收保证金20万` + `已收尾款80万`。
    - 操作指引：`请向卖方打款 100万`。
    - 千万不要让财务自己去查流水拼凑金额，否则一定会算错。

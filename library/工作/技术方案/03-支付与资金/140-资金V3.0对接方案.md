# 资金管理3.0 多结算银行对接 — 需求与设计文档
> 本文档面向开发团队，覆盖业务背景、系统设计与钱包规则、各模块改造设计详解、实施与交付保障。可直接指导编码。
>

---

## 一、业务背景与目标
### 1.1 背景
现有体系（资金管理3.0 引入前），客户签约时只能绑定**一家结算银行**（单签约模型）。资金管理3.0（系统1036）升级后，核心能力变为支持客户同时签约**多家结算银行**，即"多结算一行"——每个客户可以在工行、建行等多个银行各自独立签约、独立结算、独立记账。

### 1.2 涉及系统
| 系统编码 | 系统名称 | 定位 | 改造紧迫度 |
| --- | --- | --- | --- |
| 1036 | 资金管理3.0 | 多签约渠道 | 已就绪 |
| 1033 | 合同中心 | 资金变动，强制钱包ID透传 | 必须改造 |
| 1008 | 超级账本 | 资金变动引擎 | 必须改造 |
| 2007 | 创新挂牌 | 资金变动，强制钱包ID透传 | 必须改造 |

### 1.3 核心变化一句话
| 维度 | 改造前 | 改造后 |
| --- | --- | --- |
| 签约 | 一客户一银行 | 一客户多银行，每个银行对应独立 WALLET_ID（钱包ID） |
| 资金变动 | 不指定银行 | **每笔资金变动必须明确 WALLET_ID** |
| 账本 | 一客户一账本 | 一客户一银行一账本 |
| 交易匹配 | 不校验银行 | 卖方银行池 + 买方强制匹配 |

### 1.4 目标
完成 1033/1008/2007 三大渠道对接资金3.0 多结算银行能力，保障签约、资金变动、交易撮合、对账全链路合规运行，开发可**直接按本文档编码**。

## 二、系统设计与钱包规则
### 2.1 系统交互全景
```plain
┌──────────┐         ┌──────────┐
│   2007   │         │   1033   │
│ 创新挂牌  │         │ 合同中心  │
└────┬─────┘         └────┬─────┘
     │  资金变动           │  资金变动
     │                     │
     └──────────┬──────────┘
                ▼
        ┌───────────────┐
        │   1008 超级账本 │
        │  资金变动记账    │
        │  生成支付合同    │
        └───────┬───────┘
                │  支付合同（含 WALLET_ID）
                ▼
        ┌──────────────────┐
        │  1036 资金管理3.0  │
        │  钱包账户体系      │
        │  划转/清算/对账    │
        └──────────────────┘
```

**核心设计原则**：

1. **2007创新挂牌、1033合同中心**：作为业务发起方，将资金变动指令发送至 **1008超级账本** 进行统一记账。
2. **1008超级账本**：接收上游资金变动，完成链上记账后**生成支付合同**，推送至 **1036资金管理3.0** 执行实际资金划转。
3. **WALLET_ID** 是业务系统与超级账本之间的**唯一桥梁标识**，资金变动中必须携带 WALLET_ID，超级账本据此定位钱包账户执行操作。

### 2.2 渠道差异化设计
| 渠道 | WALLET_ID 传参规则 | 兜底策略 | 设计理由 |
| --- | --- | --- | --- |
| 1033 | 优先显式传入，解冻绑定 | 主结算行兜底 | 若异常缺失，由 1008 自动路由至主结算行进行兜底记账 |
| 2007 | **建议必传**，原则上强制校验 | 主结算行兜底 | 若因业务异常未传，由 1008 路由至主结算行做最后安全防错 |
| 1008 | 可选，优先传入。 | 主结算行兜底 | 未传时自动匹配主结算行，降低历史接口改造影响且防资金走错 |

### 2.3 WALLET_ID 概念说明
**WALLET_ID 不等于 BANK_CODE**：

+ `WALLET_ID`（钱包ID）：超级账本钱包账户体系的唯一标识，如 `10100002`（工行钱包）
+ `BANK_CODE`：银行机构编码，如 `002`（工行）、`005`（建行）

WALLET_ID 是资金操作的最小颗粒度。

**编码示例：**

| WALLET_ID | 含义 |
| --- | --- |
| 10100002 | 工行现金账户 |
| 10100005 | 建行现金账户 |
| 20100 | 信用账户 |

| 钱包号 | 名称 | 类别 | 允许支付用途 | 对外出款 |
| --- | --- | --- | --- | --- |
| 20100 | 保证金授信账户 | InnerW 内部 | 保证金支付 | 禁止 |
| 20102 | 贷款授信账户 | InnerW 内部 | 货款支付 | 禁止 |
| 90100 | 积分账户 | InnerW 内部 | 积分商品支付 | 禁止 |
| 30100 | 融资账户 | InnerW 内部 | 融资合同支付 | 禁止 |
| 30500 | 保证金融资账户 | InnerW 内部 | 保证金支付、融资还款 | 禁止 |
| 10100002 | 工行现金账户 | 银行钱包 | 保证金/手续费/货款全场景 | 可出 |
| 10100005 | 建行现金账户 | 银行钱包 | 货款支付、手续费支付 | 可出 |

**用途管控原则**：交易发起时自动校验目标钱包是否具备对应业务用途权限，无权限直接拒绝交易。

### 2.5 钱包划转与清算规则
In the 多结算银行对接的当前阶段，由于去除了主/子钱包设计，钱包账户规则进行了极大简化：

1. **无子钱包体系**：各结算银行下，客户仅维护唯一的、平级的实体现金账户钱包。
2. **不支持钱包直接划转**：不同钱包（不同银行）之间禁止直接进行线上钱包内划转，仅支持各自的出入金操作。
3. **独立清算对账**：所有银行钱包的资金清算交割均相互独立，不进行合并清算，各钱包按账本独立与结算银行进行流水核对。

### 2.6 场景-渠道-钱包匹配逻辑
| 业务场景 | 路由规则 |
| --- | --- |
| 账户入金 | 筛选已签约、开通入金权限的银行通道 |
| 账户出金 | 筛选已签约、开通出金权限的银行通道 |
| 交易-保证金支付 | 筛选用途="保证金支付"的合法钱包 |
| 交易-手续费支付 | 筛选用途="手续费支付"的合法钱包 |
| 授信查询 | 固定查询 20100 / 20102 授信钱包 |

### 2.7 主结算行逻辑设计
为应对一客多结算行情况，系统引入“主结算行”概念，用于在未指定钱包时进行资金路径默认兜底。

1. **主结算行设定规则**：
    - **首次签约默认**：客户签约的第一个结算银行卡对应的钱包，且该银行渠道在渠道管理中允许做主结算行（`IS_ALLOW_PRIMARY = 1`），系统默认将其设为主结算行（`IS_PRIMARY = 1`）。若首签渠道的 `IS_ALLOW_PRIMARY = 0`，则该签约记录的 `IS_PRIMARY` 置为 `0`（客户暂时没有主结算行，需后续签约允许的行后再指定）。
    - **新增签约不自动覆盖**：当客户签约第二家及以上的结算行时，新签约记录的 `IS_PRIMARY` 默认为 `0`，不会自动覆盖已有主结算行。
    - **手动变更约束**：客户可在前端签约管理页面手动将其他有效签约结算行设为主结算行。
        * **渠道允许校验**：目标钱包所属银行渠道在渠道管理中必须配置为 `IS_ALLOW_PRIMARY = 1`。
        * **原主结算行资金清零校验**：变更主结算行时，系统必须强制校验原主结算行账户的资产状况（可用余额及冻结金额均须为 `0`）。若原主结算行仍有资金或冻结金额，拒绝变更并提示：“原主结算行仍有资金或冻结金额，请结清后再试”。
        * 变更成功后，新主结算行的 `IS_PRIMARY` 设为 `1`，原主结算行记录的 `IS_PRIMARY` 自动置为 `0`（保证一个客户有且仅有一个有效的主结算行）。
    - **唯一性校验**：数据库通过 `CUST_ID` 与 `IS_PRIMARY` 维度的联合索引控制，保证同一个客户有效签约记录中（`SIGN_STATUS = 1`），有且仅有一个主结算行。若发生解约且解约卡为主结算行，系统需自动将剩余有效签约（且所属渠道 `IS_ALLOW_PRIMARY = 1`）中时间最早的那张卡置为主结算行，或提示用户重新指定。
2. **无 WALLET_ID 时的自动兜底路由逻辑**：
    - 当超级账本（1008）接收到任何资金变动请求时，若请求报文未携带 `WALLET_ID`，系统会根据变动明细中的 `FIRMID`（即客户ID）去 1036 资金模块查询其处于有效签约状态（`SIGN_STATUS = 1`）且 `IS_PRIMARY = 1` 的结算卡记录，并自动获取其关联的 `WALLET_ID`。
    - 匹配成功后，系统会将该 `WALLET_ID` 补充进变动明细，并以此 `WALLET_ID` 完成记账及后续的支付合同生成与清算。
    - 若查询不到任何有效的主结算行，系统直接拦截报错，提示：“未传入 WALLET_ID 且该客户未配置有效的主结算行”。

### 2.8 系统参数与版本控制设计
为了支持在部署与上线时灵活切换资金对接模式，系统引入全局参数进行运行模式控制。

1. **系统参数定义**：
    - 参数名称：`FUND_SYSTEM_VERSION`（资金系统对接版本）
    - 配置位置：Nacos 配置中心 或 数据库 `系统参数配置表`
    - 参数值选项：
        * `"1.0"`：单银行签约兼容模式（资金1.0）
        * `"3.0"`：多结算行强管控模式（资金3.0）
2. **版本控制逻辑矩阵**：

| 业务模块 | 业务逻辑项 | FUND_SYSTEM_VERSION = "1.0" | FUND_SYSTEM_VERSION = "3.0" |
| :--- | :--- | :--- | :--- |
| **1036 资金模块** | 客户签约绑定 | 限制单签：若已有有效签约记录，拒绝新签约 | 允许多签：允许签约多个不同的银行通道 |
|  | 主结算行逻辑 | 所有有效签约记录的 `IS_PRIMARY` 默认为 `1` | 严格遵守主结算行设置及变更规则 (只能有1个且校验资金) |
| **1008 超级账本** | 账务记账路由 | 强制路由至默认 `COMPANY_ID = 10100`，账本账号使用 `CUST_ID`（忽略传入的 WALLET_ID） | 按照 `WALLET_ID` 定位对应的拆分账本，公司使用 `10100 + 银行编码` |
|  | 缺失 WALLET_ID 兜底 | 自动匹配唯一的有效签约钱包进行记账 | 自动定位 `IS_PRIMARY = 1` 的主结算行进行兜底记账 |
| **2007 交易模块** | 挂/摘牌强校验 | 不进行银行通道匹配校验，不强检验钱包ID | 强制校验买卖双方银行通道匹配性，且强校验钱包用途 |

## 三、各模块改造设计详解
### 3.1 1036 资金模块 (资金管理3.0)
#### 3.1.1 业务描述与职责
负责多银行签约关系管理，维护钱包账户的基本信息与状态，并对外提供签约记录查询服务。

#### 3.1.2 数据库表变更（签约表、渠道管理表、系统配置表）
为了支持“一客多签约钱包”的业务形态以及对通道属性与对接版本的精细管控，需对签约表、渠道管理表以及系统配置表进行升级：

```sql
-- 1. [本次核心改动]：签约表字段全部大写，增加钱包ID与银行编码，修改主键/唯一索引支持同客户多笔签约；增加主结算行字段与局部索引
ALTER TABLE 签约表 ADD COLUMN WALLET_ID   VARCHAR(32) NOT NULL COMMENT '钱包ID（资金3.0分配）';
ALTER TABLE 签约表 ADD COLUMN BANK_CODE   VARCHAR(16)          COMMENT '银行机构编码';
ALTER TABLE 签约表 ADD COLUMN SIGN_STATUS TINYINT DEFAULT 1    COMMENT '1-有效 0-注销';
ALTER TABLE 签约表 ADD COLUMN SIGN_TIME   DATETIME             COMMENT '签约时间';
ALTER TABLE 签约表 ADD COLUMN IS_PRIMARY  TINYINT DEFAULT 0    COMMENT '是否为主结算行：1-是，0-否';
ALTER TABLE 签约表 ADD UNIQUE INDEX uk_cust_wallet (CUST_ID, WALLET_ID);
-- 局部唯一索引，确保单个客户只存在一个有效的主结算行
CREATE UNIQUE INDEX uk_cust_primary ON 签约表 (CUST_ID, IS_PRIMARY, SIGN_STATUS) WHERE IS_PRIMARY = 1 AND SIGN_STATUS = 1;

-- 2. [本次核心改动]：渠道管理表新增是否允许做主结算行配置字段
ALTER TABLE 渠道管理表 ADD COLUMN IS_ALLOW_PRIMARY TINYINT DEFAULT 1 COMMENT '是否允许做主结算行：1-是，0-否';

-- 3. [本次核心改动]：系统配置表中增加资金版本配置参数初始化数据
INSERT INTO 系统参数配置表 (PARAM_KEY, PARAM_VALUE, PARAM_DESC) VALUES ('FUND_SYSTEM_VERSION', '1.0', '资金系统对接版本：1.0-单银行签约兼容模式，3.0-多行签约强管控模式');
```

#### 3.1.3 接口设计与时序
+ **接口 1：签约列表查询接口**
    - **接口说明**：**[本次核心改动] 返回值结构由原“单条签约信息”升级为“签约信息数组”**，支持查询客户关联的工行、建行等所有有效签约钱包，增加返回 `IS_PRIMARY` 字段。
    - **接口返回结构**：

```json
[
  { "CUST_ID": "C0001", "WALLET_ID": "10100002", "BANK_CODE": "002", "BANK_NAME": "工商银行", "SIGN_STATUS": 1, "SIGN_TIME": "2026-06-30 12:00:00", "IS_PRIMARY": 1 },
  { "CUST_ID": "C0001", "WALLET_ID": "10100005", "BANK_CODE": "005", "BANK_NAME": "建设银行", "SIGN_STATUS": 1, "SIGN_TIME": "2026-06-30 15:30:00", "IS_PRIMARY": 0 }
]
```

+ **客户签约前置校验逻辑**
    - **校验说明**：在执行签约流程前，系统需读取全局参数 `FUND_SYSTEM_VERSION` 控制单/多签约模式。
    - **校验规则**：
        1. 若 `FUND_SYSTEM_VERSION = "1.0"`：查询该客户是否有 `SIGN_STATUS = 1` 的历史签约记录。若已存在，直接拦截签约，提示：“当前系统处于资金1.0对接模式，仅限制签约一家银行卡”。新签约成功后，其 `IS_PRIMARY` 设为 `1`。
        2. 若 `FUND_SYSTEM_VERSION = "3.0"`：解除单签限制，首签且银行渠道 `IS_ALLOW_PRIMARY = 1` 时置为 `IS_PRIMARY = 1`，其他置为 `0`。
+ **接口 2：主结算行设置与变更接口**
    - **接口说明**：客户可以将已绑定的任意一个有效结算钱包设置为当前的主结算行。
    - **接口请求参数**：

```json
{
  "CUST_ID": "C0001",
  "WALLET_ID": "10100005"
}
```

    - **处理逻辑**：
        1. 开启事务。
        2. 校验该 `CUST_ID` 与 `WALLET_ID` 对应的签约记录是否存在且 `SIGN_STATUS = 1`。
        3. **渠道属性校验**：查询目标 `WALLET_ID` 对应的银行渠道在 `渠道管理表` 中的配置。若 `IS_ALLOW_PRIMARY = 0`，拒绝设置并抛出异常，提示：“该结算银行渠道不允许设置为主结算行”。
        4. **原主结算行资金结清校验**：
            + 查询该客户当前设为主结算行 (`IS_PRIMARY = 1`) 的签约记录，获取其原钱包ID (`WALLET_ID_OLD`)。
            + 若原主结算行存在，且与待设置的新 `WALLET_ID` 不同，则调用 1008 超级账本余额查询接口。
            + 验证原钱包 `WALLET_ID_OLD` 的“可用余额 (BALANCE)”与“冻结金额 (FREEZE_BALANCE)”是否均等于 `0`。若任一不等于 `0`，拒绝变更并抛出异常，提示：“原主结算行仍有资金或冻结金额，请结清后再试”。
        5. 将该客户所有签约记录的 `IS_PRIMARY` 置为 `0`。
        6. 将指定的 `WALLET_ID` 对应的记录的 `IS_PRIMARY` 更新为 `1`。
        7. 提交事务。
+ **签约流程时序（钱包账户建立与签约记录保存）：**

```plain
客户端                    1036资金管理3.0                    1008超级账本
      │                              │                              │
      │ 1. 客户选择银行签约           │                              │
      │    (携带 BANK_CODE)          │                              │
      │─────────────────────────────→│                              │
      │ 2. 校验资格并创建签约记录      │                              │
      │    (判断是否首签：若无历史有效│                              │
      │     签约记录，且当前签约银行  │                              │
      │     渠道的IS_ALLOW_PRIMARY=1,│                              │
      │     则设IS_PRIMARY=1；否则    │                              │
      │     设IS_PRIMARY=0)           │                              │
      │←────────────────────────────│                              │
      │ 3. 返回签约成功确认          │                              │
      │←────────────────────────────│                              │
      │                              │                              │
      │                              │ 4. 签约成功通知               │
      │                              │─────────────────────────────→│
      │                              │                              │ 5. 创建客户钱包与账本
      │                              │                              │    (CUST_ID_WALLET_ID)
      │                              │                              │ 6. 返回 WALLET_ID
      │                              │←─────────────────────────────│
      │                              │                              │
```

#### 3.1.4 前端界面改动
+ **签约列表页面**：由单一签约信息展示，升级为支持多行数据的“已绑定结算银行卡列表”。
+ **新增签约页面**：新增选择签约银行的下拉框，支持多次签约不同结算银行卡。
+ **解约操作**：解约时前置校验该钱包是否存在进行中的交易，确认后发起注销。

### 3.2 1008 账本模块 (超级账本)
#### 3.2.1 业务描述与职责
作为核心的资金变动引擎，根据传入的 `WALLET_ID` 定位到具体的子账本执行链上记账，对外提供钱包余额与账本变动明细查询。

+ **接口 1：卖方挂牌/发布接口**

### 4.4 从资金1.0切换到资金3.0的过渡与数据切换方案
为确保系统平稳升级，必须对存量数据进行安全迁移，并在上线初期采用双轨兼容运行机制。

#### 4.4.1 数据切换方案 (COMPANY_ID 升级与余额迁移)
在资金1.0中，所有客户账本的 `COMPANY_ID` 均为固定的 `10100`。切换到资金3.0后，各结算行都有独立的 `WALLET_ID`（即新 `COMPANY_ID = 10100 + BANK_CODE`）。必须通过以下步骤进行历史数据平滑切换：

1. **第一步：存量签约关系与渠道管理升级**
    - **升级渠道管理表**：对所有存量有效银行渠道，默认将其 `IS_ALLOW_PRIMARY` 字段初始化为 `1`。
    - **升级签约关系表**：扫描现有签约表中的所有有效客户（`SIGN_STATUS = 1`）。
    - 根据其绑定的结算银行编码（`BANK_CODE`），生成对应的 `WALLET_ID`（即字符串拼接 `"10100"` + `BANK_CODE`）。
    - 将现有唯一的签约卡默认设为主结算行（更新 `IS_PRIMARY = 1`，前提是其所绑定的存量有效银行渠道 `IS_ALLOW_PRIMARY = 1`）。
2. **第二步：初始化新账本账户 (COMPANY_ID 升级)**
    - 对于每个有余额的存量客户，根据其新计算出的 `WALLET_ID`（新 `COMPANY_ID`），在超级账本（1008）中初始化新账本。
    - 新账本账号规则：`ACCOUNT_NO = CUST_ID + "_" + WALLET_ID`。
    - 新账本的公司标识设置为：`COMPANY_ID = 10100 + BANK_CODE` (数字型，如 `10100002`)。
3. **第三步：存量余额划转**
    - 冻结交易后，将原账本（`COMPANY_ID = 10100`）的可用余额、冻结金额等资产数据，等额结转至对应的新账本（`COMPANY_ID = 10100 + BANK_CODE`）中。
    - 原账本余额清零并归档（保持原账本记录但状态设为失效，禁止新交易录入）。
4. **第四步：历史变动流水归属转换**
    - 为了保证历史流水的可追溯性，对历史资金变动表（`资金变动表`）中 `COMPANY_ID = 10100` 的存量数据，根据客户对应的唯一签约银行，批量更新其 `WALLET_ID` 和 `FUND_ACCT_NO` 为新值。

#### 4.4.2 迁移 SQL 脚本参考
```sql
-- 1. 升级渠道管理表：初始化存量渠道是否允许做主结算行的标识
UPDATE 渠道管理表 
SET IS_ALLOW_PRIMARY = 1 
WHERE STATUS = 1;

-- 2. 升级存量签约表：补齐 WALLET_ID，并在渠道允许的情况下设为主结算行
UPDATE 签约表 s
JOIN 渠道管理表 c ON s.BANK_CODE = c.BANK_CODE
SET s.WALLET_ID = CONCAT('10100', s.BANK_CODE),
    s.IS_PRIMARY = CASE WHEN c.IS_ALLOW_PRIMARY = 1 THEN 1 ELSE 0 END
WHERE s.SIGN_STATUS = 1 AND s.WALLET_ID IS NULL;

-- 3. 迁移账本表：将原 COMPANY_ID = 10100 账本升级为新 ACCOUNT_NO 和新 COMPANY_ID
-- 下方为逻辑示意，实际执行时使用关联更新
UPDATE 账本表 a
JOIN 签约表 s ON a.CUST_ID = s.CUST_ID AND s.SIGN_STATUS = 1
SET a.ACCOUNT_NO = CONCAT(a.CUST_ID, '_10100', s.BANK_CODE),
    a.WALLET_ID = CONCAT('10100', s.BANK_CODE),
    a.COMPANY_ID = CAST(CONCAT('10100', s.BANK_CODE) AS UNSIGNED)
WHERE a.COMPANY_ID = 10100;

-- 4. 历史变动流水关联升级
UPDATE 资金变动表 f
JOIN 签约表 s ON f.CUST_ID = s.CUST_ID AND s.SIGN_STATUS = 1
SET f.WALLET_ID = CONCAT('10100', s.BANK_CODE),
    f.FUND_ACCT_NO = CONCAT(f.CUST_ID, '_10100', s.BANK_CODE),
    f.COMPANY_ID = CAST(CONCAT('10100', s.BANK_CODE) AS UNSIGNED)
WHERE f.COMPANY_ID = 10100;
```

#### 4.4.3 双轨过渡与切流策略
1. **双轨兼容运行**：
    - 核心记账系统（1008）上线后，即使上游业务系统（如老版本的 1033 或外部接口）尚未完全升级，只要它们没有在请求中携带 `WALLET_ID` 或 `FUND_VERSION`，1008 仍可通过“主结算行”机制自动路由。
    - 路由时自动匹配已迁移的新 `COMPANY_ID`（即 `10100 + 银行编码`），从而实现对上游系统的零感升级。
2. **切流上线步骤**：
    - 步骤 1：部署 1036（资金模块）与 1008（超级账本）的新版本代码。
    - 步骤 2：执行上述 DDL 与数据迁移脚本，完成余额和流水由 `10100` 向 `10100 + BANK_CODE` 的切换。
    - 步骤 3：验证各客户的新账本余额总和是否与旧账本完全一致。
    - 步骤 4：**切流配置变更**：在 Nacos 配置中心或系统参数配置表中，将全局参数 `FUND_SYSTEM_VERSION` 的值更新为 `"3.0"`，正式开启多结算行强管控模式。
    - 步骤 5：分批升级上游 1033（合同中心）、2007（创新挂牌）等系统，开始在业务层强透传具体的 `WALLET_ID`。

#### 4.4.4 回滚预案
如果上线后新版多结算行机制出现灾难性问题，需要回滚至资金1.0，按以下步骤操作：

1. **模式紧急降级**：立即在系统配置或 Nacos 中，将 `FUND_SYSTEM_VERSION` 参数修改回 `"1.0"`，让业务处理逻辑瞬间退回 1.0 单结算行模式。
2. 回滚 1008, 1033, 2007, 1036 的系统代码至旧版本。
3. 运行逆向数据脚本，将各客户名下所有拆分账本（`COMPANY_ID = 10100 + BANK_CODE`）的当前余额进行合并汇总。
4. 将汇总金额恢复至原 1.0 的旧账本中（`COMPANY_ID = 10100`，`ACCOUNT_NO = CUST_ID`）。
5. 恢复业务运行。

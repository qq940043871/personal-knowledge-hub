# 支付模拟器

这是一个非常典型且具有挑战性的B2B供应链金融或大宗商品交易场景。

核心难点在于解决**“信任不对称”**（买卖双方互不信任）与**“资金流动性”**（卖方缺钱，无法预缴保证金）之间的矛盾，同时还要满足**“税务合规”**（票款一致、银行回单显名）。

基于你的需求，我为你设计了一套**“动态分账与留置支付模型”**。

---

## 第一部分：支付模型设计原理
为了满足你的两个核心硬性指标，我们需要对账户体系和资金流转逻辑做如下设定：

### 1. 账户体系设计
+ **买方账户**：可用余额、冻结资金（履约金）。
+ **卖方账户**：可用余额、冻结资金（履约金）、**待结算冻结户**（关键创新点，用于存放从货款中截留的开票保证金）。
+ **平台/银行监管户**：用于暂存过路资金或费用。

### 2. 核心逻辑解决方案
+ **针对需求1（银行凭证显示真实双方）：**
    - **余额支付**：这通常是平台内部记账。若要银行凭证显名，必须通过银行的**“虚拟子账户”**或**“电商管家/分账系统”**底层通道。买方充值是充给“买方在平台的专属子户”，打款时由银行指令直接划拨到“卖方子户”。
    - **网银授权**：直接使用银行的**B2B支付指令**或**智能代收付**，平台仅作为指令发起方，资金直接在双方实体账户间流转（或通过银行托管户透传）。
+ **针对需求2（卖方无资金，收到货款后再冻结保证金）：**
    - **余额类策略（原子分账）**：资金到达卖方账面的**瞬间**，系统执行原子操作，将应冻结的保证金直接划入“卖方冻结户”，剩余部分划入“卖方可用余额”。
    - **网银类策略（尾款留置）**：既然是银行直连，平台无法控制卖方收到钱后的冻结。因此采用**“压款代保”**策略。即：将货款拆分为“首付款（90%）”和“尾款（10%）”。尾款本身就起到了“开票保证金”的作用，只有开票完成后，买方才支付尾款。

## 第二部分：资金模拟器（流程演示）
以下是基于你提供的节点和资金动作生成的详细模拟器。

### 场景一：余额类支付（平台内账/子账户体系）
**特点**：资金流转最灵活，系统控制力最强，支持履约金冲抵货款。
**前提**：卖方初始无开票保证金，依靠货款截留。

| 流程节点 | 动作描述 | 资金变动模拟 (假设：货款100万，履约金各5万，开票保证金10万) | 状态 |
| :--- | :--- | :--- | :--- |
| **1. 合同签订** | 冻结履约金 | **买方**：可用余额 -5万，冻结 +5万   **卖方**：可用余额 -5万，冻结 +5万 | 待交收 |
| **2. 交收申请/确认** | 校验状态 | 无资金变动 | 交收中 |
| **3. 付款 (冲抵)** | **买方支付**   (履约金转货款) | **买方**：   1. 释放履约金：冻结 -5万，可用 +5万   2. 支付货款：可用 -100万 (实际需充值95万)   3. 扣除手续费：可用 -X元      **平台/中间态**：持有100万待结算资金 | 已付款   待发货 |
| **4. 配货/收货** | 货物确认 | 无资金变动 | 已收货 |
| **5. 账单确认** | **核心步骤：**   结算+冻结 | **系统执行原子分账指令：**   1. 平台释放100万给卖方。   2. **卖方**账户瞬间变动：   - 总资产 +100万   - **立即冻结(开票保证金)**：冻结 +10万   - **实际可用入账**：可用 +90万   3. **卖方**履约金释放：冻结 -5万，可用 +5万   4. 扣除卖方手续费。 | 待开票   (资金已到卖方但部分冻结) |
| **6. 开票** | 卖方上传发票 | 无资金变动 | 开票中 |
| **7. 收票** | 买方验票通过 | **卖方**：   释放开票保证金：冻结 -10万，可用 +10万 | **流程结束** |

### 场景二：网银授权类支付（银行直连/分阶段支付）
**特点**：银行流水清晰显示买卖双方，资金不经平台资金池（合规性高）。
**策略**：由于钱直接进卖方银行卡，平台无法冻结，故采用**“90%货款+10%尾款”**模式，用未付的尾款倒逼卖方开票。

| 流程节点 | 动作描述 | 资金变动模拟 (假设：货款100万，履约金各5万，尾款即保证金10万) | 状态 |
| :--- | :--- | :--- | :--- |
| **1. 合同签订** | 冻结履约金 | **平台/银行存管**：冻结买卖双方履约金各5万 (或通过保函/预授权) | 待交收 |
| **2. 交收确认** | 生成支付指令 | 系统生成两笔支付计划：   1. 首付款：90万   2. 尾款：10万 | 待付款 |
| **3. 买方支付(首付)** | **支付货款**   (第1笔) | **买方银行卡**：-90万 ---> **卖方银行卡**：+90万   (备注：合同编号-货款)      _注：此时买方履约金暂不释放，防止不付尾款_ | 已付首款   待发货 |
| **4. 收货/账单确认** | **释放履约金** | 1. 货物无误，交易实质完成。   2. **卖方**履约金释放：退回5万。   3. **买方**履约金释放：退回5万 (或转为尾款一部分，看银行接口能力，通常建议退回以保证流水清晰)。 | 待开票 |
| **5. 开票** | 卖方开票 | 卖方为了拿到剩下的10万，必须开具100万全额发票给买方。 | 开票中 |
| **6. 收票** | 验票通过 | 买方确认收到发票。 | 待付尾款 |
| **7. 买方支付(尾款)** | **支付尾款**   (第2笔) | **买方银行卡**：-10万 ---> **卖方银行卡**：+10万   (备注：合同编号-尾款/质保金) | **流程结束** |

## 第三部分：特殊场景的逻辑处理（FAQ）
为了让模型更健壮，需要处理以下异常逻辑：

### 1. 线下支付类怎么处理？
线下支付意味着资金流不经过系统。

+ **流程**：买方线下转账 -> 卖方在系统点击“确认收款” -> **系统仅做记账**。
+ **关于开票保证金**：
    - 由于钱在线下，系统无法冻结卖方资金。
    - **解决方案**：必须利用**“卖方履约金”**。在线下支付场景下，卖方履约金不能在收货后立即释放，必须**等开完票后**，才能释放卖方履约金。
    - _风险提示_：如果履约金金额（如5万）小于税点金额（如13万），则存在卖方不开票的风险。线下支付建议要求提高卖方履约金比例。

### 2. 买方履约金冲抵货款的详细逻辑
在**余额类**支付中，这是一个高频需求。

+ **算法**：`应付金额 = 订单总额 - 已冻结买方履约金`
+ **动作顺序**：
    1. 计算差额。
    2. 买方余额支付差额。
    3. 系统将“冻结的履约金”属性变更为“货款”。
    4. 资金合并，流转至下一节点。

### 3. 卖方手续费的处理
+ **余额类**：在给卖方入账前直接扣除（收支两条线：入账100万，支出手续费X元）。
+ **网银/线下类**：由于钱直走，平台无法截流。
    - 方法A：从卖方履约金中扣除。
    - 方法B：卖方需在平台预充值手续费，否则无法操作“发货/确认收款”按钮。

## 第四部分：给开发人员的数据结构建议
设计数据库或API时，建议增加一个 **"Fund_Plan" (资金计划)** 对象：

```json
// 资金计划示例 (网银授权类)
{
  "contract_id": "HT2023112101",
  "total_amount": 1000000,
  "stages": [
    {
      "stage_name": "履约金",
      "payer": "Buyer",
      "amount": 50000,
      "status": "FROZEN",
      "trigger_node": "SIGNING"
    },
    {
      "stage_name": "首付款",
      "payer": "Buyer",
      "amount": 900000,
      "status": "PENDING",
      "trigger_node": "PAYMENT_APPLY",
      "is_direct_bank": true // 标记走网银直连
    },
    {
      "stage_name": "尾款(代保证金)",
      "payer": "Buyer",
      "amount": 100000,
      "status": "PENDING",
      "trigger_node": "INVOICE_RECEIVED", // 只有收票后才触发
      "is_direct_bank": true
    }
  ]
}
```

这套模型完美解决了你提出的“显名”和“后置冻结”的矛盾，同时兼顾了不同支付方式的特性。

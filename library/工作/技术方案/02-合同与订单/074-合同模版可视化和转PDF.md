# 合同模版可视化和转PDF

这个场景太典型了，我给你一套**工业级、稳定、能上生产**的方案，专门解决：
**Word 模板 → 变量替换 → 生成 PDF**
而且兼容你现在的 **C + Java 架构、高并发、服务化**。

## 一句话结论
**客户用 Word 编辑模板（带占位变量） → Java 服务做模板渲染 → 转 PDF → 提供下载/预览**
这是目前企业合同、电子签章系统最标准的路径。

---

## 一、Word 模板怎么设计？（客户完全无感知）
让客户/业务人员正常用 Word 写，只需要加**占位符**，比如：

```plain
甲方：{{customerName}}
身份证号：{{idNo}}
合同金额：{{amount}} 元
签订日期：{{signDate}}
```

支持的占位符风格随便选：

+ `{{var}}`
+ `${var}`
+ `{var}`
+ `[$var$]`

客户只会用 Word，**不用懂代码**。

## 二、技术实现方案（按稳定度排序）
### 方案1：最稳、生产首选 → **POI + FreeMarker + LibreOffice**
#### 流程
1. 把 Word 存成 **.ftl（FreeMarker 模板）** 或直接用 docx 替换
2. Java 读取模板，替换变量
3. 生成临时 docx
4. 调用 **LibreOffice** 命令行转 PDF

#### 优点
+ 格式保真最高
+ 支持复杂排版、表格、图片、页眉页脚
+ 高并发下可以做池化、异步
+ 开源免费

#### 缺点
+ 服务器需要装 LibreOffice

这是**合同系统最常用方案**。

优点：

+ 不用装 LibreOffice

## 三、高并发、网关扩容场景下怎么不炸服务？
你现在的架构是 **网关横向扩展 + 高并发**，合同生成是**重计算操作**，绝对不能同步生成。

### 标准架构
1. 前端/Java 收到生成合同请求
2. 直接丢 **MQ**
3. 独立的 **合同生成服务（Consumer）** 异步生成
4. 生成好上传 **MinIO/S3**
5. 生成记录写 DB
6. 前端轮询/通知获取 PDF 地址

这样：

+ 不阻塞业务接口
+ 不影响网关性能
+ 可以独立扩容合同服务
+ 不会把整个系统拖垮

## 四、你最关心的几个坑
### 1）格式乱、换行乱、字体乱
+ 服务器必须安装：宋体、黑体、Arial 等常用字体
+ 模板尽量用**简单样式**，不要用复杂艺术字
+ 优先用 LibreOffice 转换，保真度最高

### 2）并发生成导致服务器CPU打满
+ 合同生成是**CPU密集型**
+ 必须**独立服务部署**
+ 线程池限制并发，比如同一时刻最多 5 个生成

### 3）C 服务也要生成合同怎么办？
+ C 不适合做 Word→PDF
+ 最佳架构：
**C 只传业务数据 → MQ → Java 合同服务生成 → 存文件 → 通知 C**

### 4）变量漏填、格式错误
+ 做**模板校验**
+ 生成前检查必填变量
+ 失败重试 + 告警

## 核心思路（一句话）
**不让客户输变量名 → 让客户在 Word 里“插入域/书签/内容控件”
****或者在后台做“模板字段映射”，客户只管排版，不管变量叫啥。**

---

## 方案1：最通用、客户零学习成本 → **后台字段映射 + 固定占位符**
### 做法
1. **你在后台维护一套“合同字段库”**
比如：
    - 客户姓名
    - 客户身份证号
    - 合同金额
    - 签订日期
    - 抵押物地址
    - 保证人姓名
……
2. 客户上传 Word 模板，**只需要用中文标记位置**，比如：

```plain
甲方：【客户姓名】
身份证号：【身份证号码】
合同金额：【合同金额】元
```

3. 后台做**映射配置**
    - 【客户姓名】 → `customerName`
    - 【身份证号码】 → `idNo`
    - 【合同金额】 → `amount`
4. 生成时：
系统把 `【客户姓名】` 全局替换成真实值。

### 优点
+ 客户完全不用懂变量
+ 只要会打字、会标【】
+ 技术侧统一解析，不容易错

### 缺点
+ 如果客户自己把【】删了、改了，会匹配不到

---

## 方案2：最专业、企业级标准 → **Word 内容控件 / 书签**
这是**真正商用合同系统**的做法。

### 做法
1. 你提供一个**简易插件/工具栏**（或者教运营人员）
2. 在 Word 里：
**插入 → 文本 → 文档部件 → 域 / 内容控件 / 书签**
每个控件绑定一个**中文名称**，比如：
    - 书签：`客户姓名`
    - 内容控件标题：`身份证号`
3. 客户只需要：
    - 打开模板
    - 把光标放到要插入变量的地方
    - 点一下按钮插入“客户姓名”控件
4. Java 读取 docx，按**书签/内容控件**定位并替换

### 优点
+ 格式不会乱
+ 不会被客户误删
+ 支持重复区域、表格、循环列表
+ 专业、正规

### 缺点
+ 需要教运营/内勤简单操作一次

---

## 方案3：最简单、零操作成本 → **Excel/表单填字段，系统自动套模板**
### 流程
1. 客户上传一个**空白排版好的 Word**（不带任何变量）
2. 在网页上点：
    - 在“甲方”这里插入变量：客户姓名
    - 在“身份证号”这里插入变量：身份证号
    - 在金额处插入变量：合同金额
3. 系统自动在 Word 对应位置打上占位符
4. 后续生成直接替换

### 优点
+ 客户完全不用碰变量
+ 可视化操作
+ 不会出错

### 缺点
+ 前端要做一个简单的模板编辑器

---

## 方案4：最稳、最不容易出问题 → **运营维护模板，客户只选不用改**
### 真实企业常用模式
1. 你们内部运营/产品维护标准模板
2. 客户**只能选模板，不能自己改模板**
3. 客户只需要填：
    - 姓名
    - 金额
    - 日期
等表单信息
4. 系统自动套入对应变量

### 优点
+ 变量永远不会错
+ 格式永远统一
+ 合同合规、风险低

### 缺点
+ 灵活性稍弱

# 缓存一致性

在DB前面加缓存，有一个问题就是缓存和DB的一致性如何保持？因为这条DB的数据，它是两个服务同时操作的

你现在遇到的，是**分布式系统最经典的问题**：
**网关扩容 + 多级缓存 + 两个服务同时改同一条数据 → 缓存一致性怎么保证？**

我直接给你**工业级标准答案**，不绕理论，全部是线上可落地的方案。

---

## 先把你的场景说透
+ 有 **两个服务 A、B** 都会修改同一条 DB 记录
+ 你在 DB 前加了缓存（比如 Redis）
+ 问题：
    1. A 改 DB → 缓存没更
    2. B 改 DB → 缓存也没更
    3. 读到的永远是旧数据
    4. 极端情况出现 **双写冲突、缓存脏数据**

你真正要的不是“强一致”，而是：
**最终一致 + 不出现脏数据 + 高并发下不乱套**

---

## 核心原则（记住这一条就够）
### **缓存不能自己主动计算，只能被动失效**
不要更新缓存，**只删缓存**。

标准套路：
**先写数据库 → 再删除缓存**
绝对不要：先删缓存 → 再写库（会脏读）

---

## 方案1：最简单可靠 → Cache Aside Pattern（企业90%在用）
### 流程（严格按顺序）
1. **读请求：**
    - 读缓存 → 命中直接返回
    - 不命中 → 读DB → 回填缓存
2. **写请求（A服务 或 B服务 修改时）：**
    - **第一步：更新数据库**
    - **第二步：立即删除缓存**
    - 不做缓存更新！只删！

### 为什么这样能保证一致？
+ 两个服务谁改数据，谁就负责**删缓存**
+ 下一次读请求会自动拉最新DB数据回填
+ 最终一致，不会永久脏数据

### 缺点
+ 高并发读写下，会出现**极短暂的旧数据**（毫秒级）
+ 业务能接受就没问题

---

## 方案2：两个服务同时操作 → 必须统一“失效入口”
你现在的坑：
**A、B两个服务都直接操作DB → 两边都要删缓存 → 容易漏删**

### 正确结构
#### 方式A：抽取公共 DAL 层（最佳）
做一个公共组件：
`CommonDataService.updateUser(xxx)`

内部逻辑：

1. 更新DB
2. 删除缓存
3. A、B都调用它，**不直接操作DB**

这样无论谁改，缓存一定删。

#### 方式B：通过 MQ 异步删（分布式最终一致）
1. A/B 服务更新DB
2. 发送一条消息：`cache.evict:userId=123`
3. 统一消费者去删除缓存

优点：

+ 跨服务、跨语言、跨机器都能一致
+ 不会漏删

---

## 方案3：强一致需求？用“分布式锁”
如果你的业务**不能容忍 100ms 脏数据**，比如：

+ 金额、库存、状态机

### 流程
1. 修改前加**分布式锁（Redlock）**
2. 修改DB
3. 删除缓存
4. 释放锁

读请求也要加锁：

+ 加锁
+ 读缓存/DB
+ 释放锁

强一致，但**性能下降**。

---

## 方案4：终极兜底（防止任何情况不一致）
给缓存加**短期过期**
比如 5 秒、30 秒、1 分钟

即使出现脏数据，最多乱一小会儿，自动恢复。

这是**线上最稳的保命手段**。

---

## 针对你当前架构的最佳组合（直接照抄）
### 最终方案：
**Cache Aside + 统一更新入口 + 过期兜底**

1. 读：命中缓存返回，不命中查DB并回填
2. 写：
    - 两个服务统一调用一个公共方法
    - 先更新DB
    - 再删除缓存
3. 缓存设置 30s 过期
4. 关键数据加分布式锁

这样：

+ 性能高
+ 最终一致
+ 双服务修改不乱
+ 不会拖垮DB

---

## 最重要的一句话总结
**两个服务同时操作同一条数据，不要两边都写DB+缓存，
****一定要统一收口，只删缓存不更新缓存，再加过期兜底。**

# 异构系统缓存一致性

好，场景一下就清晰了：
**一个 C 服务、一个 Java 服务，都会改同一张 DB 表，你要在前面加缓存，还想保证一致。**

这种跨语言、异构服务的情况，**不能用本地方法调用、不能共用代码包**，所以方案必须走**网络协议、中间件**来统一。

我直接给你**最稳、成本最低、线上真正在用**的 3 套方案，按推荐优先级排：

---

## 方案1：统一通过 MQ 删缓存（最强、最推荐）
### 适用
+ C、Java 异构服务
+ 跨机器、跨语言、跨团队
+ 不想改动太多原有逻辑

### 原理
谁改 DB，谁就发一条 MQ 消息：
`type=update_user, id=1234`

然后**统一一个消费者去删 Redis**。

### 流程（C 和 Java 完全一样）
1. C / Java 服务
    - 先更新 DB
    - 发一条 MQ（RabbitMQ / RocketMQ / Kafka）
2. 统一消费者（可以用 Java 写一个微服务）
    - 收到消息
    - 执行：`del user:1234`

### 优点
+ 跨语言天然支持
+ 改库必触发删缓存，不会漏
+ 不侵入原有业务
+ 一致性：最终一致（毫秒级）

### 缺点
+ 多一个 MQ 组件
+ 有极短暂延迟（可接受）

---

## 方案2：C 和 Java 各自直接删 Redis（最简单快速）
### 适用
+ 想快速上线
+ 架构简单，不想加 MQ

### 做法
C 和 Java 两边**都内置 Redis 客户端**：

+ C：用 hiredis
+ Java：用 Jedis / Lettuce / Redisson

#### 统一规则（两边必须严格遵守）
1. **先更新 DB**
2. **再删除 Redis key**
绝对不要更新缓存，只删！

### 优点
+ 最快上线
+ 架构简单
+ 一致性不错

### 风险
+ 两边都要维护一套 key 规则，容易写错
+ 一边忘删就会脏数据

### 规避
+ key 规则写文档统一：`user:{id}`
+ 缓存加**5~30s 过期**，兜底

---

## 方案3：建一个“统一数据更新服务”（最规范、最干净）
### 适用
+ 长期架构
+ 不想 C、Java 都耦合 Redis
+ 希望以后扩展方便

### 结构
1. 做一个**独立微服务（Java 或 Go）**
    - 提供 HTTP / gRPC 接口
    - 接口：`/api/updateUser`
2. C 服务 → 调用这个接口
3. Java 服务 → 也调用这个接口
4. 这个统一服务内部：
    - 更新 DB
    - 删除缓存
    - 事务、一致性全部在这里控制

### 优点
+ C、Java 完全不关心缓存
+ 逻辑收口，不会乱
+ 以后加缓存、分库分表都不用改业务

### 缺点
+ 多一个服务，开发量稍大

---

## 针对你现在场景的最佳选择（直接给结论）
### 你这种：C + Java 异构、都操作同一张表
👉 **首选：方案1 MQ 异步删缓存**
👉 快速应急：方案2 两边都直接删 Redis

#### 为什么不推荐其他？
+ 分布式锁太重，影响性能
+ 强一致事务成本极高，网关场景没必要
+ 最终一致完全足够业务使用

---

## 最重要的统一规范（两边必须遵守）
不管你选哪种，**这 3 条是生命线**：

1. **先更新 DB，再删缓存**
2. **绝对不更新缓存，只删除缓存**
3. **缓存必须加过期时间（5~30s）**

满足这三条，**跨语言、双服务修改，永远不会出现长期脏数据**。

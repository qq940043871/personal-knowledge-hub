# 算号服务

那就是我的算号服务，就是现在就是每一个客户注册，我都要给他分配一个有规律的编号。这种情况下，就是我怎么能快速的？就是这么多号不让它成为系统瓶颈？

结合你这个场景：
**给每个客户分配一个有规律的编号（比如 10001、10002… 连续递增），还要高并发、不成为瓶颈**

直接给你**企业级最稳、最快**的方案，不用纠结 UUID / 雪花了。

## 核心结论
你要的是**连续、有规律、自增编号**
👉 必须用：**号段模式（号池模式）**
这是唯一能做到：
**连续不重复 + 高性能 + 不暴露总量（可选）+ 无瓶颈** 的方案

---

## 号段模式原理（一句话）
1. 数据库里只存一个当前最大值：`max_id`
2. 你的算号服务**每次批量拿一段号码**，比如一次拿 1000 个：`[10001, 11000]`
3. 本地内存直接分配，用完再去数据库取下一段
4. 数据库只需要**极少次 IO**，完全不会瓶颈

### 优点
+ 号码**绝对连续、有规律**
+ 性能极高：单机轻松扛 **上万 QPS**
+ 不会因为高并发锁表、死锁
+ 可以轻松**多实例部署**，不重复
+ 想隐藏总量也很容易：起始号从 100000 开始，或加步长

## 具体怎么实现（最简可用版）
### 1. 数据库表（只需要这一张）
```sql
CREATE TABLE customer_id_generator (
  id          int primary key auto_increment,
  biz_type    varchar(32)  not null comment '业务类型：customer',
  current_max bigint       not null default 0,
  step        int          not null default 1000,
  update_time datetime     not null default now(),
  unique key uk_biz_type (biz_type)
);
```

初始化一条：

```sql
INSERT INTO customer_id_generator (biz_type, current_max, step)
VALUES ('customer', 10000, 1000);
```

### 2. 取号逻辑（伪代码）
```plain
// 本地缓存一段号
private long current;
private long end;

// 获取客户编号
public long nextCustomerId() {
  if (current > end) {
    // 去数据库原子更新，获取新号段
    开始事务
    update customer_id_generator
    set current_max = current_max + step
    where biz_type = 'customer'
    returning current_max, step into newMax, step

    current = newMax - step + 1
    end = newMax
    提交事务
  }
  return current++;
}
```

### 3. 关键点
+ **一次取 1000 / 5000 / 10000** 号段
+ 内存分配，**几乎无 IO**
+ 数据库只用一个行锁，**完全不瓶颈**
+ 多实例部署也不会重复
+ 宕机最多浪费一段号，不影响连续性

## 按你的场景选型建议
### 场景 1：必须严格连续（客户编号不能跳号）
👉 **号段模式 + 步长 1**
但步长 1 性能会下降，适合并发不高的后台系统。

### 场景 2：连续即可，允许少量跳号（绝大多数业务）
👉 **号段模式 + 步长 1000**
性能拉满，永远不会瓶颈。

### 场景 3：不想暴露总用户量
👉 号段起始从 **100000、666666、888888** 开始
外部看不出真实注册量。

### 场景 4：超高并发（几万注册/秒）
👉 号段步长调大（5000~10000）
或用美团 Leaf、百度 UidGenerator 这类成熟组件

这种情况下怎么处理？就是客户两个客户同时过来了，然后也都拿到号了，但是另外一个客户由于某种情况失败了，导致这个号并没有真正成功

这是**最经典、最现实**的问题：
**号已经发出去了，但用户注册失败 → 号空了、不连续了。**

你现在面临的本质矛盾只有一个：

## 要么保证性能，要么保证绝对连续
**鱼和熊掌，在高并发下，不可兼得。**

我直接给你行业里通用的 3 种真实处理方案，你按业务容忍度选一个就行。

---

## 方案1：允许空号（90%公司都这么干）
### 做法
+ 号段模式正常发号
+ 注册失败，号就**丢弃**
+ 最终客户编号：1001、1002、1004、1005… 中间空一个

### 为什么可以？
+ 客户**根本看不到别人的编号**
+ 空号不影响业务、不影响统计、不影响对账
+ 性能无敌，永远不瓶颈

### 适合你
**客户编号只内部使用，不对外展示连续感。**

---

## 方案2：注册成功才真正分配号（最严谨、最推荐）
### 核心思路
**号，不在注册请求进来时发，
****而是在用户数据插入数据库成功后再发。**

### 流程
1. 用户提交注册信息
2. 校验参数、验证码、手机号重复等
3. **真正插入用户表成功**
4. 再去生成/分配 customer_id
5. 回填到用户记录

这样：
**失败 = 根本没拿号 → 不会产生空号**

### 高并发怎么不瓶颈？
+ 号段模式一次拿 1000 个
+ 内存发号，几乎零耗时
+ 回填是**事后异步/同步都可以**

这是**电商、金融系统最标准的做法**。

---

## 方案3：真·必须严格连续、不能空号（财务/证书场景）
如果你是这种：

+ 客户编号必须像身份证一样连续
+ 审计要求不能跳号
+ 空号会被监管/客户质疑

### 只能这么做（牺牲性能）
1. **开启数据库事务**
2. 锁号段表，取出下一个号
3. 插入用户
4. 成功则提交，号生效
5. 失败则回滚，号归还

### 缺点
+ 并发高了会**锁等待、性能下降**
+ 无法水平扩展
+ 高并发下一定会成为瓶颈

**除非监管强制，否则绝不推荐。**

# 什么样的数据适合提交审批流 & 审批通过后业务执行失败处理
## 一、哪些数据适合提交到审批流（Flowable通用思路）
核心原则：**提交审批的数据，必须是“业务意图完整、基础合法性校验通过，但还不允许落正式生效状态”的数据**。 不要把脏数据、缺少必填项、逻辑本身就错误的数据丢给审批人去审。

### ✅ 适合进入审批流的数据
1. **业务意图完整，必填字段全部齐全** 比如：预约金签约、订单变更、退款、合同创建；金额、主体、对象、时间、业务类型全部填完。 缺少关键字段直接前端/业务层拦截，**不发起审批**。
2. **基础规则校验已经前置通过** 例如：金额不能为负、客户状态正常、渠道编码合法、不能给自己转账。 这类属于系统硬规则，机器就能判断，不该交给人工审批人来发现。

审批流解决的是**人为决策**：是否同意这次申请；不是用来做参数校验。

3. **属于“变更类、权限受控类业务动作”**
    - 新增/修改合同、调价、退款、预付款托管、多银行签约
    - 权限敏感、资金敏感、风险高的操作
    - 修改后会影响后续业务流程，需要留痕、可回溯的操作
4. **数据状态是「待审批」中间态，尚未写入正式生效业务表** 建议模式：**一张审批业务中间表保存申请数据，审批通过才同步更新主业务表**； 不要直接拿主业务表正在使用的数据丢进审批，审批过程业务不能篡改这份待审数据。

### ❌ 不适合提交审批流的数据
1. 必填缺失、格式错误、基础业务规则不满足；
2. 查询、只读、普通新增不需要人为决策的操作；
3. 实时强交互、高吞吐高频小数据（每一笔都走审批会拖垮性能）；
4. 已经生效、已经完成的业务记录；
5. 依赖外部实时状态（比如银行接口实时可用状态）的数据。

重点区分：

+ **前置校验：系统自动做，不进审批**
+ **审批判断：人工做，只判断“这件事该不该允许做”**

## 二、审批已经通过，但后续业务执行失败怎么办
场景：Flowable审批节点走完，返回审批通过；但是执行业务逻辑时报错：例如银行渠道不可用、余额不足、外部接口超时、数据库异常、约束冲突，业务落库失败。

### 核心矛盾
审批已经通过（流程实例状态：完成），但是**业务没有真正生效**。 此时不能简单把流程回退，因为审批人已经审批完毕，不能再让审批人重复审批。

### 可选处理方案（按项目常用优先级排序）
#### 方案1：业务侧标记「审批已通过，业务执行失败」，人工介入重试（最常用）
1. Flowable流程实例正常标记为完成，**不回退流程**；
2. 业务层增加业务状态： `待审批 → 审批通过(待执行) → 业务执行成功 / 业务执行失败`
3. 执行失败记录失败原因、异常堆栈；提供后台操作员**重试按钮**；
4. 重试的时候：**不再重新走审批流程**，直接执行业务逻辑；
5. 重试多次依旧失败，转人工工单处理。

适用：外部接口波动、临时网络问题、临时资源不足，大部分资金类、签约类业务系统都是这套模式。

⚠️ 风险点： 审批通过≠业务生效。页面上一定要区分展示： “审批已通过，但业务尚未执行成功”，不能给用户造成错觉以为事情办完了。

#### 方案2：补偿+回滚，业务状态置为失败，流程不回退，支持重新发起申请
当失败原因是业务数据本身发生变化（审批的时候没问题，审批完数据变了），重试也无法修复：

1. 业务执行失败，做本地回滚，不生成正式业务单据；
2. 流程实例依旧保持完成；
3. UI提示：审批已同意，但业务执行失败，**需要重新提交申请再次审批**；
4. 用户修改数据后，发起全新流程实例。

适用：审批完成后，外部条件发生不可逆变化，旧申请数据已经不可用。

缺点：需要审批人二次审批，体验一般；适合低频风险高的操作。

#### 方案3：流程不标记完成，增加“业务回调执行节点”（Flowable事务关键点）
这里非常容易踩坑：**不要把业务执行逻辑放在Flowable的事务里面**。 Flowable事务和业务事务如果绑定在一起：业务抛异常，会把“审批通过”也回滚掉，流程会退回到审批节点，审批人明明点了同意，流程又回到待审批，业务混乱。

正确做法：

+ 用户审批人完成审批任务 → Flowable事务提交，流程流转到一个**业务回调服务任务节点**；
+ 这个服务任务内部调用业务代码；
+ 如果业务抛出异常：
    - 不要抛异常给Flowable（否则流程回滚）；
    - 在服务任务内部捕获异常，记录失败，把流程流转到自定义`业务执行失败`的状态节点，流程实例不结束；
    - 可以配置定时任务节点自动重试N次；重试耗尽，停在失败节点等待人工处理。

注意：这里流程没有`完成`，停留在自定义失败节点，可以在流程层面看到失败。但**不能再把任务扔回给审批人**。审批人的工作已经做完。

#### 方案4：事务隔离，绝对避免：审批通过和业务执行原子绑定
❌ 错误设计：审批完成的更新 和 业务生效更新放在同一个事务。 如果业务执行失败，事务回滚，审批结果也消失，审批人已经点同意，流程却回到待审批，属于严重bug。

✅ 原则：**审批结果持久化，和业务生效持久化，两个独立事务**。 审批结果一旦审批人确认，就不允许因为业务执行失败而抹除。

### 三、完整标准时序（推荐落地）
1. 前端提交申请 → **业务层前置全量校验**，校验失败直接返回，不创建流程实例
2. 校验通过：写入业务申请记录【待审批】，创建Flowable流程实例
3. 审批人处理：同意/驳回
    - 驳回：流程结束，业务状态置为审批驳回；
    - 同意：Flowable提交事务，流程流转到业务执行节点，**审批结果落库固化，不可撤销**
4. 调用业务执行逻辑：
    - 成功：业务状态更新生效，流程标记完成；
    - 失败：捕获异常，记录错误信息，业务状态 = `审批通过，业务执行失败`
5. 后台告警通知运营：支持手动重试；重试失败，用户重新提交新申请。

### 四、边界问题
1. **幂等性**：重试业务逻辑必须做幂等，防止多次执行造成重复下单、重复签约。
2. **数据一致性**：一定要业务表保存业务状态，不要完全依赖Flowable流程状态作为业务可信状态。

业务以业务库状态为准，Flowable只当做流程流转和审批留痕组件。

3. **消息/定时任务补偿**：执行失败除了手动重试，可以加定时任务扫描`审批通过待执行`的数据，自动重试几次。

## 第十章 剑圣与食堂：Java 之道与 Spring 的味觉革命

### 高司令与一次 new

Java 大陆的第一课，是剑圣**高司令**（James Gosling 的人格投影）的开山演示——**一次对象的诞生**：

```java
User u = new User("林一码");
```

"这一行里藏着三件事。"剑圣说，"`new` 让 JVM 在**堆**里划一块地；`User()` 是**构造方法**，负责开荒；`u` 是一张**引用**——注意，它是**地图，不是地本身**。两个引用可以指向同一块地，改一处、两处都变——新手村的血案，一半源于没分清'地图'和'地'。"

剑圣又讲了三大心法：

- **封装**：属性藏起来，门面只露方法——**别让人直接伸手进你的口袋**；
- **继承**：父子血脉，复用但也耦合——**改爹，全家遭殃**；
- **多态**：同一句 `animal.speak()`，猫喵狗叫——**调用方写死的是抽象，运行时才定角色**。

"还有接口（interface）：**只说'会什么'，不说'怎么会的'**。它是大陆一切解耦的起点。"

### Spring 食堂：自己种菜 vs 报菜名

大陆中部有一座传奇食堂——**Spring**。它的海报只有一句宣传语：

> **告别自己种菜做饭。报菜名，饭端到你面前。**

"传统写法里，你要什么对象就自己 `new` 什么——自己种菜、洗菜、炒菜。"老码说，"Spring 食堂改成了**控制反转（IoC）**：你只声明'我需要一份 UserDao'，容器造好，从构造器或字段**塞给你**——这一步叫**依赖注入（DI）**。"

"好处是什么？"

"**解耦**。你的代码从此不关心'菜从哪来'——今天给 MySQL 版，明天给 Mock 版，你一行不改。**组装这件事，从此不再是你代码里的责任。**"

"所有饭都现做？"

"不。食堂还有个**单例模式**：默认全店一份实例，人人共享——所以**别在单例 Bean 里存'每个客人自己的数据'**，否则 A 客的账单会出现在 B 客桌上。要存，用方法内局部变量，或 ThreadLocal（但用完必须 remove——这是后话，第十四坑会考）。"

### AOP：写字楼的门禁摄像头

食堂二楼有一面魔法墙——**AOP 切面**。

"日志、权限、事务、监控——这些逻辑像'进门刷脸'，**每层楼都要，又谁都不属于**。"老码说，"把它们从业务代码里抽出来，**横着切**进去：方法执行前打点、执行后记录、抛异常告警。业务代码对此**零感知**。"

"听起来像过滤器？"

"Web 容器里那叫 Filter，是一根烟囱里串着的层；AOP 是给**任意 Bean 的任意方法**装门禁，粒度细得多。Spring 的事务 `@Transactional`，本质就是一个 AOP 切面：**方法进了，事务开档；方法体抛异常，全档回滚**——像游戏存档，Boss 战失败自动读档。"

但老码立刻补了一个著名陷阱（此处先按下，第十四章连环坑揭晓）："记住一句——**事务魔法是'代理'施的。同类内部 this 调用，不路过代理，魔法失效。**"

## 第十一章 十四坑连环阵：老码的错题本

 Java 大陆的禁地里有一座**十四坑连环阵**——每一坑都是一位前辈用生产事故"供"出来的。老码带林一码逐坑试炼，规矩是：**进坑前说出病名，出坑时写下药方。**

**坑一·字符串 +=**：循环里 `s += x`，每次都造一个新字符串——万次循环，疯狂 GC。药方：`StringBuilder.append` 攒一块再交货。

**坑二·Arrays.asList 陷阱**：`Arrays.asList(intArray)` 会把**整个数组当成一个元素**；而且返回的 List 禁改，`add` 直接爆炸。药方：`Arrays.stream(arr).boxed()` 或 `new ArrayList<>(list)` 包装。

**坑三·HashMap 多线程 put**：并发扩容能把自己**打成环**，CPU 100% 死循环；数据凭空丢失。药方：`ConcurrentHashMap`。

**坑四·边遍历边删**：`list.remove(x)` 写在 for 里——要么 `ConcurrentModificationException`，要么**悄悄漏删**（删完 i++ 跳过了下一个）。药方：`iterator.remove()` 或 `removeIf`。

**坑五·ThreadLocal 不 remove**：线程池复用线程，上个请求存进去的用户数据**一直躺在下个线程的口袋里**——内存泄漏 + **串号**（A 用户看到 B 用户的数据，重大安全事故）。药方：`try-finally` 里 `remove()`。

**坑六·volatile 当锁**：`count++` 是"读-改-写"三步，volatile 只保证看得见、不保证原子——十个线程各加一万次，结果不到十万。药方：`AtomicInteger` 或加锁。

**坑七·Executors 快捷线程池**：`newFixedThreadPool` 队列**无界**——任务堆积直接 OOM；`newCachedThreadPool` 线程**无限**——线程爆炸。药方：手动 `new ThreadPoolExecutor`，队列设上限、线程起名字（排查日志全靠名字）、拒绝策略想清楚。

**坑八·@Transactional 同类调用**：`this.doSomething()` 绕过代理，**事务静默失效**——扣款失败也不回滚，查三天查不出原因。药方：注入自身代理调用，或把方法拆到另一个 Bean。（第十章埋的雷，炸了。）

**坑九·构造器循环依赖**：A 要 B、B 要 A，Spring 启动当场罢工。药方：`@Lazy`，或者重新设计——**循环依赖是设计问题的通知单，不是框架 bug**。

**坑十·SQL 拼接**：用户输入 `' OR '1'='1` 拖走全库——**SQL 注入**。药方：`PreparedStatement` / MyBatis 的 `#{}`（预编译是防弹玻璃窗口递条子）；`${}` 是把用户喊话直接贴上墙。

**坑十一·索引悄悄失效**：列上套函数、varchar 列用数字比、`LIKE '%x'` 前置通配——索引瞬间变成全表扫。药方：改写 SQL、右通配、类型对齐。（数据王国的伏笔。）

**坑十二·深分页**：`LIMIT 1000000, 10`——数据库**白扫前一百万行**再扔掉。药方：游标翻页 `WHERE id > 上次最大值`，或延迟关联只翻索引。

**坑十三·长事务**：一个事务里导入十万条——锁拖全库，连接池打满。药方：分批提交，事务越短越好。

**坑十四·接口不幂等**：用户连点两下"支付"，**扣两次款**。药方：Token 防重、数据库唯一索引兜底、幂等键。（消息之谷的伏笔——那里它还会再出现。）

走出阵时，林一码腿都是软的。老码说："十四坑背下来只是及格。真正的功夫是**写代码时脑子里有这十四个坑**——**老手和新手的区别，不是会不会踩坑，是踩坑之前就知道自己在坑边。**"

## 第十二章 JVM 皇宫：类加载、垃圾工与栈顶对决

### 双亲委派：收破烂前先问祖上

JVM 皇宫的**类加载庭**门口，挂着一条祖训：

> **收到一个类，先问上一级：你要不要？上级不要，我才能要。**
> ——双亲委派模型

"这是防什么？"

"**防假冒**。假如有人写了一个假的 `java.lang.String` 想混进皇宫——它先被递给祖上（启动类加载器），祖上一查：我早有正品，假冒货当场拒收。**核心类库的安全，靠的是'长辈优先'。**"

"什么时候要破坏这条规矩？"

"Web 容器。每个应用要有**自己的**类加载器——同一个类名，A 应用和 B 应用各装各的，**互不串门**。热部署更是直接扔掉旧加载器、换新的。这是后话，手写 Web 容器卷见。"

### 运行时数据区：皇宫五大分区

皇宫的地产图上画着五个区：

- **堆（Heap）**：所有对象的公共仓库，**垃圾的主产区**，GC 的主战场；线程共享；
- **虚拟机栈**：每线程一个，方法调用的"一次性餐盘"——每调一个方法**叠一个栈帧**，返回就撤盘；叠太深 = `StackOverflowError`；
- **程序计数器**：每线程一枚**书签**，记着当前执行到哪条指令——线程切走再切回，靠它续命；
- **方法区/元空间**：类的档案室——类元信息、常量池；
- **本地方法栈**：native 代码的专用餐盘区。

### GC 清洁工：从引用计数到分代

皇宫雇了三代清洁工：

"第一代，**引用计数**：每个对象挂个计数牌，谁引用+1，谁断开-1，归零就扫。"老码说，"但有**死角**：两个对象互相引用，计数永远是 1，谁也扫不走——**循环引用**。Java 不用它。"

"第二代，**可达性分析**：从一堆'**GC Roots**'（栈上引用、静态变量、常量、JNI 引用）出发**顺藤摸瓜**——摸不到的对象，就是孤儿，扫。循环引用不再是死角。"

"第三代，**分代收集**——这是集大成者：

> 基于'**大部分对象朝生暮死**'的经验：新对象进 **Eden**（幼儿园）；幼儿园满，触发 **Minor GC**，活下来的搬进**幸存区**；每挺过一轮 GC 涨一岁，岁数够大，**晋升老年代**。
> 幼儿园常扫、快扫；老年代少扫、深扫。各代用各代的算法。"

"那 GC 扫描时，业务线程还能跑吗？"

"问到了最难的一关。"老码神色一凛，"**一边开会一边打扫，怎么保证不踩脏数据？** 工程师们用'**暂停你几毫秒（STW）**'换安全，又发明了各种花样减少暂停——CMS、G1、ZGC……这一路的进化史，就是'**把停顿越压越短**'的历史。也是你未来手写 JVM 时最硬的那块骨头。"

### 内存屏障与锁的四段升级

皇宫顶层的**并发比武场**，立着 JMM（Java 内存模型）的告示：每个线程有自己的**工作内存**（副本），主内存是账本——**副本不同步，就是一切并发幽灵的根源**。`volatile` 是一道**内存屏障**：写了立刻刷账本，读了强制看最新。

锁的修炼分四段：**无锁 → 偏向锁**（只有一个线程就用不着真锁，门上贴张条）**→ 轻量级锁**（CAS 自旋，原地转圈等）**→ 重量级锁**（找操作系统帮忙排队）。**锁升级是"从客气到动真格"的阶梯。**

## 第十三章 Spring 城邦全景：从 MVC 到微服务的联邦

出了皇宫，是 Java 大陆最繁华的**Spring 城邦群**。

### DispatcherServlet：所有访客先到前台

"Web 层的大门口只有一个人：**DispatcherServlet 前台**。"老码说，"所有 HTTP 访客先到前台，前台查通讯录（HandlerMapping：哪个方法管这个路径），带客人去对的部门；部门干完活，结果回前台统一包装成 HTTP 响应。**参数自动装进对象（数据绑定），装完还体检（@Valid 校验）**——前台连违禁品都帮你查了。"

"异常呢？"

"全城一个'投诉受理处'——`@RestControllerAdvice`。一处捕获，全站接口返回统一格式。别让每个 Controller 自己写 try-catch，那是对投诉受理处的侮辱。"

### MyBatis：厨师只下单，菜谱挂墙上

数据访问层的招牌是**MyBatis**：**SQL 写在 XML 里（菜谱单独挂墙），Java 只管调接口（厨师只下单）**。动态 SQL 像"点奶茶"——`<if>` 标签按需勾选：去冰、三分糖、加珍珠，最后拼出一杯定制 SQL。

"它和 JPA 怎么选？"

"**要 SQL 的绝对控制权，用 MyBatis——复杂报表、性能敏感的场景它是王者；要少写代码、快速 CRUD，用 JPA。** 两大门派之争打了十几年，答案是看团队看场景。"

### 微服务联邦：从单体到分布式

城邦最深处，是通往**分布式联邦**的使节区。老码指着一张地图：

"单体应用是**一家大饭店**：前厅后厨一个屋檐，人多之后互相踩脚。**微服务是把大饭店拆成美食街**——每个档口独立经营：用户档、订单档、支付档，谁火爆谁扩张，谁坏了不殃及全场。"

"代价呢？"

"**分布式带来的所有问题你都得接**：档口之间怎么找到彼此（注册中心 Nacos——黄页通讯录）、怎么统一进门（Gateway 网关——小区保安总机）、怎么互相说话（OpenFeign——自动拨号代打电话的秘书）、一个档口倒了他把整条街拖垮怎么办（Sentinel 熔断——电路保险丝，电流超标先断自己保全家）。"

老码最后叮嘱："**拆微服务不是赶时髦，是为'独立部署、独立扩容、故障隔离'这三件事买单。** 单体扛得住就别拆——**分布式不是免费午餐，每一道菜都标着复杂性价签。**"

Maven 城的物流官补了最后一课："构建打包走**流水线生命周期**：compile → test → package → install，喊一声后头的工序自动全跑。依赖像快递自动捎货：A 带进 B、B 带进 C，版本冲突就 `exclusion` 拒收。**坐标（groupId:artifactId:version）是全球唯一身份证条形码。**"

## 特别篇 · GC 之夜：皇宫大扫除

> 皇宫的清洁工最怕两种夜：
> 一种是扫不完的夜，一种是——**怎么扫都扫不动的夜**。
> ——JVM 皇宫清洁工守则第一条

### 阴云：接口突然变"心电图"

十四坑连环阵通关后的第三天，Java 大陆东部一家电商老兵的营地里响起了警报。林一码一行赶到时，监控大屏上的接口耗时曲线画出了所有人最不想看到的形状——**心电图**。

每隔 30 秒，一根 800 毫秒的尖刺拔地而起，然后回落，再等 30 秒，再起。

"这不是流量毛刺。"老码扫了一眼，"这是**节律性的疼痛**——周期 = 30 秒。什么东西会这么守时？"

"定时任务？缓存过期？"小蝶猜。

"**GC。**"老龟——不，这里还没有老龟。**是老码**，他调出 GC 日志，一行行扫过去：

```
[Full GC (Ergonomics)  8192M->8103M(8192M), 0.79 sec]
```

"Full GC，30 秒一次，每次 0.8 秒，**回收前 8192M、回收后 8103M**。"林一码念完，声音冷了下来，"**只回收了 89M。堆快满了，却几乎扫不出垃圾——**这不是垃圾太多，这是**活着的对象太多**。"

### 诊断：8 个 G 的"活人"

jstat 连看几个周期：老年代占用 99%，Full GC 后 99%——**垃圾回收器在工作，但老年代里几乎没有垃圾**。

"那 8 个 G 的'活人'是谁？"老码把 `jmap -histo:live 进程号 | head -30` 甩上大屏。直方图的第一行答案呼之欲出：

```
 [I                          1,204  4,120,992,880
 com.shop.order.dto.OrderDTO  8,913,002  2,133,120,480
```

**一个巨大的 int 数组（4.1G）+ 八百九十一万个 OrderDTO（2.1G）。**

顺着引用链查下去，真凶的形状让全场倒吸冷气：一个"**热点订单内存缓存**"，设计初衷是"存最近一小时的热点订单"——但代码里的判定条件写反了：

```java
if (!cache.containsKey(orderId)) {
    cache.put(orderId, order);   // 原意：只缓存热订单
}
// 热点判定：被查询 2 次以上才入缓存 —— 但条件写成了 >
if (queryCount > 2) { ... }     // 实际：永不入缓存？
```

真相更讽刺：**热点判定逻辑根本没生效**，另一个兜底分支把**全量订单**都塞了进去，且无界、无过期。堆 8G，全量订单 8.3G——**应用把整个数据库穿在了身上，还问为什么喘不过气**。

### 会诊：三步走

> **第一步·止血（今夜）**：把"全量缓存"下线，热点订单改走 Redis；堆内存立刻回落，心电图消失。业务可用性恢复优先——**先让病人出 ICU，再谈健身**；
>
> **第二步·正骨（本周）**：真需要本地缓存的地方，上 **Caffeine**：`maximumSize` + `expireAfterWrite` + 淘汰监听——**任何本地缓存，必须有界、有期、有监控**；大数组（那个 4.1G 的 int 统计）迁出堆外或换存储；
>
> **第三步·练体（本月）**：给 JVM 配齐"体检套餐"——`-Xlog:gc*` 常开、`-XX:+HeapDumpOnOutOfMemoryError` 留遗书、G1 换上并按业务峰值的 1.5 倍规划堆——**让 GC 从'30 秒一次的心绞痛'变成'日常慢跑'**。

### 复盘：清洁工哲学

撤离前，老码在营地的白板上写下了这场夜战的总结。据说后来被 Java 大陆所有的 JVM 皇宫裱了起来：

> **一、Full GC 频繁，先分清两种病："垃圾多，扫得动"（对象生命周期短、 Survivor 太小）vs "活人多，扫不动"（缓存无界、集合泄漏）。药方完全相反。**
>
> **二、jmap -histo:live 是最便宜的 X 光——一分钟看到 8 个 G 里住着谁。**
>
> **三、任何"内存缓存"上线前，回答三个问题：存多少（上限）、活多久（过期）、满了怎么办（淘汰）。答不上来，就是给 OOM 巨兽寄存粮。**
>
> **四、GC 的终极哲学：垃圾回收器不生产垃圾，它只是垃圾的搬运工——**你写的每一行"先不清理了"，都是请给清洁工的加班单。

**【本场掉落】**：GC 心电图的读法、jstat/jmap -histo:live、两种 Full GC 病型的鉴别诊断、Caffeine 三件套（有界/过期/淘汰）、G1 与堆规划。

## 特别篇 二 · 切面暗战：谁先谁后，生死立判

> Spring 食堂的后厨有一条不成文的规矩：
> 同时来五个"门禁"检查一位客人，**谁先查、谁后查，出了事各打五十大板**。
> ——后厨黑板报·切面专栏

### 案发：一次扣款，两种结局

营地里两个项目组打架了。同样的三道切面——**日志切面、事务切面、幂等锁切面**——只是执行顺序不同，结果天差地别：

> **A 组**：锁 → 事务 → 日志。扣款接口稳如泰山；
> **B 组**：事务 → 锁 → 日志。**高峰期出现重复扣款！**

"切面不是名单上挂个名就完事，"老码把两组的执行轨迹拍在桌上，"**它们是一条责任链，顺序就是因果。** 看清楚 B 组发生了什么——"

```
B 组顺序：事务切面开档 → 锁切面拿锁 → 业务执行 → 锁切面还锁 → 事务切面提交
```

"**锁在事务里面！** 还锁的那一刻，**事务还没提交**——第二个请求瞬间抢到锁、进事务、读余额——**读到的是第一个事务还没提交的旧数据**。锁形同虚设，这就是**'锁在事务内'的经典破防**。"

### 正解：锁要罩住事务

"A 组为什么对？"

"**锁在最外层**：拿锁 → 开事务 → 干活 → **提交事务** → 才还锁。第二个请求必须等**完整闭环**结束才能进场——**锁的生命周期必须覆盖事务的生命周期**。"

老码在黑板上写下切面设计的军规三则：

> **一、画执行轨迹图，再定 @Order**——把每个切面的 before/after 画成洋葱圈，**谁包谁，一眼定生死**；
> **二、锁、幂等这些'门口的岗哨'，永远放最外圈**——它们的职责是"**放行谁**"，必须先于一切"进门后的服务"（事务、日志、审计）；
> **三、事务切面永远贴着业务**——它是"干活时的保险"，不是"门口的保安"。**把保险装在门口，等于没保险**。

### 深水区：this 调用的二次暗雷

暗战还没完。B 组改完顺序，第二天又炸——**同类内部调用，事务又失效了**（十四坑之坑八的实弹演习）。

"这次不是顺序问题，是**代理问题**。"老码祭出终极大招，"给你们看一眼'魔法的后台'——"

```java
// 你以为的调用
orderService.pay(order);
// 实际发生的调用
orderServiceProxy.pay(order);  // 代理：先开事务 → 再执行你的方法 → 提交/回滚
```

"**事务、日志、锁的魔法，全由代理（Proxy）施加。** 同类里写 `this.check()`——**check 不经过代理，魔法统统失效**。"

**三味解药**，按优雅程度排序：

> 1. **拆 Bean**：把 check 挪到另一个 Service——**结构上的问题，用结构解决**；
> 2. **自注入**：`@Autowired private OrderService self;` 调 `self.check()`——**走代理的自己的影子**；
> 3. **`AopContext.currentProxy()`**：开 `exposeProxy` 强取代理——**能用，但这是'知道自己在做坏事'的写法，最后再想**。

### 战后

老码在秘籍上为切面暗战收尾：

> **"切面是强大到危险的东西：
> 它让你不碰业务代码就能改变业务行为——
> 这意味着，出问题时，**行为和代码是分离的**。
> 所以用切面的人必须多做一个动作：
> **把'洋葱圈'画出来，贴在项目最显眼的地方。**
> 让每一个后来者知道：
> 他的一次注解，先后于谁的枪口。"**

**【本场掉落】**：切面执行顺序与 @Order、"锁罩事务"军规、代理机制与 this 失效、自注入三解药、行为与代码分离的运维代价。

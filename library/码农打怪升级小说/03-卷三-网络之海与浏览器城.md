## 第七章 江河的暗语：TCP、HTTP 与 HTTPS

大陆南边是**网络之海**——所有消息都要过海。海上有渡轮、灯塔、邮局，还有海盗。

### 三次握手：喂？听得到吗？

上船前，老码演示了海上通话的标准流程：

> "喂，听得到吗？"（SYN）
> "听得到！你听得到我吗？"（SYN+ACK）
> "听得到，开始说正事。"（ACK）

"这叫**三次握手（Three-way Handshake）**。"老码说，"两步不够——只确认了'你能听到'，没确认'我能听到你的回复'。三步，**双方都确认了'对方既能收也能发'**，才开始传真货。"

挂电话也有讲究——**四次挥手**。老码补了一个海规："分手后，主动挂断的一方要**等两分钟（2MSL）才能复航**，确保海面上最后几个漂着的'再见'不认错人。"

"这个海规会闯祸，你记下：高并发短连接的系统，一秒建一万次通话、挂一万次， ports 里的端口全在'分手等待'——**TIME_WAIT 泛滥，新连接无端口可用**。这是大促之夜的经典惨案，解法是内核参数调优加长连接复用。"

### HTTP 进化史：单车道 → 高架 → 磁悬浮

渡轮票务处立着三块牌子，记录着 **HTTP** 的进化：

- **HTTP/1.1 单车道**：一次通话运一件货，货到了才能下一件——队头一堵，全线死等。
- **HTTP/2 高架桥**：**多路复用**，一条通话里跑无限件货，编号互不干扰。
- **HTTP/3 磁悬浮**：把路基从 TCP 换成 **UDP**（QUIC），握手更快、切换基站不断线。

"但要提醒你，"老码说，"**升级不一定更快**。我见过 HTTP/2 开了反而变慢的现场——多路复用挤在一条 TCP 连接上，丢一个包，所有流一起堵。技术没有银弹，只有场景。"

### HTTPS：验介绍信，对暗号，再加密

海峡上有海盗（**中间人**），裸奔的 HTTP 信件会被偷看、篡改。于是有了 **HTTPS**，开船前三步：

1. **验介绍信**：服务器出示**数字证书**——由海务大衙门（CA）盖章，证明'我就是我'；
2. **对暗号**：双方用非对称加密协商出一把**会话密钥**——这步的数学魔法是：公开的锁、私藏的钥匙；
3. **上锁运输**：之后的货全部用对称密钥加密——快。

"讲个真实惨案。"老码说，"某天全站打不开，排查半天——**证书过期了**。就这一件事。所以后来运维的老规矩：证书自动续期（certbot）+ 到期前多地监控。**最朴素的故障，往往最致命。**"

还有一宗：**DNS 污染**——海盗在邮局门口冒充指路牌，把用户引到假岛。解法是加密解析（DoH）加多地拨测监控。

**林一码的海图总结**：一次"输入网址到看到页面"，要经过 **DNS 邮局（找地址）→ TCP 握手（建交）→ TLS 握手（对暗号）→ HTTP 运货（拿 HTML）**——而这还只是万里长征第一步。

## 第八章 浏览器城：光影魔法与水密舱

海对岸就是**浏览器城**——小蝶的故乡。这座城把 HTML、CSS、JavaScript 三种原材料，变成人类眼前的光影。

### 水密舱：多进程架构

进城先看护城河设计：城不是一座堡垒，而是**一队游轮**——**中央总管（浏览器主进程）、每个标签页一艘独立游轮（渲染进程）、一位专属画师（GPU 进程）**。

"为什么这么铺张？"林一码问。

"**水密舱**。"小蝶说，"一个网页崩了，沉的是它那一艘船，其他标签页照常航行。要是把全城的网页塞进一艘船——一个恶意页面就能带全城陪葬。**隔离，是安全的第一课。** 渲染进程还是个沙箱，里面的代码想碰你的文件系统？门都没有。"

### 渲染流水线：从文本到光影

小蝶带林一码参观了画室的四道工序：

1. **解析 HTML → DOM 树**：标签切词、按层级挂树——页面的"户口本"；
2. **解析 CSS → CSSOM 树**：样式的"家规"；
3. **合体 → 渲染树 → 布局（Layout）**：算出每个盒子的大小与位置——**盒模型**，每个元素都是一个带内衬（padding）、边框（border）、外距（margin）的盒子；
4. **绘制（Paint）与合成（Composite）**：画到图层上，GPU 拼贴上屏。

"两个词你要背下来：**回流（Reflow）与重绘（Repaint）**。"小蝶说，"改个颜色，只**补漆**，便宜；改个宽高位置，**动墙**，从布局开始全链重算——**改一个 width，祖先子孙层层连坐**，像推倒的多米诺。所以动画要用 transform 位移，别改 top/left——让 GPU 搬，别让 CPU 量。"

### 事件循环：先收桌上盘子，再接新客

城的调度室里有一台永不停歇的转盘——**事件循环（Event Loop）**：

> 同步任务做完 → 清空**微任务**（Promise、MutationObserver）→ 取**一个**宏任务（定时器、点击）→ 再清微任务 → 该渲染渲染 → 循环往复。

"微任务是 VIP 插队单，但**必须在本轮清空**才轮到下一个宏任务。"小蝶说，"面试官最爱考 setTimeout 和 Promise 谁先跑——记住：**先收桌上盘子（微），再接新客（宏）**。"

### 缓存幽灵：发版日，用户集体活在过去

城里展示柜封存着一桩经典事故：

> 发版日，代码全新、服务器全新，用户打开却全是**旧页面**。回滚也没用——因为回滚的也是"旧"，用户看到的还是"更旧"。

"元凶：**HTTP 缓存**。"小蝶解释，"缓存分两种：**强缓存**——保质期内（Cache-Control: max-age）直接用本地货，都不问厨房；**协商缓存**——保质期过了，问一句厨房'改没改'（带 ETag），没改回一句 **304 Not Modified**，空手而归却省下全部行李。"

"事故的真相是：HTML 被强缓存太久，新版的 JS 文件名（带 hash）都不知道。**修复配方**：HTML 用协商缓存，JS/CSS 用文件名 hash + 长强缓存——发版即新，命中照旧。**再配 CDN 刷新。**"

"**缓存是性能之友，也是一致性之敌。** 你在 Redis 王国会再遇这句话。"老码在一旁补刀。

### XSS：一条评论偷走全站 Cookie

临走前，安全官给两人上了一课。展示柜里另一桩案子：

> 评论区允许直接渲染用户输入。某个用户发了条评论，内容是一段 `<script>`。所有看过这条评论的人，Cookie 被神不知鬼不觉地发往海盗港。

"这叫 **XSS 跨站脚本**。"安全官说，"**用户输入是不可信的**——展示前要消毒（转义/DOMPurify），再加 **CSP** 内容安全策略，规定'哪里的代码才有资格执行'。同源策略是门禁：协议+域名+端口，差一个字都算外人；CORS 是给外区访客发的临时通行证——发不发、发给谁，服务器说了算。"

## 第九章 海峡要塞：Nginx 经纪人与它的分身术

浏览器城和大陆腹地之间，横着一条最繁忙的海峡。海峡口的**NG 要塞**，是全大陆流量进门的第一站。

### 经纪人：反向代理

"明星为什么需要经纪人？"要塞官吏问。

"挡私生饭？安排档期？"

"都对，但最核心的是：**对外只有一个电话号码，身后多少位真人，外界永远不知道**。"官吏说，"这就是**反向代理**。客户端以为自己在跟服务器说话，其实请求先进要塞，要塞按规矩转给**内网的真实服务器**——真实 IP 从不出镜，攻击面瞬间缩小。"

"那**正向代理**呢？"

"反过来——**躲在客户端身后**。翻墙工具就是它：服务器不知道真正的访问者是谁。记住口诀：**正向代理藏客户端，反向代理藏服务器。**"

### 分身术：负载均衡四式

要塞背后通常站着好几台真实服务器，流量怎么分？官吏演示了四种分身术：

- **轮询**：流水席，一人一桌挨个来——最公平；
- **加权轮询**：大饭店多分几桌——机器配置不同，强者多劳；
- **ip_hash**：老顾客固定给熟客经理——同一 IP 永远同一台，会话不用搬家；
- **least_conn**：谁闲找谁——处理时长悬殊时最稳。

"配上**健康检查**：连续犯三次错的服务器**停职**（max_fails/fail_timeout），病好了自动复岗；再养一台**替补（backup）**，平时坐在替补席，主力全倒它顶上。"

"要是流量大到要塞自己也顶不住呢？"

"要塞分层：**LVS/SLB 在四层**管端口转发，快；**Nginx 在七层**看内容转发，灵活。再往上加 **CDN**——把静态货提前囤到全球各地的前置仓，用户就近取货。这一整套，就是'**日请求从百万到八亿**'那场远征的地图。"

### 限流：闸机与插队

大促前夕，要塞演练"**限流**"。官吏给了四件兵器：

1. **固定窗口**：每分钟最多 N 个——简单，但窗口边界能塞双倍；
2. **滑动窗口**：窗口会滑，边界作弊失效；
3. **令牌桶**：系统定期发币，**持币入场**——允许合理突发；
4. **漏桶**：出口恒速滴水——把洪峰削成平流。

"限流是**主动牺牲一部分体验，保住整体存活**。"官吏说，"这句话很冷，但每个撑过大促的老兵都懂：**全挂，等于全输；限流，还赢一半。**"

## 特别篇 · 大促前夜：TIME_WAIT 风暴

> 海峡要塞的档案柜里，有一张被翻烂的纸条：
> **"28000 个端口，正在集体'分手等待'。"**
> ——那是某年大促前夜，值守老兵留下的遗言式笔记。

### 战前：一场没人当回事的演练

大促前 48 小时，要塞演练。压测流量只开到预估的六成，一个不起眼的告警闪了一下，又灭了：

> **端口使用率 62%**

值班的新兵看了一眼："还没到阈值，先不管。"

林一码盯着那个数字，忽然想起老码在渡轮上讲过的海规——**挂断的一方要等两分钟（2MSL）才能复航**。他心里咯噔一下：压测六成流量，端口已经 62%？

他抓过终端，敲下那条经典的一行：

```
ss -s | grep -i timewait
```

屏幕跳出的数字让他头皮发麻：**TIME_WAIT：18402**。

"风暴已经在路上了。"

### 战时：28000 个分手

大促开始。第 11 分钟，预警曲线像被拽着往上拽——**TIME_WAIT：27,833**。

第 19 分钟，第一声惊雷：

> **connect: Cannot assign requested address**

新连接**没有端口可用了**。每一次 HTTP 短连接（建交→运输→挂断），都会留下一个"分手等待"的 TIME_WAIT 占着端口——**大促的每一秒，都在举办上万场分手仪式**。而这座岛的临时港口（本地临时端口池）总共只有几万个泊位。

"关都关不掉吗？！"

"**这就是它可怕的地方——它不是 bug，它是协议的设计。**"老码赶到，"那两分钟的等待，是为了确认海面上最后的'再见'不认错人，防止旧连接的幽灵包污染新连接。**你不能取消等待，你只能少分手、多复用、扩大港池。**"

### 战术：三招退敌

> **第一招·复用（治本）**：把服务的出站连接改成长连接池——**一次建交，多次运输**。HTTP 客户端开 keep-alive，连接池上限、空闲回收全部配齐。**握手从每请求一次变成每实例一次，TIME_WAIT 直接断崖**；
>
> **第二招·开门（治标）**：内核参数三连——`tcp_tw_reuse=1`（允许主动方安全复用等待中的端口，配合时间戳防幽灵包）、`tcp_max_tw_buckets` 调大（提高"分手所"容量，超出者强制清场）、`ip_local_port_range` 拓宽到 `1024 65535`（**港池扩容一倍**）；
>
> **第三招·改命（釜底抽薪）**：查罪魁——一个轮询任务在用**每次新建短连接**的方式调下游！改成连接池 + 批量接口，**风暴的源头直接消失**。

三招落下，20 分钟后监控回绿：**TIME_WAIT：3411**，端口使用率 8%。

### 战后：老兵的笔记

要塞档案柜里，那张烂纸条旁边多了一行新字，是林一码添的：

> **"TIME_WAIT 不是敌人，是协议的教养。
> 但高并发短连接，就是把教养当成本。
> ——长连接，是并发世界的礼貌，也是性能。"**

以及一条被他抄进秘籍的排障口诀：

> **看到 "Cannot assign requested address"——**
> **先看 TIME_WAIT，再看端口池，最后查谁在狂建短连接。**

**【本场掉落】**：TIME_WAIT 的 2MSL 本质、tcp_tw_reuse 与时间戳、临时端口池、长连接池化、演练告警"闪一下"的教训（**阈值告警要看趋势，不是只看越线**）。

## 特别篇 二 · 缓存幽灵：发版日的平行世界

> 浏览器城的都市传说里，有一个「缓存幽灵」：
> 它不吓人，它只是**让一部分人永远活在过去**。
> ——城里人叫它"我明明更新了啊"

### 事故：两个世界

那是一次再普通不过的发版。前端姑娘小蝶把新页面推上服务器，检查、验收、下班——一切完美。

第二天上午，客服爆炸了：

> 用户 A：新功能好用！
> 用户 B：什么新功能？我界面上根本没有！
> 用户 C：我这儿**一半新一半旧**，按钮点了没反应！

同一个时刻，同一个网址——**三个人，三个平行世界**。

"这就是缓存幽灵的三种形态。"小蝶带上工具，"**A 拿到了新世界；B 被强缓存锁死在旧世界；C 最可怕——新旧混装，HTML 是新的，JS 是旧的（或反过来），接口对不上，页面精神分裂。**"

### 逐层揭皮

**第一层·问清楚"谁旧"**：让用户截图 + F12 Network 面板核对资源版本。"凭感觉猜'是不是缓存'，是新手病——**先拿到证据：哪个文件、哪个版本、From memory cache 还是 From disk cache 还是 200**。"

**第二层·找出锁**：B 用户的 HTML 响应头里赫然写着：

```
Cache-Control: max-age=31536000
```

"**HTML 被强缓存了一年！** 发版对它来说等于不存在——它在保质期内根本不会来问服务器。"小蝶倒吸凉气，"更糟的是 CDN 也信了这套头——**边缘节点把旧 HTML 分发给了半个城**。"

**第三层·解出 C 的分裂**：C 的 HTML 是新的（引用 v2 的 JS），但 v2 的 JS 文件名没带 hash，浏览器用了本地缓存的 v1——**新剧本，旧演员**。

### 驱灵术：一套组合拳

驱灵的配方，后来成了全城发版的圣经：

> **1 · HTML：协商缓存**——`Cache-Control: no-cache`（意思是"每次都要来问"）+ ETag/Last-Modified。**HTML 永远最新**，代价只是每次一趟 304 的问答；
> **2 · JS/CSS/图片：文件名加 hash + 强缓存一年**——`app.a3f9c2.js`。**内容一变，名字就变，"缓存"自然失效**——这是最优雅的失效：**不改缓存，改地址**；
> **3 · 发版流程**：先传静态资源（新 JS 先就位）→ 再发 HTML（剧本最后翻篇）→ **回滚顺序反过来**——**先换演员，再换剧本**，C 型分裂就永远不会发生；
> **4 · CDN**：发版后主动**刷新缓存目录**（purge），别等 TTL 自然过期；HTML 的 CDN 缓存时间设短或直回源。

组合拳落地后的第一个发版日，客服异常安静。小蝶在黑板上写下驱灵咒语：

> **"内容不变，名字不变，缓存永生；
> 内容一变，名字必变，缓存自灭。
> ——让失效发生在'名字'上，而不是'时间'上。**

### 尾声：幽灵的低语

临走前，小蝶盯着监控上一条残余的旧版请求（某个偏僻节点还在发旧 hash 的请求），忽然低声说：

"知道缓存幽灵最像什么吗？像**分布式的数据一致性**——你在 Java 大陆会遇到主从延迟，在消息之谷会遇到重复投递，它们都是同一个哲学问题的化身：**'我的世界'和'你的世界'，凭什么必须一样？**

"缓存的世界里没有'立刻'，只有'**多久以内**'。**接受这个设定，再设计你愿意等多久——这就是全部的缓存策略学。**"

**【本场掉落】**：强缓存/协商缓存分层策略、文件名 hash 失效法、先资源后 HTML 的发版顺序、CDN purge、缓存与分布式一致性的同构。

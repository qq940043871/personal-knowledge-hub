## 第十四章 MySQL 王国：图书馆、时光机与闪回神术

### Buffer Pool：畅销书摆前台，库房在郊区

 MySQL 王国的主殿里，立着一条国训：

> **磁盘是仓库，内存才是柜台。**

"王国的命脉叫 **Buffer Pool**。"老国王说，"所有读写先走内存柜台：读——畅销书（热数据页）直接从柜台拿；写——**先改柜台上的书，标记'脏页'，后台慢慢写回郊区仓库**。"

"那改了没落盘，突然断电呢？"

"问到王国最深的恐惧了。所以我们有**日志三兄弟**：

- **Redo Log（流水账）**：改动先记流水账并落盘——断电了，**凭流水账把没写完的重做一遍**（Write-Ahead Logging，先记账再干活）；
- **Undo Log（后悔药）**：每次改动前留底——要回滚，按底稿撤销；
- **Double Write（安全气囊）**：怕写页写到一半断电产生'半页残页'，先抄一份完整页到安全区。"

"这一整套哲学，你记住八个字：**先记日志，再动数据。** 日后你手写数据库，这就是第一块基石。"

### B+ 树图书馆：三层楼住两千万行

王国最大的藏书楼就是那棵传说中的 **B+ 树**：

- **上层只放指路牌（索引节点）**，**所有真实数据全在一楼（叶子节点）**；
- 一楼的叶子之间**手拉手串成有序链**；
- 王国的"书"按 16KB 一页装订，一页住几十行，上层一页能指路上千个孩子。

"三层楼，就能住下约 **两千万行**——任何一次查找，最多翻三次楼。"老国王说，"这就是为什么我们常说'**索引查询是常数级体验**'。"

**回表**则是馆里的另一个人情规则：你查二级索引（比如按姓名建的目录），目录上只记着**主键**——拿着主键还得**回一楼书架取完整一行**。要是目录上直接印着你查的答案（比如"姓名→年龄"的**覆盖索引**），就**不用回表**，快一大截。

"还有**最左前缀**：复合索引像电话簿**先姓后名**——跳过姓直接查名，查不到。`WHERE b=1 AND a=2` 在 (a,b) 索引上照样能用 a——优化器会帮你排序，但**跳过 a 只查 b，神仙难救**。"

### MVCC 时光机：各看各的快照

王国的传说级神器，是**多版本并发控制（MVCC）**：

"每一行数据都拖着一条**历史版本链**（靠 Undo Log 串起来）。每个事务进场时领一张'**快照票**'——决定它看哪个版本。**读的人看旧照片，写的人写新数据，互不排队。**"

"这就是'读写不阻塞'的秘密。但它有个惊人的副产品——**幻读防线**。可重复读级别下，你的快照锁定在进场那一刻；写操作还会把'**连空地都锁上**'（**间隙锁**：考场防作弊，把空座位也封了）——防止别人往你看过的范围里插新行。代价就是：间隙锁是**死锁和锁超时的惯犯**，这也是很多老兵把隔离级别降为读已提交的原因。"

### 死锁法庭：独木桥上的判官

法庭上正在审一桩死锁案：事务 A 握着行 1 要行 2，事务 B 握着行 2 要行 1——独木桥两头犟驴。

"InnoDB 里有位**判官（死锁检测）**：发现环路，**挑损失小的一方当祭品**（回滚它），放行另一方。"老国王说，"工程戒律只有三条：**按同一顺序访问资源、事务要短、索引要对**（索引错→锁范围大→更容易撞）。"

### 闪回神术：binlog 千里救数据

王国的镇国之宝，是**主从复制**用的 **binlog**——它把每一笔改动都记成操作录像。

**名场面**：某夜值班手滑，一条 `UPDATE` 忘了带 `WHERE`，全表工资被改错。

> 第一步：**立刻锁库止血**，别让脏数据扩散；
> 第二步：`mysqlbinlog` 从录像带里**截取那条误操作之前的位置点**；
> 第三步：把录像**倒放闪回**（或用备份+录像重放到误操作前一秒），数据归位。

"binlog 本是给从库当教学录像带的，关键时刻却能救命。"老国王说，"配套制度：**危险语句上工单审核、生产库默认开安全模式（safe-updates）、最好配上延迟从库（故意慢半小时）当'后悔药仓'。**"

王国的另一根支柱是**主从复制**：总部（主库）发录像，分店（从库）照做。**半同步复制**=至少等一家分店**签收回执**才确认成功——防"主库宕机丢录像"。但注意分店的录像回放可能延迟——**主从延迟**的现场是：用户刚下单，刷新页面订单"消失"了（读到从库旧数据）。解法：读写分离路由到主库、并行复制。

## 第十五章 Redis 国：一只蚂蚁军团的闪电战

数据王国隔壁是**Redis 国**——一个由**一只蚂蚁**统治的神奇国度。

### 单线程：一个厨房永远不打架

"全副武装的核心只有**一个线程**——所有命令排队进厨房。"蚂蚁女王说，"你们听起来不可思议？但**单线程意味着：永远没有锁竞争、没有上下文切换、没有并发 bug**。快，一半靠内存，一半靠'不内耗'。"

"那你凭什么扛十万 QPS？"

"**IO 多路复用**——就是你在 IO 客栈见过的那面门铃墙（epoll）。Redis 6.0 之后升级了：**传菜的多线程，做菜仍是一个厨子**——网络读写并行，命令执行仍然串行，快与稳兼得。"

它的兵器库里摆着五大常规兵器：**String**（万能储物格）、**Hash**（对象收纳盒）、**List**（ conveyor 传送带，可两头进出）、**Set**（防重会员名册，可随机抽奖）、**ZSet**（**排行榜神器**——底层就是新手村见过的**跳表**：多级快速电梯，插队查询都是 O(logN)）。

### RDB 与 AOF：快照与监控录像

"蚂蚁也会死，数据要留后。"女王展示两条保命路线：

- **RDB**：定时给全屋**拍快照**——恢复快，但**两次快照之间的事故会丢**；
- **AOF**：**监控录像逐帧记**——最安全，但带子长、倒带慢；
- **混合持久化**：照片开头 + 录像接续，兼顾快与全。

"拍快照（BGSAVE）有个名场面：fork 一个子进程去拍照，靠**写时复制**不耽误正事——但内存一大，fork 那一下也能卡住主线程。大内存 + 高写入的机器，这是坑。"

### 缓存三头龙：穿透、击穿、雪崩

Redis 国的边境线上，盘踞着 Bug 魔王的得力干将——**缓存三头龙**。

**第一头·穿透**：不停查询**根本不存在的数据**（比如用负数 id 狂刷）——缓存里永远没有，每次都**直捅数据库**。

> 解法一：**布隆过滤器**——门口保安拿着一本"可能存在的花名册"，**没登记的一律不进**（代价：极小的误判率）；
> 解法二：把"查无此人"也缓存成空值，短 TTL。

**第二头·击穿**：某个**顶流热点 key** 到期瞬间，一万请求同时冲进数据库抢补货。

> 解法：**互斥锁**——只放一个人进去补货，其余在门外等；或**逻辑过期**——到期了先返回旧的，后台默默续期。

**第三头·雪崩**：整点打烊，**大批 key 同一秒集体过期**，数据库被全员流量压塌。

> 解法：**过期时间加随机数，错峰打烊**；**多级缓存**（本地 Caffeine 顶第一波，Redis 顶第二波）；集群高可用防止单点。

"三头龙的本质是同一句话："女王总结，"**缓存是数据库的护城河——护城河干涸的瞬间（没有、过期、集体过期），就是数据库挨打之时。**"

### 分布式锁：占座与验指纹

第三关是权谋戏——**分布式锁**。多台机器抢一个活，谁抢到锁谁干：

> **SETNX 占座**（key 不存在才设成功）+ **过期时间**——为什么必须带过期时间？**怕占座者猝死，锁死全场**。

但这里有著名的连环惨案：A 占座，业务超时，锁到期自动释放；B 进场占座；**A 回来干完了活，伸手就把 B 的锁拆了**——然后 C 也进场……

> 解法：**拆锁用 Lua 脚本"先验指纹再拆"**——锁里存着 A 的身份证，核对是自己的才能拆。A 超时被赶就认，不能误伤。
> 更稳的方案：看门狗自动续期；或者用 ZooKeeper 的临时节点锁（消息之谷你会见到）。

### ES 分馆：倒排索引

王国还有一座**Elasticsearch 分馆**，专攻全文搜索。它不按"书找页"（正查），而是**先分词，建"词→文档"的字典（倒排索引）**——查"土豆"，直接命中所有含"土豆"的书，不用翻全书。配上**分片+副本**（图书馆分馆藏书且互为备份）、**聚合分析**（结账时收银机顺便汇总账本）——它就是搜索与日志分析之王（ELK 的 E）。

## 特别篇 · 闪回之夜：三分钟的错，三小时的赎

> MySQL 王国的传说里，每个 DBA 都要过一道心关：
> **不是"永不手滑"——是"手滑之后，知道下一秒该做什么"。**
> ——王国安全殿 wall 上的第一课

### 02:14:51 · 三秒钟的灾难

那是一个再普通不过的深夜。王国的值班学徒小墨在处理一个工单："把灰度名单里用户的会员等级重置为 1"。

他打开终端，凭肌肉记忆敲出：

```sql
UPDATE user SET member_level = 1;
```

敲完，回车。然后他僵住了——**WHERE 条件呢？**

WHERE 条件还在他准备下一个窗口粘贴的剪贴板里。

**全表 2200 万行，member_level 全部变成了 1。**

小墨的手指悬在键盘上方，大脑一片空白。02:14:54，监控告警炸响：客服工单暴增、会员权益系统集体报错、财务对账异常。

### 02:15:00 · 黄金十分钟：止血三连

老龟带着林一码冲进值班室时，小墨还没从惊恐里缓过来。老龟一把按住他的手——**不关终端、不重启、不删任何东西**，然后口述三连：

> **第一连：锁死现场**——`SET GLOBAL read_only = ON;` **立即锁库只读**。宁可业务全停，不可脏数据扩散——**它是止血带，不是棺材**；
> **第二连：保住录像**——确认 binlog 开着、格式是 ROW，记录下当前 binlog 文件名和位点。**录像带在，一切都有救**；
> **第三连：划定案发时间**——从工单系统、审计日志精确锁定：案发于 **02:14:51**，误操作语句的 GTID。

"记住这个顺序，"老龟对小墨说，声音稳得可怕，"**慌乱的人会删 binlog——那是烧毁证据。你要做的每一件事，都围绕'把现场原样交给三小时后的自己'。**"

### 02:30 · 闪回神术：把时间倒放

应急指挥部成立。方案 A（从最近备份恢复）被否：备份是昨晚 3 点的，**会丢 23 小时新数据**。方案 B 被推上桌——**binlog 闪回**。

原理朴素得震撼：**ROW 格式的 binlog 记录的是"每一行改之前的样子和之后的样子"**——误操作把 2200 万行的 member_level 从"各自的原值"改成了"1"，那么**把 2200 万条 ROW 事件的 BEFORE 和 AFTER 互换、倒序重放**，就是一次完美的时间倒放：

```bash
# 1. 截取案发时间段的 binlog
mysqlbinlog --start-datetime="2025-03-12 02:14:50" \
            --stop-datetime="2025-03-12 02:14:55" \
            --base64-output=decode-rows -v mysql-bin.002315 > incident.sql

# 2. 闪回工具反转 ROW 事件（before/after 互换），生成"赎罪 SQL"
# 3. 先在影子库全量演练——确认影响行数=2200 万、内容=原值
# 4. 校验通过，主库执行
```

"**先在影子库练，练熟了再上主库**——闪回 SQL 本身也是一条大事务，直接怼主库等于二次事故。"老龟盯着执行进度条，"三小时前的你们，给现在的我们留了完整的证据链；现在的我们，别给明天的自己留新的坑。"

### 05:47 · 数据归位

05:47:03，闪回执行完毕。抽样校验：会员等级分布与案发前快照**完全一致**。`read_only` 关闭，业务恢复。

客服队列里排着的三万个"我的会员呢"工单，还没来得及批量回复，就陆续变成了"怎么自己好了"。

小墨瘫在椅子上，看着自己那双"闯了祸"的手。老龟递给他一杯热水，说了那晚最轻也最重的一句话：

> "今晚救了你的不是运气，是三样东西：**ROW 格式的 binlog、没删的录像带、和你没伸手乱按的那几秒钟**。
> 从明天起，你会变成王国最好的 DBA——因为**踩过深渊的人，才真的知道栏杆该修在哪**。"

### 制度：把深渊装上栏杆

复盘会上，四道栏杆落地，此后再无此类事故：

1. **安全模式常开**：`sql_safe_updates=1`——**无 WHERE/无索引条件的 UPDATE/DELETE，直接拒绝执行**；
2. **工单双人复核**：所有写操作走审核平台，**高危语句必须第二双眼睛**；
3. **延迟从库**：搭一台**故意慢 30 分钟**的从库——它是"后悔药仓库"，任何误操作，30 分钟内可从它抢救原值；
4. **演练常态化**：每季度一次"闪回演习"——**在演练桌上练过一千次止血的人，实战时手才不会抖**。

**【本场掉落】**：ROW binlog 的 before/after 镜像、闪回三步（截取→反转→影子库演练）、read_only 止血带、延迟从库后悔药仓、sql_safe_updates。

## 特别篇 二 · 幻读迷雾：连空气都锁住的考官

> 数据王国的深夜课堂，永远从一句反问开始：
> **"你觉得没被锁住的行，真的没人管吗？"**
> ——老龟·锁术公开课

### 案发：INSERT 集体超时

王国西境的商户连夜报警：**订单表的 INSERT 从昨晚开始集体超时**。查锁表——没有行锁冲突；查死锁——判官没响警报。**但所有插入，就是进不去。**

老龟带林一码赶到，查了一个正在运行的会话，倒吸一口凉气：

> 某报表任务开着事务，执行了
> `SELECT * FROM orders WHERE created_at BETWEEN '03-10' AND '03-11' FOR UPDATE`
> 然后**去泡咖啡了**（事务半小时没提交）。

"它锁了什么？"

"**不止那两天存在的行——是那个'区间'本身。**"老龟说，"**可重复读级别防幻读的代价：间隙锁（Gap Lock）——把区间里'还不存在的行'的空隙也封死**。考场防抄袭，把空座位也封了。**现在，任何落在 03-10~03-11 区间的新订单 INSERT，都在等一块'被封住的空气'。**"

### 课堂：三种读，三种命

林一码当场补了锁术的核心课。同一个 SELECT，三种写法三种命：

> **普通读（快照读）**：`SELECT ...`——走 **MVCC 时光机**，看快照，**不加锁**，谁也不挡；
> **当前读·行锁**：`SELECT ... FOR UPDATE`（或 UPDATE/DELETE）——**读最新版本并加锁**；**有索引**时只锁命中的行和相邻间隙；
> **当前读·无索引**：条件列没索引——**InnoDB 不知道哪些行匹配，只能全表走一遍，间隙锁把整张表都封了**。

"所以凶手不止报表任务，"老龟指向第二个共犯，"**created_at 没索引**——一个'本想锁三天数据'的查询，**锁住了整张表的所有空隙**。"

### 解锁：三步拆弹

> **1 · 止血**：`KILL` 掉泡咖啡的报表事务——空隙瞬间解封，INSERT 恢复。**慢事务是间隙锁的所有惯性事故之源**；
> **2 · 拆弹**：给 created_at 建索引——**锁从'全表'缩回'区间'**；
> **3 · 定规**：报表查询改用普通读（快照）或改读从库——**报表要的是'过去的一致'，不是'现在的锁'**；确需当前读的，事务里**锁完立刻用完**，绝不夹带业务逻辑。

老龟补了一层心法："**RR（可重复读）的间隙锁是'防幻读'的代价，RC（读已提交）没有间隙锁、幻读认了——所以很多互联网老兵把隔离级别降为 RC，用'允许看见新行'换'锁更少、并发更高'。** 没有完美的级别，只有匹配场景的选择。**但改隔离级别是架构级决定，要全团队评审，不是一句 set session 的任性。**"

### 尾声：空气也值钱

离开西境前，老龟在锁术课堂的黑板上留下一句被抄遍王国的话：

> **"行锁锁住的是数据，
> 间隙锁锁住的是可能性。
> 摧毁一个系统最快的方式，
> 不是抢走它已有的东西——
> 是**封死它所有'还没发生'的可能**。"**

**【本场掉落】**：快照读 vs 当前读、间隙锁的触发与范围、无索引当前读=锁全表、慢事务之殇、RR 与 RC 的权衡。
